# AGENTS.md — hermes-step-pipeline

Плагин Hermes: конвейер шагов «план → постановка → исполнение → ревью → журнал».
Репозиторий общий: ни имён проектов-потребителей, ни их бизнес-логики внутри быть не должно.

**С чего начать новую сессию:** прочитать `docs/CONTEXT.md` — там история, принятые
решения с обоснованием, состояние, грабли и что осталось.

| Документ | О чём |
|---|---|
| `docs/CONTEXT.md` | контекст проекта: откуда взялся, архитектура, решения, состояние, грабли |
| `README.md` | как ставить и пользоваться (для человека) |
| [docs/PLAN-FORMAT.md](docs/PLAN-FORMAT.md) | нормативный формат плана: разделы, шаги, журнал, что читает каждый парсер |
| `CHANGELOG.md` | что менялось и когда (semver) |
| `step_pipeline/templates/` | план, промт, `pipeline.json` — образцы для проектов |

## Границы

- `step_pipeline/engine/` — единственный источник движка. Копии в проектах
  (`.pipeline/`) руками не правятся: их обновляет `hermes pipeline setup --upgrade`
  (он же приводит `.hermes/skills/` к версии плагина, прежнее — в `.pipeline/roles-backup/`).
- `step_pipeline/roles/` — универсальные роли. Предметные скиллы проекта живут в проекте.
- Всё проектное — в `pipeline.json` проекта, не в коде плагина.
- **`driven_plans` и `profiles` в `pipeline.json` меняет только владелец.** Шаг конвейера
  их не трогает: какие планы ведёт страж и какими профилями — решение человека, а не
  исполнителя. Остальные ключи шаг может править, если они входят в его объём.
  Причина: шаг 1-S11 один раз «нормализовал» конфиг и снял план 4 с ведения — конвейер
  молча перестал его вести.
- Секреты — только в `.env` профиля Hermes; в коде, логах, UI и тестах их нет.

## Проверки перед коммитом

```bash
python -m pytest                        # 600+ тестов: плагин + движок (tests/engine/)
ruff check .                            # линтер разработки (requirements-dev.txt)
hermes plugins validate step_pipeline   # манифест, инструменты, security-скан
```

Без `-q`: в `pytest.ini` он уже стоит, второй `-q` скрывает итог прогона.
Ломающее изменение движка или формата `pipeline.json` — минимум минор версии
в `plugin.yaml` и запись в `CHANGELOG.md`.

**Golden-вердикты** (`tests/engine/golden/`) сравнивают решение стража с эталоном.
Осознанно изменил поведение — перезапиши эталон и проверь diff глазами:

```bash
GOLDEN_UPDATE=1 python -m pytest tests/engine/test_golden_verdicts.py
```

## Конвенции

- Комментарии, docstring'и, сообщения пользователю, коммиты — по-русски.
- Зависимости — только stdlib и Hermes; внешние пакеты не добавлять.
- Движок обязан работать без установленного плагина: он копируется в проект.
- UI слушает только localhost; в предпросмотре действия запрещены.
- CI: ubuntu + windows, python 3.11/3.13; `hermes plugins validate` — если CLI есть.

## Типовые задачи

**Добавить роль.** Скилл в `step_pipeline/roles/<имя>/SKILL.md`, строка в
`SKILL_CATEGORIES` (`setup_flow.py`) — какая категория `.hermes/skills/` её получит,
и упоминание в `templates/pipeline.json.example` (роль + лимиты).

**Изменить движок.** Правится только `step_pipeline/engine/`; затем `pytest` целиком
(тесты движка в `tests/engine/`), инкремент версии, `CHANGELOG.md`, а в проектах —
`hermes pipeline setup --upgrade`.

**Выпустить версию.** версия в `plugin.yaml` → `CHANGELOG.md` → коммит → тег `vX.Y.Z`
→ `git push origin vX.Y.Z`.

**Изменить UI.** `step_pipeline/ui/index.html` (без сборки), данные — `snapshot.py`,
тесты — `tests/test_ui_server.py`, `tests/test_preview.py`.
