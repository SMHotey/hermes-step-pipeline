# Changelog

Формат: [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии — semver.
Ломающее изменение поведения движка или формата `pipeline.json` — минимум минор.


## 0.10.0 — 05.11.2026

`REQUEST_CHANGES` по постановке больше не останавливает конвейер: постановку переписывает
роль prompter, после каждого круга ревью ставится заново.

### Изменено

- `decide` (правило 3): вердикт `REQUEST_CHANGES` по ревью постановки ставит карточку
  `planloop:<план>:<шаг>:promptfix:<N>` роли `profiles.prompter` с телом «переписать
  постановку» (закрыть блокирующие находки, сверить факты с HEAD, обновить `recon_commit`,
  прогнать `.pipeline/check_task_prompt.py`, коммит только файла постановки).
- После завершения карточки переписывания ревью ставится заново с номером круга:
  `planloop:<план>:<шаг>:promptreview:<N>` (первый круг остаётся без номера).
  Раньше `auto`-режим не переспрашивал ревью у свежей постановки — переписанная
  постановка уходила в исполнение без проверки.
- Стоп — только по исчерпании `max_fix_rounds`, при падении карточки, при нераспознанном
  вердикте и когда отчёт ревью не обновлён после закрытия карточки (защита от вердикта
  прошлого круга).
- Режим `prompt_review: never` по-прежнему не запускает ревью постановок, но не обрывает
  уже начатую цепочку переписывания.

## 0.9.0 — 04.11.2026

Два автоматических круга правок по ревью вместо одного. Раньше второй `REQUEST_CHANGES`
сразу останавливал конвейер и требовал владельца; теперь исполнитель получает ещё один
круг, и страж останавливается только по исчерпании лимита.

### Добавлено

- Мультипроектная панель: реестр `projects.json` в home профиля плюс разовые пути
  (`--extra-project`), переключатель в шапке, сводная таблица «проект, план, следующий
  шаг, закрыто, стоп, простой» и маршрут `GET /api/projects`; действия адресуются
  выбранному проекту полем `project` и подписаны его именем, проект без `.pipeline`
  помечается «не установлен». Ключ `project_root` в `config_schema` задаёт проект по
  умолчанию для `hermes pipeline` без `--project`.

### Изменено

- `decide`: карточка правок создаётся, пока число кругов меньше лимита
  (`max_fix_rounds`, по умолчанию 2) — ключи `planloop:<план>:<шаг>:fix:<N>` и
  `...:review:<N+1>` идут подряд, без остановки между первым и вторым кругом.
- `pipeline.json`: новый ключ `max_fix_rounds` (целое ≥ 1). `1` возвращает прежнее поведение.
  Мусор в ключе — ошибка конфигурации, а не молчаливое умолчание.
- Текст стопа говорит о лимите, а не о «втором REQUEST_CHANGES»:
  `REQUEST_CHANGES по шагу <шаг> — исчерпан лимит автоматических кругов правок (N)`.
- Правило закреплено в `docs/CONSTITUTION.md` (п. 4) и в таблице решений `docs/CONTEXT.md`;
  шаблон `templates/pipeline.json.example` обновлён.

Примечание: отметка версии 0.8.0 ставилась только в установленной копии плагина, в этом
CHANGELOG она не отражена.


## 0.7.0 — 04.11.2026

Конвейер больше не стоит между шагами и не начинает шаг по постановке, которая разъехалась
с кодом (план 2, шаг S6). Поведение движка по умолчанию меняется: `prefetch_prompt: true`,
`prompt_review: "auto"`.

### Добавлено

- Предзаказ постановки следующего шага: пока шаг N в работе, страж сразу заказывает
  постановку N+1 (ключ карточки `planloop:<план>:<шаг N+1>:prompt`). Повторных заказов нет:
  тик видит карточку заказа и просто ждёт. У последнего шага плана постановка не
  заказывается — иначе конвейер встал бы на закрытии последнего шага.
- Гейт закрытия: шаг N не закрывается в журнале, пока нет постановки N+1. Вместо записи
  журнала страж заказывает постановку и уведомляет владельца «шаг N принят, но закрыть не
  могу: нет постановки N+1»; как только постановка появилась, шаг закрывается сам.
  Гейт живёт в решении, поэтому не тратит действие тика на повторный отказ.
- Ревью постановки перед стартом шага (`prompt_review: auto | always | never`): свежая
  постановка (в шапке `recon_commit`, и с этого коммита до HEAD нет правок вне `docs/`)
  стартует без ревью; устаревшая — только после APPROVE ролью `reviewer`, отчёт
  `docs/reviews/<план>-<шаг>-prompt.md` с тем же `recon_commit`.
- В заказе постановки промптеру добавлен пункт: писать `recon_commit` в шапку постановки.

### Исправлено

- Неизвестный режим `prompt_review` в `pipeline.json` теперь ошибка конфигурации с перечнем
  допустимых значений, а не молчаливое умолчание: настройка не должна теряться тихо.

## [0.6.0] — 2026-11-03

**Почему панель «не работала».** После переименования плагина (`step-pipeline` → `step_pipeline`)
в `plugins/` остались копии с прежним именем: Hermes грузил старую копию, поэтому
`hermes pipeline` мог не находиться, а сервер отдавал старую страницу без вкладок.

### Исправлено
- `setup --upgrade` убирает из `plugins/` копии нашего плагина с чужим именем
  (`plugin-backups/<профиль>/`) и включает актуальный id в профиле, затем проверяет,
  что команда `hermes pipeline` отвечает.
- `hermes pipeline ui` отказывается садиться на порт, где уже отвечает другой UI:
  на Windows двойная привязка порта проходила молча, и старый сервер продолжал отдавать
  старую страницу. Теперь внятная ошибка с подсказкой `--stop` / `--port`.
- `/api/health` отдаёт `version` и `ui_sha`; панель показывает их в шапке — сразу видно,
  какая версия и какая страница реально работают.

### Изменено
- `setup --upgrade` теперь обновляет и роли: `.hermes/skills/...` приводится к версии
  плагина, прежняя копия уезжает в `.pipeline/roles-backup/<роль>-<время>/` (путь
  добавляется в `.gitignore`). До этого роли копировались только при первой установке,
  и правки `step_pipeline/roles/` не доезжали до поставленных проектов вовсе.

### Тесты
- `test_health_reports_version_and_ui_sha`, `test_busy_port_is_reported_not_silently_reused`,
  `test_busy_version_none_on_free_port`.
- `test_upgrade_refreshes_changed_role_and_keeps_backup`,
  `test_upgrade_leaves_fresh_roles_alone`, `test_setup_refreshes_roles_only_with_force`.
- `tests/conftest.py`: `HERMES_HOME` изолируется на `tmp_path` — прогон тестов больше
  не трогает настоящие `plugins/` разработчика (иначе `--upgrade` уносил бы его копии
  в `plugin-backups/`).
