## 0.44.2 — 26.11.2026

**Пуш паузы — одно сообщение на чат, а не на бота.** Адрес пуша считался парой
(токен, чат), а у каждого проекта в реестре свой бот: три проекта с включёнными
уведомлениями слали в один чат три одинаковых «⏸ Все проекты на паузе» (живой случай —
26.11.2026, 12:12:28: `doorsystem` и `gapaudit` записали один и тот же пуш). Теперь
адрес — пара (чат, префикс): текст собирается из общего `pause_text` и префикса проекта,
поэтому одинаковые сообщения схлопываются, а разные префиксы и разные чаты получают своё.
Токен берётся у первого готового проекта этого чата.

- `pause_channels` (ui_server): ключ дедупликации `(chat, prefix)` вместо `(token, chat)`.
- Тест `tests/test_ui_server.py::test_pause_push_goes_once_per_chat`: три проекта и три
  бота в одном чате дают один пуш; другой чат и другой префикс — свой пуш; неготовый
  канал и выключенный проект молчат.

**Мастер установки сверяет, что запускает cron-джоба стража.** Джоба узнавалась по имени:
проект, заведённый старой обёрткой, оставался на `plan_gate_tick.py` навсегда, хотя мастер
писал «джоба уже есть (тик-скрипт обновлён)». Старая обёртка не читает `.env` профиля,
поэтому тик молчал уведомлениями — все сообщения шли только из панели (doorsystem,
26.11.2026: в каждом запуске `[notify] нет токена/чата`).

- `cron_jobs(driver)` разбирает `cron list` на джобы: id, статус, имя, скрипт, рабочий каталог.
- `tick_job_state(job, project)` говорит, что не так: чужой скрипт или не тот рабочий каталог.
- `ensure_cron` устаревшую джобу перевешивает: `cron edit <id> --script pipeline_tick.py
  --no-agent --workdir <проект>`; при отказе — предупреждение и готовая команда руками.
- Тесты: разбор вывода `cron list`, перевешивание устаревшей джобы, молчание на верной.

## 0.44.1 — 26.11.2026

**Один стоп плана — одно сообщение в Telegram.** Панель строила событие `plan_stopped`
на каждую журнальную строку `stop`, а текст брала из стоп-флага (он один на план).
Ключ дедупликации нёс шаг журнальной строки, поэтому пять строк с разными шагами давали
пять разных ключей с одинаковым текстом: панель слала одно и то же сообщение по разу
в `NOTIFY_GAP` секунд. Живые случаи: doorsystem, план 34 (24 и 26.11.2026) — до пяти
одинаковых «инцидент плана 34: карточка шага … в статусе blocked»; gapaudit, план 1 —
три «стоп плана 1: остановка владельца».

- `_notify_event` принимает `dedupe` — метку вместо шага в ключе для событий, которые
  к шагу не относятся.
- `_stop_dedupe` даёт метку эпохи стопа из стоп-флага (`at`), без неё — из времени файла:
  один стоп — один ключ, новый стоп после снятия — новый ключ и новое сообщение.
- `_notify_candidates` берёт стоп-флаг авторитетом: нет флага (стоп сняли) — события нет,
  дата — самая свежая строка `stop` плана, иначе время файла флага.
- Тест `tests/test_ui_server.py::test_plan_stop_notifies_once_per_stop_flag`: три строки
  `stop` с разными шагами дают одно событие, повторные кадры молчат, снятый стоп молчит,
  новый стоп с новой меткой доставляется снова.

тем же словарём.** Словарь F01–F09 объявлен одним местом — `registry.py`

линтером отчёта. Формат файла реестра не менялся: код живёт ведущим в тексте колонки
«Находка», поэтому реестры шага читаются прежним парсером, а реестры плана 7 — без миграции.

- `registry.FINDING_CODES`, `FINDING_CODE_TITLES`, `FINDING_CODE_RE`, `finding_code`,

- `gate.report_finding_codes` фильтрует найденное словарём (код вне словаря шаг не держит);
  `gate.report_unknown_codes`/`report_unknown_codes_at` — линтер отчёта.
- Машинные проверки кодов: `gate.commit_files`, `gate.step_file_offenders` (F01 по списку

## 0.43.0 — 26.11.2026

**Закрытие шага держится на прогоне и коммите; вердикт ревью — второе условие.** Шаг с
пунктом «Прогон» закрывается решением `close_policy_decision`: основание — зелёные прогоны
и существующий коммит, а допуск по риску требуется для `normal` и `high` (`APPROVE` или
принятие с замечаниями). У риска `low` отчёта ревью может не быть вовсе — вторые руки там
машинный прогон гейта, а не ревьюер (п.7 конституции в редакции 8a7c036). Находка с кодом
(`F01`…`F09` в тексте пункта раздела находок) держит шаг при любом риске и открывает круг
правок до лимита, после которого — инцидентный стоп с числами.

- `gate.close_policy_decision` (якорь `ANCHOR:закрытие`) — одно место решения о закрытии:
  битый или непустой реестр шага отдаёт решение прежним ветвям, шаг без «Прогона» идёт
  прежним путём слово в слово (legacy-планы не меняются), отсутствие доказательства даёт
  действие `step_runs`, красные прогоны и бюджет — прежние решения `runs_gate_decision`,
  затем предполётная проверка постановки N+1, находки с кодом и допуск по риску.
- `run_gate`: фаза прогонов закрытия — прогоны исполняются в том же тике, решение
  пересчитывается; повторное `step_runs` на том же sha становится стопом, а не вторым
  запуском. Сбой чтения/записи доказательства — тот же инцидентный стоп, что и у S2.
- `run_gate`/`close_step`: коммит закрытия берётся из отчёта ревью, а при закрытии по
  прогонам — из доказательства (sha, на котором прогоны исполнялись); отчёт ревью входит в
  коммит только если он есть (иначе `git add` падал бы 128 и вешал `pending_commit`).
  Строка журнала закрытия по прогонам — счётчик прогона и «вердикта нет — риск low»;
  строки APPROVE и «принято с замечаниями» не изменились.
- `gate.report_finding_codes`/`report_finding_codes_at` — коды находок отчёта тем же
  разбором области, что и классы; закрытый словарь кодов и проверку кода вне словаря
  оставляет за собой шаг S4, здесь коды только блокируют. Метка распознаётся в любом
  регистре (`f06` = `F06`): строчный код держит шаг так же, как верхний.
- Находка с кодом проверяется и в прежних ветвях вердикта: `APPROVE` и «принятие с
  замечаниями» больше не закрывают шаг, если в отчёте есть код.
- `tick`: действие в записи истории — применённое, а не выбранное до `run_gate` (иначе
  запись говорила «step_runs: журнал: добавлена строка» при фактическом `close_step`).
- Golden-вердикты: три новых случая — `11-close-low-no-verdict` (низкий риск закрывается
  без вердикта), `12-normal-no-verdict` (normal без APPROVE стоит), `13-code-finding-blocks-low`
  (находка с кодом держит low и открывает круг правок); прежние десять эталонов не
  перезаписаны. `golden_kit` маскирует длительность прогона в счётчике (`<сек>`): секунды —
  время стенда, а не решение стража.
- Тесты: `tests/engine/test_close_policy.py` — девять случаев (закрытие low, стоп normal,
  legacy без «Прогона», красный прогон, отсутствие доказательства, открытый реестр,
  AMBIGUOUS у low, находка с кодом, постановка N+1).
- Документы: инвариант 3 в `docs/CONTEXT.md` переписан, в `docs/PLAN-FORMAT.md` §9 добавлено
  отличие линтера от движка по закрытию прогоном.

## 0.42.4 — 25.11.2026

**Прогон с цепочкой `&&` и `*.cmd`-обёрткой запускается.** Строка «- Прогон: `npm --prefix
web ci && npm --prefix web run build`» плана 4 проекта self-analyzer не запускалась вовсе:
красный прогон за 0.4 с, `FileNotFoundError [WinError 2]`. Причин две, и обе в движке.

- `runs_argv` разворачивает первый токен через `shutil.which` (`PATH` и `PATHEXT`):
  `CreateProcess` дописывает к имени только `.exe`, поэтому `npm`/`npx`/`yarn` на Windows
  (`*.cmd`) не находились, хотя человек ту же строку в `cmd` исполняет. Оболочки это не
  поднимает — D1 в силе.
- `runs_segments`: `a && b` — две команды, вторая идёт только после успеха первой; код
  строки — код последней исполненной, таймаут считается на всю цепочку. Режется по СЛОВАМ
  (`shlex.split`), поэтому `&&` внутри кавычек остаётся аргументом.
- Тесты: `test_runs_exec.py::test_segments_split_on_and_only`,
  `::test_and_chain_runs_both_commands`, `::test_and_chain_stops_after_red`,
  `::test_first_token_resolves_through_path`, `::test_missing_command_is_red_without_code`.

## 0.42.3 — 25.11.2026

**Панель читает реестр установки, а не пустой профильный.** Панель, запущенная из профиля
(например, `hermes pipeline ui --project …` в сессии профиля `pipeline`), брала
`HERMES_HOME/projects.json` — а там `{"projects": []}`. В итоге в таблице проектов оставался
один конвейер: тот, ради которого панель подняли. Корневой реестр при этом знал четыре.

- `project.install_home()` схлопывает профильный путь до корня установки — то же правило,
  что у сторожа (`watchdog._root_home`).
- `project.projects_file()` сначала берёт `<корень>/projects.json`, и только если его нет —
  профильный. `PIPELINE_PROJECTS_FILE` по-прежнему сильнее обоих.
- Поток событий ждёт свежий снимок (`ttl=None`), а не отдаёт прошлый: кадр «изменение»
  обязан нести изменённые данные. Иначе изменение терялось — поток помечал отпечаток
  обработанным, а в кадр попадал кэш (регресс 0.42.2, `test_tick_pushes_event_with_new_card`).
  Запросы страницы (`GET`/`POST`) по-прежнему получают прошлый снимок сразу, чтобы одна
  заклинившая сборка не подвешивала панель.
- Тесты: `test_project_env.py::test_projects_file_prefers_install_root_over_profile`,
  `::test_projects_file_falls_back_to_profile_without_root_registry`,
  `test_ui_server.py::test_tick_pushes_event_with_new_card`.

## 0.42.2 — 25.11.2026

**Панель отвечает: сборка снимка идёт в одиночку, а внешняя команда больше не висит на чужих
пайпах.** Симптом: страница открывается, полоса
обновления висит, `/api/projects` отвечает 80 с, `/api/snapshot` не укладывается в пять минут,
в браузере «панель не работает». Причина не в сети и не в порту: сборка снимка стоит три запуска
движка (17.6 с `gate.py --plans` + 2.2 с `--status` + 1.5 с `next_step.py` на 17 планах), а
кэш жил 2.5 с — меньше, чем интервал опроса страницы (30 с) и переподключения потока событий
(25 с). Каждый вопрос строил снимок заново, запросы вставали в очередь на замке сборки.

- Снимок берёт строки планов из того же кэша, что и сводка реестра (`panel_pause.plans`), а не
  поднимает `gate.py --plans` своим путём: одна сборка на страницу вместо двух. Предпросмотр
  идёт прежним путём — движок плагина и свои переменные окружения.
- У `snapshot()` появился `max_age`: сколько живёт запись с тем же отпечатком источников.
  Панель передаёт `SNAPSHOT_MAX_AGE = 60` (её опрос — 30 с), агент и тесты остаются на 2.5 с.
  Изменение файлов по-прежнему видно сразу — кэш снимается отпечатком, а не только сроком.
- Сборка снимка больше не держит общий замок: одна сборка на ключ (`_INFLIGHT`), остальные
  запросы панели получают прошлый снимок сразу. Живой случай 24.11.2026: `gate.py --plans`
  соседнего проекта провисел двадцать минут, сборка держала замок, и `/api/snapshot`
  перестал отвечать вовсе — при этом `/api/health` отвечал за 0.01 с. Агент (без `max_age`)
  по-прежнему ждёт свежий ответ; `clear_cache` поднимает номер поколения, чтобы сборка,
  начатая до сброса, не легла в кэш.
- «Антидребезг» только у потока событий: `EVENTS_MIN_BUILD = 3` с. Цикл сверяет отпечаток
  раз в 0.5 с, а сборка дольше — на работающем конвейере поток превращался в непрерывную
  очередь сборок. Изменение не теряется: отпечаток не «съедается», кадр уходит на следующем
  витке после паузы. Запросы страницы (`/api/snapshot`, действия) по-прежнему видят правку
  на первом же запросе — контракт «инвалидация отпечатком, а не по TTL» не тронут.
- Дедупликация сборки строк планов (`panel_pause.plans`, `_INFLIGHT`): сторож паузы
  (сверка раз в 10 с) и вкладки панели просили строки одновременно и поднимали каждая свой
  `gate.py --plans`. Кто пришёл вторым — получает прошлые строки, если они есть, иначе ждёт
  чужую сборку.
- Таймаут внешней команды больше не ждёт чужие пайпы: `project.run` и `gate._run` убивают
  процесс и ждут его вывод не дольше `KILL_WAIT_SECONDS = 5` с. На Windows
  `subprocess.run(timeout=…)` после убийства ждёт читающие потоки бесконечно, если дескриптор
  остался у потомка (`gate.py` сам поднимает `next_step.py` и `hermes`) — один такой вызов
  держал поток панели двадцать минут. Регресс:
  `test_ui_control.py::test_run_timeout_does_not_wait_for_grandchildren`.
- Замеры на живом репозитории (17 планов): повторный `/api/snapshot` — 0.2–0.7 с вместо 21.4 с,
  `/api/projects` — 0.13 с вместо 17.9 с. Пересборка на реальное изменение файлов — 10–18 с

- **Номер круга правок виден в карточке**: тело правки пишет «круг 2 из 4» вместо «круг 1»
  в каждой карточке, тело ревью объясняет лимит, а не «второй отказ уходит владельцу».
- **Умолчание `max_fix_rounds` = 2 осталось**, но ключ теперь честно управляет обоими

что вернёт его в работу. Статус плана считает решение стража, а не наличие стоп-файла.

### Добавлено

- `gate.py --plans`: поля `state` (`running` / `stopped` / `closed` / `not-driven`),
  `state_label`, `reason`, `note` и `action` (`kind`, `text`, `command`) — готовая
  рекомендация «что сделать» с командой (`resume`, `unblock`, `tick`, `unhold`,
  `approve`, `drive`, `cron`, `none`).
- Функция `plan_view(cfg, p, driven, cron_ok)` в `step_pipeline/engine/gate.py`: одна
  строка состояния на план из `build_ctx` + `decide`, сбой движка даёт строку с причиной,
  а не падение всего `--plans`.
- Вкладка «Обзор» панели: строки планов вместо чипов — бейдж статуса, следующий шаг,
  полная причина остановки и подсказка «что сделать» с готовой командой.
- Поля `state` и `state_label` в строке сводки реестра проектов (`ui_server.py`).

### Изменено

- Стоп-флаг перестал быть статусом: «остановлен» считается по решению стража, поэтому
  остаточный `plan_<N>_stop.json` больше не рисует ложный стоп, а показывается пометкой
  «стоп снят (было: …)». Снимок панели (`stop`, `overview`, строка прогресса) и сводка
  реестра берут состояние из строки плана с запасным путём на старое поле.
- Панель: контейнер `#plans` переехал из «Потока текущего шага» в «Обзор»; бейдж режима
  и подсказки кнопок считаются по `state`, а не по `p.stop`.

  `planloop:<план>:<шаг>:promptfix:<N>` роли `profiles.prompter` с телом «переписать

  уже начатую цепочку переписывания.

Два автоматических круга правок по ревью вместо одного. Раньше второй `REQUEST_CHANGES`

## 0.7.0 — 04.11.2026

Конвейер больше не стоит между шагами и не начинает шаг по постановке, которая разъехалась
с кодом (план 2, шаг S6). Поведение движка по умолчанию меняется: `prefetch_prompt: true`,
`prompt_review: "auto"`.

### Добавлено

- Предзаказ постановки следующего шага: пока шаг N в работе, страж сразу заказывает
  постановку N+1 (ключ карточки `planloop:<план>:<шаг N+1>:prompt`). Повторных заказов нет:
  тик видит карточку заказа и просто ждёт. У последнего шага плана постановка не
  заказывается — иначе конвейер встал бы на закрытии последнего шага.
- Гейт закрытия: шаг N не закрывается в журнале, пока нет постановки N+1. Вместо записи
  журнала страж заказывает постановку и уведомляет владельца «шаг N принят, но закрыть не
  могу: нет постановки N+1»; как только постановка появилась, шаг закрывается сам.
  Гейт живёт в решении, поэтому не тратит действие тика на повторный отказ.
- Ревью постановки перед стартом шага (`prompt_review: auto | always | never`): свежая
  постановка (в шапке `recon_commit`, и с этого коммита до HEAD нет правок вне `docs/`)
  стартует без ревью; устаревшая — только после APPROVE ролью `reviewer`, отчёт
  `docs/reviews/<план>-<шаг>-prompt.md` с тем же `recon_commit`.
- В заказе постановки промптеру добавлен пункт: писать `recon_commit` в шапку постановки.

### Исправлено

- Неизвестный режим `prompt_review` в `pipeline.json` теперь ошибка конфигурации с перечнем
  допустимых значений, а не молчаливое умолчание: настройка не должна теряться тихо.

## [0.6.0] — 2026-11-03

**Почему панель «не работала».** После переименования плагина (`step-pipeline` → `step_pipeline`)
в `plugins/` остались копии с прежним именем: Hermes грузил старую копию, поэтому

  (`plugin-backups/<профиль>/`) и включает актуальный id в профиле, затем проверяет,

  на Windows двойная привязка порта проходила молча, и старый сервер продолжал отдавать
  старую страницу. Теперь внятная ошибка с подсказкой `--stop` / `--port`.
- `/api/health` отдаёт `version` и `ui_sha`; панель показывает их в шапке — сразу видно,
  какая версия и какая страница реально работают.

### Изменено
- `setup --upgrade` теперь обновляет и роли: `.hermes/skills/...` приводится к версии
  плагина, прежняя копия уезжает в `.pipeline/roles-backup/<роль>-<время>/` (путь
  добавляется в `.gitignore`). До этого роли копировались только при первой установке,
  и правки `step_pipeline/roles/` не доезжали до поставленных проектов вовсе.

### Тесты
- `test_health_reports_version_and_ui_sha`, `test_busy_port_is_reported_not_silently_reused`,
  `test_busy_version_none_on_free_port`.
- `test_upgrade_refreshes_changed_role_and_keeps_backup`,

- Записи `.gitignore`: `.pipeline/`, `.hermes/`, `docs/templates/`, `.idea/` —
  артефакты установки и IDE больше не висят в `git status`.

  мёртвых ключей, лицензия на месте, `.gitignore` закрывает артефакты, README без
  старого имени) и `tests/test_cli_ui_port.py` (порт из конфига проекта и перекрытие

### Почему

- Два имени жили одновременно: `plugins update` и `plugins remove` резолвят каталог
  `plugins/step_pipeline`, а `plugins list` и `plugins show` печатают имя из манифеста,
  поэтому половина команд README не выполнялась. Смена имени в манифесте — минор,
  потому что установленные копии с прежним `plugins.enabled` требуют одного
  `hermes plugins enable step_pipeline`.

## [0.3.0] — 2026-11-02

Тик не запускается на разъехавшейся копии движка.

### Добавлено

- Маркер целостности `.pipeline/ENGINE.sha256` — sha256 по содержимому всех `.py`
  движка; пишется при `setup` и `setup --upgrade`.
- Проверка перед тиком: `gate.py --run` сверяет движок с маркером и при расхождении
  не выполняется (код 3, в stderr — команда обновления). Легаси-установки без маркера
  продолжают работать.
- Тесты `tests/engine/test_engine_integrity.py`: стабильность хеша, дрейф, пустой
  маркер, легаси, согласованность `setup_flow` и движка.

### Почему

- Прецедент 02.11.2026: в проекте работала копия `gate.py` (1364 строки), в плагине
  лежала другая (1599 строк) — обе с `VERSION 0.2.0`. План двигали две разные логики:
  один конвейер шёл по шагам, которые считал следующими по своей версии разбора.

## [0.2.0] — 2026-11-01

Конвейер отвечает в чате и перестал молчать под cron.

### Добавлено

- Приём команд владельца из Telegram: `gate.py --commands` — один `getUpdates` с offset
  в `.pipeline/state/tg_offset.json`. Команды `/status`, `/plans`, `/stop [причина]`,
  `/resume`, `/hold ШАГ`, `/unhold ШАГ`, `/help`. Отвечаем только в настроенный чат,
  чужие сообщения игнорируем, на вебхуке (409) сообщаем причину, а не молчим.
- `setup` заводит вторую cron-джобу «бот команды» раз в минуту (no-agent) и кладёт
  `profiles/<профиль>/scripts/pipeline_commands.py`: страж идёт раз в 10 минут,
  а `/status` и `/stop` столько ждать нельзя.
- Ключ `notify.commands` в `pipeline.json` (включён по умолчанию там, где включены
  уведомления).

### Исправлено

- Тик-скрипт сам читает `.env` профиля: cron шлюза отдаёт `HERMES_HOME`, но не переменные,
  поэтому уведомления движка молчали (в stderr уходило только `[notify] нет токена/чата`).
- Установленный тик-скрипт получил UTF-8 в stdio и поиск `gate.py` по четырём местам:
  раньше это была урезанная копия без того и другого.
- `setup` делает `skills trust` всем трём ролям, а не только исполнителю: иначе воркеры
  постановщика и ревьюера падали `Unknown skill(s)` и карточка уходила в `blocked`.

### Тесты

- 126 тестов; новые: `tests/engine/test_tg_commands.py` (15), `tests/engine/test_tick.py` (7).

## [0.1.0] — 2026-11-01

Первая рабочая версия: конвейер шагов как плагин Hermes.

### Добавлено

- CLI `hermes pipeline setup|status|run|ui|doctor|notify-test|config`.
- Движок конвейера в `<проект>/.pipeline/`: реестр планов по файлам, контракт шага из
  плана, страж «шаг → постановка → исполнение → ревью → журнал → следующий шаг»,
  идемпотентные карточки канбана, инцидентные и владельческие стоп-флаги, ручной допуск.
- Роли-скиллы: orchestrator, prompter, reviewer, next-step, plan-authoring,
  agent-prompt-authoring.
- Локальный UI (stdlib, без сборки): поток шага, планы, шаги, карточки, журнал,
  кнопки тик/стоп/продолжить, настройки, самопроверка Telegram.
- Фоновый запуск UI: `--detach` (PID в `.pipeline/ui.json`), `--stop`.
- Предпросмотр без установки: `--preview` читает настоящие планы и карточки проекта
  движком плагина, ничего не записывая; действия выключены.
- Мастер установки спрашивает токен бота (скрытый ввод, проверка `getMe`), находит
  chat id через `getUpdates`, шлёт тестовое сообщение; уведомления через Bot API.
- Создание борды, профилей ролей (clone + `reasoning_effort=max`), лимитов канбана,
  cron-джобы стража, `.gitignore`.
- Маркер `.pipeline/VERSION` и `setup --upgrade`: обновление движка в проекте без
  переустановки плагина и без потери конфига.
- Инструменты агента: `pipeline_status`, `pipeline_run`, `pipeline_control`.
- Тесты: 48 плагина + 48 движка (e2e с поддельным `hermes`, фейковый Bot API, UI, предпросмотр).
