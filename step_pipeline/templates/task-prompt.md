## 5. Как проверить (гейты)

```
<команда 1>   # ожидается: <число> passed, EXIT=0
<команда 2>   # ожидается: <вывод/файл>
```

Точечный прогон — `python -m pytest -m "not slow"` по затронутым файлам: медленные тесты
помечены `slow` и в точечный прогон не входят; полный (без `-m`) — один раз перед коммитом.

Вывод писать в файл: `<команда> > "$TMPDIR/gate.log" 2>&1; echo EXIT=$?`, затем
`grep` по файлу. Код возврата смотреть у pytest, а не у хвоста пайпа.

## 7. Формат отчёта

До коммита, по порядку: `diff stat` → ключевые диффы → самостоятельные решения с
причиной → строки гейтов (команда + число + EXIT) → что сознательно не сделано →
отклонения от промта → вопросы. Язык — язык проекта.

## 8. Вопросы (≤3, каждый с ценой вариантов)

Строкой в форме стража: `Q1: <вопрос> — A) <вариант> (цена) / B) <вариант> (цена) —
рекомендация A`. Вопрос с ID останавливает шаг до ответа владельца: пока он открыт, страж
не заказывает ни карточки шага, ни ревью. Номер `Q<N>` — свой для каждого вопроса отчёта;
без ответа через `notify.answer_timeout` секунд принимается рекомендация, поэтому буква
рекомендации — обязательный выбор автора («рекомендация нет» тоже допустимо: тогда вопрос
ждёт человека). `<Ответ уже есть в постановке — вопрос не задаётся.>`

## 9. Ревью (обязательно)

Шаг не закрывает исполнитель: после гейтов — независимое ревью ролью `reviewer`
(скилл `pipeline-reviewer`) по плану и коду; вердикт APPROVE или REQUEST_CHANGES.
При REQUEST_CHANGES шаг остаётся открытым, находки правятся, ревью повторяется.
Отчёт ревьюера — `<reviews_dir>/<план>-<шаг>.md`, ровно одна строка вердикта.
