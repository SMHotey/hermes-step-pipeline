# 0001. Один шаг за тик: почему параллельных шагов нет

Статус: принято
Дата: 2026-11-04
Шаг: план 2, §S5 (ссылки — в разделе «Ссылки»)

## Контекст

Тик — единственное место, где конвейер двигает работу: cron запускает `gate.py --run` каждые
10 минут, и за один тик страж обходит ВСЕ ведомые планы. Фактическое поведение на момент
написания (HEAD `a20da0d`; номера строк привязаны к нему, съехавшую строку искать по имени
символа):

- обход ведомых планов: `tick()` идёт по списку `driven_plans` (`driven_specs` в
  `registry.py`), сейчас ведомы два плана;
- предел действий за тик — `max_actions` из `pipeline.json` проекта, умолчание 1
  (`MAX_ACTIONS_DEFAULT`, `gate.py:134`; чтение ключа `max_actions_of`, `gate.py:1099-1113`,
  битое значение приводится к 1);
- не больше одного действия НА ШАГ за тик — инвариант D5: `step_key` (`gate.py:2168`) и
  проверка «шаг … уже получал действие в этом тике» (`gate.py:2426-2433`);
- шаг внутри плана сериализован: пока карточка последнего шага не в терминальном статусе,
  план отдаёт `idle` с причиной «шаг … в работе: карточка …» (`gate.py:780-782`) — значит
  одновременно живут шаги РАЗНЫХ планов, а не два шага одного плана;
- один тик за раз: блокировка каталога состояния `state_io.acquire` (`gate.py:2647`);
  параллельность возможна только внутри тика, между тиками — нет;
- карточка шага живёт дольше тика и работает в ОБЩЕМ дереве: `_create_card` создаёт её с
  `--workspace dir:<репозиторий>` (`gate.py:1006`), отдельных worktree нет.

Расхождение с формулировкой плана: §Контекст плана говорит, что «тик по построению делает
одно действие», а код после шага 1-S14 допускает `max_actions > 1`. Фактический инвариант
строже и другой: одно действие за тик на шаг, а не одно действие на тик целиком. План этим
ADR не правится — документ фиксирует поведение кода.

## Варианты

### Вариант A. Строго последовательный тик (текущее поведение)

Что даёт: в каждый момент одно дерево меняет один шаг; коммит, пуш и вердикт ревьюера
относятся к одному состоянию дерева; инвариант «один шаг — один круг ревью» не размывается;
дисциплина воркера («`git add` только файлами шага») остаётся подстраховкой, а не несущей
конструкцией.
Цена: второй план ждёт, пока не освободится шаг первого; время шага = работа агента плюс
ожидание тика (замеры — в разделе «Цена и риск»).
Риск: узкое место — один исполнитель и один ревьюер; при росте числа планов очередь растёт
линейно, и это замечается только по метрикам, а не по ошибкам.

### Вариант B. По одному действию на каждый ведомый план за тик (сегодня реализуемо ключом `max_actions`, умолчание 1)

Что даёт: два плана продвигаются в одном тике; ключ уже есть в конфиге и шаблоне
`pipeline.json`, писать код не нужно.
Цена: оба конфликта — по git-дереву и по каналу ревью. Git-дерево: у всех шагов одно дерево
(`--workspace dir:`, `gate.py:1006`), запрет `git add -A` держится на инструкции в теле
карточки (`gate.py:478`), а не на проверке; страж проверяет только существование коммита
(`git cat-file -e <sha>^{commit}`, `gate.py:2041`), состав коммита не сверяется; пуш идёт из
того же дерева, поэтому два пуша за тик конкурируют. Канал ревью: профиль ревьюера один
(`profiles.reviewer` в `pipeline.json`), карточка ревью создаётся на попытку
(`planloop:<план>:<шаг>:review:<n>`, `gate.py:1967`), а вердикт выносится по дереву, которое
в это время меняет второй шаг.
Риск: чужой коммит уезжает в чужой пуш, и это видно только по диффу; ревьюер судит код,
которого в дереве уже нет; два `REQUEST_CHANGES` на одном дереве дают правки, конфликтующие
по файлам, — цена ошибки не падение, а тихая потеря работы.

### Вариант C. Параллельные шаги с непересекающимися файлами (не реализовано)

Что даёт: максимум скорости — шаги, не трогающие одни и те же файлы, идут одновременно, без
ожидания тика.
Цена: те же два конфликта, что у B, плюс два новых. Первый — детектор пересечения файлов до
старта шага: объявленный в плане список «Файл:» неполон, правки по ревью выходят за него,
значит нужен отдельный worktree на шаг, а это ломает `--workspace dir:` (`gate.py:1006`) и
проверку коммита по общему HEAD (`gate.py:2041`). Второй — второй канал ревью: профиль
ревьюера на шаг, иначе два вердикта пишутся по одному дереву.
Риск: конфликт слияния в общем дереве и «зелёный» вердикт по коду, которого в дереве уже
нет; отказ обнаруживается на ревью, а не на старте.

## Решение

Выбран вариант A — текущее поведение. Последовательный тик — единственный вариант, при
котором коммит, пуш и вердикт ревьюера относятся к одному состоянию дерева, и это свойство
не требует ни нового кода, ни дисциплины воркеров: без реальной потребности в скорости
параллельность покупает время ценой двух конфликтов, которые сегодня гасятся инструкциями.

`max_actions > 1` этим ADR не рекомендуется, пока не сработали триггеры из раздела
«Триггеры пересмотра». Ориентир на случай пересмотра — не выше 3 (оценка, не замер: прогонов
с `max_actions > 1` в истории нет).

## Цена и риск

Чем платим за A (замеры на 04.11.2026):

- действие внутри тика занимает секунды, а не минуты: 15 записей в `.pipeline/state/history.jsonl`,
  `duration_s` от 1,9 до 20,0 с — почти всё время шага уходит на ожидание следующего тика
  (cron каждые 10 минут), а не на вычисление;
- время шага целиком: шаг 2-S4 — ≈35 мин (карточка создана 21:40, коммит `e8c2654` в 22:15),
  шаг 3-S4 — ≈61 мин (21:50 → коммит `56fb091` в 22:51); источник — `git log` и записи
  `create_step` в истории;
- за вечер 03.11.2026 закрыто два шага при двух ведомых планах: `close_step` = 2 за 7 дней в
  истории, накопительно `metrics.plans` — план 2: 4, план 3: 3.

Чем заплатим при B (оценка, замеров нет — прогонов с `max_actions > 1` не было):

- коммитов и пушей в одном дереве станет больше: до двух коммитов и двух пушей за тик вместо
  одного, и каждый пуш тащит правки соседнего шага, если воркер ошибся с `git add`;
- ревью у одного профиля пойдут парами, и вердикт будет относиться к дереву, изменившемуся
  после начала ревью;
- кругов правок станет больше: конфликт по файлам в общем дереве добавляет минимум один круг
  на конфликт (оценка).

## Триггеры пересмотра

Решение пересматривается, если выполнено хотя бы одно условие:

1. закрытых шагов ≥ 6 в день суммарно по всем планам на скользящем окне 7 дней, ИЛИ
2. одновременно в работе ≥ 3 планов.

Замер — одна read-only команда (на диск не пишет):

```
python .pipeline/gate.py --plan 2 --status --json
```

Ключи: `metrics.actions_7d` (действия по видам за окно), `metrics.plans` с `steps_closed` по
каждому плану.

База на 04.11.2026: 15 действий за 7 дней (`create_step` 8, `close_step` 2, `create_review` 3,
`create_fix` 2), закрыто шагов — план 2: 4, план 3: 3, ведомы два плана (`driven_plans`).
До порога (1) далеко: два закрытия за вечер против шести в день; до порога (2) — один план.
