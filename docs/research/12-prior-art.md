## Вопрос разведки

Ищем готовое для трёх вещей плана: (1) «вход, на котором снята постановка, устарел» —
пересобрать на свежем HEAD и продолжить, а не встать с инцидентом, при этом без бесконечной
пересборки; (2) вердикт по постановке ставится по закрытому списку находок (что открыто —
блокирует, что закрыто — нет), а не по счётчику кругов; (3) бюджет кругов правок задаётся
классом риска шага, а не ручной правкой `pipeline.json` под конкретный шаг, и видно метрику
циклов. Подходящее отличается тремя признаками: работает на Python 3.11 без внешних пакетов
(инвариант «только stdlib и Hermes»), не тянет сервер, базу или Node-сборку, состояние читает
из файлов проекта. Всё, что не проходит по этим трём признакам, годится только как источник
идей — вердикт «своё».

## Практики, которые берём и куда они ложатся

| Практика | Откуда | Как у нас | Шаг |
|---|---|---|---|
| Расхождение с объявленным состоянием лечится пересборкой, а не остановкой; пересборка идёт до зафиксированной версии входа | `selfHeal`/drift в Argo CD | ветка «вердикт не про эту версию» в `_prompt_review_decision` заказывает `create_prompt_fix` с причиной `stale-recon`, прошлый recon и список коммитов между версиями кладутся в карточку промптера | S1 |
| Устаревание определяется по хешу того, от чего зависит артефакт, а не по «HEAD сдвинулся» | Turborepo fingerprint | сверка не только `recon_commit`, но и списка файлов, на которые опиралась постановка: сдвиг HEAD без изменения этих файлов пересбор не требует | S1 |
| Существующая работа не выбрасывается при смене базы — её пересобирают на новой базе | `rebaseWhen: behind-base-branch` в Renovate | пересбор постановки на текущем HEAD с сохранением уже принятых находок, а не новый ревью с нуля | S1 |
| Бюджет повторов — числом попыток, а не «пока не надоест», плюс список причин, на которые не повторяем вовсе | Temporal `RetryPolicy` | `max_stale_rebuilds` (дефолт 2) на шаг; ошибки не про свежесть (нет файла, нет отчёта) в этот счётчик не идут | S1, S3 |
| Вердикт — по неразрешённым замечаниям: пока хоть одно открыто, приёмки нет; закрытые не мешают | Правило submit по `unresolved_comments_count(0)` в Gerrit | `docs/reviews/prompt-<N>-<ШАГ>-findings.md`, таблица со статусами `открыто`/`закрыто`/`не блокирует`; блокирует только `открыто`, пустой реестр = `APPROVE` | S2 |
| Блокируют находки не ниже объявленного класса, остальные остаются в отчёте | `-fail-level` в reviewdog | у находки в реестре есть класс; в S2 блокирует только `открыто`, а «не блокирует» остаётся строкой отчёта и не продлевает цикл | S2 |
| Круг, который не закрыл ни одной находки, не открывает новый круг | Обратная сторона того же правила Gerrit (нулевой прогресс к `unresolved=0`) | отказ с причиной «правка не закрыла ни одной находки» и переход к владельцу вместо следующего круга | S2 |
| Бюджет итераций — свойство шага, а не один глобальный ключ | `intensity`/`period` в child spec OTP-супервизора | `max_fix_rounds` остаётся базой, для `Риск: high` — `max_fix_rounds_high`, для `critical` — 8; значения в `pipeline.json` | S3 |
| Часть сбоев не считается в бюджет вовсе, часть закрывает работу сразу | `podFailurePolicy` (`Ignore`/`FailJob`) в Job | классификация причин отказа постановки: «нет отчёта ревью» — сразу владельцу, «вход устарел» — в бюджет пересборок | S3 |

## Отброшенные и почему

- SonarSource/sonarqube (11182★, LGPL-3.0, 2026-11-13) — сервер с базой и веб-UI ради гейта по находкам; идея «гейт по новым находкам» уже покрыта Gerrit и reviewdog, а тянуть продукт нельзя по инварианту «только stdlib и Hermes».
- bazelbuild/bazel (26102★, Apache-2.0, 2026-11-13) — JVM-сборщик и свой сервер кэша; идея хеша входа дешевле берётся у Turborepo.
- treeverse/dvc (15973★, Apache-2.0, 2026-11-09) — версионирование данных и артефактов, у нас вход — текст плана и файлы репозитория, кэша артефактов нет.
- danger/danger-js (5519★, MIT, 2026-10-26) — Node-рантайм ради правил на пул-реквестах; у нас нет PR-процесса, а находки живут в файле отчёта.
- github/spec-kit (149779★, MIT, 2026-11-12) — практика «правка отдельным кругом и повторное ревью» уже взята в плане 6 и работает; для постановки нужен вердикт по реестру, а не ещё один круг.
- Temporal Server, Argo CD, Argo Workflows как продукты — не применимы: свои серверы и базы, а у нас шаг исполняет страж из файлов проекта; взяты только принципы повторов и сверки.
- Renovate как продукт — AGPL-3.0 и Node: код и дословный текст не переносятся, взята одна идея (`rebaseWhen: behind-base-branch`).

## Итог

Готового продукта, который закрывает связку «протухший вход пересобирается без остановки +
вердикт постановки по закрытому списку находок + лимит кругов по классу риска» без внешних
зависимостей, нет: все кандидаты — либо серверы с базой (Temporal, Argo CD, Argo Workflows,
SonarQube), либо Node/JS-инструменты (Renovate, Danger, Turborepo, reviewdog), либо чужой
код под несовместимой лицензией. Готовые практики есть, и они дешёвые: сверка входа по хешу
и пересборка до зафиксированной версии (Argo CD, Turborepo, Renovate) — S1; вердикт по
неразрешённым замечаниям и порог по классу находки (Gerrit, reviewdog) — S2; бюджет попыток
у самого шага плюс список неретраибельных причин (Temporal, OTP, k8s Job) — S3. Все дни своей
реализации уже стоят в шагах плана, дополнительных зависимостей разведка не добавляет,
поэтому состав шагов и их объём не меняются. Правку раздела «Разведка» плана по этой карточке
делает отдельный шаг (S4) или карточка правки постановки, а не разведчик.

Решение: go — берём практики (Argo CD и Turborepo для свежести входа, Gerrit и reviewdog для
реестра находок, Temporal/OTP/Job для бюджета по риску), своё — механика стража и файл
реестра; продуктов не берём ни одного, лицензия AGPL (Renovate) — только идеи.
