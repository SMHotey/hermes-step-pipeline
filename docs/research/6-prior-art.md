# Разведка: план 6 «Панель: планы проектов, обновление всех движков, прогресс ревью плана»

План: `docs/plans/6-plany-panel.md`. Дата: 2026-11-12.
Метод: GitHub API (`/repos` — звёзды, дата пуша, лицензия; `/license` — файл лицензии
читался целиком), первичные страницы: MDN (showOpenFilePicker), docs.python.org
(tkinter.filedialog), kubernetes.io (Deployment), freedesktop.org (systemd.service).
Ограничение: код чужих проектов не копировался, взяты только идеи и оценки.

## Вопрос разведки

Ищем готовое для четырёх вещей плана: (1) окно панели, из которого планы всех проектов
запускаются, останавливаются, утверждаются, удаляются, а новый план выбирается файлом в
системном диалоге; (2) реестр планов всех проектов с состоянием и действием в строке;
(3) раздача обновления движка по всем проектам с ожиданием окна, пока в проекте идёт шаг;
(4) учёт кругов ревью плана с возможностью дать ещё один круг правок сверх лимита.
Подходящее отличается тремя признаками: работает на Python 3.11 без внешних пакетов
(инвариант «только stdlib и Hermes»), не требует сборки фронтенда и не тянет отдельный
сервер, базу или Node/k8s; слушает только localhost; состояние читает из файлов проекта.

## Отброшенные кандидаты и почему

- pywebview — второй GUI-стек и зависимость ради диалога, который даёт stdlib; окно панели и так браузер на localhost.
- Electron — Node-сборка и десятки мегабайт рантайма при том, что панель уже работает в браузере.
- htmx — страница уже на ванильном JS без сборки, выгоды нет, а vendored-файл в репозитории нарушает «без зависимостей».
- NiceGUI — тянет fastapi и uvicorn, то есть внешние пакеты; Streamlit — свой рантайм, автоперезапуск скрипта и переписывание UI с нуля.
- File System Access API — MDN: «Limited availability», не Baseline, нужен secure context; в Firefox и Safari метода нет, а браузер владельца не выбираем.
- filelock — движку запрещены внешние пакеты, а примитив уже есть: `step_pipeline/engine/state_io.py:113,162` (`os.open` с `O_CREAT | O_EXCL`).
- Watchtower — только Docker и обновление по таймеру, без понятия «идёт ли работа в проекте».
- systemd — код под GPL-2.0 переносить нельзя, а лишний сервис на Windows-хосте ради дебаунса не нужен.
- Ansible — GPL-3.0, инвентарь и SSH-транспорт там, где у нас локальные пути из `projects.json`.
- Rundeck — отдельный Java-сервис с ACL ради одной кнопки «обновить».
- Airflow, Dagster, Prefect, Backstage (47458 / 16392 / 24151 / 34831 звёзд, Apache-2.0, коммиты 2026-11-12, 2026-11-10, 2026-11-12, 2026-11-12) — свои серверы, базы и Node-сборка под задачу «таблица планов и четыре действия».
- Argo CD и Kubernetes как продукты — не применимы: у нас нет подов и кластера, взяты только принципы ожидания и порядка.

## Итог

Готового продукта, который закрывает связку «планы всех проектов + действия из панели +
раздача движка с ожиданием окна + круги ревью плана» без внешних зависимостей и сборки,
нет. Готовые части есть, и они дешёвые: нативный диалог файла — `tkinter` из stdlib
(0 дней, берём); «дождись окна, потом меняй» — принципы RollingUpdate и sync waves
(0 дней как идеи, 3 дня своей реализации в S8); правка плана отдельным кругом с повторным
ревью — практика spec-kit, у нас ложится на маркер `plan_<N>_rounds.json` (S1, S7).
Все UI-фреймворки, оркестраторы и раскаточные системы отвергнуты по инварианту «только
stdlib и Hermes»: панель остаётся страницей без сборки, решение по «что доступно»
считает сервер, а не страница. Правки в план по этой разведке внёс страж карточкой правки
(цикл §5a: план → разведка → правка → ревью), а не шаг плана; адреса правок и их число
записаны в разделе «Разведка» плана.

Решение: go — делаем своим: stdlib-диалог (S4), собственный роллаут с ожиданием окна
(S8), маркер дополнительного круга правок (S1, S7), реестр планов на существующем
`gate.py --plans` с кэшем 5 с (S2, S5, S6); из чужого берём только принципы.
