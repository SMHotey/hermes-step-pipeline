# Живой план доработок плагина: панель, уведомления, очередь планов

> Дата: 18.11.2026. Основание: жалобы владельца того же дня и разбор кода панели и движка.
> Артефакт разведки: `docs/research/15-prior-art.md`. Смежные документы: `docs/CONTEXT.md`
> (§9 «Что осталось», §11 «Цикл плана и его метрики»), `docs/PLAN-FORMAT.md`, `CHANGELOG.md`.

Конституция: AGENTS.md — план отвечает п.1 (план файлом в git), п.3 (у каждого шага
стоп-сигнал), п.6 (разведка до решения), п.7 (гейт — команда и прогон), п.9 (новых
зависимостей нет).

Этот план — общий список того, что нужно поправить в самом конвейере. Его ведёт владелец
вместе с разработчиком: найденное дописывается в раздел «Находки» сразу, без отдельного
согласования, а набор шагов растёт по мере разбора. Правки движка выпускаются по одному
шагу за раз, с тестами и записью в `CHANGELOG.md`.

## Цель

Четыре жалобы владельца закрыты и подтверждены тестом, а не глазами: фильтр на вкладке
«Планы» фильтрует, исполненные планы не задваиваются на «Обзоре», причина выключенного
канала уведомлений видна в `doctor` и лечится одной командой, черновики запускаются
очередью по номерам. Плюс закрыт класс «ошибку формы плана видно только в момент
утверждения».

## Разведка

Артефакт: **`docs/research/15-prior-art.md`** (разведка 18.11.2026: почему не срабатывает
`hidden`, где задваиваются исполненные планы, в каком порядке движок обходит ведомые планы,
почему `plan_lint` не доезжает до проектов, чего не хватает каналу DoorSystem).

Решение: go — правки внутри репозитория, новых внешних зависимостей нет.

Правки по разведке: 0

Лицензии кандидатов: собственный код репозитория под MIT; документация MDN (правило
`[hidden]`, `Intl.Collator`) — CC-BY-SA-2.5; обе ссылки в артефакте.

## Находки

Сюда дописывается всё, что найдено по ходу работы. Формат строки: дата, адрес, симптом,
причина, чем проверено. Закрытая находка остаётся с пометкой «закрыто» и ссылкой на шаг.

- F1 (18.11.2026) Вкладка «Планы»: фильтр по проекту, состоянию и тексту не даёт никакой
  реакции. Причина: строки планов скрываются атрибутом `hidden`, а правило
  `.plan-card { display: grid }` в `step_pipeline/ui/index.html` перебивает встроенное
  `[hidden] { display: none }` — браузер считает элемент видимым. Закрыто в 0.36.0 (шаг S1).
- F2 (18.11.2026) «Обзор»: список исполненных планов виден дважды — в свёрнутом блоке
  «Исполненные планы» (`#ov-closed`) и в общем списке строк планов (`#plans`), который
  закрытые не отфильтровывает. Закрыто в 0.36.0 (шаг S2).
- F6 (19.11.2026) Правка плана по ревью упиралась в стоп «расширила план»: допуск считался
  по числу находок, закрытых НА ТОМ ЖЕ круге, а на первом круге статусы ещё `открыто` — их
  меняет сама правка. Допуск выходил нулевым, и любая правка по ревью вставала. Живой
  случай: план 2 проекта self-analyzer, рост 13 % (1351 символ: 10371 → 11722). Закрыто в
  0.37.0: правило понижено до замера (`max_plan_growth.enforce: false` — умолчание, решение
  владельца), допуск берётся по `max(закрыто, заказано)`.
- F3 (18.11.2026) DoorSystem: канал уведомлений выключен. Факты: в `pipeline.json`
  `notify.enabled=false` и `notify.skipped=true`, у профиля `doorsystem` нет
  `STEP_PIPELINE_TELEGRAM_BOT_TOKEN` в `.env`. Установка шла с `--no-telegram`, токена не
  заводили. `doctor` показывает это как проблему, но рецепта «что сделать» не даёт.
  Шаг S5, открыто.
- F4 (18.11.2026) Черновики планов нельзя запустить очередью по номерам: утверждение
  переносило файл и писало привязку к sha256, но номер в `driven_plans` не добавляло;
  ведомые планы задавались вручную списком (`["8", "13", "6"]`), порядок обхода числовой, и
  один план даёт одно действие за проход. То есть очередь возможна, а жеста «запустить
  очередь утверждённых черновиков» нет.
  **Закрыто частично 0.36.0:** утверждение само добавляет номер в `driven_plans`
  (`plan_accept.drive_plan`, решение владельца 18.11.2026), поэтому утверждённые по очереди
  черновики встают в ведение и идут по возрастанию номера. Осталось показать очередь на
  вкладке «Планы» — шаг S4.
- F5 (18.11.2026) Ошибку формы плана видно только в момент утверждения: `plan_lint.py`
  (правила «Разведки», лицензий, файлов) живёт в плагине и не доезжает до проекта —
  в `ENGINE_FILES` его нет, поэтому пред-гейт `.pipeline/analyze.py` проверяет только
  согласованность шагов с деревом. Прецедент: план 2 проекта self-analyzer прошёл
  `analyze.py` («расхождений нет») и был отвергнут при приёме. Шаг S3, открыто.

## Шаги

### S1. Фильтр вкладки «Планы» действительно скрывает строки

- Цель: выбор проекта или состояния и ввод текста убирают из списка лишние карточки.
- Файлы: `step_pipeline/ui/index.html`, `tests/test_ui_plans_filter.py`.
- Что сделать: правило `[hidden]` в CSS панели (`.plan-card[hidden]`, `.plan-row[hidden]`,
  `.draft-card[hidden]` — `display: none`); проверить, что фильтр шагов на вкладке «Шаг» и
  фильтры ленты действий не страдают тем же классом ошибки; тест читает страницу и
  требует правило для каждого класса строк.
- Тесты/гейты: `python -m pytest tests/test_ui_plans_filter.py tests/test_ui_plans_tab.py`
  → 0 failed; `ruff check .` → All checks passed.
- Готово = в странице есть правило скрытия для трёх классов строк, и на живой панели
  выбор проекта оставляет только его карточки.
- Риск: low
- Важно: правило `[hidden]` с высокой специфичностью может спрятать элементы, которые
  сейчас видны намеренно (бейджи, блоки предпросмотра) — проверка перечнем, а не «на глаз».
- Стоп: если фильтр ломает отрисовку вкладки целиком — откат CSS и разбор по строкам.

### S2. Исполненные планы живут в одном месте

- Цель: на «Обзоре» закрытые планы видны только в свёрнутом блоке с выбором проекта.
- Файлы: `step_pipeline/ui/index.html`, `tests/test_ui_overview_plans.py`.
- Что сделать: в отрисовке `#plans` отбросить строки с состоянием «закрыт»; подпись под
  списком говорит, где искать закрытые; тест: страница фильтрует по состоянию и подпись
  про «Исполненные планы» на месте.
- Тесты/гейты: `python -m pytest tests/test_ui_overview_plans.py` → 0 failed;
  `ruff check .` → All checks passed.
- Готово = на живой панели число строк в `#plans` равно числу планов без закрытых, а
  закрытые видны в блоке «Исполненные планы».
- Риск: low
- Важно: закрытый план перестанет подсвечиваться как текущий, если он выбран, — проверка
  отдельным случаем.
- Стоп: если владелец захочет обратного (всё в одном списке) — шаг отменяется, находка
  остаётся с пометкой «решение владельца».

### S3. Пред-гейт и утверждение судят по одним правилам: интеграция `plan_lint.py` в проект

- Цель: модуль `plan_lint.py` доезжает до проекта, и `analyze.py` показывает те же ошибки
  формы, что и приём плана.
- Файлы: `step_pipeline/engine/config.py`, `step_pipeline/engine/analyze.py`,
  `step_pipeline/plan_lint.py`, `step_pipeline/setup_flow.py`,
  `tests/engine/test_analyze_lint_parity.py`.
- Что сделать: доставлять `plan_lint.py` в `.pipeline/` вместе с движком (список копируемых
  файлов и маркер `ENGINE.sha256`), из `analyze.py` вызывать его находки, когда модуль
  лежит рядом; пред-гейт печатает их в своём формате и возвращает код ошибки; тест:
  план без таблицы кандидатов валит `analyze.py` так же, как приём.
- Тесты/гейты: `python -m pytest tests/engine/test_analyze_lint_parity.py
  tests/test_setup_engine_files.py` → 0 failed; `ruff check .` → All checks passed.
- Готово = `hermes pipeline setup --upgrade` в проекте кладёт `plan_lint.py` в `.pipeline/`,
  и пред-гейт на плане без кандидатов возвращает тот же текст, что приём.
- Риск: high
- Важно: новые файлы движка обязаны доехать до живых проектов, иначе пред-гейт молча
  останется старым — проверка маркером и `doctor`.
- Стоп: если доставка файла требует ломать контракт `ENGINE_FILES` — вынести в отдельный
  шаг и не выпускать половину.

### S4. Очередь планов видна на вкладке «Планы»

- Цель: владелец видит, какие планы в ведении и какой из них страж возьмёт следующим, — по
  возрастанию номера, без чтения `pipeline.json`.
- Файлы: `step_pipeline/ui/index.html`, `tests/test_plans_queue.py`.
- Что сделать: на вкладке «Планы» строка очереди — номера из `driven_plans` по возрастанию,
  отметка «следующий» у первого незакрытого, счётчик ведомых; данные берёт снимок
  (`/api/projects` уже отдаёт состояние планов), страница ничего не досчитывает; тест:
  ответ с тремя ведомыми планами даёт очередь `6 → 8 → 13`, а план вне ведения в неё не
  попадает.
  Порядок обхода уже числовой: проверено на живом плагине — `driven_plans` `["8", "13", "6"]`
  даёт обход `6, 8, 13`. Ведение после утверждения уже пишется само (0.36.0), так что шаг
  показывает очередь, а не заводит её.
- Тесты/гейты: `python -m pytest tests/test_plans_queue.py tests/test_ui_plans_tab.py`
  → 0 failed; `ruff check .` → All checks passed.
- Готово = на живой панели вкладка «Планы» показывает очередь по возрастанию и помечает
  следующий план, а план без ведения в очередь не попадает.
- Риск: normal
- Важно: очередь может выстроить планы, которые конфликтуют по файлам — подпись «следующий»
  не обещает, что он начнётся раньше остальных при стоп-флаге.
- Стоп: если владелец хочет ручной порядок вместо числового — шаг переделывается под
  список приоритетов.

### S5. Канал уведомлений: причина видна и лечится

- Цель: `doctor` по выключенному каналу печатает не только «выключен», но и чего не хватает
  (токен в `.env` профиля, чат), а для DoorSystem канал заводится и включается.
- Файлы: `step_pipeline/doctor.py`, `docs/CONTEXT.md`, `tests/test_doctor_notify.py`.
- Что сделать: в проверке уведомлений различать три случая — отключено владельцем, нет
  токена в профиле, нет чата; каждый со своей командой-рецептом; тест на три случая;
  для DoorSystem выполнить рецепт (владелец даёт токен и чат, значения кладутся в `.env`).
- Тесты/гейты: `python -m pytest tests/test_doctor_notify.py` → 0 failed;
  `ruff check .` → All checks passed.
- Готово = `hermes pipeline doctor` в DoorSystem показывает «канал настроен» после
  заполнения `.env`, а до заполнения — чего именно не хватает.
- Риск: low
- Важно: строки с секретами не должны попадать в вывод и в тесты — только имена переменных.
- Стоп: если токена для DoorSystem нет — шаг остаётся с половиной (диагностика), включение
  канала отдельной карточкой у владельца.
