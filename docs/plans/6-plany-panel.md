# 6. Панель: планы проектов, обновление всех движков, прогресс ревью плана

Конституция: docs/CONSTITUTION.md

Цель: панель становится рабочим местом владельца по планам — планы добавляются,
запускаются, останавливаются, утверждаются и удаляются из окна панели, «Обзор» отвечает
на вопрос «что сейчас в работе», обновление движка раздаётся по всем проектам без помех
идущему шагу, а ревью плана и правки по нему видны числом и временем, с ручным кругом
правок сверх лимита.

## Контекст

Сейчас панель показывает планы только того проекта, на который запущена, и только
читает их: утверждение есть кнопкой, а запустить план в работу, остановить, удалить или
добавить новый можно лишь командами в терминале. Реестр проектов при этом уже есть
(`projects.json`), и на «Обзоре» видна сводка всех проектов — то есть данные по чужим
планам панель и так получает, но управлять ими не умеет.

Движок раздаётся по проектам отдельно: `hermes pipeline update` обновляет сам плагин,
`hermes pipeline setup --project X --upgrade` довозит `.pipeline/` в проект. При десятке
проектов это ручной обход, а обновление движка во время идущего шага опасно: подмена
`.pipeline/gate.py` под работающим тиком.

Ревью плана и правки по его результатам живут карточками `planloop:<план>:planreview:<круг>`
и `planloop:<план>:planfix:<круг>` (`gate.py:163-164`: `PLAN_REVIEW_KEY`, `PLAN_FIX_KEY`;
у первого круга номер в ключе не пишется — `planloop:6:planreview`, поэтому круги считаются
по префиксу), но в панели их не видно: на вкладке «Шаг» показан
прогресс шага, а плановый этап — нет. Лимит кругов (`max_fix_rounds`, конституция п.4)
исчерпан — страж ставит owner-стоп, и владельцу остаётся только переутверждение плана,
хотя нужен ровно один дополнительный круг правок.

Текущий дефект «Обзора» (требование владельца, 12.11.2026): блок «Обзор» рисует ВСЕ планы
проекта, а не только ведомые. `snapshot.py:615-624` собирает `progress` по всем строкам
`out["plans"]` и кладёт в строку `driven`, но не фильтрует; `ui/index.html:1405-1417`
(`ov-bars`) выводит все строки подряд. Поэтому план, убранный из `driven_plans`, остаётся
в «Обзоре» с нулевым прогрессом — владелец видит как «в работе» то, что конвейер не ведёт.
Признак `driven` уже приходит в строке; фильтр нужен на стороне снимка (S6), а не
отдельным списком планов.

## Разведка

Артефакт: `docs/research/6-prior-art.md` (12.11.2026, роль `scout`): 15 кандидатов,
лицензии, живость, цена в днях, отброшенные — с причиной. План берёт из артефакта
вердикты дословно; в таблицу внесены кандидаты, которые меняют решения плана.

| Кандидат | Лицензия | Что даёт | Цена в днях | Вердикт |
|---|---|---|---|---|
| `tkinter.filedialog` (python/cpython) | PSF-2.0 | нативный диалог выбора файла из stdlib | 0 + 2 в S4 | берём |
| pywebview | BSD-3-Clause | окно с WebView и мостом JS↔Python, свой тулкит на каждую ОС | 2 + 0.5 на релиз | своё |
| Electron | MIT | десктоп-клиент целиком: окно, меню, диалоги, автообновление | 5 + Node-сборка | своё |
| File System Access API (WICG) | W3C Software and Document License | `showOpenFilePicker` в браузере, без серверного диалога | 1 | своё |
| RollingUpdate (kubernetes) | Apache-2.0 | принцип «дождись окна, потом меняй» | 0 (идея) + 1.5 в S8A | берём |
| sync waves / health gates (argo-cd) | Apache-2.0 | порядок с ожиданием готовности, итог по каждому объекту | 0 (идея) + 1 в S8B | берём |

«Своё» у pywebview, Electron, File System Access API и systemd — идею берём, код нет:
второй GUI-стек, Node-сборка, нестандартный API браузера и GPL-код не проходят инвариант
«только stdlib и Hermes». В таблицу сознательно не внесены семь кандидатов таблицы
артефакта (`docs/research/6-prior-art.md:24-37`) — htmx, NiceGUI, Streamlit, filelock,
Watchtower, Ansible, Rundeck, — и четыре отвергнутых в прозе артефакта (`:66`): Airflow,
Dagster, Prefect, Backstage. Все отвергнуты по тому же инварианту и решений плана не
меняют (filelock заменяет уже существующий примитив
`step_pipeline/engine/state_io.py:113,162`).

Решение: go — делаем своим: диалог выбора файла на `tkinter` из stdlib (S4), собственный
«роллаут» с ожиданием окна (S8, S8A, S8B), дополнительный круг правок плана — маркер
состояния, который читает страж (S1, S7), реестр планов — на существующем
`gate.py --plans` с кэшем 5 с (S2, S5, S6). Готовые оркестраторы и UI-фреймворки
отвергнуты: у проекта инвариант «только stdlib и Hermes».

## Допущения

- «Обзор» показывает планы в состоянии `running` (решение стража) и только их; «в работе»
  значит ровно `state: running` из `plan_view`, а не «есть файл плана». План, снятый с
  ведения (`driven_plans` без номера), в «Обзоре» не показывается ни в каком виде — он
  живёт на вкладке «Планы» с состоянием «не ведётся»; остановка, закрытие и «не ведётся»
  — только на вкладке «Планы».
- «Запустить в работу» = добавить номер плана в `driven_plans` проекта и снять стоп-флаг.
  Это действие владельца из панели, а не шага конвейера.
- «Удалить план» = убрать файл плана, запись утверждения, стоп-флаг, состояние плана и
  маркер кругов; отказ, если у плана есть карточки в работе.
- Проводник открывает сервер панели (она слушает только localhost), диалог — stdlib
  `tkinter`; если окно недоступно, панель предлагает ввести путь руками.
- Дополнительный круг правок — жест владельца; автоматических кругов столько, сколько
  стоит в `max_fix_rounds` проекта (`pipeline.json:5`, умолчание движка 2), а не «два»
  (конституция, п.4).
- Обновление во всех проектах идёт тремя шагами: плагин из GitHub-релиза (S8), раздача
  движка по реестру с ожиданием окна (S8A), статус раскатки (S8B); проект в работе ждёт
  окна, а не прерывает шаг.
- Маршруты панели живут в `step_pipeline/ui_server.py` двумя диспетчерами: `do_GET`
  (`ui_server.py:2054-2110` — сюда идут ветви S2 и S6) и `do_POST`

### S7. Блок «Ревью плана» на вкладке «Шаг» и ручной круг правок (2 дн) `pipeline`

- Цель: на вкладке «Шаг» видно, на каком круге ревью плана работа стоит, сколько времени
  ушло на ревью и правки, и кнопка даёт ещё один круг правок, когда лимит исчерпан.
- Файл: `step_pipeline/plan_review_progress.py`, `step_pipeline/plan_rounds.py`,
  `step_pipeline/snapshot.py`, `step_pipeline/ui/index.html`, `step_pipeline/ui_server.py`,
  `tests/test_ui_plan_review_block.py`, `tests/test_plan_review_progress.py`
- Что сделать: блок «Ревью плана» собирается там же, где уже собирается прогресс шагов, —
  в `_plan_progress` (`snapshot.py:814-834`), вторым читателем борды и вторым запуском
  `hermes kanban` на рендер не заводится (запрет `plan:265-266`): путь к базе —
  `proj.board_db` (`step_pipeline/project.py:583-591`, env важнее конфига), карточки —
  `cards(db, key_prefix=f"planloop:{id}:")` (`snapshot.py:104`; префикс фильтруется в SQL,
  а не окном «последние N задач», применено в `snapshot.py:826`), прогоны — `_card_runs`
  (`snapshot.py:827`, объявление `:1293`), находки — разбор отчёта `_review`
  (`snapshot.py:833`, объявление `:1022`) → `progress.findings`. Снимок отдаёт готовый блок
  `plan_review`; `plan_review_progress.py` (время кругов, этап) и `plan_rounds.py` (маркер)
  считают по карточкам, которые им передал `_plan_progress`, и борду сами не открывают.
- Круги: модуль читает карточки `planloop:<план>:planreview:<круг>` и
  `planloop:<план>:planfix:<круг>` и считает круги (сделано/лимит) по префиксу ключа — у
  первого круга номера в ключе нет (`planloop:6:planreview`), а сегмент `review` занят
  ревью шага (`planloop:<план>:<шаг>:review:<попытка>`), путать виды нельзя. Единица счёта —
  те же карточки, что у движка: **карточки правок** (`planfix`) текущей эпохи, не карточки
  ревью (`_plan_review_decision`: `epoch_cards`/`epoch_fixes` ограничены `reset_at`,
  `gate.py:1963-1969`, порог `len(epoch_fixes) >= max_rounds`, `gate.py:1994`; до 0.25.2
  бюджет считался по ревью и давал 2–4 ревью подряд при живом лимите). Граница эпохи —
  `review_reset_at` записи `plan_<N>_approval.json` (`plan_accept.py:368`, читается как
  `approval_reset_at`, `gate.py:1813`): в счёт идут карточки с `created_at >= reset_at`,
  без записи — все. Счёт по карточкам ревью дал бы «4 из 4» там, где движок видит «3 из 4»,
  а после переутверждения — «5 из 4» при свежей эпохе 0: ровно то расхождение, которое
  запрещает конституция п.4 (0.25.4 закрепила правило: `--accept` начинает бюджет заново).
  Считает время каждого круга, текущий этап и находки; действие `plan_fix` пишет
  маркер `plan_<N>_rounds.json` в каталоге `paths.state` (+1 круг) и снимает owner-стоп;
  кнопка «Ещё круг правок» активна только при исчерпанном бюджете кругов, только у плана и
  только пока ручной круг не израсходован. Бюджет — тот же, что у движка из S1:
  `max_fix_rounds` плюс `extra_fix_rounds` из маркера `plan_<N>_rounds.json` в каталоге
  `paths.state` (поля `extra_fix_rounds`, `at`, `reason`); панель читает тот же файл и то же
  правило сложения, иначе в проекте с лимитом 4 и одним ручным кругом блок показал бы
  «5 из 4», условие «исчерпано» не наступало бы ни на одном круге, а один жест владельца
  превращался бы в неограниченный цикл (конституция п.4).
- Гейты: `python -m pytest tests/test_ui_plan_review_block.py tests/test_plan_review_progress.py`
  → 10 passed (10 новых: оба файла новые, в `tests/` их нет — 5 + 5)
- Готово = блок показывает «круг N из бюджета» тем же счётом, что движок: в этом проекте при
  исчерпании 4 из 4, в копии с `max_fix_rounds: 2` — 2 из 2, в копии с `max_fix_rounds: 4` и
  `extra_fix_rounds: 1` — 4 из 5 и кнопки «Ещё круг правок» нет (ручной круг не
  израсходован); после переутверждения плана (`review_reset_at` в записи утверждения) блок
  показывает 0 из бюджета, а не N из N; на эпохе с карточками ревью без ответной карточки
  правки — N из бюджета, а не N+1 (счёт по `planfix`, а не по `planreview`);
  время ревью и время правок, находки текущего отчёта; кнопка появляется
  только при исчерпанном бюджете и `extra_fix_rounds == 0`, жест пишет маркер и снимает
  стоп, а следующий тик заказывает карточку правки (проверяется тестом движка из S1)
- Риск: normal
- Стоп, если маркер, записанный панелью, движок читает иначе (разошлись имена полей), —
  вопрос владельцу; две копии правила сводить в одну точку, а не «починить тестом».
- Важно: чтение маркера в движке и в плагине — две копии одного правила (движок вендорится
  и не импортирует плагин, решение D5); расхождение ловится тестом-сторожем на оба чтения.

### S8A. Раскатка движка по реестру с ожиданием окна (1.5 дн) `pipeline`

  конвейера помечен `skipped`
- Риск: high
- Стоп, если окно не находится дольше 30 минут, — стоп и отчёт владельцу, а не молчаливое
  ожидание.
- Важно: `copy_engine` и роли обновляются только в окне между шагами — подмена
  `.pipeline/gate.py` под работающим тиком ломает идущий шаг; поэтому в проверке «идёт
