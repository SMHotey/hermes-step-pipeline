# План 4 — режим планировщика в одном профиле

## Цель

В сессии проекта, работающей под одним профилем, по фразе «составь план» включается
режим планирования: агент сначала уточняет неоднозначности, затем пишет план по
правилам конвейера в черновик, прогоняет линтер, предъявляет план владельцу и ждёт
подтверждения. Режим включён по умолчанию и выключается командой
`hermes pipeline plan-mode off` и тумблером в панели. При выключенном режиме агент на
фразу не реагирует, скилл планирования не загружается, а страж не ведёт план, который
не был утверждён владельцем.

## Контекст

- Профиль один. Отдельного профиля-планировщика нет и быть не должно: планирование —
  это режим текущей сессии, а не вторая сессия.
- Плагин умеет три вещи, которых достаточно для режима: `register_system_prompt_section`
  (текст в промт новой сессии), `register_hook("pre_tool_call")` (вето на загрузку
  скилла в текущей сессии) и `register_cli_command` (переключатель в терминале).
  Перехватить текст сообщения в CLI плагин не может — распознаёт фразу модель, а плагин
  задаёт, что модель об этой фразе знает и вправе ли она грузить скилл.
- Движок планы читает как `plans_dir.glob("*.md")` без рекурсии: подкаталог `drafts/`
  страж не видит, черновик сам не начнёт исполняться на тике cron.
- Зависимость: линтер плана (`step_pipeline/plan_lint.py`) — это шаг 1-S8 плана 1.
  S6 без него не начинать; остальные шаги от него не зависят.
- Грабли, которые план обязан не наступить: `skills.disabled` в профиле — глобальный для
  всех проектов, поэтому режим хранится в состоянии проекта, а не в конфиге профиля;
  раздел системного промпта замораживается при старте сессии, поэтому переключение
  действует со следующей сессии, а для текущей работает вето в `pre_tool_call`.

## Шаги

### S1. Состояние режима и чтение/запись (0.5 дн)

- Файл: `step_pipeline/plan_mode.py`, `tests/test_plan_mode.py`

- Что сделать: модуль с `read_mode(project) -> bool` и `write_mode(project, on)`;
  состояние в `<корень>/.pipeline/state/plan_mode.json` (`{"plan_mode": true}`, дата
  изменения), отсутствие файла или каталога читается как «включён»; запись атомарная —

- Готово = pytest по модулю зелёный, отсутствие файла даёт «включён», запись оставляет

  вето просто не появятся в новых сессиях (в проекте движок обновляется отдельно).

### S6. Черновики и утверждение плана (1.5 дн)

- Файл: `step_pipeline/plan_accept.py`, `step_pipeline/cli.py`,
  `tests/test_plan_accept.py`
- Тесты/гейты: `python -m pytest tests/test_plan_accept.py` → 9 passed
- Что сделать: `hermes pipeline plan --list|--check|--accept <N>`; `--list` показывает
  черновики и утверждённые планы с номерами; `--check` проверяет черновик — вызывает
  линтер `step_pipeline/plan_lint.py`, если он уже есть (шаг 1-S8), а пока его нет,
  делает минимальные проверки сам: разбор через `.pipeline/next_step.py --json`,
  у каждого шага непустые пункты «Файл» и «Тесты/гейты» и непустой критерий приёмки,
  журнал из пяти колонок с идентификатором шага во второй, нет повторяющихся
  идентификаторов; `--accept` отказывает, если проверки нашли ошибки, затем переносит
  файл из `<plans_dir>/drafts/` в `<plans_dir>/`, пишет `plan_<N>_approval.json` с sha256
  файла, датой и именем профиля; повторный accept того же содержимого ничего не
  дублирует и сообщает «уже утверждён».
- Готово = проверки работают и без `plan_lint.py`, и с ним, accept с ошибками
  возвращает код 1 и печатает ошибки, успешный accept переносит файл и создаёт запись
  с хэшем, совпадающим с содержимым файла, повторный accept не перезаписывает дату
  первого утверждения
- Важно: черновики лежат только в подкаталоге — движок читает `plans_dir.glob("*.md")`
  без рекурсии, поэтому неутверждённый план стражу не виден. Второй линтер не заводить:
  когда появится `plan_lint.py`, `--check` обязан делегировать ему, а свои проверки
  оставить только как запасной путь.

### S7. Страж не ведёт неутверждённый план (1 дн)

- Файл: `step_pipeline/engine/gate.py`, `step_pipeline/engine/registry.py`,
  `tests/engine/test_approval.py`, `plugin.yaml`, `CHANGELOG.md`
- Тесты/гейты: `python -m pytest` → passed, инкремент минорной версии
- Что сделать: перед постановкой карточки сверять утверждение — читать
  `plan_<N>_approval.json` из каталога состояния, пересчитывать sha256 файла плана;
  нет записи или хэш не совпал — план пропускается с причиной «план не утверждён» или
  «план изменён после утверждения»; при включённом `notify` отправлять это владельцу
  не чаще одного раза на план. Исключение только для уже идущих планов: если записи
  нет, но у плана есть файл состояния или закрытые шаги в журнале, страж пишет
  унаследованную запись (`"inherited": true`, дата, sha256) и продолжает вести план,
  сообщая об этом одной строкой в stdout. Иначе шаг перекрывает сам себе дорогу —
  после него не смог бы идти ни один из текущих планов.
- Готово = страж не заказывает карточку для нового плана без утверждения и печатает
  причину, для плана с несовпавшим хэшем ведёт себя так же, для плана с закрытыми
  шагами пишет унаследованную запись и продолжает работу, для утверждённого плана
  работает как раньше, полный прогон pytest зелёный, версия в plugin.yaml поднята,
  запись в CHANGELOG.md есть
- Важно: для новых проектов это ломающее изменение поведения, поэтому минор версии и
  строка в CHANGELOG. Обновление движка в самом проекте (`hermes pipeline setup
  --project . --upgrade`) — отдельное действие владельца; до него страж в проекте
  работает по прежней логике, и это нормально: сначала движок в исходниках, потом
  обновление у потребителей.
