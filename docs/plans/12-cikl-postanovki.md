## Разведка

Артефакт: **`docs/research/12-prior-art.md`** (снимается в S0). Вопросы: как в индустрии решают
«артефакт устарел» без остановки пайплайна (CAS/etag/lease, идемпотентные перезапуски, «retry
with fresh input»), как ведут трекер находок ревью и как ограничивают итерации по классу риска.
Кандидаты и лицензии — в артефакте; без лицензии кандидат не берётся.

Решение: **не принято до S0**. Правки по разведке: 0 — разведка не снята.

## Допущения

1. Сверка идёт по `recon_commit`: шапка постановки (`RECON_RE`, `gate.py:253`, `gate.py:635`) против
   первой строки отчёта ревью; решение принимает `_prompt_review_decision` (`gate.py:2766-2812`),
   правило D6 — `gate.py:1744`.
2. Постановка снимается заранее (prefetch), поэтому HEAD успевает уйти на любом коммите между
   снятием и ревью. Сейчас это стоп, а не пересбор: за день дважды лечилось вручную карточками
   `planloop:6:S8A:promptfix:1` и `:2`.
3. Для шага лимит кругов — `max_fix_rounds` (`config.py:74`, дефолт 2; в проекте поднят до 6),
   исчерпание даёт стоп владельцу (`gate.py:2053`). Для плана реестр находок уже есть (7-S1/S2),
   для постановки аналога нет — отсюда «шестой круг приносит новую находку».
4. Голдены вердиктов (`tests/engine/golden/`) — контракт стража: S1 меняет ветку решения, значит
   требует осознанной перезаписи эталонов с просмотром diff.

## Шаги

### S0. Разведка: свежесть входа и трекер находок (0.5 дн) `pipeline`

- Цель: понять, что из отраслевых решений применимо без внешних зависимостей: «вход протух →
  пересобрать, а не упасть», и «вердикт по закрытому списку, а не по счётчику».
- Файл: `docs/research/12-prior-art.md` (новый)
- Работа: кандидаты — (а) CAS/optimistic concurrency: перечитать вход и повторить; (б) idempotent
  retry с новым входом; (в) реестр находок как условие приёмки (у нас уже в 7-S1/S2);
  (г) лимит итераций по классу риска. По каждому: что даёт, чего стоит, лицензия.
  Гейт: `python .pipeline/scout_report.py docs/research/12-prior-art.md` → PASS.
- Тесты/гейты: `python .pipeline/scout_report.py docs/research/12-prior-art.md`
- Прогон: `python .pipeline/scout_report.py docs/research/12-prior-art.md`
- Стоп, если: ни один кандидат не проходит по лицензии — тогда решение «оставляем как есть» и план
  закрывается без кода.
- Риск: разведка сведётся к пересказу наших же планов 7 и 10 — тогда вердикт не ставится.
- Готово = артефакт с вердиктом `go|no-go` и списком кандидатов с лицензиями.

### S1. Протухшая постановка пересобирается, а не останавливает план (1.5 дн) `pipeline`

- Цель: расхождение `recon_commit` постановки и отчёта ревью перестаёт быть остановкой: страж сам
  заказывает пересбор постановки (как `promptfix`), с ограничением, чтобы не зациклиться.
- Файл: `step_pipeline/engine/gate.py`, `step_pipeline/engine/config.py`, `tests/engine/test_prompt_fresh.py` (новый)
- Работа: в `_prompt_review_decision` ветка «вердикт не про эту версию» (`gate.py:2790-2812`)
  заменяется на решение `create_prompt_fix` с причиной `stale-recon`; ключ карточки —
  `planloop:<план>:<шаг>:promptfix:<N>` (как сегодня вручную); счётчик пересборок в состоянии плана,
  лимит `max_stale_rebuilds` (дефолт 2) — после него стоп владельцу с точной причиной.
  В карточку промптера кладётся: прошлый recon, текущий HEAD, список коммитов между ними.
  Ветка «без строки `recon_commit` в отчёте» (`gate.py:2832`) сохраняется как есть.
- Тесты/гейты: `pytest tests/engine/test_prompt_fresh.py tests/engine/test_golden_verdicts.py`; при
  осознанном изменении поведения — `GOLDEN_UPDATE=1` и просмотр diff.
- Прогон: `python -m pytest tests/engine/test_prompt_fresh.py -v`
- Стоп, если: пересбор запускается чаще двух раз подряд на один шаг — тогда стоп владельцу и
  находка в S3 (лимит по риску не сходится).
- Риск: бесконечная пересборка при активной разработке (каждый коммит двигает HEAD) — лечится
  лимитом и тем, что пересбор идёт на HEAD, зафиксированный в карточке.
- Готово = расхождение recon не даёт `incident`-стопа; на живом проекте шаг продолжается после
  автоматического пересбора, счётчик виден в `--status`.

### S2. Реестр находок постановки: вердикт по закрытому списку (1.5 дн) `pipeline`

- Цель: «круги исчерпаны» перестаёт быть счётчиком: ревью постановки ведёт накопительный реестр
  находок, и вердикт ставится по нему — как это уже сделано для плана в 7-S1/S2.
- Файл: `step_pipeline/engine/gate.py`, `step_pipeline/engine/config.py`, `step_pipeline/roles/pipeline-plan-reviewer/SKILL.md`, `tests/engine/test_prompt_findings.py` (новый)
- Работа: файл `docs/reviews/prompt-<N>-<ШАГ>-findings.md`, таблица
  `| ID | Класс | Находка | Что сделать | Статус |`; статусы `открыто`, `закрыто`, `не блокирует`;
  блокирует только `открыто`. Ревьюер обязан в каждом круге отмечать, какие находки прошлого круга
  закрыты (сегодня это делает словами, в отчёте 6-S8A такие таблицы уже появляются де-факто).
  Правило приёмки: круг правок, который закрыл 0 находок, не открывает новый круг, а уходит владельцу
  с причиной «правка не закрыла ни одной находки».
- Тесты/гейты: `pytest tests/engine/test_prompt_findings.py tests/engine/test_golden_verdicts.py`
- Прогон: `python -m pytest tests/engine/test_prompt_findings.py -v`
- Стоп, если: реестр не создаётся на шагах без находок — тогда пустой реестр означает `APPROVE`.
- Риск: реестр станет формальностью («закрыто» без правки) — проверка: у закрытой находки в отчёте
  есть адрес и строка, которая её закрывает.
- Готово = вердикт постановки считается по реестру; на 6-S8A-подобном шаге видно, что закрыто, а что
  открыто, и сколько кругов осталось по делу.

### S3. Лимит кругов по классу риска и метрика циклов (1 дн) `pipeline`

- Цель: лимит перестаёт быть ручной настройкой под конкретный шаг: он зависит от риска шага, а
  метрика «кругов на постановку» видна в статистике.
- Файл: `step_pipeline/engine/config.py`, `step_pipeline/engine/gate.py`, `step_pipeline/stats.py`, `tests/engine/test_fix_rounds_risk.py` (новый)
- Работа: `max_fix_rounds` остаётся базой (`config.py:74`), но для шага с `Риск: high` берётся
  `max_fix_rounds_high` (дефолт 6), для `critical` — 8, для `normal` — база. Значения — ключи
  `pipeline.json`, не код. В `stats.py` — метрика «кругов правок и пересборок на шаг» и «доля шагов,
  где круг закрыл 0 находок».
- Тесты/гейты: `pytest tests/engine/test_fix_rounds_risk.py tests/test_stats.py`
- Прогон: `python -m pytest tests/engine/test_fix_rounds_risk.py -v`
- Стоп, если: лимит по риску маскирует настоящую проблему (шаг на 8 кругах) — тогда находка в S2, а
  не повышение лимита.
- Риск: метрика начнёт стимулировать «закрывать находки ради счётчика» — поэтому пара «кругов» и
  «закрыто находок за круг» считается вместе.
- Готово = лимит берётся из риска шага, метрики видны, ручная правка `pipeline.json` под конкретный
  шаг больше не нужна.

## Что НЕ входит в план

1. **Отмена кругов правок вообще** — бюджет остаётся (конституция п.4), меняется только предмет
   вердикта и способ закрытия цикла.
2. **Остановка текущего цикла 6-S8A** — шаг доводится на действующих правилах; план 12 включается
   следующим, чтобы не менять правила под работающий шаг.
3. **Автоматическое утверждение плана** — правка плана по разведке и ревью плана остаются как есть.
4. **Правка `driven_plans`/`profiles` шагом** — порядок ведения планов задаёт владелец.
