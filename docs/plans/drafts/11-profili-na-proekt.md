# План 11. Профили на проект: изоляция ролей вместо общих имён

> Дата: 14.11.2026. Черновик. Основание: запрос владельца 14.11.2026 — заводить профили под каждый
> проект автоматически, чтобы воркеры разных проектов не пересекались; исполнитель — по имени
> проекта; служебные роли получают скиллы из пакета плагина, а не из чужого профиля.
> Смежные документы: `docs/plans/drafts/10-smotritel-sessiy.md` (S1 создаёт профиль смотрителя тем же
> механизмом), `docs/plans/7-svodimost-revyu.md` (S7 — дрейф движка), `step_pipeline/setup_flow.py`.

Конституция: `docs/CONSTITUTION.md`, 10 пунктов. План отвечает: п.1 (изоляция — часть установки, а не
ручная настройка), п.2 (у каждого изменения есть шаг, коммит и прогоны), п.4 (правка `profiles`
остаётся за владельцем: мастер только предлагает ключи), п.5 (решения по именам профилей названы
отдельно от кода), п.6 (сначала разведка — S0), п.10 (`default` и чужие профили не трогаются).

## Разведка

Артефакт: **`docs/research/11-prior-art.md`** (снимается в S0). Вопросы разведки: как в Hermes
устроены профили (клон, скиллы, лимиты, гейтвей), что копирует `profile create --clone-from`, как
резолвятся скиллы у cron-воркера, и какие схемы изоляции воркеров применяются вне Hermes (namespaces,
systemd-шаблоны `name@instance`, Ansible-роли, `git worktree`-на-проект). Кандидаты и их лицензии —
в артефакте; без лицензии кандидат не берётся.

Решение: **не принято до S0**. Правки по разведке: 0 — разведка не снята.

## Допущения

1. `profile create <имя> --clone-from <источник>` копирует **всё**: `config.yaml`, `.env`, `SOUL.md`,
   скиллы (`--no-skills` несовместим с клоном — проверено CLI 14.11.2026). Значит «наследование от
   `default`» — это одноразовая копия, а не живая связь: расхождение после клона никто не отслеживает.
2. Имя профиля допускает дефис (проверено: `zz-probe-dash` создан и удалён) — схема
   `<slug>-<роль>` технически возможна.
3. `slug` проекта берётся из `projects.json` (`id`), а не из имени каталога: реестр — единственный
   источник, `C:\Users\malik\gapaudit` уже расходится с именем проекта.
4. Скиллы роли в профиль ставит мастер (`setup`), а не клон: клон от `default` притащил бы все
   скиллы `default`, включая не относящиеся к делу.
5. `default`-профиль принадлежит другой сессии и не клонируется «как есть» без `--clone-from` —
   источником берётся конфиг, но не память и не история.

## Шаги

### S0. Разведка: как Hermes изолирует профили и что копирует клон (0.5 дн) `pipeline`

- Цель: до кода известно, что именно даёт изоляцию, а что — иллюзию: клон копирует или наследует,
  где резолвятся скиллы у cron-воркера, как живут ключи в нескольких `.env`.
- Файл: `docs/research/11-prior-art.md` (новый)
- Работа: кандидаты — (а) профиль-на-проект с junction плагина; (б) общие служебные роли + очередь;
  (в) один профиль на роль с лимитом `kanban.max_in_progress_per_profile`; (г) внешние схемы
  (systemd `@instance`, Ansible, k8s namespace) как источник предохранителей. По каждому: что даёт,
  чего стоит, лицензия. Гейт: `python .pipeline/scout_report.py docs/research/11-prior-art.md` → PASS.
- Тесты/гейты: `scout_report.py` PASS; артефакт лежит в `docs/research/`.
- Прогон: `python .pipeline/scout_report.py docs/research/11-prior-art.md`
- Стоп, если: ни один кандидат не проходит по лицензии или требует внешнего пакета — тогда решение
  «оставляем общие роли» и план закрывается без кода.
- Риск: разведка превратится в описание Hermes-доков без вывода — тогда вердикт не ставится.
- Готово = артефакт с вердиктом `go|no-go`, кандидаты с лицензиями, правки плана по разведке внесены.

### S1. Правило имени и реестр профилей проекта (0.5 дн) `pipeline`

- Цель: у проекта появляется предсказуемый набор профилей `slug` (исполнитель), `slug-prompter`,
  `slug-reviewer`, `slug-scout`; имя проверяется до создания, коллизия — отказ, а не «взяли что было».
- Файл: `step_pipeline/setup_flow.py`, `step_pipeline/engine/config.py`, `tests/test_profile_naming.py` (новый)
- Работа: функция `profile_slug(project_id)` — latin lowercase, `[a-z0-9-]`, длина ≤ 24, отказ на
  пустом/числовом/занятом имени; `role_profile(project_id, role)` собирает `<slug>` и `<slug>-<роль>`.
  Проверка занятости идёт через `hermes profile list` один раз за установку (не по вызову на роль).
  Ключи `profiles` в `pipeline.json` мастер **предлагает** (`--print-profiles`), записывает только по
  `--yes` владельца — `AGENTS.md` п.2 про `driven_plans`/`profiles` не отменяется.
- Тесты/гейты: `pytest tests/test_profile_naming.py tests/test_setup_flow.py`
- Прогон: `python -m pytest tests/test_profile_naming.py -v`
- Стоп, если: занятое имя принадлежит профилю не нашего реестра — тогда решение владельца, а не
  переименование чужого профиля.
- Риск: два проекта с одинаковым `id` в реестре — тогда отказ по уникальности `slug`.
- Готово = имя строится одной функцией, тесты на отказы зелёные, `--print-profiles` печатает набор.

### S2. Создание профилей проекта из пакета, без клона скиллов (1.5 дн) `pipeline`

- Цель: `hermes pipeline setup --project <путь>` доводит профили до рабочего состояния: модель,
  лимиты, доверенные каталоги, junction плагина, `.env`, без копирования чужой памяти и истории.
- Файл: `step_pipeline/setup_flow.py`, `tests/test_setup_profiles.py` (новый)
- Работа: `ensure_project_profiles()` переиспользует уже существующие кирпичи —
  `ensure_role_profile()` (клон драйвера + `agent.max_turns`, `kanban.max_in_progress*=1`,
  `failure_limit`), `link_plugin_profile()` (junction на установленный пакет), `ensure_plugin_enabled()`,
  `write_env()`. Источник конфига — `default` (модель/провайдер), а не чужой проект; `--clone-from
  default` только для `config.yaml`, скиллы ставятся отдельно (S3). Память и сессии не копируются.
  `.env`: один источник — ссылка на файл профиля-эталона (`profiles/<slug>/.env`), остальные роли
  читают его; копий ключа не заводим.
- Тесты/гейты: `pytest tests/test_setup_profiles.py`; на Windows — junction создаётся и удаляется.
- Прогон: `hermes pipeline setup --project C:/Users/malik/PycharmProjects/DoorSystem --profiles --yes`
- Стоп, если: `default` недоступен (другая сессия) — тогда источником становится профиль проекта,
  а расхождение печатается предупреждением, а не глушится.
- Риск: `--clone-from` тащит чужие скиллы; обходим тем, что профиль создаётся пустым, а скиллы
  ставит мастер (S3) — тест на «в профиле нет скиллов чужого проекта».
- Готово = повторный запуск идемпотентен, профили ролей существуют, лимиты и плагин на месте.

### S3. Скиллы ролей — из пакета плагина, с версией (1 дн) `pipeline`

- Цель: скилл роли в профиле всегда соответствует версии пакета; «скилл старше пакета» видно, а не
  ловится по симптому «skill not found» в cron.
- Файл: `step_pipeline/setup_flow.py`, `step_pipeline/doctor.py`, `tests/test_roles_version.py` (новый)
- Работа: `SKILL_CATEGORIES` остаётся, но установка идёт из пакета с маркером версии
  (`profiles/<профиль>/.skills-version.json`: имя скилла → версия плагина); `setup --upgrade`
  переустанавливает только изменившиеся; `doctor` даёт находку `skill-stale` при расхождении.
  Тот же маркер пишется в `.hermes/skills` проекта — cron и интерактивная сессия видят одно и то же.
- Тесты/гейты: `pytest tests/test_roles_version.py tests/test_doctor*.py`
- Прогон: `hermes -p doorsystem pipeline doctor`
- Стоп, если: скилл в профиле правился руками — тогда diff показывается владельцу, а не затирается.
- Риск: маркер разъедется с фактическим содержимым — тогда сверка по sha256, а не по номеру версии.
- Готово = `doctor` ловит устаревший скилл, `--upgrade` лечит, руками ничего не копируется.

### S4. Проверки в doctor и панели: профили видны (1 дн) `pipeline`

- Цель: сломанная установка профилей видна до тика: нет профиля роли, профиль без плагина, лимит
  `max_in_progress_per_profile ≠ 1`, ключи не читаются, карточка не показывает свой проект.
- Файл: `step_pipeline/doctor.py`, `step_pipeline/snapshot.py`, `tests/test_doctor_profiles.py` (новый)
- Работа: находки `profile-missing`, `profile-no-plugin`, `profile-limits`, `profile-env`;
  в снапшоте и панели у карточки — `project` рядом с `assignee`; в `pipeline.json` реестр
  `projects.json` читается диспетчером, а не угадывается по имени профиля.
- Тесты/гейты: `pytest tests/test_doctor_profiles.py tests/test_ui_server.py`
- Прогон: `hermes pipeline doctor`
- Стоп, если: панель начнёт показывать чужие профили как «свои» — тогда проект берётся из карточки,
  а не из имени профиля.
- Риск: лишний шум в doctor на legacy-проектах — находки только для ведомых планов.
- Готово = по одному `doctor` видно состояние профилей всех проектов реестра.

### S5. Миграция живых установок и откат (1 дн) `pipeline`

- Цель: pipeline, doorsystem и gapaudit переезжают на `<slug>-<роль>` без простоя; старые общие
  профили остаются, пока владелец не решит иначе; откат — одной командой.
- Файл: `step_pipeline/setup_flow.py`, `docs/MIGRATION.md` (новый), `tests/test_profiles_migrate.py` (новый)
- Работа: `setup --migrate-profiles` создаёт новые профили, переносит `profiles` в `pipeline.json`
  (по `--yes`), оставляет старые профили включёнными до первой успешной недели; журнал переноса в
  `.pipeline/state/profiles.json`; откат `--rollback-profiles` возвращает ключи из журнала.
- Тесты/гейты: `pytest tests/test_profiles_migrate.py`; прогон на gapaudit в режиме `--dry-run`.
- Прогон: `hermes pipeline setup --project C:/Users/malik/gapaudit --migrate-profiles --dry-run`
- Стоп, если: в момент миграции идёт шаг (running-карточка) — миграция ждёт окна.
- Риск: две карточки на один шаг при переключении — ключи карточек не меняются, меняется только
  assignee, поэтому дублей нет.
- Готово = три проекта работают на новых профилях, откат проверен на одном из них.

### S6. Документация, версия, раскатка (0.5 дн) `pipeline`

- Цель: правило имён и порядок миграции описаны там, где их читают: README, ARCHITECTURE, CONTEXT.
- Файл: `README.md`, `docs/ARCHITECTURE.md`, `docs/CONTEXT.md`, `CHANGELOG.md`, `step_pipeline/plugin.yaml`
- Работа: раздел «Профили проекта» в README, схема изоляции в ARCHITECTURE, решение — в CONTEXT §решения;
  версия минорная (меняется установка), запись в CHANGELOG; `templates/pipeline.json.example` получает
  комментарий про `<slug>-<роль>`.
- Тесты/гейты: `python -m pytest`, `ruff check .`, `hermes plugins validate step_pipeline`
- Прогон: `python -m pytest`
- Стоп, если: после раскатки тик живого проекта падает на отсутствии профиля — тогда раскатка
  откатывается, а находка идёт в S4.
- Риск: доки описывают схему, которой нет в коде — сверка примеров с `--print-profiles`.
- Готово = версия выпущена, доки совпадают с поведением, потребители обновлены.

## Что НЕ входит в план

1. **`default`-профиль не трогается**: он принадлежит другой сессии и другому владельцу; источник
   конфига читается, но не переписывается.
2. **Удаление чужих профилей**: на хосте 23 профиля (writer, sales, lawyer и др.) — план их не
   переименовывает и не удаляет, даже если имя похоже на проектный `slug`.
3. **Общая очередь на роль вместо изоляции** — вариант из разведки (S0), но не цель этого плана.
4. **Смотритель сессий** — план 10; здесь только то, что ему нужно от профилей (существование, лимиты).
5. **Правка `driven_plans`/`profiles` шагом** — по `AGENTS.md` это владелец; мастер предлагает ключи.
