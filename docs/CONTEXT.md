# Контекст проекта — конвейер шагов (hermes-step-pipeline)

Документ для передачи между сессиями и людьми: что это, откуда взялось, как устроено,
что уже сделано и что осталось. Обновлён 2026-11-01.

---

## 1. Что это

Плагин Hermes, который ведёт план шаг за шагом без участия человека:

```
план (docs/plans/N-*.md)
   → постановка (роль prompter пишет промт шага, гейт формы)
   → исполнение (роль-исполнитель делает шаг, коммит)
   → ревью (отдельный профиль reviewer, вердикт в docs/reviews/)
   → журнал (пишет только гейт, после проверки вердикта И коммита)
   → следующий шаг (cron каждые 10 минут, тик = одно действие)
```

Ключевое: решения принимает **скрипт**, а не агент. Агенты пишут код и вердикты,
гейт читает файлы и выполняет действия. Поэтому конвейер нельзя «уговорить» проскочить
шаг, а состояние всегда восстановимо из репозитория проекта.

## 2. Откуда взялось

Выделено из проекта DoorSystem, где та же схема жила жёстко привязанной к продукту:
`scripts/plan_gate.py` + роли `saas-prompter` / `saas-reviewer` + скилл
`doorsystem-plan-next-step` + PG-слоты, `build.bat`, PySide и прайсы.

В переносимую версию **не** попало: имена проектов, бизнес-логика, предметные скиллы,
сборка exe, слоты тестовой БД. Попало: сам механизм, роли, шаблоны, установщик, UI.

Один из прежних выводов, определивших архитектуру: `APPROVE` от ревьюера недостаточно —
нужен ещё коммит, иначе шаг «закрыт» на словах. И журнал пишет только гейт, иначе
агент может закрыть шаг, которого не было.

## 3. Принятые решения (и почему)

| Решение | Причина |
|---|---|
| Отдельный репозиторий, не внутри продукта | свой semver и релизы; продуктовые гейты (сборка, миграции, полный прогон) не должны касаться общего инструмента; установка = `hermes plugins install` |
| Движок — 7 скриптов на stdlib | работает без зависимостей и без самого плагина; копируется в проект как `.pipeline/` |
| Плагин не импортирует движок, только subprocess | проекты могут нести разные версии движка; изоляция и понятные ошибки |
| Движок в проекте вендорится и помечается `.pipeline/VERSION` | cron и ревью работают без установленного плагина; `setup --upgrade` обновляет без потери конфига |
| Идемпотентные ключи карточек `planloop:<план>:<шаг>:<вид>` | повторный тик не плодит дубли, воркер может упасть и перезапуститься |
| Ровно один круг правок | второй `REQUEST_CHANGES` — эскалация владельцу, иначе цикл «правь-правь» бесконечен |
| Стопы двух видов | инцидентный снимается сам после устранения причины; владельческий («остановка после выполнения шага») — только `--resume`, иначе решение человека теряется |
| UI только на 127.0.0.1, без авторизации | это панель владельца на его машине, а не сетевой сервис |
| Telegram — только уведомления (Bot API) | не конфликтует с уже подключённым ботом-шлюзом профиля |
| Предпросмотр без установки (`--preview`) | можно посмотреть настоящий проект, ничего в него не записав |
| Постановка N+1 до закрытия N; ревью постановки перед стартом | владелец 03.11: шаг не считается выполненным, пока нет постановки следующего; устаревшая постановка проверяется ревьюером против HEAD, свежая (recon_commit = HEAD) идёт без ревью; реализация — план 2 S6 |

    next_step.py         контракт следующего шага из плана

## 5. Инварианты (нарушать нельзя)

1. Гейт — скрипт, не агент. Никаких «агент решит, можно ли закрыть шаг».
2 Шаг не начинается без постановки: нет промта — карточка prompter, а не «исполнитель догадается».
3. Журнал пишет только гейт, и только при `APPROVE` + существующем коммите.
4. Секреты — только в `.env` профиля; в логах и UI токен не появляется.
5. В репозитории нет имён и предметной логики проектов-потребителей.
6. Действия в предпросмотре запрещены, панель слушает только localhost.

## 8. Грабли, уже пойманные (не наступать снова)

- **Постановку нельзя писать одним куском.** Воркер промптера упирается в лимит вывода
  модели (`finish_reason=length`), файл не создаётся, карточка уходит в повтор и дважды
  выжигает `max_runtime` 2700 с. Правило в скилле: части по 40–70 строк + `wc -l` после
  каждой. Тест-сторож: `tests/test_roles.py::test_prompter_skill_writes_prompt_in_chunks`.
- **Адреса кода в спеке — только якоря.** Строки разъезжаются после каждой вставки, ревью
  ловит это как блокирующее. Формат `файл.py#ANCHOR:имя` → комментарий `# ANCHOR:имя`.
  Тест-сторож: `tests/test_roles.py::test_spec_anchors_resolve_to_code` (якорь без кода или
  задвоенный якорь валит прогон).
- **Улучшения ролей живут в `step_pipeline/roles/`, а не в `.hermes/`.** `.hermes/` в
  `.gitignore` — правка там не доезжает до других проектов и не попадает в коммит.
  Тесты-сторожа: `test_reviewer_skill_requires_recommendations_section`,
  `test_prompter_skill_writes_prompt_in_chunks`.
- **`hermes` в PATH не гарантирован.** Тесты не должны звать настоящий бинарник:
  подделывать `proj.run_hermes` (иначе CI на ubuntu падает `FileNotFoundError: 'hermes'`).
- **Windows-консоль cp1251.** Любой русский вывод движка падал `UnicodeEncodeError`,
  и страж выглядел сломанным. В `main()` каждого скрипта и в CLI плагина stdout/stderr
  переключаются на UTF-8 с `errors="replace"`.
- **`pytest.ini` уже содержит `-q`.** Дополнительный `-q` в командной строке даёт `-qq`
  и итоговая строка «N passed» пропадает — это не поломка тестов.
- **Борда канбана.** `kanban --board <b> init` сам борду не создаёт: нужно
  `kanban boards list` → `boards create` → `init`.
- **Диспетчеризация CLI Hermes.** Обработчик команды — `args.handler`
  (`set_defaults(func=…)` молча ничего не делает).
- **`plugins validate` показывает caution `dump_all_env`** — ложное срабатывание на слово
  в тексте документации, не секрет.
- **Предпросмотр vs установка.** `--preview` ничего не пишет в проект; если нужен
  работающий конвейер в проекте — это `setup`, он создаёт `.pipeline/`, роли, борду, cron.
- **cron шлюза не отдаёт `.env` профиля.** В no-agent джобе приходит `HERMES_HOME`
  профиля, а `STEP_PIPELINE_TELEGRAM_*` в окружении нет: уведомления движка молчат,
  хотя `hermes pipeline notify-test` из CLI работает. Поэтому тик-скрипт сам дочитывает
  `profiles/<профиль>/.env` (см. 1-S17); проверять канал надо не CLI-командой, а пробой
  в контексте джобы.
- **`skills trust` нужен каждой роли, а не только драйверу** (1-S15): иначе воркер падает
  `Unknown skill(s): pipeline-prompter`, карточка уходит в `blocked` по `failure_limit`.
- **Ключ провайдера должен быть сохранён в профиле, а не в переменной окружения** (1-S16):
  профиль с `source: env:OPENCODE_GO_API_KEY` работает в интерактивной сессии и падает
  под демоном шлюза с `No usable credentials found`.
- **22 % у `gate.py` — артефакт подпроцессов, а не «непроверено»** (1-S10): e2e-тесты зовут
  `gate.py` из `.pipeline/` временного проекта, и без крючка `sitecustomize.py` +
  `COVERAGE_PROCESS_START` дочерний процесс не меряется вовсе. `source = step_pipeline`
  вместо `include` и отсутствие `[paths]` возвращают артефакт: копия из temp остаётся
  отдельной строкой отчёта, а `step_pipeline/engine/gate.py` — низкой. `COVERAGE_FILE`
  задавать только абсолютным, иначе данные ребёнка пишутся в его cwd и `combine` их не
  находит.

## 9. Что осталось

- Публичный репозиторий или private — решение владельца (сейчас private).
- «Почтальон» между ролями (переписка промптер↔исполнитель↔ревьюер через Telegram
  или kanban-мост) — в DoorSystem эту роль играл отдельный мост.
- Реальная установка в DoorSystem вместо предпросмотра — только с согласия владельца
  (добавит `.pipeline/`, `pipeline.json`, 6 ролей в `.hermes/skills`).
- Actions в CI — сделано 1-S10: `actions/checkout@v7` и `actions/setup-python@v7`,
  валидация манифеста вынесена отдельным job `manifest` (composite action
  `plugin-validate@v2026.9.24`), молчаливого «шаг пропущен» больше нет.
- Покрытие — сделано 1-S10, замер честный (с подпроцессами): TOTAL 77 %, `gate.py` 82 %,
  порог `fail_under = 75` по правилу `floor(TOTAL − 2)`. Следующая цель 1-S12: `tick.py`
  (32 %) и `step_card.py` до 80 %; `step_card.py` сейчас в отчёт не попадает вовсе — его
  не импортирует ни движок, ни тесты, поэтому мерить там нечего, пока S12 не позовёт его.
- Генератор standalone-версии движка, если понадобится работа без Hermes вообще.

## 10. План работ (после 0.1.0)

Разбор проекта 0.1.0 дал 28 шагов работ, они лежат планами конвейера в `docs/plans/`
и уже разбираются движком (`--list-plans`: 14 + 5 + 9 шагов):

| План | О чём |
|---|---|
| `1-stabilnost.md` | дефекты P1–P3: формат ссылки на коммит, pathspec-коммит, блокировка тика, crash-proof `main`, единый парсер плана, UTF-8 в подпроцессах, CSRF панели, линтер плана, сторож простоя, покрытие и CI, манифест, тесты cron-пути, спека формата, `max_actions` |
| `2-upravlenie.md` | риск шага и ручной допуск, переписка ролей в карточках, история тиков и метрики, команды владельцу боту, ADR о параллельности |
| `3-panel.md` | панель: кэш и живое обновление, обзор «что сделает Тик», экран шага, мастер установки, проверки в панели, мультипроектность, валидация конфигурации, клавиатура и темы, лента событий |
| `4-planner.md` | режим планировщика в одном профиле: флаг состояния и переключатели (CLI, панель), промт-секция с фразами-триггерами, вето на загрузку скилла при выключенном режиме, протокол роли (уточнения → черновик → линтер → предъявление), черновики и утверждение плана, страж не ведёт неутверждённый план |

Порядок: 1 → 2 → 3. Шаги 3-S2, 3-S3, 3-S5, 3-S9 опираются на линтер (1-S8), метрики
(2-S3) и риск шага (2-S1); остальные независимы. План 4 ни от чего не блокируется:
шаг 4-S6 вызывает линтер 1-S8, если тот уже есть, а пока его нет — проверяет черновик
сам, чтобы план не ждал чужого шага.

Движок в проекте — вендорированная копия в `.pipeline/`. Правки `step_pipeline/engine/`
в проекте не действуют, пока владелец не выполнит `hermes pipeline setup --upgrade`;
поэтому S7 плана 4 меняет логику стража в исходниках и не рвёт текущий прогон.

Найдено прогоном этих же планов через движок: пункт «Готово = …» с двоеточием внутри
(`Готово = шаг с Риск: high …`) теряет критерий целиком — `section_blocks` режет пункт по
первому двоеточию, и `_READY_RE` ищет «Готово» уже в остатке. Это учтено в шаге 1-S5;
до его выполнения в планах не ставить двоеточие в пункте «Готово =».
