# Контекст проекта — конвейер шагов (hermes-step-pipeline)

Документ для передачи между сессиями и людьми: что это, откуда взялось, как устроено,
что уже сделано и что осталось. Обновлён 2026-11-16.

---

## 1. Что это

Плагин Hermes, который ведёт план шаг за шагом без участия человека:

```
план (docs/plans/N-*.md)
   → разведка (роль scout пишет docs/research/N-prior-art.md с вердиктом на кандидата)
   → правка плана (отметка «Правки по разведке: N»)
   → ревью плана (вердикт и метка plan_sha256: в docs/reviews/plan-N.md)
   → постановка (роль prompter пишет промт шага, гейт формы)
   → исполнение (роль-исполнитель делает шаг, коммит)
   → ревью (отдельный профиль reviewer, вердикт в docs/reviews/)
   → журнал (пишет только гейт, после проверки вердикта И коммита)
   → следующий шаг (cron каждые 10 минут, тик = одно действие)
```

Каждый переход оставляет артефакт, который проверяется гейтом, а не памятью агента.

Ключевое: решения принимает **скрипт**, а не агент. Агенты пишут код и вердикты,
гейт читает файлы и выполняет действия. Поэтому конвейер нельзя «уговорить» проскочить
шаг, а состояние всегда восстановимо из репозитория проекта.

## 2. Откуда взялось

Выделено из внутреннего проекта владельца, где та же схема жила жёстко привязанной к
продукту: `scripts/plan_gate.py` + роли `<проект>-prompter` / `<проект>-reviewer` +
скилл `<проект>-plan-next-step` + слоты тестовой БД, `build.bat`, PySide и прайсы.

В переносимую версию **не** попало: имена проектов, бизнес-логика, предметные скиллы,
сборка exe, слоты тестовой БД. Попало: сам механизм, роли, шаблоны, установщик, UI.

Один из прежних выводов, определивших архитектуру: `APPROVE` от ревьюера недостаточно —
нужен ещё коммит, иначе шаг «закрыт» на словах. И журнал пишет только гейт, иначе
агент может закрыть шаг, которого не было.

## 3. Принятые решения (и почему)

| Решение | Причина |
|---|---|
| Отдельный репозиторий, не внутри продукта | свой semver и релизы; продуктовые гейты (сборка, миграции, полный прогон) не должны касаться общего инструмента; установка = `hermes plugins install` |
| Движок — 7 скриптов на stdlib | работает без зависимостей и без самого плагина; копируется в проект как `.pipeline/` |
| Плагин не импортирует движок, только subprocess | проекты могут нести разные версии движка; изоляция и понятные ошибки |
| Движок в проекте вендорится и помечается `.pipeline/VERSION` | cron и ревью работают без установленного плагина; `setup --upgrade` обновляет без потери конфига |
| Идемпотентные ключи карточек `planloop:<план>:<шаг>:<вид>` | повторный тик не плодит дубли, воркер может упасть и перезапуститься |
| Круги правок по риску шага (ключ `max_fix_rounds`, по умолчанию 2; `max_fix_rounds_high` — 6) | после первого `REQUEST_CHANGES` исполнитель получает ещё круг: одна правка редко закрывает все замечания; эскалация владельцу — по исчерпании лимита, иначе цикл «правь-правь» бесконечен. Владелец 15.11.2026: у шага с `Риск: high` предел выше (план 12, S3) — опасный шаг дороже, и цена ошибки в нём выше; классов ровно три, ступени выше `high` нет |
| Реестр находок постановки (`prompt-N-SX-findings.md`, план 12 S2) | владелец 15.11.2026. До 0.28.0 реестры постановок ревьюеры вели по скиллу, но страж их не читал: вердикт брался из текста отчёта, и «все замечания закрыты» было неотличимо от «отчёт написан до правки» — круг правок уходил в переписывание уже исправленного (замер: 76 ревью постановок, 47 переписываний). Реестр сильнее отчёта: действующий вердикт считается по статусам, блокирует только `открыто`, класс маршрута не выбирает. Колонки «Шаг» нет — постановка принадлежит одному шагу |
| Круг правок открывается только блокирующей находкой (план 13, S1; 0.35.0) | вердикт и классы находок не сверялись, поэтому `REQUEST_CHANGES` из одних замечаний открывал круг правок. Замер 15.11.2026: 47 шагов, 72 ревью, 27 правок, 520 мин правок из 5 860 мин шагов, в 24 отчётах ревью шагов 61 % находок стилистические, 12-S3 — два круга без блокирующей находки. Теперь вердикт считается по классам: блокирующая находка по-прежнему держит шаг, а круг из замечаний без блокирующего класса не заказывается — шаг закрывается строкой «принято с замечаниями», замечания остаются в реестре неблокирующими |
| Реестр находок шага (`step-НОМЕР-ШАГ-findings.md`, план 13 S2; 0.35.0) | у круга правок не было памяти: круг N+1 судил закрытое заново и открывал новые темы (12-S3, 6-S3). Страж заводит файл из отчёта первого `REQUEST_CHANGES` (по строке на пункт с меткой класса), дальше ведёт ревьюер; шаг держит только статус `открыто`; словарь — классы находок (`блокирующая`, `значимая`, `стилистическая`), а не классы-маршруты постановки. Порядок решения: реестр шага → сверка вердикта с классами → лимит кругов |
| Выпуск объявляется тегом **и** GitHub Release (принято при выпуске патча `0.28.1`, 15.11.2026; слова владельца ждёт — §9) | `update.latest` (`step_pipeline/update.py::latest`) читает `/releases/latest` и берёт теги только фолбэком, поэтому выпуск «только тегом» автообновлению невидим: после `v0.28.0` (тег без релиза) `hermes pipeline update --check` продолжал отвечать «на GitHub 0.27.1». Прежний Д6 постановки 12-S4 («только тег, плагин находит обновление по тегам») отменён — его посылка ложна. Цена обратного: версии у потребителей расходятся, пока владелец не обновит руками |
| Пауза по расписанию (`quiet_hours`, до двух окон системного времени; 0.28.2) | владелец 15.11.2026: нужны часы, в которые конвейер не трогает проект сам — ночь и обед. Окна считает движок по локальному времени ОС (как `notify.digest_at`), в окне `--run` выходит с кодом 0 и не делает ни одного действия: cron не должен получать ошибку за каждый ночной тик. Начало окна включается, конец — нет (в 07:00 работа уже идёт); окно через полночь — `23:00`–`07:00`. Мусор в окнах — ошибка конфигурации, а не тихое умолчание: иначе владелец думает, что пауза стоит, а конвейер работает. Команды владельца (`--stop`/`--resume`/`--hold`) паузы не слушают |
| Стопы двух видов | инцидентный снимается сам после устранения причины; владельческий («остановка после выполнения шага») — только `--resume`, иначе решение человека теряется |
| UI только на 127.0.0.1, без авторизации | это панель владельца на его машине, а не сетевой сервис |
| Telegram — только уведомления (Bot API) | не конфликтует с уже подключённым ботом-шлюзом профиля |
| Адрес Bot API — из окружения (`STEP_PIPELINE_TELEGRAM_API_BASE`, фолбэк на `TELEGRAM_API_BASE_URL`) | там, где `api.telegram.org` заблокирован, и конвейер, и шлюз идут через один прокси-воркер Cloudflare; движок не читает базу настроек, потому что работает и без плагина. Воркер пропускает только токены из своего `BOT_TOKENS` — новый бот в списке иначе получит 404 ([docs/TELEGRAM-PROXY.md](TELEGRAM-PROXY.md)) |
| Предпросмотр без установки (`--preview`) | можно посмотреть настоящий проект, ничего в него не записав |
| Постановка несёт адреса фактов символами и командами, а не `файл:строка` (план 8, S2A) | владелец 15.11.2026. Замер истории (48 шагов): 76 ревью постановок, 47 переписываний; в режиме `prompt_review: auto` ревью заказывается только для протухшей постановки, поэтому первое ревью всегда судило дрейф адресов (12-S3: 2 находки из 5 — чистый сдвиг строк после закрытия S2). Отмена предзаказа постановки обсуждалась и отклонена: она стоит 50–70 мин простоя на старте шага, а дрейф по свежести уже лечится пересборкой (`:promptfix-stale:`, 12-S1); выключение предзаказа без `prompt_review: always` вообще выключает ревью постановок — «свежая идёт без ревью» записано решением строкой выше |
| Предзаказ постановки N+1 до закрытия N; ревью постановки перед стартом | владелец 03.11: шаг не считается выполненным, пока нет постановки следующего; устаревшая постановка проверяется ревьюером против HEAD, свежая (recon_commit = HEAD) идёт без ревью; реализация — план 2 S6. Владелец 05.11: `REQUEST_CHANGES` по постановке не останавливает конвейер — страж ставит карточку промптеру «переписать постановку» (`:promptfix:<N>`), после неё ревью повторяется (`:promptreview:<N>`); стоп только по исчерпании `max_fix_rounds` |
| Один шаг за тик: параллельных шагов нет, ключ `max_actions` — предел действий, а не параллельность ([ADR 0001](adr/0001-odin-shag-za-tik.md)) | конфликт по git-дереву и по каналу ревью дороже выигрыша в скорости; пересмотр — по числовым триггерам из ADR |
| Поведение стража зафиксировано golden-вердиктами (`tests/engine/golden/`, 0.23.0) | у `gate.py` 4907 строк и ~18 % непокрытых ветвей — Telegram-диалог, стопы, риск-допуск. Пока вердикты проверялись только утверждениями в тестах «по месту», регрессия в непокрытой ветке проходила молча, а слово «поведение не меняется» было обещанием. Теперь состояние проекта и ожидаемое решение лежат в репозитории данными: раннер гоняет настоящий `gate.py`, маскирует время/пути/sha и сравнивает по путям |

## 4. Состав

```
step_pipeline/
  plugin.yaml        манифест (имя, версия, kind: backend, provides_tools)
  __init__.py        регистрация CLI и инструментов агента
  cli.py             hermes pipeline setup|status|run|ui|doctor|notify-test|config
  project.py         поиск корня проекта, чтение pipeline.json, вызовы hermes, UTF-8 stdio
  setup_flow.py      мастер установки, копирование движка/ролей, upgrade, cron, .env
  snapshot.py        снимок состояния для UI и инструментов (только чтение)
  stats.py           метрики цикла (разведка, правки, ревью плана) — только чтение файлов проекта
  telegram.py        Bot API: getMe, getChat, getUpdates, sendMessage
  tools.py           инструменты агента pipeline_status / pipeline_run / pipeline_control
  ui_server.py       HTTP-сервер панели (stdlib)
  ui_control.py      фоновый запуск/остановка панели (PID, лог)
  ui/index.html      одностраничная панель
  engine/            движок, который копируется в проект как .pipeline/
    __init__.py          пустой пакетный `__init__`: модули запускаются файлами из `.pipeline/`
    analyze.py           анализ согласованности плана, разведки и дерева проекта
    approval.py          утверждение плана: «можно ли начинать шаги» и привязка ревью к версии
    check_task_prompt.py гейт формы промта (9 обязательных блоков)
    config.py            конфиг проекта + UTF-8 stdio, список `ENGINE_FILES`
    gate.py              страж: шаг → ревью → журнал → следующий шаг
    next_step.py         контракт следующего шага из плана
    plan_cycle.py        корректировка плана по разведке: якорь, вердикт, отметка, дифф
    registry.py          планы, журнал, стоп-флаги
    scout_report.py      гейт артефакта разведки: разделы, таблица кандидатов, вердикты
    state_io.py          атомарная запись файлов состояния и блокировка тика
    step_card.py         карточка канбана на шаг
    tick.py              один тик для cron
  roles/             скиллы ролей: orchestrator, prompter, reviewer, next-step,
                     plan-authoring, agent-prompt-authoring
  templates/         план, промт, pipeline.json, фрагмент проекта-AGENTS
tests/               тесты плагина; tests/engine/ — тесты движка отдельным слоем
```

Артефакты прогонов (`docs/prompts/`, `docs/reviews/`, `docs/research/`, `docs/templates/`)
живут и у потребителей, и здесь: репозиторий ведёт сам себя, поэтому каталоги заполнены.
Замер 16.11.2026, 09:05: в `docs/prompts/` 33 постановки, в `docs/reviews/` 71 отчёт, в
`docs/research/` 8 разведок `<N>-prior-art.md`, в `docs/templates/` 1 шаблон. Счётчики
растут с каждым шагом (ревью этого шага добавит свой отчёт), поэтому это замер момента, а
не константа.
`docs/prompts/`, `docs/reviews/` и `docs/templates/` перечислены в `.gitignore` (правила 13,
14, 10), поэтому в публикацию они не входят; `docs/research/` — в git (10 файлов: восемь
разведок и два шаблона). Правило публикации: в публикацию имена и логика потребителей не входят —
журналы `docs/plans/*.md` ссылаются на файлы, которых в публикации нет (формат артефактов —
[docs/PLAN-FORMAT.md](PLAN-FORMAT.md)).

## 5. Инварианты (нарушать нельзя)

1. Гейт — скрипт, не агент. Никаких «агент решит, можно ли закрыть шаг».
2 Шаг не начинается без постановки: нет промта — карточка prompter, а не «исполнитель догадается».
3. Журнал пишет только гейт, и только при `APPROVE` + существующем коммите.
4. Секреты — только в `.env` профиля; в логах и UI токен не появляется.
5. В репозитории нет имён и предметной логики проектов-потребителей.
6. Действия в предпросмотре запрещены, панель слушает только localhost.

## 6. Состояние на 2026-11-18

- Версия `0.42.2` (25.11.2026): панель перестала пересобирать снимок на каждый кадр и
  перестала зависать насовсем. Сборка стоит три запуска движка (17.6 с `--plans` + 2.2 с
  `--status` + 1.5 с `next_step.py` на 17 планах), а кэш жил 2.5 с — меньше интервала опроса
  страницы (30 с) и переподключения потока (25 с), поэтому запросы вставали в очередь на замке
  сборки (живой случай: `/api/projects` — 80 с, `/api/snapshot` — больше пяти минут).
  Что сделано: строки планов в снимке берутся из кэша `panel_pause.plans`; у `snapshot()` есть
  `max_age` (панель — 60 с, агент — 2.5 с); поток событий пересобирает снимок не чаще
  `EVENTS_MIN_BUILD = 3` с; сборка идёт в одиночку на ключ (`_INFLIGHT` и в `snapshot`, и в
  `panel_pause.plans`), а пришедшие вторыми получают прошлый ответ вместо ожидания; внешняя
  команда с таймаутом убивается и её пайпы ждутся не дольше `KILL_WAIT_SECONDS = 5` с
  (`project.run`, `gate._run`). Последнее — корень «панель не отвечает»: на Windows
  `subprocess.run(timeout=…)` после убийства ребёнка ждёт читающие потоки бесконечно, если

  её снимает работа по `gate.py --plans` (15 вызовов `build_ctx` на 15 планов), это следующий шаг.

## 8. Грабли, уже пойманные (не наступать снова)

- **Профиль роли делят между проектами только по признаку, а не «для чистоты скиллов».** Общий
  профиль держит замок `kanban.max_in_progress_per_profile: 1`: пока постановка DoorSystem
  писалась в общем `prompter`, постановка движка ждала — 60–110 минут на карточку, и второй
  проект стоял в очереди (замер 22.11.2026). Смешивания скиллов при этом не происходит:
  роли приходят из `<проект>/.hermes/skills`, карточка несёт рабочее дерево проекта, профиль
  знания проекта не переносит. Признаки разведения: другая модель/провайдер/набор
  инструментов; факты проекта в памяти профиля; роль — бутылочное горлышко (ожидание
  свободного профиля больше 20 % времени шага); своя методика роли. Драйвер и постановщик —
  по проекту, `pipeline-keeper`/`pipeline-orchestrator`/`pipeline-observer` — общие.
  Порядок: `hermes profile create <проект>-<роль> --clone-from <драйвер>`, затем
  `hermes pipeline setup --project <проект> --upgrade` — он же оформляет новому профилю
  доверие проекту; без доверия карточка падает на старте. С 0.40.0 это не договорённость,
  а код: умолчание роли считается от имени проекта (`setup_flow.role_profile_default`),
  явно указанный чужой профиль `setup` не принимает (код 2 с рецептом), а `doctor`
  предупреждает «профиль <роль> обслуживает ещё проект <имя>». Допущение 8 плана 17.
- **Пауза панели — жест реестра, а не свойство вкладки.** Плашку «Пауза запрошена, но
  остановлены не все планы: нет данных» владелец видел при живой паузе (25.11.2026), и это
  были две разные ошибки. Снимок читал `state.pause` выбранного проекта, а заполняет его
  только сторож на состоянии сервера: у соседних проектов состояние создаётся на первом
  обращении и пусто всегда. И в реестре лежал остаток `pause` без жеста (`requested_at: 0`,
  `projects: {}`, только отметки доставки) — `panel_pause.mark` писал его через
  `if not marker`, а `read_pause` всегда возвращает словарь с полями, так что проверка не
  срабатывала. С 0.42.5 пауза — это `requested_at` или непустые `projects`; отметка без
  жеста не пишется; снимок берёт жест с сервера; экран различает `pending` («ещё считается»)
  и пустой `unstopped` («останавливать нечего»). Проверки —
  `tests/test_panel_pause.py::test_pause_state_is_registry_wide_across_tabs` и соседние.
- **Обновление движка не сбрасывает паузы работы.** Своё `quiet_hours` проекта остаётся
  байт в байт: `upgrade` его не пишет, `build_config` не перезаписывает (`{**base, **existing}`).
  Проект, у которого окон ещё нет, получает ТЕКУЩИЕ значения владельца из реестра
  (`projects.json` → `pause: {enabled, windows}`) — иначе после смены шаблона плагина проект
  молча терял бы паузы, а «по умолчанию» в шаблоне окон нет вовсе. `enabled: false` с
  непустыми окнами — осознанное «паузы выключены», его не трогаем. Правило владельца
  23.11.2026; проверка — `tests/test_pause_inherit.py`.

- **Выключенный канал уведомлений в `doctor` говорит причину и рецепт (15-S5).** До 0.37.2
  любая из трёх причин печаталась одной немой строкой «Telegram: не настроен»: владелец не
  знал, канал выключен его решением (`notify.skipped`) или шаг установки не закрыт, и какой
  командой это лечится. Теперь `doctor.notify_rows` различает «выключен владельцем», «нет
  переменной токена», «нет переменной чата», а у включённого канала с обеими переменными
  пингует Bot API; к каждой причине приложена команда (`setup --telegram-token … --yes
  --no-smoke` или `config --set notify.enabled true`). Сети при выключенном канале нет —
  постановка 15-S5 требует, чтобы тест на три состояния шёл без Telegram. Тест-сторож:
  `tests/test_doctor_notify.py` (8 тестов).
- **Постановку нельзя писать одним куском.** Воркер промптера упирается в лимит вывода
  модели (`finish_reason=length`), файл не создаётся, карточка уходит в повтор и дважды
  выжигает `max_runtime` 2700 с. Правило в скилле: части по 40–70 строк + `wc -l` после
  каждой. Тест-сторож: `tests/test_roles.py::test_prompter_skill_writes_prompt_in_chunks`.
- **Адреса кода в спеке — только якоря.** Строки разъезжаются после каждой вставки, ревью
  ловит это как блокирующее. Формат `файл.py#ANCHOR:имя` → комментарий `# ANCHOR:имя`.
  Тест-сторож: `tests/test_roles.py::test_spec_anchors_resolve_to_code` (якорь без кода или
  задвоенный якорь валит прогон).
- **Улучшения ролей живут в `step_pipeline/roles/`, а не в `.hermes/`.** `.hermes/` в
  `.gitignore` — правка там не доезжает до других проектов и не попадает в коммит.
  Доезжает она через `setup --upgrade`: роль приводится к версии плагина, прежняя копия
  уходит в `.pipeline/roles-backup/` (с 0.6.0; до этого роли копировались только при
  первой установке и правки в проектах не обновлялись никогда).
  Тесты-сторожа: `test_reviewer_skill_requires_recommendations_section`,
  `test_prompter_skill_writes_prompt_in_chunks`,
  `test_upgrade_refreshes_changed_role_and_keeps_backup`.
- **`setup --upgrade` берёт движок из УСТАНОВЛЕННОГО плагина, а не из чекаута.** Если сам
  плагин когда-то был поставлен копией из рабочего чекаута (git на Windows отдаёт CRLF),
  копии в проектах уносят CRLF и mtime чекаута, а `hermes pipeline update` переписывает
  плагин в LF — `doctor` сверяет байты и красит «копия расходится с плагином при равной
  версии», хотя код тот же (разница только в переводах строк). Лечится повторным
  `setup --upgrade` после `update`: `copy_engine` сравнивает байты и перезаписывает файл.
  Маркер `ENGINE.sha256` этого не ловит — он считается от самой копии. С `0.32.0` повторять
  руками не нужно: `update` раскатывает движок сам (`rollout.after_update`).
- **Сгенерированный cron-скрипт молчит, если у него нет точки входа.** `pipeline_update.py`
  (автообновление) собирался из `setup_flow.UPDATE_SCRIPT` и не заканчивался
  `if __name__ == "__main__"`: `main()` объявлялась и не вызывалась, джоба каждый день
  выходила с кодом 0 и ничего не обновляла — «автообновление есть» на бумаге, а плагин
  стоял на прежней версии (найдено 17.11.2026 при разборе 6-S9). Правило: у любого
  сгенерированного скрипта точка входа проверяется тестом, который запускает его
  подпроцессом (`tests/test_rollout_after_update.py::test_cron_script_rolls_engine_after_successful_update`),
  а не чтением текста. Второе в том же месте: cron-джоба ходит под `HERMES_HOME` СВОЕГО
  профиля, а панель на этом хосте — с реестром хоста (`%LOCALAPPDATA%\hermes\projects.json`).
  Поэтому раскатку делает `rollout.registries()` — корневой реестр и все `profiles/*`:
  пакет на хосте один, значит и движок в проектах всех реестров должен стать один. Ходить
  только по реестру своего профиля нельзя — он на живой установке оказался пустым
  (`{"projects": []}`), и `update` честно рапортовал «раскатывать нечего». То же правило
  с 0.42.3 действует и для панели: `project.projects_file()` берёт `<корень>/projects.json`,
  профильный — только если корневого нет (25.11.2026 панель, поднятая из профиля, показывала
  один проект вместо четырёх).
- **`profile_dir` не слушает `HERMES_HOME`.** `project.profile_dir()` берёт `LOCALAPPDATA`/`~`,
  поэтому тест, который зовёт `setup --upgrade`/`ensure_update_cron`, писал скрипты
  автообновления в ЖИВЫЕ `profiles/<имя>/scripts/` (найдено 17.11.2026: в `default` и `demo`
  лежали скрипты с путём реестра из pytest-tmp). Подмена — в autouse-фикстуре
  `tests/conftest.py`, не в отдельных тестах.
- **`hermes` в PATH не гарантирован.** Тесты не должны звать настоящий бинарник:
  подделывать `proj.run_hermes` (иначе CI на ubuntu падает `FileNotFoundError: 'hermes'`).
- **Windows-консоль cp1251.** Любой русский вывод движка падал `UnicodeEncodeError`,
  и страж выглядел сломанным. В `main()` каждого скрипта и в CLI плагина stdout/stderr
  переключаются на UTF-8 с `errors="replace"`.

  `gate.parse_question_lines(текст)` → **0 вопросов**, хотя §8 содержит Q1 с вариантами и
  рекомендацией. Следствие: вопрос не попадает в `plan-N-questions.md`, страж не встаёт «до
  ответа», ответ владельца нигде не фиксируется, а шаг молча идёт по рекомендации автора.
  Живой случай: Q1 плана 2 (self-analyzer) — ответ «A» владелец дал в чате 20.11.2026, в реестр
  вопросов он не попал. Лечение: разрешить необязательные `**` в регулярке (и перед `Q`, и вокруг
  двоеточия), тест-сторож на три формы строки (`Q1:`, `- Q1:`, `**Q1:`); дополнительно —
  предупреждение стража, если в постановке есть `Q\d+:` без зарегистрированного вопроса.

  `CreateProcess` дописывает к имени только `.exe`, а `npm` на Windows — `npm.cmd` в `PATH`
  (человек ту же строку в `cmd` исполняет); и `&&` после `shlex.split` уезжал аргументом в

  будущее: строка прогона обязана запускаться и в bash, и в `cmd` — `|`, `>`, `;` и

планы 10/11/12 (номера заняли другие темы) и маршрут. Правка плана обнуляет его
утверждение: план 6 и план 8 перед постановкой в работу нужно утвердить заново.

Движок в проекте — вендорированная копия в `.pipeline/`. Правки `step_pipeline/engine/`
в проекте не действуют, пока владелец не выполнит `hermes pipeline setup --upgrade`;
поэтому S7 плана 4 меняет логику стража в исходниках и не рвёт текущий прогон.

Найдено прогоном этих же планов через движок: пункт «Готово = …» с двоеточием внутри
(`Готово = шаг с Риск: high …`) теряет критерий целиком — `section_blocks` режет пункт по
первому двоеточию, и `_READY_RE` ищет «Готово» уже в остатке. Это учтено в шаге 1-S5;
до его выполнения в планах не ставить двоеточие в пункте «Готово =».

## 11. Цикл плана и его метрики

Цикл до первого шага исполнения — четыре звена, и у каждого свой артефакт:

| Звено | Артефакт |
|---|---|
| План | `docs/plans/N-имя.md` с журналом шагов |
| Разведка | `docs/research/N-prior-art.md` — таблица кандидатов, у каждого вердикт |
| Правка плана | отметка `Правки по разведке: N` в тексте плана |
| Ревью плана | `docs/reviews/plan-N.md` — вердикт и метка `plan_sha256:` |
| Утверждение | `.pipeline/state/plan_N_approval.json` |

`step_pipeline/stats.py` считает по этим файлам четыре числа; ручного ввода нет:

- «планов с разведкой» — планы, у которых есть раздел «Разведка» и артефакт
  `N-prior-art.md` рядом;
- «вердиктов без готового решения» — строки таблицы кандидатов, где вердикта «берём» и
  «форкаем» нет: «своё» и «не берём» значат «готовое решение отвергнуто осознанно»;
- «правок по разведке на план» — сумма N из отметок, делённая на число планов с отметкой;
- «ревью плана с первого раза» — планы с вердиктом, привязанным к текущей версии плана,
  и ровно одним кругом ревью в истории тиков.

Пятое число — цена кругов правок шага (план 12, S3; `stats.cycle_metrics`): круги на шаг
(`rounds_per_step`, обе серии — `:fix:` и `:promptfix:`), сами круги правок (`fix_rounds`),
пересборки постановок (`stale_rebuilds`), закрытые находки постановок (`findings_total`,
`findings_closed`, `closed_per_round`) и доля шагов, где круг не закрыл ни одной находки
(`zero_close_steps` из `zero_close_base`). Считается по истории тиков (`history.jsonl`) и
реестрам `prompt-N-SX-findings.md`, а не назначается: у проекта без кругов или без реестров
числа пустые («—»), и это честнее нуля.

Где видно: `hermes pipeline status` печатает строку «Цикл: …», панель показывает блок
«Цикл плана» на вкладке «Обзор». В `gate.py --status` этих чисел нет намеренно: страж
решает, что делать сейчас, а метрики цикла на решение не влияют.

### Глобальная пауза и автозагрузка (0.25.0)

`step_pipeline/panel_pause.py` — жест «Остановить после шага» на весь реестр, `autostart.py` —
запуск панели при входе в систему. Решения и причины:

- **пауза — это команды движка, а не новый механизм.** Каждому открытому плану каждого
  проекта уходит `gate.py --stop --plan N` (owner-флаг). Поэтому шаг, который идёт сейчас,
  доигрывается, а следующий не начинается — ровно то, что обещает подпись кнопки, и без
  правок движка;
- **«открытый план»** — план, у которого есть следующий шаг (`next` не пуст). Закрытым
  планам флаги не ставятся: иначе панель показывала бы «СТОП» у давно законченного плана;
- **намерение хранится, состояние считается.** В `projects.json` (ключ `pause`) лежат время
  жеста, проекты и планы — по ним «Запустить всё» снимает ровно свои флаги. Подпись кнопки,
  наоборот, считается из стоп-флагов и борд, поэтому переживает перезагрузку страницы и не
  расходится с реальностью, если флаг сняли руками;
- **кнопка смотрит на `all_stopped`, уведомление — на `all_paused`.** «Запустить всё» можно
  нажать и во время последнего шага (передумал) — это разрешено; «Все проекты на паузе»
  отправляется только когда в реестре не осталось карточек в работе;
- **жест идёт в фоне, а не в HTTP-запросе.** `gate.py --stop` берёт блокировку тика, а её
  держит идущий шаг — до получаса (`state_io.STALE_AFTER`). Синхронный ответ висел бы
  ровно в тот момент, когда стоп нужнее всего, а таймаут процесса убивал бы `--stop`
  до записи флага. Поэтому `act_pause_all`/`act_resume_all` возвращают `started: true`
  сразу, работу делает поток, состояние приходит в снимке (`pause.working`), а второй
  жест во время работы отклоняется с 409 — два потока дрались бы за ту же блокировку;
- **сторож паузы живёт отдельным потоком** (`watch_pause`, шаг 10 с): снимок не запускает
  движок по соседним проектам, а уведомление уходит в момент, когда закрылась последняя
  карточка. `gate.py --plans` кэширован в `panel_pause`: запись снимается отпечатком
  источников (файлы планов, состояние, борда, отчёты), а `PLANS_TTL` (120 с) страхует то,
  чего в отпечатке не видно. Предел обязан быть больше одного запроса панели, иначе
  запись первого проекта истекала внутри того же запроса (F03 прогонов 14-S2);
- **пуш один на жест.** Адреса Telegram дедуплицируются по (токен, чат): у проектов часто
  один бот. Отметка доставки — в маркере (`notified_at`), а не в памяти: перезапуск панели
  не повторяет сообщение. В браузере всплытие показывается только на переходе «не все» →
  «все на паузе», чтобы открытие панели не всплывало старую паузу;
- **автозагрузка читает систему, а не настройки.** Чекбокс показывает состояние задачи
  `Pipeline_Panel` (Windows) или файла автозапуска (linux/macOS). Уже включённая автозагрузка
  не перезаписывается: `enable` отвечает «уже включено» — иначе панель затирала бы чужой
  сценарий запуска;
- **порт пишется настоящий.** Автозагрузка получает порт только после `bind` (`serve`
  выставляет его в состояние сервера); со случайным портом включение отказывает — запись
  «порт 0» означала бы, что панель поднимается на новом адресе каждый вход;
- **тесты не трогают систему:** `autostart` принимает подменяемый runner (фейковый
  `schtasks`) и каталог home, а linux/macOS-пути уводятся в `XDG_CONFIG_HOME`/tmp.

### Прогресс шага (0.24.0)

`step_pipeline/progress.py` отвечает на три вопроса панели: насколько выполнен шаг, сколько
ревью нашло ошибок и сколько осталось. Правила — в докстринге модуля (P1–P7), коротко:

- процент шага идёт по каноническому пути постановка → исполнение → ревью → журнал,
  вес этапа — его доля в длительности шага; открытый шаг 100 % не показывает;
- веса учатся: при `min_samples` замерах на этап (по умолчанию 3) они считаются по медианам
  длительностей закрытых карточек плана, иначе действуют умолчания 10/55/25/10; настройка —
  `ui.progress` в `pipeline.json` (движок её не читает);
- круг правок идёт отдельным отрезком и полосу не откатывает: иначе добавленная работа
  выглядела бы откатом уже сделанной;
- находки ревью считаются по разделу «Находки» отчёта шага; неразобранный раздел даёт «?»,
  а не ноль; история кругов не хранится — отчёт один файл и перезаписывается, поэтому
  счётчик всегда про текущий круг;
- остаток — сумма медиан оставшихся этапов плюс открытые круги; вилка по квартилям, без
  нужного числа замеров — пометка «грубо», без замеров вовсе — оценки нет.

Ограничения счёта — чтобы числа не читались как больше, чем они есть:

- круги ревью берутся из `history.jsonl` движка; файл обрезается до 2000 строк, поэтому
  у очень старого плана круги могут быть недосчитаны;
- вердикт считается только привязанным к текущей версии плана (метка `plan_sha256:`
  совпала с sha256 версии плана — файла без содержимого журнала, 0.22.1; метка по сырым
  байтам принимается, пока файл не менялся); иначе состояние `stale` — «APPROVE был, но
  план правился». Строка журнала версией не считается: закрытие шага вердикт не сбрасывает;
- план без строки `Конституция:` в шапке движок ревью не назначает вовсе — в снимке это
  `skipped`, а не долг «нет отчёта»;
- две разные строки вердикта в одном отчёте — `invalid`: конвейер не угадывает, какая
  из них главная;
- старый пятиколоночный артефакт считается по последней ячейке строки, поэтому вердикты
  «не берём» попадают в «без готового решения».

Чего проект не делает:

- не начинает шаг без постановки — нет промта, значит карточка промптеру (инвариант 2);
- не закрывает шаг на словах: только APPROVE плюс существующий коммит (инвариант 3);
- не начинает шаги плана без свежего вердикта ревью плана (`approval.review_status`);
- не берёт готовое решение без вердикта на кандидата (`scout_report`, проверка R3);
- не считает метрики руками и не правит историю: `stats.py` только читает файлы проекта;
- не трогает владельческие ключи `profiles` и `driven_plans` в `pipeline.json`.
