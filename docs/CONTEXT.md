# Контекст проекта — конвейер шагов (hermes-step-pipeline)

Документ для передачи между сессиями и людьми: что это, откуда взялось, как устроено,
что уже сделано и что осталось. Обновлён 2026-11-08.

---

## 1. Что это

Плагин Hermes, который ведёт план шаг за шагом без участия человека:

```
план (docs/plans/N-*.md)
   → разведка (роль scout пишет docs/research/N-prior-art.md с вердиктом на кандидата)
   → правка плана (отметка «Правки по разведке: N»)
   → ревью плана (вердикт и метка plan_sha256: в docs/reviews/plan-N.md)
   → постановка (роль prompter пишет промт шага, гейт формы)
   → исполнение (роль-исполнитель делает шаг, коммит)
   → ревью (отдельный профиль reviewer, вердикт в docs/reviews/)
   → журнал (пишет только гейт, после проверки вердикта И коммита)
   → следующий шаг (cron каждые 10 минут, тик = одно действие)
```

Каждый переход оставляет артефакт, который проверяется гейтом, а не памятью агента.

Ключевое: решения принимает **скрипт**, а не агент. Агенты пишут код и вердикты,
гейт читает файлы и выполняет действия. Поэтому конвейер нельзя «уговорить» проскочить
шаг, а состояние всегда восстановимо из репозитория проекта.

## 2. Откуда взялось

Выделено из внутреннего проекта владельца, где та же схема жила жёстко привязанной к
продукту: `scripts/plan_gate.py` + роли `<проект>-prompter` / `<проект>-reviewer` +
скилл `<проект>-plan-next-step` + слоты тестовой БД, `build.bat`, PySide и прайсы.

В переносимую версию **не** попало: имена проектов, бизнес-логика, предметные скиллы,
сборка exe, слоты тестовой БД. Попало: сам механизм, роли, шаблоны, установщик, UI.

Один из прежних выводов, определивших архитектуру: `APPROVE` от ревьюера недостаточно —
нужен ещё коммит, иначе шаг «закрыт» на словах. И журнал пишет только гейт, иначе
агент может закрыть шаг, которого не было.

## 3. Принятые решения (и почему)

| Решение | Причина |
|---|---|
| Отдельный репозиторий, не внутри продукта | свой semver и релизы; продуктовые гейты (сборка, миграции, полный прогон) не должны касаться общего инструмента; установка = `hermes plugins install` |
| Движок — 7 скриптов на stdlib | работает без зависимостей и без самого плагина; копируется в проект как `.pipeline/` |
| Плагин не импортирует движок, только subprocess | проекты могут нести разные версии движка; изоляция и понятные ошибки |
| Движок в проекте вендорится и помечается `.pipeline/VERSION` | cron и ревью работают без установленного плагина; `setup --upgrade` обновляет без потери конфига |
| Идемпотентные ключи карточек `planloop:<план>:<шаг>:<вид>` | повторный тик не плодит дубли, воркер может упасть и перезапуститься |
| Два круга правок (ключ `max_fix_rounds`, по умолчанию 2) | после первого `REQUEST_CHANGES` исполнитель получает ещё круг: одна правка редко закрывает все замечания; эскалация владельцу — по исчерпании лимита, иначе цикл «правь-правь» бесконечен |
| Стопы двух видов | инцидентный снимается сам после устранения причины; владельческий («остановка после выполнения шага») — только `--resume`, иначе решение человека теряется |
| UI только на 127.0.0.1, без авторизации | это панель владельца на его машине, а не сетевой сервис |
| Telegram — только уведомления (Bot API) | не конфликтует с уже подключённым ботом-шлюзом профиля |
| Адрес Bot API — из окружения (`STEP_PIPELINE_TELEGRAM_API_BASE`, фолбэк на `TELEGRAM_API_BASE_URL`) | там, где `api.telegram.org` заблокирован, и конвейер, и шлюз идут через один прокси-воркер Cloudflare; движок не читает базу настроек, потому что работает и без плагина. Воркер пропускает только токены из своего `BOT_TOKENS` — новый бот в списке иначе получит 404 ([docs/TELEGRAM-PROXY.md](TELEGRAM-PROXY.md)) |
| Предпросмотр без установки (`--preview`) | можно посмотреть настоящий проект, ничего в него не записав |
| Постановка N+1 до закрытия N; ревью постановки перед стартом | владелец 03.11: шаг не считается выполненным, пока нет постановки следующего; устаревшая постановка проверяется ревьюером против HEAD, свежая (recon_commit = HEAD) идёт без ревью; реализация — план 2 S6. Владелец 05.11: `REQUEST_CHANGES` по постановке не останавливает конвейер — страж ставит карточку промптеру «переписать постановку» (`:promptfix:<N>`), после неё ревью повторяется (`:promptreview:<N>`); стоп только по исчерпании `max_fix_rounds` |
| Один шаг за тик: параллельных шагов нет, ключ `max_actions` — предел действий, а не параллельность ([ADR 0001](adr/0001-odin-shag-za-tik.md)) | конфликт по git-дереву и по каналу ревью дороже выигрыша в скорости; пересмотр — по числовым триггерам из ADR |

## 4. Состав

```
step_pipeline/
  plugin.yaml        манифест (имя, версия, kind: backend, provides_tools)
  __init__.py        регистрация CLI и инструментов агента
  cli.py             hermes pipeline setup|status|run|ui|doctor|notify-test|config
  project.py         поиск корня проекта, чтение pipeline.json, вызовы hermes, UTF-8 stdio
  setup_flow.py      мастер установки, копирование движка/ролей, upgrade, cron, .env
  snapshot.py        снимок состояния для UI и инструментов (только чтение)
  stats.py           метрики цикла (разведка, правки, ревью плана) — только чтение файлов проекта
  telegram.py        Bot API: getMe, getChat, getUpdates, sendMessage
  tools.py           инструменты агента pipeline_status / pipeline_run / pipeline_control
  ui_server.py       HTTP-сервер панели (stdlib)
  ui_control.py      фоновый запуск/остановка панели (PID, лог)
  ui/index.html      одностраничная панель
  engine/            движок, который копируется в проект как .pipeline/
    config.py            конфиг проекта + UTF-8 stdio
    registry.py          планы, журнал, стоп-флаги
    next_step.py         контракт следующего шага из плана
    check_task_prompt.py гейт формы промта (9 обязательных блоков)
    step_card.py         карточка канбана на шаг
    gate.py              страж: шаг → ревью → журнал → следующий шаг
    tick.py              один тик для cron
  roles/             скиллы ролей: orchestrator, prompter, reviewer, next-step,
                     plan-authoring, agent-prompt-authoring
  templates/         план, промт, pipeline.json, фрагмент проекта-AGENTS
tests/               тесты плагина; tests/engine/ — тесты движка отдельным слоем
```

Артефакты прогонов (`docs/prompts/`, `docs/reviews/`, `docs/research/`, `docs/templates/`)
конвейер создаёт в **проекте-потребителе**; в этом репозитории их нет — журналы
`docs/plans/*.md` ссылаются на файлы, которые в публикацию не входят.

## 5. Инварианты (нарушать нельзя)

1. Гейт — скрипт, не агент. Никаких «агент решит, можно ли закрыть шаг».
2 Шаг не начинается без постановки: нет промта — карточка prompter, а не «исполнитель догадается».
3. Журнал пишет только гейт, и только при `APPROVE` + существующем коммите.
4. Секреты — только в `.env` профиля; в логах и UI токен не появляется.
5. В репозитории нет имён и предметной логики проектов-потребителей.
6. Действия в предпросмотре запрещены, панель слушает только localhost.

## 7. Быстрые команды

```bash
python -m pytest                 # все тесты (без -q: в pytest.ini уже стоит -q)
hermes plugins validate step_pipeline
hermes pipeline setup --project <путь>              # установка (спросит токен бота)
hermes pipeline setup --project <путь> --upgrade    # обновить движок в проекте
hermes pipeline status  --project <путь>
hermes pipeline run     --project <путь>            # один тик стража
hermes pipeline ui      --project <путь> --detach
hermes pipeline doctor  --project <путь>
```

## 8. Грабли, уже пойманные (не наступать снова)

- **Постановку нельзя писать одним куском.** Воркер промптера упирается в лимит вывода
  модели (`finish_reason=length`), файл не создаётся, карточка уходит в повтор и дважды
  выжигает `max_runtime` 2700 с. Правило в скилле: части по 40–70 строк + `wc -l` после
  каждой. Тест-сторож: `tests/test_roles.py::test_prompter_skill_writes_prompt_in_chunks`.
- **Адреса кода в спеке — только якоря.** Строки разъезжаются после каждой вставки, ревью
  ловит это как блокирующее. Формат `файл.py#ANCHOR:имя` → комментарий `# ANCHOR:имя`.
  Тест-сторож: `tests/test_roles.py::test_spec_anchors_resolve_to_code` (якорь без кода или
  задвоенный якорь валит прогон).
- **Улучшения ролей живут в `step_pipeline/roles/`, а не в `.hermes/`.** `.hermes/` в
  `.gitignore` — правка там не доезжает до других проектов и не попадает в коммит.
  Доезжает она через `setup --upgrade`: роль приводится к версии плагина, прежняя копия
  уходит в `.pipeline/roles-backup/` (с 0.6.0; до этого роли копировались только при
  первой установке и правки в проектах не обновлялись никогда).
  Тесты-сторожа: `test_reviewer_skill_requires_recommendations_section`,
  `test_prompter_skill_writes_prompt_in_chunks`,
  `test_upgrade_refreshes_changed_role_and_keeps_backup`.
- **`hermes` в PATH не гарантирован.** Тесты не должны звать настоящий бинарник:
  подделывать `proj.run_hermes` (иначе CI на ubuntu падает `FileNotFoundError: 'hermes'`).
- **Windows-консоль cp1251.** Любой русский вывод движка падал `UnicodeEncodeError`,
  и страж выглядел сломанным. В `main()` каждого скрипта и в CLI плагина stdout/stderr
  переключаются на UTF-8 с `errors="replace"`.
- **`pytest.ini` уже содержит `-q`.** Дополнительный `-q` в командной строке даёт `-qq`
  и итоговая строка «N passed» пропадает — это не поломка тестов.
- **Борда канбана.** `kanban --board <b> init` сам борду не создаёт: нужно
  `kanban boards list` → `boards create` → `init`.
- **Диспетчеризация CLI Hermes.** Обработчик команды — `args.handler`
  (`set_defaults(func=…)` молча ничего не делает).
- **`plugins validate` показывает caution `dump_all_env`** — ложное срабатывание на слово
  в тексте документации, не секрет.
- **Предпросмотр vs установка.** `--preview` ничего не пишет в проект; если нужен
  работающий конвейер в проекте — это `setup`, он создаёт `.pipeline/`, роли, борду, cron.
- **cron шлюза не отдаёт `.env` профиля.** В no-agent джобе приходит `HERMES_HOME`
  профиля, а `STEP_PIPELINE_TELEGRAM_*` в окружении нет: уведомления движка молчат,
  хотя `hermes pipeline notify-test` из CLI работает. Поэтому тик-скрипт сам дочитывает
  `profiles/<профиль>/.env` (см. 1-S17); проверять канал надо не CLI-командой, а пробой
  в контексте джобы.
- **`skills trust` нужен каждой роли, а не только драйверу** (1-S15): иначе воркер падает
  `Unknown skill(s): pipeline-prompter`, карточка уходит в `blocked` по `failure_limit`.
- **Ключ провайдера должен быть сохранён в профиле, а не в переменной окружения** (1-S16):
  профиль с `source: env:OPENCODE_GO_API_KEY` работает в интерактивной сессии и падает
  под демоном шлюза с `No usable credentials found`.
- **22 % у `gate.py` — артефакт подпроцессов, а не «непроверено»** (1-S10): e2e-тесты зовут
  `gate.py` из `.pipeline/` временного проекта, и без крючка `sitecustomize.py` +
  `COVERAGE_PROCESS_START` дочерний процесс не меряется вовсе. `source = step_pipeline`
  вместо `include` и отсутствие `[paths]` возвращают артефакт: копия из temp остаётся
  отдельной строкой отчёта, а `step_pipeline/engine/gate.py` — низкой. `COVERAGE_FILE`
  задавать только абсолютным, иначе данные ребёнка пишутся в его cwd и `combine` их не
  находит.
- **TLS: корни берём из certifi, а не из хранилища ОС** (0.19.2). В хранилище Windows
  лежат просроченные корни (DST Root CA X3 и другие), и OpenSSL строил через них
  просроченный путь для Let's Encrypt: панель показывала «✗ Telegram: сеть недоступна:
  certificate has expired» при живом сертификате сервера. `telegram.py`, `update.py` и
  `engine/gate.py` строят контекст из `STEP_PIPELINE_CA_BUNDLE` / `HERMES_CA_BUNDLE` /
  `SSL_CERT_FILE` / `REQUESTS_CA_BUNDLE` / `CURL_CA_BUNDLE`, иначе из `certifi`.
- **Плагин включается по профилям, а не глобально** (0.19.3). В профиле без своего
  каталога плагина `plugins enable step_pipeline` отвечает `No plugin named`, и
  `hermes pipeline` там просто нет. Мастер связывает профиль драйвера с установленным
  пакетом (junction на Windows, симлинк на POSIX) и повторяет включение; для остальных
  профилей — вручную `hermes -p <профиль> plugins enable step_pipeline`.
- **Разведка — четвёртая роль, и профиль ей нужен свой** (0.19.4). Движок берёт
  `profiles.scout`, а без ключа — профиль с именем `scout`; шаг конфиг не пишет, поэтому
  мастер заводит профиль разведки клоном драйвера и пишет `profiles.scout` сам.
  `setup --upgrade` заводит недостающий профиль, не переписывая настройки существующего.
  Проверка: `doctor` считает роли из `roles_from_config` — разведка попадает туда, только
  когда задана в конфиге.

- **Разведка — предусловие ревью, и правку плана заказывает страж карточкой, а не
  владелец руками** (0.20.0). Артефакт разведки на месте (`docs/research/<N>-prior-art.md`),
  а план её не учёл — раньше страж каждый тик отвечал `idle`, карточек не заказывал, и
  цикл «план → разведка → правка → ревью → утверждение» стоял. Теперь `_scout_fix_decision`
  заказывает плановое действие `create_scout_fix` (`planloop:<N>:scoutfix:<круг>`,
  профиль/скиллы/лимит — как у правки по ревью), тело карточки несёт находки P1-P4.
  Бюджет — `PLAN_REVIEW_MAX_ROUNDS` кругов, дальше стоп владельца с находками; упавшая
  карточка — инцидентный стоп. Проверка P4 требует, чтобы раздел «Разведка» ссылался на
  артефакт СВОЕГО плана: ссылка на чужой `prior-art.md` — FAIL. Утверждение страж не
  пишет: после правки плана простой с готовой командой `hermes pipeline plan --accept N`.
  Тесты-сторожа: `tests/engine/test_scout.py` (scoutfix), `test_plan_cycle.py` (P4),
  `test_approval.py` (переутверждение).

- **Переутверждение плана владельцем открывает новый бюджет кругов ревью** (0.21.0).
  Бюджет `PLAN_REVIEW_MAX_ROUNDS` считался по всем карточкам ревью плана за его жизнь:
  после owner-stop («второй REQUEST_CHANGES — решает владелец») правка плана ничего не
  меняла — следующий тик упирался в те же два круга и ставил тот же стоп. Живой случай:
  план 1 в `gapaudit` — 14 находок, владелец готов править, а конвейер к нему не
  возвращается. Теперь `plan_accept._write_approval` пишет `review_reset_at`, и бюджет
  считается только по карточкам после этой метки: сброс требует явного действия
  владельца, поэтому сам цикла «правка → ревью → правка» не заводит. Вторая половина
  правила: вердикт, написанный про прежнюю версию плана, не превращается в карточку
  правок — если переутверждение позже последней карточки ревью, страж заказывает свежий
  круг ревью (проверка стоит после «отчёт обновлён после карточки», поэтому устаревший
  отчёт по-прежнему даёт стоп, а не круг). Тесты:
  `tests/engine/test_plan_review.py::test_reapproval_after_owner_stop_opens_new_review_round`,
  `::test_reapproval_resets_review_budget`.
- **Ключ круга правок плана уникален на всю историю** (0.21.1). Номер в ключе считался
  по кругу ревью; после `plan --accept` (0.21.0) круг снова 1, ключ `planfix:1` занят
  done-карточкой, `hermes kanban create` идемпотентен и возвращал её — страж писал
  «выполнено» каждые 10 минут без новой работы (живой случай: `gapaudit`, тики 20:01–20:43).
  Теперь номер — следующий свободный по созданным правкам (`next_fix_round`), а заказ,
  вернувший закрытую карточку, даёт инцидентный стоп и тревогу (`reused_card`).
  Бюджет кругов ревью плана читается из `max_fix_rounds` проекта (умолчание 2) — владелец
  может разрешить больше автоматических правок, не трогая код. Наследование записи
  утверждения (`inherit_approval`) сохраняет `review_reset_at`: правка плана меняет файл,
  и без переноса метки бюджет снова считался за всю жизнь плана — поправленный план не
  доходил до ревьюера, страж ставил owner-stop «второй REQUEST_CHANGES».
- **Тревога владельцу, когда конвейер завис** (0.21.1). Сообщение начинается с
  «ВНИМАНИЕ!!! Требуется починить конвейер.» и несёт блоки: что случилось, доказательства,
  что сделать, команды. Поводы: `notify.stuck_repeats` (по умолчанию 3) одинаковых
  действий подряд, заказ с закрытой карточкой, стоп-флаг (инцидент или решение владельца),
  сбой тика, несовпадение движка с `ENGINE.sha256` (раньше такой тик молча выходил с
  кодом 3 — уведомлений не было вовсе). Одна тревога на причину в час — отметки в
  `<state_dir>/attention.json`. Тесты: `test_closed_card_on_create_raises_alarm`,
  `test_attention_text_has_loud_header_and_plan`, `test_attention_is_throttled_per_reason`,
  `test_note_action_streak_counts_identical_actions`, `test_next_fix_round_skips_taken_keys`.
- **Джобы конвейера проверяются при обновлении движка** (0.21.0). `--no-cron` пишет отказ
  в `.pipeline/cron.json` (`skipped: true`), `ensure_cron_all` заводит страж, приём команд
  и автообновление одним входом, а `setup --upgrade` проверяет их каждый раз, кроме явного
  отказа. Раньше проект, поставленный до появления метки, оставался без джоб навсегда:
  страж не тикал, карточки не заказывались (пример — `gapaudit`, план утверждён, шаги
  стоят).

- **Панель подставляет `.env` профиля проекта в окружение движка** (0.20.1). Движок берёт
  токен уведомлений из окружения процесса (`notify.token_env`), а не из файла; `.env`
  читают только `doctor` (напрямую) и сам `hermes -p <профиль> …`. Панель запускается
  задачей планировщика без профиля проекта, поэтому её тик молчал при живом токене, а
  чужой `STEP_PIPELINE_TELEGRAM_*` из окружения сервера уводил уведомления чужому боту
  (симптом: сообщения «в основной канал Hermes» вместо проектного). Теперь
  `project.run_engine` кладёт `.env` профиля драйвера между окружением процесса и
  `extra_env`, поэтому у каждого проекта в одной панели свой бот. Переменные канала из
  окружения при этом вычищаются (`project.engine_env`): в окружении панели лежит ещё и
  `STEP_PIPELINE_TELEGRAM_API_BASE` — прокси основного бота, и токен проекта через чужой
  прокси даёт `HTTP 404 от Telegram`. `telegram.*` принимают `env` проекта, поэтому
  тест уведомлений в панели, зеркало ленты, `doctor` и `pipeline notify-test` ходят
  каналом проекта. Проверка: `token_set` в снимке панели и тест уведомления из UI;
  тесты — `tests/test_project_env.py`.

## 9. Что осталось

- Публичный репозиторий или private — решение владельца. Репозиторий к публикации
  подготовлен (теги, release, зелёный CI, безопасность и лицензия); переключение
  видимости и переписывание истории (имена проектов и локальные пути в старых
  коммитах) — за владельцем.
- «Почтальон» между ролями (переписка промптер↔исполнитель↔ревьюер через Telegram
  или kanban-мост) — в прежнем проекте эту роль играл отдельный мост.
- Реальная установка в чужой проект вместо предпросмотра — только с согласия владельца
  (добавит `.pipeline/`, `pipeline.json`, роли в `.hermes/skills`).
- Actions в CI: `actions/checkout@v7` и `actions/setup-python@v7`; `hermes plugins
  validate step_pipeline` идёт шагом в `tests-matrix` (ubuntu/3.11), после установки
  hermes-agent — молчаливого «шаг пропущен» нет.
- Покрытие — сделано 1-S10, замер честный (с подпроцессами): TOTAL 77 %, `gate.py` 82 %,
  порог `fail_under = 75` по правилу `floor(TOTAL − 2)`. Следующая цель 1-S12: `tick.py`

  не импортирует ни движок, ни тесты, поэтому мерить там нечего, пока S12 не позовёт его.

Движок в проекте — вендорированная копия в `.pipeline/`. Правки `step_pipeline/engine/`

первому двоеточию, и `_READY_RE` ищет «Готово» уже в остатке. Это учтено в шаге 1-S5;
до его выполнения в планах не ставить двоеточие в пункте «Готово =».

## 11. Цикл плана и его метрики

Цикл до первого шага исполнения — четыре звена, и у каждого свой артефакт:

| Звено | Артефакт |
|---|---|
| План | `docs/plans/N-имя.md` с журналом шагов |
| Разведка | `docs/research/N-prior-art.md` — таблица кандидатов, у каждого вердикт |
| Правка плана | отметка `Правки по разведке: N` в тексте плана |
| Ревью плана | `docs/reviews/plan-N.md` — вердикт и метка `plan_sha256:` |
| Утверждение | `.pipeline/state/plan_N_approval.json` |

`step_pipeline/stats.py` считает по этим файлам четыре числа; ручного ввода нет:

- «планов с разведкой» — планы, у которых есть раздел «Разведка» и артефакт
  `N-prior-art.md` рядом;
- «вердиктов без готового решения» — строки таблицы кандидатов, где вердикта «берём» и
  «форкаем» нет: «своё» и «не берём» значат «готовое решение отвергнуто осознанно»;
- «правок по разведке на план» — сумма N из отметок, делённая на число планов с отметкой;
- «ревью плана с первого раза» — планы с вердиктом, привязанным к текущей версии плана,
  и ровно одним кругом ревью в истории тиков.

Где видно: `hermes pipeline status` печатает строку «Цикл: …», панель показывает блок
«Цикл плана» на вкладке «Обзор». В `gate.py --status` этих чисел нет намеренно: страж
решает, что делать сейчас, а метрики цикла на решение не влияют.

Ограничения счёта — чтобы числа не читались как больше, чем они есть:

- круги ревью берутся из `history.jsonl` движка; файл обрезается до 2000 строк, поэтому
  у очень старого плана круги могут быть недосчитаны;
- вердикт считается только привязанным к текущей версии плана (метка `plan_sha256:`
  совпала с sha256 файла); иначе состояние `stale` — «APPROVE был, но план правился»;
- план без строки `Конституция:` в шапке движок ревью не назначает вовсе — в снимке это
  `skipped`, а не долг «нет отчёта»;
- две разные строки вердикта в одном отчёте — `invalid`: конвейер не угадывает, какая
  из них главная;
- старый пятиколоночный артефакт считается по последней ячейке строки, поэтому вердикты
  «не берём» попадают в «без готового решения».

Чего проект не делает:

- не начинает шаг без постановки — нет промта, значит карточка промптеру (инвариант 2);
- не закрывает шаг на словах: только APPROVE плюс существующий коммит (инвариант 3);
- не начинает шаги плана без свежего вердикта ревью плана (`approval.review_status`);
- не берёт готовое решение без вердикта на кандидата (`scout_report`, проверка R3);
- не считает метрики руками и не правит историю: `stats.py` только читает файлы проекта;
- не трогает владельческие ключи `profiles` и `driven_plans` в `pipeline.json`.
