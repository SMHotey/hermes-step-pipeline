## 2. Что сделано по находкам

1. **[блокирующая] `gate.py::_decide_base`, ветка `create_rereview`.**
   Было: признак аномалии — только вердикт отчёта (`prev_verdict["verdict"] == "REQUEST_CHANGES"`),
   поэтому шаг, закрытый «с замечаниями», на следующем тике получал карточку
   `planloop:<план>:<шаг>:rereview:1`, а после неё — стоп владельцу.
   Стало: новый `gate.py::journal_closed_with_remarks(p, step_id)` читает четвёртую колонку строки
   журнала закрытого шага и ищет там маркер `REMARKS_EVIDENCE = "принято с замечаниями"` (тем же
   текстом, что пишет `_evidence`, — константа теперь одна на оба места). Признак попадает в
   `ctx["prev_closed_remarks"]` (`build_ctx`; на сбое сборщика — `False`), а ветка повторного ревью
   получила условие `and not ctx.get("prev_closed_remarks")`. Ветка остаётся сторожем расхождения
   «журнал закрыл НЕ по замечаниям, а ревью требует правок» — ручное «ЗАКРЫТ» при отчёте
   `REQUEST_CHANGES` по-прежнему даёт ровно один повторный круг, второй отказ — стоп.
2. **[значимая] `docs/ARCHITECTURE.md` §5.4.** Буллет `REQUEST_CHANGES` → «`REQUEST_CHANGES`
   с блокирующей находкой → карточка правок…; без блокирующей находки круг не открывается — см.
   блок ниже»; абзац «Отдельная ветка — шаг, закрытый при REQUEST_CHANGES» дополнен оговоркой:
   ветка срабатывает только при закрытии НЕ по замечаниям, а закрытие «с замечаниями» — штатное
   состояние и ветку не задевает.
3. **[стилистическая] шапка `gate.py`.** Строка состояний `REQUEST_CHANGES` разбита на две: «есть
   блокирующая — карточка правок (1-й раз), стоп + уведомление (2-й раз)» и «блокирующих нет — шаг
   закрывается с замечаниями, замечания — строками реестра находок плана».
4. **[стилистическая] версии ролей.** `pipeline-reviewer` 1.4.0 → **1.5.0**,
   `pipeline-plan-reviewer` 1.1.0 → **1.2.0**.

## 5. Решения, принятые самостоятельно

- Признак закрытия читается из журнала, а не из состояния плана: журнал — единственное
  доказательство закрытия, и он же переживает смену сессии/машины. Чтение одного файла плана на
  тик, `OSError` → `False` (ветка ведёт себя как прежде, решение не падает).
- Текст маркера вынесен в константу `REMARKS_EVIDENCE`, `_evidence` строит строку из неё: два
  независимых литерала разошлись бы при первой же правке формулировки.
- В golden 09 добавлена постановка S2 — иначе второй тик доказывал бы только заказ постановки.
