## 2. Что сделано (4.1–4.9)

1. **4.1. Разбор находок отчёта.** Было: решение смотрело на слово «блокирующая» в тексте

   класс берётся из метки в начале пункта (`[блокирующая]`, `[значимая]`, `[стилистическая]`,
   подметка после дроби — в `sublabels`), считается `blocking/significant/style/labeled/unlabeled`

2. **4.2. Сверка вердикта.** Было: `REQUEST_CHANGES` → всегда круг правок. Стало, в порядке
   (порядок обязателен): нечитаемый отчёт → стоп «отчёт ревью не читается…»; нет раздела «Находки» →
   стоп формата; ни одной метки класса → стоп формата с «поправь отчёт»; `blocking == 0` → закрытие
   с замечаниями; `blocking > 0` → прежний круг правок (бюджет `max_fix_rounds` не тронут). В ветке
   `APPROVE` — обратная сверка: `blocking > 0` при `APPROVE` → стоп «вердикт APPROVE расходится с
   классами: блокирующих находок N…». Форматные ошибки проверяются **до** бюджета кругов, поэтому
   круг не расходуется.
3. **4.3. Замечания в реестр плана.** Было: замечания жили только в отчёте. Стало: при закрытии шага
   `_register_remarks` дописывает по строке на значимую и стилистическую находку — `kind = стиль`,

   пункты без метки строкой не становятся. Писание идёт после журнальной строки и только если она
   добавлена; отказ записи реестра → инцидентный стоп («журнал уже закрыт, реестр не записан»).

## 5. Решения, принятые самостоятельно

- **Порядок ветвей:** ошибки формата — до бюджета кругов. Иначе битый отчёт съедал круг, а поломка
  формата стоила бы шагу одной из двух попыток.
- **Вид стопов — инцидентный** (`_classes_stop` не ставит `kind=owner`): причина уходит вместе с
  правкой отчёта, владельцу не нужно снимать флаг руками.
- **Класс `стиль` в реестре** (вопрос 2, A): словарь `FINDING_KINDS` не расширялся — это зона S6 и
  `docs/PLAN-FORMAT.md`; класс ревью остался меткой в тексте.
- **Преамбула реестра сохраняется:** `write_findings` больше не перезаписывает файл с нуля, иначе
  привязка `plan_sha256:` терялась при первой же записи замечаний.
- **Тема коммита фиксируется в `pending_commit`:** при замечаниях тема отличается от прежней, и
  пересборка её в `retry_pending` по вердикту дала бы «APPROVE» в теме закрытия с замечаниями.
- **Разбор понимает обе живые формы:** класс берётся и из подразделов `### Блокирующие/Значимые`
  (2 отчёта из 53), а не только из меток в скобках (0 из 53). Без этого шаг покраснел бы на
  собственном корпусе и на контракте `test_comments` (его отчёт — подразделы).

## 7. Отклонения от постановки (без сглаживания)

1. **Два коммита вместо одного (§4.9).** Первый (`f0bb4ba`) ушёл до того, как я сверил файл с §4.8:
   имена тестов и имена golden-случаев расходились с фиксированными, текст причин — с §4.2, карточка
   ревью — с §4.5. Доводка вынесена отдельным коммитом `9386943`; переписывать уже отправленную
   историю `main` без решения владельца не стал.
2. **`details` у стопов — строкой, а не списком (§4.2).** Потребитель `run_gate` делает
   `extra.splitlines()` и ждёт строку; список сломал бы уведомление. Содержимое — ровно три пункта
   «что сделать», как в §4.2.
3. **Отчёт без заголовка «Находки», но с подразделами-классами форматом не считается (§4.2).**
   Строгое чтение остановило бы 2 живых отчёта и сломало `test_comments`, который постановка требует
   не менять. Компромисс: подразделы классов дают классы пунктам; отчёт вовсе без классов —
   по-прежнему стоп формата (случай 10 это и проверяет).
4. **Причины стопов — дословно из §4.2, без имени файла отчёта в хвосте.** Имя полезно, но
   постановка задаёт текст причины; сверх задания ничего не дописывал.
5. **`case.json` новых случаев** — по образцу соседних (`note`, `approved`, `ticks`, `seed_cards`,
   `untracked`), текст `note` свой.
