## Расхождения постановки с планом/кодом

Это не находки исполнителю: ADR описывает фактическое поведение кода (§4.3 постановки), местами
расходясь с её же §2/§4.1, — так и должно быть.

1. §2 `:74` — «параллельность возможна только внутри тика, между тиками — нет» — неверно: карточки
   живут и работают между тиками (`task_runs` run 120/121/122, `history.jsonl`). Верно: тики не
   пересекаются, а карточки сериализует кап профиля. ADR исправил (`:24-30`).
2. §2 `:90-91` — «два шага в работе → два ревью у одного профиля и два вердикта по дереву» —
   неверно: у `reviewer` тот же кап 1, ревью идут по одному; конфликт — ревью и шаг другого профиля
   (run 122 22:21:31–22:48:48 против run 121 22:18:30–22:52:16). ADR исправил (`:69-71`).
3. §4.1 п.4 — «чем платим за A: шаг ждёт тик» — верно лишь отчасти: основная цена — очередь к
   единственному воркеру, тик добавляет до ~10 мин только на переходе между артефактами. ADR
   исправил (`:50-52`, `:110-116`).
4. §4.1 п.2 требует git-конфликт в цене B как следствие `max_actions`. По коду при капе 1 шаги и в B
   идут подряд, а два коммита/пуша за тик может дать только страж, и он коммитит лишь перечисленные
   файлы (`commit_and_push`, `gate.py:361-390`: `git add -- <файлы>` + `git commit -- <файлы>`),
   правки шага в такой коммит не попадают. Верно: git-конфликт между шагами достижим только при
   поднятом капе, а реальный эффект B — сокращение простоя между тиками и учащение пересечений
   «ревью и шаг». ADR следует постановке дословно (`:62-67`, `:122-123`) — это находка постановке.
5. §4.1 п.6 «без номеров строк в самом ADR» против §4.1 п.1-2, где номера заданы дословно, —
   противоречие постановки; исполнитель разрешил в пользу п.1-2 (номера привязаны к HEAD `a20da0d` и
   продублированы именами символов). Приемлемо, при переиспользовании постановку стоит выровнять.
6. Карточка ревью запрещает полный набор тестов, но её же раздел «Гейты шага» требует
