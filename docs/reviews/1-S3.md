## 5. Расхождения постановки с планом/кодом

1. **Тест 2 постановки (строка 100).** Постановка требует: дочерний процесс держит блокировку → убить →
   `--run` → «ровно одна карточка с ключом `planloop:1:S1:prompt`», повторный `--run` без второго действия.
   В коде тест предсоздаёт файл постановки (`test_lock.py:190-192`) и ждёт ключ `planloop:1:S1:step`
   (`:206`). **Право в коде:** на реальном движке каждый тик, сняв инцидентный стоп по отсутствующей
   постановке, заново заказывает промпт (`gate.py:997-1018`), поэтому вариант постановки давал бы новую
   карточку на каждом тике (замер: три тика → три строки с одним ключом). Предсозданный файл постановки
   переводит тик в идемпотентную ветку «карточка шага уже есть» — там повторный тик действительно ничего
   не делает. Требование «одна карточка» сохранено по смыслу, ключ другой.
2. **Формулировка «Готово 1» §S3 «ровно одно действие».** Блокировка даёт взаимное исключение, но не
   идемпотентность самого действия: если первый тик успевает завершиться за время ожидания (5 с), второй
   выполняет полный тик на свежем состоянии и повторяет заказ постановки. Это не дефект шага — правка живёт
   вне разрешённой поверхности (`decide`/`run_gate`/`tick` запрещены), а формулировка требует поведения,
   которого у движка нет. На приёмку шага не влияет: журнал и состояние не портятся (проверено), повторный
   заказ — отдельная задача (находка 2).

## 6. Находки

Блокирующих нет.

**[значимая] `state_io.py:113-125`** — окно гонки на POSIX: файл блокировки создаётся пустым (`os.open`
на `:113`) и наполняется только на `:131`; тик, прочитавший его в этом окне, получает `holder() → None`,
считает блокировку протухшей (`:119`) и снимает её без ожидания (`:122`) — оба процесса считают себя
держателями, то есть возможен ровно тот двойной тик, который закрывает шаг. Правило замерено: пустой
`tick.lock` снимается за 0.8 с (§3). На Windows гонка гасится тем, что `unlink` открытого файла падает с
`OSError` (дескриптор `os.open` не даёт разделения на удаление), и второй процесс возвращает `None`
(`:117-118`); на POSIX `unlink` успешен, файл исчезает, первый держатель остаётся со «своим» невидимым
файлом. Ожидание: перед снятием нечитаемой блокировки перечитать её через `STEP` (0.1 с) и снимать, только
если она снова нечитаема — правка в разрешённом шаге файле, свойство «не встать навсегда» сохраняется.

**[значимая, вне объёма шага] `gate.py:997-1018`** — повторный тик после инцидентного стопа заново заказывает
постановку: на заглушке борды три тика дают три карточки с одним `idempotency_key` (мой замер §3); на
реальной борде дедупликация по ключу скроет дубль карточки, но действие всё равно повторится. Правка
требует `decide`/`create_step`, что шагом запрещено, поэтому — отдельная задача (идемпотентность заказа
постановки), не блокер S3. Именно эта особенность движка делает недостижимой буквальную формулировку
«ровно одно действие» (§5 п. 2).

**[стилистическая] `state_io.py:161-169`** — `locked()` объявлен контрактом постановки, но нигде не
используется (движок работает через `acquire`/`release`) и не покрыт ни одним из шести тестов. Риск
проявится, когда им начнут пользоваться: поведение (`yield None` внутри контекста) не проверено.

**[стилистическая] `state_io.py:35`** — `WAIT = float(os.environ.get("PIPELINE_LOCK_WAIT") or 5)`:
нечисловое значение переменной уронит импорт модуля, то есть весь `gate.py` не стартует, и вместо
