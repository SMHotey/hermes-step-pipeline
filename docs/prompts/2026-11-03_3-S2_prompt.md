## 6. Как проверить (гейты)

Из корня репозитория (Windows, bash), по порядку. Второй `-q` не добавлять: он уже в
`pytest.ini`, двойной скрывает итог.

    .venv/Scripts/python.exe -m pytest; echo EXIT=$?                         # ДО правки: базовая линия
    .venv/Scripts/python.exe -m pytest tests/test_preview.py; echo EXIT=$?  # после правки
    .venv/Scripts/python.exe -m pytest; echo EXIT=$?                        # после правки
    hermes plugins validate step_pipeline

Ожидается: `tests/test_preview.py` — `6 passed`, `failed` нет, `EXIT=0`; полный прогон
после правки — `EXIT=0` и `passed` ровно на 1 больше базовой линии (базовая линия — твой
замер до правки, число в отчёт); `hermes plugins validate` — без FAIL (caution про
`dump_all_env` известен, `docs/CONTEXT.md:130`; CLI нет — не блокер, отметить в отчёте).
Код возврата читать по `; echo EXIT=$?`, а не по хвосту пайпа.

Отдельно, руками (не тестом) — фактическое состояние живого проекта:

    .venv/Scripts/python.exe -c "from step_pipeline import snapshot; import json; d = snapshot.snapshot(r'C:/Users/malik/PycharmProjects/hermes-step-pipeline', plan='3'); print(json.dumps(d['overview'], ensure_ascii=False, indent=2))"

В отчёт — распечатанный `overview` целиком: `tick_label`, `tick_available`,

## 10. Решения и допущения

- D1. `overview` считается в `snapshot.py`, а не в странице: гейт шага — `pytest`, значит
  подпись и правило доступности должны быть проверяемы питоном, а страница остаётся
  рисовальщиком.
- D2. Подпись строится от ДЕЙСТВИЯ решения, а «заказ постановки» — от факта отсутствия
  постановки: страж выдаёт `create_step` и для «шаг», и для «карточка постановки»
  (`gate.py:1385-1405`), различить их по `action` нельзя.
- D3. «Тик» недоступен при предпросмотре и при любом стоп-флаге ВЫБРАННОГО плана (так
  буквально сказано в §S2). Снятие — кнопка «Продолжить» (`--resume` снимает стоп любого
  вида, `gate.py:1878-1881`) или cron-тик. Существующий ключ `stop` снимка (любой стоп по
  всем планам) не переиспользуется: действия в панели адресованы выбранному плану,
  поэтому чужой стоп не должен глушить кнопку.
- D4. Поля названы `tick_label`, `tick_available`, `tick_disabled_reason`, `waiting`,
  `fix_rounds`, `prompt`, `risk`, `progress`, `checks` — страница читает их, тест
  утверждает их значения; других имён не вводить.
- D5. Формат длительности и поиск постановки повторяют движок (`gate.py:_ago`,
  `gate.py:prompt_rel`) копией, потому что движок вендорится в проект и импортировать его
  из плагина нельзя. Расхождение форматов ловится ревью.
- D6. Число шагов плана считается по файлу (заголовки раздела шагов по `step_id_regex`), а
  не запуском `next_step.py`: четвёртый запуск движка на сборку — регресс критерия шага
  3-S1 «не больше 20 запусков в минуту».
- D7. Кругов правок берутся из карточек снимка (последние 30, `snapshot.py:58-75`). Для
  текущего шага этого достаточно; карточка правок старше 30 записей в обзор не попадёт —
  ограничение назвать в отчёте, а не обходить запуском движка.
- D8. Бейдж критичных проблем — только задел: `overview.checks = None`. Проверки (doctor,
  линтер планов) — объём шага S5; в критериях «Готово =» §S2 бейджа нет.
- D9. Строка «Тик: заказ постановки S2» проверяется на фикстуре без постановки: на живом
  проекте постановка шага S2 создана этим шагом, и правильным следствием будет
  «Тик: шаг S2». Фактическая строка живого проекта — в отчёт.
- D10. Ровно один новый тест: §S2 обещает 6 passed при сегодняшних 5. Дополнительные
  проверки собираются в тот же тест, а не в новый — число из плана не переписываем.
- D11. Тест обязан выставить `PIPELINE_KANBAN_DB`: без него `project.board_db`
  (`project.py:128-136`) читает настоящую борду профиля, и карточки чужого проекта могут
  изменить решение стража.
- D12. Базовая линия полного прогона замеряется ДО правки и приводится фактическим числом:
  в `tests/` и `tests/engine/` 274 функции `test_`, а `passed` зависит от параметризации,
  поэтому «плюс один» проверяется по факту, а не по арифметике.
- D13. Версия и `CHANGELOG.md` не меняются: правка аддитивная, движок и формат
  `pipeline.json` не тронуты, прецедент — закрытие 3-S1 (коммит af9dca9 без версии).

## 11. Ревью (обязательно)

Шаг закрывает не исполнитель. После кода и гейтов шаг уходит на независимое ревью роли
`reviewer` (скилл `pipeline-reviewer`): отчёт `docs/reviews/3-S2.md`, первая строка блока
«Объект ревью» — коммит шага в обратных кавычках, вердикт APPROVE или REQUEST_CHANGES по
контракту §1 и плану §S2 (`docs/plans/3-panel.md`, строки 42–53). Ревьюеру доступны план
и код; отчёт исполнителя источником фактов не считается.
При REQUEST_CHANGES шаг остаётся открытым: находки правятся, ревью повторяется.
Строку «ЗАКРЫТ» в журнале и коммит закрытия делает страж после APPROVE.
