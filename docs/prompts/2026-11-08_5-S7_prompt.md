### 4.7 Спека формата и версия

14. `docs/PLAN-FORMAT.md:130-133` — пункт «Исполнитель» дополнить: токен маршрутизируется
    ключом `routing` (`frontend`, `backend`, `devops`, `designer`, `security`), явный
    профиль из `profiles` сильнее предметки, неизвестный токен — инцидентный стоп без
    карточки. Номера строк в скобках пересчитать `grep -n` после правок.
15. `docs/PLAN-FORMAT.md:275-281` (§7, таблица ключей) — строка `routing` с умолчанием
    `{}` и правилом «предметка даёт профиль; неизвестный токен — стоп».
    `docs/PLAN-FORMAT.md:404` (П11) — в колонке «Адрес в коде» поставить резолвер
    (`gate.py` с номерами строк или якорь), в колонке тестов — файл
    `tests/engine/test_assignee_routing.py`. Если добавляешь `#ANCHOR:имя` в спеку, в
    коде обязан появиться ровно один комментарий `# ANCHOR:имя`
    (`tests/test_roles.py:113-123`).
16. `step_pipeline/plugin.yaml:2` — минор от фактической версии на момент исполнения: на
    HEAD `0.12.3`, S6 в дереве ведёт к `0.12.4`, ожидание — `0.13.0`. В `CHANGELOG.md`
    запись сверху: «Добавлено» — ключ `routing`, резолвер исполнителя, инцидентный стоп на
    неизвестный токен, README ролей; «Изменено» — неизвестный исполнитель больше не уезжает
    драйверу молча.

Решения, принятые за тебя (не переигрывать):

- маршрут живёт в новом ключе `routing`; `profiles` и `driven_plans` не трогаются;
- пять предметок известны движку по имени; без записи в `routing` они ведут к драйверу —
  поведение существующих проектов сохраняется;
- явный профиль сильнее предметки: токен, совпавший со значением `profiles`, идёт как есть;
- разбор «Исполнитель:» в `next_step.py` не меняется, П11 дополняется, а не переписывается;
- README описывает восемь скиллов: семь ролей конвейера плюс методика
  `agent-prompt-authoring`;
- версия — минор, а не патч: меняется поведение движка и формат `pipeline.json`.

## 5. Как проверить (гейты)

Рабочий каталог — корень репозитория. Все прогоны — до и после правок, вывод в файл,
код возврата смотреть у pytest, а не у хвоста пайпа.

```
# 0. Замер ДО правок (число записать в отчёт, оно же база для гейта 4)
.venv/Scripts/python.exe -m pytest > "$TMPDIR/s7_before.log" 2>&1; echo EXIT=$?
grep -E "passed|failed|error" "$TMPDIR/s7_before.log" | tail -1

# 1. Новый файл: гейт плана — ровно шесть тестов и все зелёные
.venv/Scripts/python.exe -m pytest tests/engine/test_assignee_routing.py > "$TMPDIR/s7_routing.log" 2>&1; echo EXIT=$?
# ожидается: 6 passed, EXIT=0

# 2. Соседи, которые обязаны остаться зелёными; было 34 теста, столько же ожидается
.venv/Scripts/python.exe -m pytest tests/engine/test_next_step.py tests/engine/test_step_card.py tests/engine/test_gate_e2e.py tests/engine/test_max_actions.py > "$TMPDIR/s7_neigh.log" 2>&1; echo EXIT=$?
# ожидается: 34 passed, EXIT=0

# 3. Роли и спека: адреса и якоря
.venv/Scripts/python.exe -m pytest tests/test_roles.py > "$TMPDIR/s7_roles.log" 2>&1; echo EXIT=$?
# ожидается: 7 passed, EXIT=0

# 4. Полный набор
.venv/Scripts/python.exe -m pytest > "$TMPDIR/s7_all.log" 2>&1; echo EXIT=$?
# ожидается: ровно (число из шага 0 + 6) passed, 1 skipped, EXIT=0.
# Твёрдой цифры тут нет: полный набор зависит от того, закоммичен ли S6.
# Замер дерева на момент постановки: 511 функций def test_, из них 5 — тесты S6;
# отсюда ожидание «базовое число плюс шесть», фактическое число обязательно в отчёт.

# 5. Манифест плагина (если CLI есть)

# ожидается: отчёт без ошибок, EXIT=0; CLI недоступен — строка «CLI нет» в отчёте
```

которого не было в замере шага 0, — это стоп-сигнал 5, а не «починю заодно».

## 6. Стоп-сигналы

Остановиться и доложить (не адаптировать по смыслу), если:

1. На старте `git status --porcelain` показывает незакоммиченные правки
   `step_pipeline/engine/gate.py`, `config.py` или `step_card.py` — это работа шага S6 или
   параллельной сессии; правка тех же файлов даст конфликт. Дождаться их коммита и только
   потом начинать.
2. Понадобилось менять `profiles` или `driven_plans` в `pipeline.json` — владельческие
   ключи; это решение владельца, а не шага.
3. Понадобилось править разбор «Исполнитель:» в `next_step.py` или переписывать П11 — вне
   объёма шага.
4. `tests/test_roles.py:53` требует другого числа ролей, чем восемь, или в дереве
   появился/исчез каталог роли — значит библиотеку ролей меняют параллельно.
5. Гейт красный по причине, которой не было в замере шага 0 (например падает
   `tests/engine/test_approval_order.py` — это S6): доложить с точной строкой падения, не
   чинить заодно.
6. Механизм маршрута потребовал менять `_create_card` (`gate.py:1833`) или формат ключей
   карточек — признак, что резолвер делается не там, где надо.

Формат доклада: что обнаружено (файл и строки), замер (команда и вывод), варианты с ценой,
рекомендация.

## 7. Формат отчёта

До коммита, по порядку, на русском:

1. `git diff --stat` — какие файлы и сколько строк.
2. Ключевые диффы: резолвер и ветка стопа в `gate.py`, `routing` в `config.py` и шаблоне,
   README ролей, строка в `CHANGELOG.md`.
3. Решения, принятые самостоятельно, с причиной (спорное — вопрос владельцу, не догадка).
4. Строки гейтов: команда, фактическое число `passed`, `EXIT`, и рядом замер шага 0.
5. Отклонения от постановки — по пунктам, с обоснованием.
6. Что сознательно не сделано (S8, `docs/CONTEXT.md`, UI, профили Hermes под предметки).

## 8. Вопросы (≤3, каждый с ценой)

1. Число ролей: план говорит «семь», дерево держит восемь, и `tests/test_roles.py:53` уже
   пинит восемь. Принято: семь ролей конвейера плюс отдельная строка методики
   `agent-prompt-authoring` в README. Нужна ли строка про методику, или достаточно семи
   ролей? Цена второго варианта — минус одна строка README, пять минут.
2. Место маршрута: новый ключ `routing` (цена — владельцу ничего подтверждать не надо) или
   ключ внутри `profiles` (цена — правка владельческого ключа: шаг останавливается и ждёт
   владельца, плюс круг ожидания)?
3. Проекты с токеном `backend` в планах, но без `routing` в конфиге: принято «предметка без
   записи ведёт к драйверу», то есть поведение прежнее. Строгий вариант — требовать запись
   в `routing` для каждой предметки; цена — такие проекты встанут на первом же шаге до
   правки конфига владельцем. Оставляем мягкий вариант?

## 9. Ревью (обязательно)

Шаг не закрывает исполнитель. После зелёных гейтов — независимое ревью ролью `reviewer`
(скилл `pipeline-reviewer`) по плану `docs/plans/5-platforma.md` и по коду. Отчёт
исполнителя ревьюеру источником фактов не является. Вердикт — APPROVE или
REQUEST_CHANGES, ровно одна строка вердикта в `docs/reviews/5-S7.md`. При REQUEST_CHANGES
шаг остаётся открытым: находки правятся, ревью повторяется. Строка «ЗАКРЫТ» в журнале
плана и коммит закрытия — только после APPROVE.
