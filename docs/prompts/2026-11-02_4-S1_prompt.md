  S2 (`status` печатает путь и что изменилось) и S3 (снимок панели). Других новых имён API нет.
- **D4.** Настоящим булевым считается только `isinstance(value, bool)`. Строка `"false"`,
  число, `null`, список — «непригодное содержимое» → предупреждение и `True`.
- **D5.** `read_mode` не бросает исключений никогда (его позовут из хука в S4); `write_mode`
  бросает `OSError` наружу — это явное действие пользователя, CLI и панель обязаны показать
  ошибку, а не проглотить её.
- **D6.** `changed_at` — ISO-8601 локального времени с точностью до секунды
  (`datetime.now().isoformat(timespec="seconds")`): дату читают машины (`--json` в S2, снимок в
  S3), поэтому `time.strftime("%d.%m.%Y %H:%M:%S")` как в движке не годится.
- **D7.** Предупреждение идёт только в `stderr` и ровно одной строкой: `--json` в S2 и снимок
  в S3 не должны получить мусор в stdout.
- **D8.** Тест импортирует `from step_pipeline import plan_mode`; `tests/helpers.py` не
  правится (общий файл с S2/S3), корень репозитория уже в `sys.path` через `conftest.py`.
- **D9.** Ровно шесть тестов, без классов и параметризации: план фиксирует «6 passed».

## 5. Как проверить (гейты)

Из корня репозитория. Код возврата смотреть у самой команды, а не у хвоста пайпа; логи — вне
репозитория (`$TMPDIR`; если переменная пуста, возьми `$LOCALAPPDATA/Temp`):

```
C:/tmp/venv-s2b/Scripts/python.exe -m pytest tests/test_plan_mode.py > "$TMPDIR/p4-s1-module.log" 2>&1; echo EXIT=$?
# после п. 1 (тесты есть, модуля нет) ожидается: 1 error, EXIT=2 — RED
# после п. 2 (модуль создан) ожидается: 6 passed, EXIT=0 — GREEN
C:/tmp/venv-s2b/Scripts/python.exe -m pytest > "$TMPDIR/p4-s1-all.log" 2>&1; echo EXIT=$?
# ожидается: 143 passed, EXIT=0 (замер до шага: 137 = 48 плагина + 89 движка, плюс 6 новых)
grep -nE "^(from|import) .*(engine|state_io)" step_pipeline/plan_mode.py
# ожидается: пусто, EXIT=1 — движок не импортирован
git status --porcelain
# перед коммитом ожидается: ?? step_pipeline/plan_mode.py, ?? tests/test_plan_mode.py;
# A  .idea/.gitignore, M docs/CONTEXT.md, ?? .hermes/, ?? .pipeline/, ?? docs/plans/4-planner.md,
# ?? docs/templates/, ?? pipeline.json — чужие, остаются как были
git show --stat --oneline HEAD
# после коммита ожидается: ровно два файла и sha коммита
```

`-q` к командам не добавлять: в `pytest.ini` уже стоит `addopts = -q`, второй `-q` скрывает
итоговую строку. Запись плана «`python -m pytest tests/test_plan_mode.py` → 6 passed» означает
то же самое; в отчёте — фактическое число прошедших и `EXIT`.

Дополнительно, без правок кода, проверить руками, что модуль ведёт себя как заявлено на
настоящем каталоге вне pytest (временный каталог в `$TMPDIR`, `pipeline.json` не нужен):
`read_mode` на пустом каталоге → `True`; `write_mode(temp, False)` → файл
`.pipeline/state/plan_mode.json` с `plan_mode: false`; `read_mode` → `False`; второй
`write_mode(temp, True)` → в каталоге ровно один файл. Замер приводится в отчёте одной строкой.

## 6. Стоп-сигналы

Остановиться и доложить (не адаптировать по смыслу), если:
- `proj.state_dir` ведёт себя не так, как описано в фактах (нет функции, другой приоритет
  `paths.state`, падает без `pipeline.json`) — значит расхождение промта с кодом;
- чтобы позеленеть, нужна правка файла вне двух разрешённых — включая `tests/helpers.py`
  (добавить алиас), `tests/conftest.py`, `step_pipeline/project.py` или `engine/state_io.py`;
  это значит, что граница шага выбрана неверно;
- атомарность не получается без импорта движка или без правки `engine/` — доложить, а не
  тащить чужой модуль в плагин;
- существующий тест покраснел из-за нового модуля (импорт пакета, конфликт имён) — доложить
  имя теста и вывод; чужие тесты не править и ожидания не подгонять;
- шесть тестов не получаются без параметризации или классов — план фиксирует «6 passed»;
  седьмой тест или параметризация меняют число;
- битый файл нельзя прочитать так, чтобы предупреждение ушло ровно одной строкой в `stderr`
  (например, исключение печатает в stdout) — доложить фактический вывод обеих потоков;
- для «Готово =» нужна новая зависимость, переменная окружения или ключ `pipeline.json` — это
  выход за объём шага;
- интерпретатора с pytest нет (`C:/tmp/venv-s2b` пропал) — создать своё окружение через `uv`
  вне репозитория и назвать его в отчёте; в системный `python` пакеты не ставить;
- полный прогон красный по посторонней причине (кодировка консоли, отсутствие `hermes`,
  сеть) — доложить числа и текст ошибки, чужие тесты не править.

Формат доклада: что обнаружено (файл и строки), замер командой, варианты с ценой, рекомендация.

## 7. Формат отчёта

По-русски, до и после коммита, по порядку: `git status --porcelain` до коммита → `git diff
--stat` после `git add` → содержимое обоих файлов по существу (сигнатуры, формат payload,
текст предупреждения, как сделана атомарная запись) → RED-прогон (команда, `EXIT`, фактический
текст ошибки сборки) → GREEN-прогон (6 passed, `EXIT`) → полный прогон (фактическое число
passed, `EXIT`) → `grep` по `engine`/`state_io` с выводом → ручной замер на временном каталоге
→ самостоятельные решения с причиной → что сознательно не сделано → отклонения от промта →
sha коммита и ветка пуша.

## 8. Вопросы (2, каждый с ценой)

1. Каталог состояния: `proj.state_dir(project)` (вариант A, рекомендую) или жёстко
   `.pipeline/state` (вариант B)? Цена A: путь уважает `paths.state` проекта, но в проекте с
   изменённым `paths.state` файл ляжет не туда, где его ждёт буква плана. Цена B: буквальное
   совпадение с планом, зато второй источник истины рядом с движком
   (`engine/config.py:205-207`) и риск разойтись с каталогом стопа при настройке проекта.
2. Непригодное содержимое файла (например `{"plan_mode": "false"}` строкой): считать «включён»
   с предупреждением (вариант A, рекомендую) или трактовать строку как `false` (вариант B)?
   Цена A: безопасное умолчание и честная строка в `stderr`, но испорченный файл не выключает
   режим до ручной правки. Цена B: `bool("false")` — истина, то есть попытка передать строку
   даёт обратный результат; либо понадобится собственный разбор строк, которого нет в плане.

## 9. Ревью (обязательно)

Шаг не закрывает исполнитель. После гейтов — независимое ревью ролью `reviewer`
(скилл `pipeline-reviewer`) по плану и коду: §S1 `docs/plans/4-planner.md`, `git show` коммита
шага, сами `step_pipeline/plan_mode.py` и `tests/test_plan_mode.py`; отчёт исполнителя
источником фактов не является. Отчёт ревьюера — `docs/reviews/4-S1.md`, ровно одна строка
вердикта: `APPROVE` или `REQUEST_CHANGES`, и первая строка блока «Объект ревью» — коммит шага в
бэктиках. При `REQUEST_CHANGES` шаг остаётся открытым, находки правятся, ревью повторяется.
Строку журнала и закрытие шага делает страж после `APPROVE`.
