Р6. «Лента действий из плана 2, S3» (§S9, строка 177): в плане 2 S3 создан только `history.jsonl` и метрики движка; экрана ленты не было ни в одной постановке. Лента строится с нуля поверх того же файла — источник считается существующим, экран нет.

## 4. Решения (приняты постановщиком; исполнитель их не пересматривает, спорное — вопросом)

D1. Лента — новая вкладка «Лента» (`data-tab="events"`, панель `id="tab-events"`) между «Шаг» и «Проверки», плюс ключ `events` в снимке. Серверный блок «Лог действий» (`index.html`, заголовок «Лог действий», 343) не трогаем: это лог самой панели, другой источник. Цена варианта «секция на Обзоре» — теряется место под фильтры и таблицу.

D2. Источник ленты — только чтение `history.jsonl` из каталога состояния. Движок не запускается, состояние не пишется. Окно — последние `EVENTS_LIMIT = 200` валидных записей в обратном порядке (свежие сверху). Счётчики: `total` — число ВАЛИДНЫХ записей всего файла (не `len(rows)`: окно обрезается `limit`, и при >200 валидных `total` больше `len(rows)`), `bad` — битых, «всего непустых строк в файле = total + bad», `limit = 200`. У `gate.history_lines` (функция `history_lines`) `total` считает все непустые строки, включая битые, — это ДРУГАЯ величина, ссылаться на неё как на эталон нельзя. Разбор свой, по тем же правилам валидности (объект JSON, числовой `ts`, непустой `action`), потому что движок импортировать нельзя: `snapshot.py` копируется в проект отдельно от плагина (`snapshot.py:304-308`). Файла нет или он не читается — пустая лента и текст-объяснение, а не ошибка снимка.

D3. Строка ленты: `ts`, `at`, `plan`, `step`, `kind` (значение `action`), `label` (человеческая подпись), `detail`, `commit`, `card`, `review`, `flag`. `card` — идентификатор вида `t_` + 6+ hex-символов, извлечённый из `detail` регуляркой (живой пример: `detail: "карточка шага: t_40bbe197"`), иначе пустая строка; в строке ленты карточка выводится ссылкой/подписью рядом с коммитом (§6.3) — поле не «мёртвое». `review` — путь отчёта ревью вида `docs/reviews/3-S9.md` (каталог из `paths.reviews`, имя «номер плана — номер шага», тот же путь строит `snapshot._review`, `snapshot.py:793-794`), если файл существует, иначе пустая строка. Цена: разбор `detail` регуляркой — хрупко к смене формулировки движка, зато не требует правок `gate.py`.

D4. Подсветка `flag`: `bad` — `kind == "stop"` (страж пишет стоп-флаг с `kind=incident` при инциденте — `write_stop`/`stop_incident` — и в историю уходит строка `stop`: в живой истории таких 3); `warn` — `kind == "create_fix"` (круг правок); иначе пустая строка. Цена варианта «вычислять инцидент по стоп-файлу» — стоп-файл хранит только последний стоп, история его переживает.

D5. Фильтры и поиск — клиентские (`filterEvents`): селект плана («все планы» + планы из `data.plans`), поле шага (подстрока без учёта регистра), селект вида действия (по встреченным `kind`, подписи из `label`), поиск по `detail` + `label` + `step`. Счётчик «показано N из M» и строка «ничего не найдено» — на странице. Причина — Р5: серверных параметров фильтрации нет, `ui_server.py` вне объёма.

D6. Время: у этапа длительность = «сейчас» минус начало; начало — `task_runs.started_at` текущей попытки карточки, иначе `tasks.started_at`, иначе `tasks.created_at`. `heartbeat` — не длительность, а живость: `heartbeat_ts = tasks.last_heartbeat_at` (если колонки нет — пусто), `stale = (now - heartbeat_ts) > 300` при `HEARTBEAT_STALE = 300`; подпись «молчит N» строится `_duration`. Цена иной трактовки — одно выражение в расчёте и правка теста 6.

D7. Этапы: карточки шага группируются по суффиксу ключа `planloop:{план}:{шаг}:{этап}` (ключи — §2). Подписи этапов: `prompt` — «Постановка», `promptreview` — «Ревью постановки», `step` — «Исполнение», `review:N` — «Ревью N», `rereview:N` — «Повторное ревью N», `fix:N` — «Правки N», `promptfix:N` — «Переписывание постановки N», иной суффикс — как есть. Роль — по `assignee`: `profiles.prompter` — «постановщик», `profiles.reviewer` — «ревьюер», остальные — «исполнитель» (карточки правок тоже исполнитель, Р2), пустой `assignee` — «—». Интервалы не пересекаются: этапы сортируются по началу, эффективное начало этапа = максимум из своего начала и конца предыдущего этапа, эффективный конец = минимум из своего конца (у идущего — сейчас) и границы шага; `seconds = max(0, конец - начало)`. Так сумма этапов не превышает длительности шага по построению. Цена варианта «не схлопывать пересечения» — сумма может превысить шаг и гейт §S9 не выполнится.

D8. Итоги по ролям — в ответе `/api/step` (в снимок не тащим: экран шага уже знает план), ДВА разных ключа, имена не пересекаются: `roles` — по плану (все карточки плана, `cards(db, limit=1000, key_prefix="planloop:{план}:")`, правило D7 по каждому шагу); `step_roles` — по самому шагу (только его этапы). Строки — «роль / этапов / сумма времени»; в каждом ключе сумма по ролям равна сумме этапов по построению. Цена варианта «один ключ на два уровня» — тест 5 и тест 7 требуют разного, и `#step-roles` показывает плановые числа.

D9. Попытки: `task_runs` по `task_id` карточек шага, порядок по `started_at`; таблицы нет — пустой список, а не падение (образец чтения по факту — `_capacity` в правках S8, `ui_server.py:805-892`; после коммита S8 он в дереве). Поля попытки: номер, `started_at`, `ended_at`, `seconds`, `duration`, `outcome` (значение как есть, пусто — «идёт» по `ended_at IS NULL`), `label` (человеческая подпись исхода), `bad`, `rate_limited` (Р3), `waited` = `started_at` минус `created_at` карточки, `waited_text`, `current`, `output` (текст `summary` и `error`, обрезка `CARD_TEXT_LIMIT`, пометка обрезки). Цена варианта «отдельный маршрут для попыток» — новый маршрут в `ui_server.py`, а он вне объёма.

D10. Форматы: метки времени шага — `%d.%m.%Y %H:%M` (минуты, локальное время процесса), `at` ленты — как записано в истории (с секундами), при отсутствии — из `ts` тем же форматом с секундами. Нет метки — `null` в полях `*_ts` и пустая строка в текстовых, плюс `note` с объяснением. Нулей и `Invalid Date` не бывает.

D11. Живой тик: страница раз в секунду переписывает текст у элементов с `data-start` (epoch) и `data-live="1"`; формат — «1 ч 05 мин 12 с», у молчащей карточки — «(молчит 12 мин)» по `data-heartbeat` и `HEARTBEAT_STALE`. Функция — `tickTimes()`, таймер — `setInterval(tickTimes, 1000)`, отдельно от 30-секундного `refresh` и SSE. Закрытые этапы тик не трогает.

D12. Никаких новых маршрутов и правок `ui_server.py`, `project.py`, `engine/**`, `tests/helpers.py`, `tests/conftest.py`, `plugin.yaml`. Всё, что нужно, читается из `snapshot.py` и рисуется в `index.html`.

## 7. Как проверить (гейты)

Интерпретатор — `.venv/Scripts/python.exe` (Python 3.11.15), команды из корня репозитория. В `pytest.ini` уже стоит `-q` — второй `-q` не добавляй (`AGENTS.md`). Вывод каждого гейта — дословно в отчёт, с числом `passed`/`failed`.

Порядок жёсткий: Г1, Г2, Г3, Г4 — до коммита; затем коммит (§9 п. 6); затем Г5 (проверка самого коммита); отчёт — после Г5 (он называет коммит и его файлы, поэтому раньше писать его нечем).

Г1. Тесты файла шага:

    .venv/Scripts/python.exe -m pytest tests/test_ui_server.py

Ожидается: `0 failed`, `0 error`; собрано = база на старте шага + 10 (десять новых функций §6.6). Базу измерь до первой правки: `git show HEAD:tests/test_ui_server.py | grep -c "^def test_"` → на recon 98; собираемое число — из вывода pytest `--collect-only` до правок. Если в наборе есть `skipped` (машинозависимые git/симлинки) — их число не должно вырасти.

Г2. RED-доказательство — главный критерий «сделано»: новые тесты обязаны падать на базовом коммите, где ни ленты, ни времён нет:

    git worktree add ../sp-s9-red HEAD
    cd ../sp-s9-red

    cd C:/Users/malik/PycharmProjects/hermes-step-pipeline
    git worktree remove ../sp-s9-red --force

Ожидается: код возврата pytest не 0; среди выбранных `0 passed` — все десять падают (на базовом коммите нет ни `events` в снимке, ни `times`/`stages`/`roles` в `/api/step`, ни `task_runs` в чтении, ни разметки `#events-*`/`tickTimes`). Если часть тестов на базе зелёная — тест не про шаг, перепиши его. Гейт без RED не принимается. Защита от пустого прогона: до запуска сверь `grep -c "^def test_" tests/test_ui_server.py` = база + 10, а в выводе жди строку `10 failed`; `no tests run` или `0 selected` — это опечатка в `-k`, а не RED, гейт не сдан. Если `git apply` не принимает патч из-за перевода строк (autocrlf), скопируй файл целиком — `cp tests/test_ui_server.py ../sp-s9-red/tests/` — и запусти те же `-k`: RED по копии считается.

## 9. Формат отчёта

Отчёт — в комментарии карточки шага (её создаёт страж по ключу `planloop:3:S9:step`), после Г5 (в отчёте есть хеш и файлы коммита). Язык — русский. Обязательные пункты:

1. Что сделано: по пунктам 6.1-6.6, с адресами новых символов (`file:line`).
2. Гейты: дословные выводы Г1-Г4 с числами `passed`/`failed` и строкой `собирается N`, результат `git show --stat` (Г5).
3. RED: дословный вывод pytest из worktree на базовом коммите — что падало и сколько.
4. Соответствие C1-C7: один пункт — одна строка «да, тест N» либо «нет, потому что».
5. Расхождения: что из §3 подтвердилось иначе, чем записано, — с фактом и командой.
5а. Ручная проверка фильтров (JS тестом не покрыт): сколько строк было, сколько осталось после фильтра по плану, по шагу, по виду и после поиска — четыре числа и имена фильтров.
6. Коммит: `feat(ui): лента событий, время шагов и этапы ролей` — одним коммитом, только три файла, сообщение без упоминания карточки.
7. Журнал: «ЗАКРЫТ» не ставился, план не правился — отдельной строкой.
8. Отклонения от постановки: где поступил иначе и почему; спорное — вопросом в этот же отчёт.

Строка ревью в отчёте не нужна: ревью вызывает страж, ты только фиксируешь, что шаг сдан на ревью.

## 10. Вопросы

Открытых вопросов, блокирующих работу, нет: все развилки закрыты решениями D1-D12. Три места, где решение могло быть иным, названы с ценой — если владелец ответит до старта, следуй его ответу.

В1. Роль карточки правок (D7, Р2): принято — по `assignee`, то есть исполнитель, потому что так создаёт карточку движок (действие `create_fix`). Цена иной трактовки (план пишет «ревьюер») — одна строка в карте ролей и правка теста 5.

В2. Длительность идущего этапа (D6, Р7): принято — от начала попытки, heartbeat отдельным признаком живости «молчит N». Цена варианта «длительность от последнего heartbeat» — одно выражение и правка теста 6.

В3. Место итогов по ролям (D8): принято — `/api/step` двумя уровнями (план и сам шаг), потому что снимок о плане уже там, а пункт «по шагу видно, сколько работали роли» иначе не доказывается. Цена варианта «снимок и Обзор» — второй проход по карточкам плана в `_build_snapshot` и правка теста 7.

## 11. Ревью (обязательно)

Шаг уходит на независимое ревью роли `reviewer` (`pipeline-reviewer`): после твоих зелёных гейтов страж создаёт карточку ревью по ключу `planloop:3:S9:review:1`, и ревьюер сверяет план (`docs/plans/3-panel.md`, §S9) и код. Вердикт — `APPROVE` либо `REQUEST_CHANGES`:

- `REQUEST_CHANGES` — шаг остаётся открытым, находки правит исполнитель, ревью повторяется. Отчёт исполнителя ревьюеру не источник фактов: он смотрит план, код и тесты сам (прецедент — `docs/reviews/3-S7.md`).
