## 2. Контекст (факты) и решения

Дальше — решения, принятые до тебя. Они не обсуждаются в коде: если реализация расходится с решением, шаг останавливается (см. §6).

**R1. `state` — четыре значения, порядок проверки жёсткий.** Строка плана получает ровно одно:

1. `closed` (подпись «закрыт») — у плана нет открытого шага (`ctx["next"]` пуст; сюда же случай `no_steps`, когда раздел шагов не распознан: причина в `reason` объяснит разницу).
2. `not-driven` (подпись «не ведётся») — номера плана нет в `registry.driven_ids(cfg)`.
3. `stopped` (подпись «остановлен») — стоп-флаг держит конвейер: `stop_kind(stop) == "owner"` (стоп владельца держит всегда) **или** `stop_kind(stop) == "incident"` и в решении `decision.get("incident")` истинно.
4. `running` (подпись «идёт») — всё остальное.

Порядок именно такой: план 1 в проекте закрыт и не ведётся одновременно, а на панели он обязан быть «закрыт», иначе приёмка плана («закрытые 1–4») не выполняется.

**R2. `note` — пометка снятого стопа.** Если стоп-файл существует, но решение его не держит (`decision.get("clear_incident")` истинно, причина исчезла), состояние — `running`, а в `note` строка ровно такого вида: `стоп снят (было: ` + значение `stop["reason"]` + `)`. Причина берётся целиком, без обрезки. Во всех прочих случаях `note` — пустая строка.

**R3. `reason` — полная причина, без сокращений и без многоточия.** Источники по состояниям: `stopped` с владельческим стопом — `stop["reason"]`; `stopped` по инциденту — `decision["reason"]`; `closed` — `decision["reason"]`; `not-driven` — строка движка `план не в driven_plans — конвейер его не ведёт`; `running` — `decision["reason"]`. Обрезки, `…` и `textwrap` здесь запрещены: панель показывает причину с переносом строк.

**R4. `action` — одно действие на план, словарь ровно из восьми `kind`.** Поля `{kind, text, command}`; `command` — готовая копируемая строка либо пустая. Приоритет — сверху вниз, побеждает первое совпадение:

| kind | text | command | когда |
|---|---|---|---|
| `resume` | `снять стоп: Продолжить` | `python .pipeline/gate.py --plan {id} --resume` | `stopped` по стопу владельца |
| `unblock` | `решение владельца по {card}, затем разблокировать` | `hermes kanban --board {board} unblock {card}` | `stopped` по инциденту, и в `ctx["cards"]` + `ctx["prev_cards"]` есть карточка со статусом `blocked` |
| `tick` | `устранить причину и запустить тик` | `python .pipeline/gate.py --plan {id} --run` | `stopped` по инциденту без blocked-карточки; а также сбой движка (§R5) |
| `unhold` | `снять ручной допуск: unhold {step}` | `python .pipeline/gate.py --plan {id} --unhold {step}` | `decision["action"] == "hold_risk"` либо следующий шаг есть в `ctx["hold"]` |
| `approve` | `утвердить план` | `hermes pipeline plan --accept {id}` | `decision.get("approval_blocked")` |
| `drive` | `добавить план в driven_plans` | пустая строка | `state == "not-driven"` |
| `cron` | `включить джобу стража` | cron-команда из R6 | у плана есть открытый шаг, нет стопа, hold и неподтверждённого утверждения, а метки `.pipeline/cron.json` в проекте нет |
| `none` | `закрыт, действий не требуется` при `closed`, пустая при `running` | пустая строка | остальное |

**R5. Движок: одна функция-сборщик строки состояния, один вызов решения на план.** В `gate.py` рядом с `plans_rows` появляется функция `plan_view(cfg, p, driven, cron_ok)`; она возвращает словарь с ключами `state`, `state_label`, `reason`, `note`, `action` и ничего не пишет на диск. Внутри — `ctx = build_ctx(p)` и `decision = decide(ctx)` (те же вызовы, что у `--status`; `build_ctx` уже ловит `SystemExit` сборщика шагов). `except GateError as exc` → `state="stopped"`, `reason=str(exc)`, `action={"kind": "tick", ...}`: панель обязана показать строку с причиной, а не уронить весь `--plans`. `plans_rows` строит по одному `plan_view` на план и кладёт его ключи в строку; `next` и `risk` берутся из того же `ctx` (`ctx["next"]`), чтобы сборщик шагов запускался **один** раз на план, а не дважды.

Стоимость. `--plans` сейчас 3,5 с на 5 планов; новые вызовы — это `build_ctx`, он несёт тот же сборщик и один `git diff`, когда постановка есть. Никаких новых подпроцессов, никаких `hermes`-команд внутри `plans_rows`: `--plans` зовут панель и сводка реестра, лишние секунды там нельзя. Замер — гейт G7, порог 30 с.

Неизменное: `stop` (сам стоп-файл с `kind`) остаётся в строке как есть — на него завязаны существующие тесты; `closed` остаётся числом; порядок строк — `registry.specs(cfg)`.

`cdp_shot.mjs` — навигация, активация вкладки, явный `refresh()`, снимок через CDP:

```javascript
const [, , url, out, w = "1600", h = "1400"] = process.argv;
const ver = await (await fetch("http://127.0.0.1:9333/json/version")).json();
const ws = new WebSocket(ver.webSocketDebuggerUrl);
let id = 0; const waiters = new Map();
const send = (method, params = {}, sessionId) => new Promise((res, rej) => {
  const msg = {id: ++id, method, params}; if (sessionId) msg.sessionId = sessionId;
  waiters.set(msg.id, {res, rej}); ws.send(JSON.stringify(msg));
});
await new Promise((r) => ws.addEventListener("open", r, {once: true}));
ws.addEventListener("message", (ev) => {
  const msg = JSON.parse(ev.data);
  const wtr = msg.id && waiters.get(msg.id);
  if (!wtr) return; waiters.delete(msg.id);
  msg.error ? wtr.rej(new Error(msg.error.message)) : wtr.res(msg.result);
});
const {targetId} = await send("Target.createTarget", {url});
const {sessionId} = await send("Target.attachToTarget", {targetId, flatten: true});
await send("Page.enable", {}, sessionId);
await send("Emulation.setDeviceMetricsOverride",
           {width: Number(w), height: Number(h), deviceScaleFactor: 1, mobile: false}, sessionId);
await new Promise((r) => setTimeout(r, 4000));
await send("Runtime.evaluate", {expression: "refresh()", awaitPromise: true}, sessionId);
await new Promise((r) => setTimeout(r, 2500));
const {data} = await send("Page.captureScreenshot", {format: "png"}, sessionId);
const fs = await import("node:fs");
fs.writeFileSync(out, Buffer.from(data, "base64"));
console.log("снимок записан:", out);
ws.close(); process.exit(0);
```

`cdp_text.mjs` — тот же CDP, но без снимка: печатает значение выражения со страницы (нужен для строки G8). Проверен отдельно, ходит в свою вкладку без flatten-сессий:

const send = (method, params = {}) => new Promise((resolve) => {
  const mid = ++id; waiting.set(mid, resolve);

});
await send("Page.enable");

await new Promise((r) => setTimeout(r, 6000));

Останавливайся и докладывай (не «адаптируй по смыслу») в любом из случаев:

1. **Код расходится с постановкой по существу:** например, `decide` больше не отдаёт `incident`/`clear_incident`, или `build_ctx` перестал ловить `SystemExit` сборщика; или в проекте уже есть чужая реализация `state` в `plans_rows`. Доклад: что нашёл, чем это ломает R1–R6, варианты.
2. **Нужна миграция, правка данных или конфигурации владельца:** `pipeline.json`, `.pipeline/`, журнал плана, установка/переустановка плагина, `setup --upgrade`. Это вне шага: остановись и опиши, что именно требуется.
3. **Гейт красный по посторонней причине:** падает тест, который ты не трогал, или `hermes plugins validate` даёт новое предупреждение не из твоего кода. Сначала проверь, воспроизводится ли падение на `HEAD` без твоих правок (`git stash` не делать — копия дерева в отдельный каталог); если да — стоп и доклад с точной командой и выводом.
4. **`--plans` стал медленнее 30 с** или требует новых подпроцессов/`hermes`-вызовов — решение не выполнено, оптимизировать «в обход» R5 запрещено.
5. **Снимок не получился ни по процедуре §4.8:** доклад с командой и выводом, без подмены доказательства текстовым описанием; «снимок потом сделает владелец» — тоже стоп (нужен ответ владельца, а не тишина).
6. **Появилось желание изменить `plans_table`, форму `stop` или словарь `progress`:** это вне объёма; стоп и предложение отдельной карточкой.

## 7. Формат отчёта

Отчёт — до коммита (коммитит страж), в свою карточку шага (`planloop:5:S2A:step`, у текущего воркера это его собственная карточка), разделы по порядку:

1. **Что сделано** — по пунктам §4, с именами файлов и строк: что добавлено, что переписано.
2. **Проверка** — таблица гейтов G1–G10: команда, фактическая итоговая строка, `EXIT`. Числа — фактические, не «зелёные».
3. **Строка плана 5 из живого JSON** — дословный фрагмент вывода `--plans --json` по плану 5 (state, state_label, reason, action) и время прогона.
4. **Снимки** — пути PNG, размеры, что видно на каждом (какие статусы, какие подписи), и вывод DOM-проверки.
5. **Расхождения и решения** — что в коде оказалось не так, как описано в §0/§2; какие мелкие решения принял сам (и почему); какие правки стенда делал (в копии!).
6. **Не сделано и почему** — например, `plans_table` остался прежним, копия движка в `.pipeline/` не обновлена (нужен `setup --upgrade` владельцем).
7. **Что требует владельца** — если есть: обновление копии движка, переустановка плагина 0.10.0, ответ на вопрос из §8.

Никаких «вроде работает»: каждый пункт — с цифрой или строкой вывода.

## 8. Вопросы (≤3, каждый с ценой вариантов)

1. **Нужна ли готовая команда для строки «не ведётся»?** По умолчанию в `action.command` пусто, а текст называет ключ `driven_plans`: правка этого ключа — решение владельца, автоматическую команду движок не печатает. Цена альтернативы (команда `hermes pipeline config --set driven_plans` в подсказке): владелец может нажать её без обдумывания и включить ведение плана случайно — считаю это дороже, чем отсутствие команды.
2. **Достаточно ли одного снимка или нужен второй со снятым стопом?** По умолчанию делаем оба PNG (основной и `…-cleared.png`): приёмка плана требует, чтобы снятый стоп-флаг не рисовал ложный «остановлен». Цена отказа: этот случай доказывается только тестом, а не панелью.

## 9. Ревью (обязательно)

Шаг закрывает не исполнитель, а роль `reviewer` (`pipeline-reviewer`): после кода и гейтов карточка уходит на независимое ревью по плану (`docs/plans/5-platforma.md`, §S2A) и по коду; отчёт исполнителя ревьюеру не источник фактов, он его только сверяет с кодом и гейтами. Вердикт — `APPROVE` или `REQUEST_CHANGES` в файле ревью (`docs/reviews/5-S2A.md`).

При `REQUEST_CHANGES` шаг остаётся открытым: находки правятся, гейты прогоняются заново, ревью повторяется. Строка «ЗАКРЫТ» в журнале плана и коммит закрытия — только после `APPROVE`; ни то, ни другое исполнитель не делает.
