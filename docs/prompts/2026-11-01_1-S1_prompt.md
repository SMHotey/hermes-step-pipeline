## 1. Роль и цель

Ты — разработчик движка `hermes-step-pipeline` (Python 3.11, только stdlib). Результат:
`step_pipeline/engine/gate.py` печатает в карточке ревью строку-образец ссылки на коммит
с ровно одной парой бэктиков, страж разбирает эту строку в sha без ручной правки, при
APPROVE в журнал плана попадает sha вместо прочерка — и всё это закреплено тремя тестами
в новом файле `tests/engine/test_review_card.py`.

## 4. Что сделать

1. `step_pipeline/engine/gate.py:464` — в литерале строки убрать внешнюю пару бэктиков (бэктик сразу после двух пробелов и бэктик перед точкой) и оба обратных слэша перед бэктиками вокруг образца sha. Итог: в отрендеренной строке ровно **2 бэктика и 0 бэкслешей**, и эти два бэктика стоят вокруг образца sha; сам образец (в угловых скобках), текст предложения («Без него стражу нечего сверять.») и отступ в два пробела не меняются → результат: `COMMIT_RE` находит sha в отчёте, собранном из этой строки.
2. `tests/engine/test_review_card.py` — новый файл, ровно **три** теста, общий помощник на модуле:
   - помощник `card_commit_line(project)` — `config_mod.load(project)` → `gate.resolve_paths(cfg, "1")` → `gate.review_card_body(p, STEP, 1, "docs/reviews/1-S1.md", None)`; из тела выбрать **одну** строку, где есть и слово «коммит», и слово «сверять» (в теле есть вторая строка со словами «Объект ревью» — это заголовок пункта, `gate.py:463`; `assert len(lines) == 1` с текстом найденного). Литерал шага взять по образцу `tests/engine/test_gate_decide.py:10-12`.
   - тест 1 «одна пара бэктиков»: число символов обратной кавычки в строке равно двум, обратных слэшей в строке нет (проверка через `line.count` и подстроку-бэкслеш).
   - тест 2 «строка из карточки разбирается в тот же sha»: заменить фрагмент в угловых скобках (образец sha) на `a1b2c3d` через `re.sub` по регулярке (не хардкодом самого образца), записать отчёт `## ВЕРДИКТ: APPROVE` + эта строка + строка гейтов в `gate.review_path(p, "S1")`, затем `v = gate.verdict_of(p, "S1")`; утверждать `v["verdict"] == "APPROVE"` и `v["commit"] == "a1b2c3d"`.
   - тест 3 «при APPROVE в журнал попадает sha, а не прочерк»: повторить подготовку отчёта, как в тесте 2 (вынести запись отчёта и вердикт в общий помощник, тесты не должны зависеть друг от друга), затем `gate.append_journal_row(p, "S1", STEP["title"], v["commit"] or "", "гейты: 3 passed")`, прочитать `p.plan_file`, найти строку журнала, у которой вторая колонка начинается с `S1`, и утверждать, что третья колонка равна `a1b2c3d`.
3. Доказать RED до правки: тесты пишутся ПЕРВЫМИ, прогоняются на текущем `gate.py` (ожидание: 3 failed, причины — 4 бэктика, `commit is None`, «—» в журнале), только потом правится строка 464 и прогон даёт 3 passed.
4. Коммит и пуш только двух файлов: `git add step_pipeline/engine/gate.py tests/engine/test_review_card.py`, сообщение на русском, `git push`. Строку журнала плана не трогать — её пишет страж после APPROVE.

Решения, принятые за тебя (не переигрывать):
- **D1.** Ровно три теста: план требует «3 passed».
- **D2.** Журнал проверяется через `append_journal_row`, а не через `run_gate`/`close_step`: `close_step` зовёт `git cat-file -e` (`gate.py:886`) в каталоге фикстуры, который не является git-репозиторием, и поставит инцидентный стоп вместо строки журнала.
- **D3.** Селектор строки — одновременное наличие слов «коммит» и «сверять»; выбор по «Объект ревью» неоднозначен.
- **D4.** Версия, `CHANGELOG`, `plugin.yaml` в этом шаге не меняются; расхождение с «граблями» плана (строка 49) вынесено в вопрос 1.
- **D5.** Образец sha подставляется регуляркой, чтобы тест не зависел от текста образца.

Образец стиля: `tests/engine/test_gate_decide.py:1-25` — плоские импорты, литерал `STEP`, фикстура `project`; структуру копировать, смысл свой.

## 5. Как проверить (гейты)

Из корня репозитория; вывод в файл, код возврата смотреть у pytest, а не у хвоста пайпа:

```
python -m pytest tests/engine/test_review_card.py > "$TMPDIR/s1-card.log" 2>&1; echo EXIT=$?
# после правки ожидается: 3 passed, EXIT=0; до правки — 3 failed (это RED, его надо показать)
python -m pytest > "$TMPDIR/s1-all.log" 2>&1; echo EXIT=$?
# ожидается: 99 passed, EXIT=0 (96 сейчас по замеру grep -c '^def test_' по tests/: 48 движка + 48 плагина, плюс 3 новых)
git status --porcelain
# до коммита ожидается: `M step_pipeline/engine/gate.py` и `?? tests/engine/test_review_card.py`; чужие правки из блока 2 остаются как были
git show --stat --oneline HEAD
# после коммита ожидается: в коммите ровно два файла (изменённый gate.py и новый тест) и его sha
```

`-q` к командам не добавлять: в `pytest.ini` уже стоит `addopts = -q`, второй `-q` скрывает итоговую строку с числом прошедших. Запись плана «`python -m pytest tests/engine/test_review_card.py -q` → 3 passed» означает то же самое; отчитываться числом прошедших и `EXIT`.

## 6. Стоп-сигналы

Остановиться и доложить (не адаптировать по смыслу), если:
- позеленеть тестам мешает не строка 464, а `COMMIT_RE` или `verdict_of` — значит правка не та: расширять регулярку запрещено, потому что бэкслеши в markdown-тексте карточки останутся;
- RED не воспроизвёлся (тесты зелёные до правки) — неверный селектор строки или не тот файл;
- правка требует второго места в `step_pipeline/` или в `.pipeline/`;
- полный прогон красный по причине, не относящейся к шагу (кодировка консоли, отсутствие `hermes` в PATH) — доложить с числами и текстом ошибки;
- `git status` показывает в индексе файлы вне двух разрешённых.

Формат доклада: что обнаружено (файл и строки), замер командой, варианты с ценой, рекомендация.

## 7. Формат отчёта

По-русски, до и после коммита, по порядку: `git diff --stat` → дифф `gate.py:464` и полный текст нового теста → RED-прогон (команда, `EXIT`, три имени упавших тестов и строки утверждений) → GREEN-прогон (3 passed, `EXIT`) → полный прогон (число passed, `EXIT`) → самостоятельные решения с причиной → что сознательно не сделано → отклонения от промта → sha коммита и ветка пуша.

## 8. Вопросы (≤3, каждый с ценой)

1. Трогать ли версию и `CHANGELOG` в этом шаге? «Грабли» плана (строка 49) требуют минимум минорной версии на любое изменение поведения движка, но §S1 перечисляет ровно два файла. Вариант A (рекомендую, D4): шаг без bump, версия и `CHANGELOG` — отдельным релизным действием; цена — плагин 0.1.0 увозит багфикс, маркер `.pipeline/VERSION` в проектах обновится только после `setup --upgrade`. Вариант B: поднять 0.1.0 → 0.2.0 и записать в `CHANGELOG` этим же коммитом; цена — выход за объём §S1 и находка ревьюера «расширение объёма».

## 9. Ревью (обязательно)

Шаг не закрывает исполнитель. После гейтов — независимое ревью ролью `reviewer` (скилл `pipeline-reviewer`) по плану и коду: §S1 `docs/plans/1-stabilnost.md`, `git show` коммита шага, сами файлы и тесты; отчёт исполнителя источником фактов не является. Отчёт ревьюера — `docs/reviews/1-S1.md`, ровно одна строка вердикта: `APPROVE` или `REQUEST_CHANGES`, и первая строка блока «Объект ревью» — коммит шага в бэктиках. При `REQUEST_CHANGES` шаг остаётся открытым, находки правятся, ревью повторяется. Строку журнала и закрытие шага делает страж после `APPROVE`.
