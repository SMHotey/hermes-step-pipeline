## 1. Роль и цель

Ты — исполнитель шага S2 плана 5 в репозитории плагина `hermes-step-pipeline`. Рабочая
директория — `C:\Users\malik\PycharmProjects\hermes-step-pipeline`, оболочка — bash
(git-bash), интерпретатор — `.venv/Scripts/python.exe`. Код, комментарии, тесты, сообщения
и отчёт — по-русски (`AGENTS.md`, «Конвенции»).

Результат шага одним абзацем: разведка готовых решений становится ролью конвейера с
профилем, карточкой и проверяемым исходом — каталог роли
`step_pipeline/roles/pipeline-scout/SKILL.md` (таймбокс 30 минут, артефакт по §5a формата,
разрешённый исход «готового нет»), ключи `scout` в `profiles`/`skills`/`runtimes` конфига
проекта и шаблона, строка роли в `SKILL_CATEGORIES` (установщик её копирует), действие
движка `create_scout` с ключом вида `planloop:5:scout` (номер плана между двоеточиями),
которое для плана действующего формата без артефакта разведки заводит ровно одну карточку
и держит план в состоянии
«ждёт разведку», пока карточка не закрыта; повторный тик дубля не делает, «готового нет»
закрывает ожидание как валидный исход, а провал карточки без этой фразы ставит инцидентный
стоп.

Шаг закрывает не исполнитель: после зелёных гейтов карточка уходит на независимое ревью
роли `reviewer` (`pipeline-reviewer`), и только APPROVE даёт запись «ЗАКРЫТ» в журнале
плана.

Контракт шага (из §S2 плана, `docs/plans/5-platforma.md:49-60`), по нему сверяется ревью:

## 2. Контекст (факты) и решения

### 2.1. Что известно про движок и тесты (проверено чтением)

- **Образец действия.** `create_prompt` в `apply` (`gate.py:2375-2400`): берёт данные шага,

  `create_card(...)` с телом из `prompt_order_body`, профилем `p.cfg.prompter`, скиллами

  `--max-runtime`, `--workspace` с путём проекта, `--tenant`; id карточки вылавливается из
  вывода (`t_…`).
- **Чистое решение.** `decide` (`gate.py:901-925`) — обёртка над `_decide_base`
  (`:928-1081`): стоп-флаг владельца, инцидентный флаг, предзаказ постановки N+1. Внутри
  `_decide_base`: отсутствие шага (`:930-939`), утверждение плана (`:941-948`), прошлый шаг

- **D1. Дискриминатор «план действующего формата» — строка `Конституция:` в шапке плана**
  (между `# `-заголовком и первым заголовком уровня 2+; норматив — `PLAN-FORMAT.md:191`,
  образец — `docs/plans/5-platforma.md:3`). Планы без этой строки (2, 3, 4 и все фикстуры
  тестов движка) карточку разведки не получают. Причина: планы 2-4 открыты и в

  тестов не имеют ни строки, ни артефакта — покраснел бы почти весь `tests/engine/`.
- **D2. «Разведка уже есть» — файл артефакта** `docs/research/5-prior-art.md` (имя
  собирается из номера плана и суффикса `-prior-art.md`);
  каталог берётся из `paths.research` (умолчание `docs/research`), у плана 5 это
  `docs/research/5-prior-art.md` (файл существует, 52 строки). Путь читается сырым словарём
  конфига, `step_pipeline/engine/config.py` не правится. Следствие: на этом репозитории шаг
  не заводит ни одной карточки (у плана 5 артефакт есть) — живая борда не трогается.
- **D3. Ключи и умолчания:** `profiles.scout` → `scout`, `skills.scout` →
  `["pipeline-scout"]`, `runtimes.scout` → `30m`. Нет ключа, пустая строка, не список,
  битое значение → умолчание, без исключения (образец поведения — `max_actions_of`).
- **D4. Всё, что нужно чистому решению, считается в `build_ctx`:** `ctx["scout_needed"]`
  (признак «разведка нужна»), `ctx["scout_cards"]` (карточки по префиксу ключа
  `planloop:5:scout`) и `ctx["scout_note"]` (пояснение «разведка: готового нет — план
  идёт своим решением» либо пустая строка). Файл плана читается один раз в `build_ctx`;
  в `decide` никаких чтений файлов не добавляется.
- **D5. Шаблон `templates/pipeline.json.example` получает только `skills.scout` и
  `runtimes.scout`.** `profiles` в шаблоне не трогаем: мастер установки всё равно
  перезаписывает его тремя ролями (`setup_flow.py:531`), а `tests/test_setup_flow.py:69`
  сверяет этот словарь равенством — лишний ключ покрасил бы чужой тест.
- **D6. Место проверки — в `_decide_base` сразу после блока утверждения** (`:941-948`) и до
  ветки прошлого шага. Причина: разведка — предусловие плана, как и утверждение; при уже
  идущем шаге карточка разведки существует, и проверка бездействует.
- **D7. Трактовка исходов:** карточка не в `TERMINAL` → `idle` с причиной «ждёт разведку
  плана N» с id карточки и её статусом (она же попадает в `waiting_reason` через
  `watch_idle`); `done` → план идёт дальше; провал (`crashed`, `timed_out`, `gave_up`,
  `blocked`) с маркером «готового нет» в `result` или `error` → валиден, план идёт дальше;
  провал без маркера → `stop` (инцидентный) с карточкой, статусом и текстом ошибки в
  причине. Профиль `scout` в Hermes заводит владелец (в списке профилей его нет — факт);
  создание профилей мастером — шаг S11, вне объёма.
- **D8. Объём расширяется четырьмя файлами сверх списка шага, каждый — с причиной:**
  `tests/test_roles.py` (счётчик ролей 6 → 7, `:53`; иначе собственный гейт шага красный),

## 7. Формат отчёта

Отчёт — в карточку, по-русски, до коммита и до запроса ревью:

1. Что сделано — по девяти файлам, с якорями: разделы новой роли и её `description`,
   добавленные ключи, строка `SKILL_CATEGORIES`, константы и функции движка (`scout_needed`,
   `plan_has_constitution`, `_scout_decision`, `scout_card_body`, ветка `create_scout`),
   места в `build_ctx` и `_decide_base`, восемь тестов по именам.
2. Гейты: по каждому из §5 — точная команда, число из вывода (`8 passed`, `204 passed`,
   `468 passed`, `7 passed`, `1 passed`, три строки `scout`, `version: 0.11.0`), `EXIT`.
3. Расхождения recon с фактом: адрес съехал, имя символа или статуса иное, число тестов не
   то (в том числе влияние незакоммиченного шага S1) — с командой и выводом.
4. Принятые внутри шага решения и отклонения от D1-D8 — отдельными строками с причиной;
   применённый вариант вопросов §8 назвать явно («работал по умолчанию (а)»).
5. Что сознательно не сделано: разбор артефакта и гейт по нему (S3), корректировка плана
   (S4), подписи действия в панели (`snapshot.py`, S8), профиль `scout` в Hermes (S11),
   исходы `needs-clarification`/`kill` в движке, обновление копии `.pipeline/`
   (`hermes pipeline setup --upgrade`), `docs/CONTEXT.md` и `AGENTS.md`.
6. Список изменённых файлов из `git status --porcelain` — с отдельной пометкой, какие из
   них файлы шага S1 (не твои).

Отчёт не заменяет ревью и не закрывает шаг.
