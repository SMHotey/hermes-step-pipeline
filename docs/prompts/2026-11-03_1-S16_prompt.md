## 1. Роль и цель

Ты — разработчик плагина `hermes-step-pipeline` (Python 3.11, зависимости — только stdlib
и Hermes). Код, комментарии, коммит и отчёт — по-русски.

Цель шага: установка перестаёт быть «зелёной» на веру. `doctor` отвечает на вопрос «а ключ
провайдера сохранён в профиле, а не взят из переменной окружения сессии», а сам `setup`
в конце заводит по одной карточке-эху на каждую роль и ждёт её закрытия: либо в логе
«роли стартуют», либо конкретная причина (нет ключа, нет доверия, нет навыка) с готовой
командой починки. Мёртвый конвейер с зелёным `OK` больше не выдаётся за успех.

Готово = выполнено всё перечисленное:

1. В `doctor` есть проверка сохранённого ключа по каждой из трёх ролей: читается
   `auth.json` профиля, запись провайдера, у которой `source` начинается на `env:`,
   сохранённой НЕ считается; проблема печатается с готовой командой починки, при полном
   успехе — строка-заметка. Слово «план» в новых строках не встречается.
2. В `run_setup` в конце мастера выполняется смоук: по карточке-эху на роль (драйвер,
   промптер, ревьюер) с навыками роли из `pipeline.json`, ожидание закрытия в пределах
   одного дедлайна, разбор статуса и причины из борды.
3. Причина провала берётся из реальных полей борды (`last_failure_error`, `result`,
   последнее событие) и печатается вместе с командой починки, подобранной по причине.
4. Смоук провален — `run_setup` возвращает `3` и печатает «смоук: N из 3»; смоук не
   выполнялся (флаги `--no-smoke`, `--no-profiles`, `--no-cron` или `--upgrade`) — код `0`.
5. `python -m pytest tests/test_setup_flow.py` → `19 passed` (13 существующих + 6 новых),
   `EXIT=0`; новые тесты фиксируют проверку ключа в `doctor`, три карточки на роли,
   причину с командой починки, пропуск смоука и таймаут ожидания.
6. Полный набор `python -m pytest` → без падений, `EXIT=0`, число `passed` ровно на 6
   больше baseline, снятого ДО правок; `tests/test_plan_lint.py` и `tests/engine/**`

### 2.1 Главное расхождение плана с кодом: поля `worker_output` в борде нет

План (§S16:267-268) требует «печатать причину из worker_output». Такого поля нет ни в
CLI, ни в схеме борды. Проверено:

- `hermes kanban show t_647c27f0 --json | grep -o '"[a-z_]*":'` — в ответе есть `runs`
  с ключами `outcome`, `summary`, `error`, но `worker_output` отсутствует;
- схема живой борды (`pragma table_info`, борда `step-pipeline`):
  `task_runs(id, task_id, profile, step_key, status, claim_lock, claim_expires,
  worker_pid, worker_started_at, max_runtime_seconds, last_heartbeat_at, started_at,
  ended_at, outcome, summary, metadata, error)`,
  `tasks(... , result, idempotency_key, consecutive_failures, worker_pid,
  worker_started_at, last_failure_error, ...)`,
  `task_events(id, task_id, run_id, kind, payload, created_at)`.

Решение — D6/D7 ниже: причина берётся из `tasks.last_failure_error`, затем из
`tasks.result`, затем из последнего `task_events.payload`. Движок читает борду так же:
`step_pipeline/engine/gate.py:371-393` (`read_cards`) берёт ровно
`COALESCE(result,''), COALESCE(last_failure_error,'')` по `idempotency_key LIKE`.

### Задача 1. Читатели профиля в `setup_flow.py` (D1, D2)

- `profile_provider(profile) -> str` — прочитать `proj.profile_dir(profile) / "config.yaml"`

  конфига профиля; пустая строка, если он не определён (тогда `doctor` печатает проблему по
  D3 без `auth add`).

### Задача 3. Смоук в `setup_flow.py` (D4-D9)

Константы рядом с `DEFAULT_ROLES` (`setup_flow.py:471`): `SMOKE_TIMEOUT = 300`,

  `run_smoke`, и в блоке «Готово» (`:791-795`) добавляется строка вердикта:

- Код возврата по D9.
