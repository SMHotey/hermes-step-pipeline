## 1. Роль и цель

Ты — исполнитель шага S3 плана 2. Сейчас о ходе конвейера можно судить только по
состоянию плана: применённые действия лежат в `last_actions` (последние 20 записей) и
исчезают вместе с ним, «сколько шагов шло», «сколько было кругов правок», «сколько
инцидентов» посчитать не из чего. Шаг делает ход конвейера измеримым: каждое выполненное
действие дописывается строкой JSONL в историю проекта, история не растёт бесконечно,
а снимок отдаёт посчитанные по ней метрики под ключом `metrics`.

Готово = на демо-проекте после нескольких тиков `metrics` содержит непустые числа,
совпадающие с журналом плана; файл истории ограничен по числу строк и по размеру;
испорченная строка JSONL не ломает подсчёт — пропускается и считается в `bad_lines`.

Строку «ЗАКРЫТ» в журнале, коммит закрытия и ревью делает не ты: журнал закрывает страж
после APPROVE ревьюера, ревью — роль `reviewer`.

   шага; (3) `complete(db, ":step")` → `gate --run` → карточка ревью; (4) отчёт
   `docs/reviews/1-S1.md` с `## ВЕРДИКТ: APPROVE` и `Объект ревью: коммит ` + sha из
   `git rev-parse HEAD`, `complete(db, ":review:1")` → `gate --run` → в плане `| ЗАКРЫТ |`.
   Затем `snap = snapshot.snapshot(root)` (импорт `from step_pipeline import snapshot`).
   Утверждается: `"metrics" in snap`; `m["actions_7d"] == {"create_step": 2,
   "create_review": 1, "close_step": 1}`; `m["actions_7d_total"] == 4`;
   `m["history"]["lines"] == 4`; `m["history"]["bad_lines"] == 0`;
   `m["plans"]["1"]["steps_closed"] == 1` и текст плана содержит ровно одну строку
   `| ЗАКРЫТ |` (число совпадает с журналом); `m["plans"]["1"]["step_seconds"]["measured"]
   == 1`; `m["plans"]["1"]["incidents"] == 0` (стоп первого тика — инцидент внутри
   действия `create_step`, отдельного действия `stop` в истории нет).

## 7. Стоп-сигналы

Остановиться и доложить (не адаптировать по смыслу), если:

- для истории или метрик требуется новый файл в `step_pipeline/engine/` либо правка
  `setup_flow.ENGINE_FILES` / `tests/engine/engine_kit.py` — это вне объёма шага (D10);
- `remember_action` вызывается не из двух мест, названных в §2, или в движке уже есть
  запись истории (факт расходится с постановкой);
- метрики требуют чтения борды, сети или запуска `next_step.py`, либо правки формата
  `pipeline.json` (D12);
- тест шага нельзя сделать без правки `stub_hermes.py`, `engine_kit.py` или чужого теста;
- гейт красный по причине, не относящейся к шагу (например, чужой WIP `0.5.9` ломает
  `tests/test_manifest_hygiene.py`): зафиксировать команду, число и вывод, чужие правки
  не трогать (`git stash` и `git checkout` по ним запрещены), доложить с рекомендацией;
- ожидаемое число прогона разошлось с фактическим больше чем на допустимое: гейт
  считается красным, отчёт идёт с обоими числами.

Формат доклада: что обнаружено (файл и строки), замер командой, варианты с ценой,
рекомендация.

## 8. Формат отчёта

До коммита, по порядку: `git diff --stat` → ключевые диффы (по одному абзацу на файл) →
самостоятельные решения с причиной (включая отклонения от D-решений) → строки гейтов
(команда, фактическое число, EXIT) → замер истории на демо-проекте из теста 6 (число строк
и размер файла) → подтверждение, что `.pipeline/state/history.jsonl` не попал в `git status`
(каталог состояния в `.gitignore`, `setup_flow.py:372-375`) → что сознательно не сделано →
вопросы. Язык — русский. После APPROVE ревьюера — коммит трёх файлов шага и пуш.

## 9. Вопросы

Решение по каждому принято по умолчанию (A) и работу не блокирует; если владелец выберет B,
это отдельный шаг, а не переделка этого.

1. «Время шага» — A: от первого действия по шагу до `close_step` (цена 0, метрика
   показывает, сколько конвейер ведёт шаг) или B: сумма `duration_s` действий шага
   (+0.5 дня, метрика видит только работу стража, но не ожидание карточек)?
2. Где видны метрики — A: только ключ `metrics` в снимке, как требует план (цена 0) или
   B: плитка на экране «Обзор» (`ui/index.html` + тест UI, +1 день, в объём S3 не входит)?
3. Пределы ротации — A: константы движка 2000 строк и 512 КиБ (цена 0, формат конфига не
   меняется) или B: ключи `history` в `pipeline.json` (+правка формата, шаблона и
   `docs/PLAN-FORMAT.md`)?

## 10. Решения и допущения

- D1. Файл истории: `Path(cfg.state_dir) / "history.jsonl"`, то есть по умолчанию
  `.pipeline/state/history.jsonl` проекта. Каталог состояния в `.gitignore`
  (`setup_flow.py:372-375`), поэтому история не попадает в git и не мешает коммиту шага.
- D2. Точка записи — `remember_action` (`gate.py:1880-1895`): это единственное место, куда
  попадает каждое применённое действие, оба вызова уже там (`gate.py:1980`, `gate.py:2198`).
  Отдельная функция «запиши историю» вызывается из него; `last_actions` остаётся.
  `retry_pending` действием не считается (`gate.py:1907-1908`) и строки истории не получает.
- D3. Длительность: `time.monotonic()` до и после `run_gate`, в историю — секунды с тремя
  знаками (`round(delta, 3)`). Замер живёт в двух вызывающих местах, а не в `run_gate`:
  у `run_gate` восемь путей возврата, и оборачивать их все ради замера — лишний риск.
- D4. Формат строки истории (один объект = одна строка, `ensure_ascii=False`):
  `{"ts": 1793745600.123, "at": "03.11.2026 20:00:00", "plan": "1", "step": "S1",
  "action": "create_step", "duration_s": 1.25, "detail": "…", "commit": ""}`.
  `ts` — число (epoch, float), для окна и разностей; `at` — тем же форматом, что в
  `last_actions`; `detail` обрезается до 200 символов, как там же; `step` — пустая строка,
  если решение шага не адресует; `commit` — пустая строка, пока коммита не было.
- D5. `sha` коммита: `run_gate` в ветке `close_step` кладёт в результат `result["commit"]` —
  sha фактического коммита стража из `detail.commit_and_push`, если первый токен `detail`
  совпадает с `^[0-9a-f]{7,40}$`; иначе `verdict.get("commit") or ""`. Остальные ветки
  `run_gate` ключ `commit` не заводят; `remember_action` берёт пустую строку по умолчанию.
- D6. Ротация: дописать строку → если строк больше `HISTORY_MAX_LINES` (2000), оставить
  последние 2000 → если размер больше `HISTORY_MAX_BYTES` (524288), выбрасывать самые
  старые строки, пока не уложится (последняя строка не выбрасывается никогда) → записать
  целиком через `state_io.atomic_write_text`. Обрезка идёт по строкам, а не по байтам:
  разрезанная строка JSONL — это битая строка.
- D7. Битые строки: не JSON, JSON не объект, нет `ts` или `action` → строка считается
  битой (`bad_lines`), в подсчётах не участвует, исключение наружу не выходит. Файла нет
  или он не читается → нули, а не падение.
- D8. Метрики — `history_metrics(cfg, now=None)`, ничего не пишет:
  `{"generated_at": "03.11.2026 20:00:00", "window_days": 7,
    "actions_7d": {"create_step": 2, "close_step": 1}, "actions_7d_total": 3,
    "plans": {"1": {"steps_closed": 1,
                    "step_seconds": {"avg": 12, "median": 12, "measured": 1},
                    "fix_rounds": 0, "incidents": 0}},
    "history": {"lines": 3, "bad_lines": 0, "size_bytes": 912}}`.
  Смысл чисел: `actions_7d` — строки с `ts` не старше `now - 7*86400`, по видам действия;
  `actions_7d_total` — их сумма; `step_seconds` — по шагам, у которых в истории есть и
  первое действие, и `close_step`: разница `ts`, среднее и медиана по этим шагам
  (чётная медиана — среднее двух центральных, округление до целых), `measured` — сколько
  шагов измерено; `fix_rounds` — строки `action == "create_fix"`, `incidents` — строки
  `action == "stop"` (стоп-действие применяется в `gate.py:1770-1782`), оба счёта по всей
  истории, не по окну; `steps_closed` — число строк журнала плана со статусом «ЗАКРЫТ»
  (`_journal_rows` + `registry.status_of_row`), поэтому это число совпадает с журналом;
  строка `plans` есть у каждого ведомого плана (`registry.driven_specs`), даже если в
  истории по нему ничего нет; сбой по одному плану даёт нули и не ломает остальные.
- D9. Отдача: `--status --json` получает `metrics` (ветка `gate.py:1581-1585`); снимок —
  ключ `metrics` в начальном `out` и значение из ответа `--status` (`snapshot.py:919-937`,
  `snapshot.py:950-956`). Кэш снимка инвалидируется сам: файлы состояния входят в отпечаток
  (`snapshot.py:197-201`); `preview`-режим получает нули, а не падение.
- D10. Новый модуль движка не заводить: движок копируется в проекты фиксированным списком
  (`setup_flow.py:34-35`, `tests/engine/engine_kit.py:25-27`), новый файл сломал бы копию и
  проверку целостности (`gate.py:94-104`) — это правки вне объёма шага. Вся история и
  метрики живут в `gate.py`; тест — `tests/engine/test_history.py`, ровно шесть тестов из
  §5.1 (имена функций могут отличаться, число и утверждения — нет).
- D11. `pipeline.json` не меняется: ни `history`, ни `metrics`. Пределы ротации — константы
  движка, окно метрик — тоже. Формат конфига и его шаблон вне объёма шага.
- D12. Версия плагина и `CHANGELOG.md` не трогаются: в дереве чужая незаконченная работа с
  `version: 0.5.9` и одноимённым разделом в `CHANGELOG.md`. Версию поднимает владелец при
  выпуске; в отчёте это фиксируется наблюдением, а не правкой.
- D13. UI не трогается: план требует только ключ снимка. Плитка метрик — план 3.
- D14. `.pipeline/` этого репозитория не обновляется: после того как правка движка попадёт
  в плагин, копию в проектах обновляет владелец (`hermes pipeline setup --upgrade`), и тик
  этого репозитория до обновления остановится на проверке целостности — это ожидаемое
  поведение, а не дефект шага. В отчёт — строкой.

## 11. Ревью (обязательно)

Шаг не закрывает исполнитель: после гейтов — независимое ревью ролью `reviewer`
(скилл `pipeline-reviewer`) по плану `docs/plans/2-upravlenie.md` §S3 и по коду.
Ревьюеру доступны план и код; отчёт исполнителя источником фактов не считается.
Формат вердикта: ровно одна строка `ВЕРДИКТ: APPROVE` или `ВЕРДИКТ: REQUEST_CHANGES` в
отчёте `docs/reviews/2-S3.md`. При REQUEST_CHANGES шаг остаётся открытым: находки правятся,
гейты прогоняются заново, ревью повторяется. Строку «ЗАКРЫТ» в журнале и коммит закрытия
делает страж после APPROVE.
