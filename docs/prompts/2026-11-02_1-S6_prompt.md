- **D7.** Версия и `CHANGELOG.md` не меняются (`plugin.yaml:2` — `0.2.0`).
- **D8.** Ровно четыре новых теста (в файле станет 10), существующие 6 не правятся.
- **D9.** Цифра плана «105 passed» считается устаревшей: гейт — фактический прогон,
  ожидание `165 passed` (161 + 4). В отчёте — фактическое число рядом с ожидаемым.
- **D10.** `engine.state_io._pid_alive` не трогаем и с `_alive` не объединяем: плагин не
  импортирует движок, объединение — отдельная задача (в «не входит»).

## 5. Как проверить (гейты)

Из корня репозитория; код возврата смотреть у pytest, а не у хвоста пайпа; логи — вне
репозитория (`$TMPDIR`; если переменная пуста, возьми `$LOCALAPPDATA/Temp`; если путь пришёл
с обратными слэшами — приведи к прямым):

```
VPY=C:/tmp/venv-s2b/Scripts/python.exe
$VPY -m pytest tests/test_ui_control.py > "$TMPDIR/s6-red.log" 2>&1; echo EXIT=$?
# после п. 1, движок и плагин НЕ тронуты: ожидается 4 failed, 6 passed, EXIT=1
$VPY -m pytest tests/test_ui_control.py > "$TMPDIR/s6-green.log" 2>&1; echo EXIT=$?
# после пп. 2-3: ожидается 10 passed, EXIT=0
$VPY -m pytest > "$TMPDIR/s6-all.log" 2>&1; echo EXIT=$?
# после п. 4: ожидается 165 passed, EXIT=0, строки "warnings summary" в логе нет
grep -c "warning" "$TMPDIR/s6-all.log"
# ожидается: 0
```

Нагрузочность фильтра (проба вне репозитория, кода шага не касается). Создать каталог
`$TMPDIR/s6-probe` и в нём файл `test_thread_probe.py`:

```python
import threading

def boom():
    raise RuntimeError("проба S6")

def test_thread_exception_fails():
    thread = threading.Thread(target=boom)
    thread.start()
    thread.join()
```

```
$VPY -m pytest "$TMPDIR/s6-probe/test_thread_probe.py" -p no:cacheprovider > "$TMPDIR/s6-probe.log" 2>&1; echo EXIT=$?
# ожидается: 1 failed, EXIT=1, в выводе PytestUnhandledThreadExceptionWarning и RuntimeError
```

Машинная проверка «нет `text=True` без `encoding`». Скрипт — в `$TMPDIR/s6_scan.py`
(вне репозитория), запуск из корня:

```python
import ast, sys
from pathlib import Path

bad = []
for path in list(Path("step_pipeline").rglob("*.py")) + list(Path("tests").rglob("*.py")):
    tree = ast.parse(path.read_text(encoding="utf-8"))
    for node in ast.walk(tree):
        if not isinstance(node, ast.Call) or not isinstance(node.func, ast.Attribute):
            continue
        if node.func.attr not in {"run", "Popen", "check_output"}:
            continue
        if not (isinstance(node.func.value, ast.Name) and node.func.value.id == "subprocess"):
            continue
        names = {kw.arg for kw in node.keywords}
        if "text" in names and "encoding" not in names:
            bad.append(f"{path}:{node.lineno}")
print("вызовов с text=True без encoding:", len(bad))
for item in bad:
    print(item)
sys.exit(1 if bad else 0)
```

```
$VPY "$TMPDIR/s6_scan.py" > "$TMPDIR/s6-scan.log" 2>&1; echo EXIT=$?
# ожидается: "вызовов с text=True без encoding: 0", EXIT=0
```

Скрипт смотрит синтаксис вызовов, поэтому сам `run` (kwargs собираются словарём) он не
разбирает: то, что `run` действительно передаёт UTF-8 и `errors="replace"`, доказывает тест
`test_run_helper_decodes_with_replace` поведением. В отчёте привести оба доказательства рядом.

Остальные гейты:

```
grep -n "filterwarnings" -A2 pytest.ini
# ожидается: одна строка error::pytest.PytestUnhandledThreadExceptionWarning под ключом
git status --porcelain
# перед коммитом: M pytest.ini, M step_pipeline/project.py, M step_pipeline/ui_control.py,
# M tests/test_ui_control.py; плюс чужие как были: M docs/CONTEXT.md, ?? .hermes/,
# ?? .pipeline/, ?? docs/templates/, ?? pipeline.json
git show --stat --oneline HEAD
# после коммита: ровно четыре файла шага и sha коммита
git branch -r --contains HEAD
# после пуша: origin/main
hermes plugins validate step_pipeline
# ожидается: Validation passed (CLI есть в PATH)
```

К `pytest` не добавлять `-q`: в `pytest.ini` уже стоит `addopts = -q`, второй `-q` скрывает
итоговую строку. В отчёте — фактические числа и `EXIT` каждого прогона.

## 6. Стоп-сигналы

Остановиться и доложить (не адаптировать по смыслу), если:
- полный прогон красный на тесте вне четырёх разрешённых файлов — доложить имя, ожидание и
  факт; чужой тест не править и не подгонять;
- после правки `_alive` предупреждение о потоке всё равно возникает — значит источник в другом
  потоке; доложить трейсбек и тест, фильтр не отключать, чужой код не править;
- фактическое число тестов до правок не 161 (или после не 165) — доложить фактическое и
  разбивку по файлам; тесты не переименовывать, не удалять и не добавлять сверх четырёх;
- чтобы починить `_alive`, требуется менять аргументы `tasklist`, лезть в `Popen`/`start`
  или в `step_pipeline/engine/*` — это выход за объём шага, доложить;
- чтобы прогон стал зелёным, нужен ещё один фильтр (`ignore::`, `default::`) или глобальный
  `-W error` — доложить, фильтры не расширять;
- RED оказался не таким, как обещано (например, все 10 тестов зелёные до правок) — доложить
  имена и вывод, тесты под код не подгонять;
- интерпретатор без pytest 9 (нет `pytest.PytestUnhandledThreadExceptionWarning`) — создать
  окружение через `uv` вне репозитория и назвать его в отчёте; в системный `python` пакеты
  не ставить;
- прогон красный по посторонней причине (кодировка консоли, отсутствие `hermes`, сеть) —
  доложить числа и текст ошибки.

Формат доклада: что обнаружено (файл и строки), замер командой, варианты с ценой,
рекомендация.

## 7. Формат отчёта

По-русски, до и после коммита, по порядку: `git diff --stat` → ключевые диффы
(`project.run` и два враппера, `_alive` и `stop`, `pytest.ini`, четыре новых теста) →
RED-прогон (команда, `EXIT`, имена четырёх упавших тестов и строки утверждений) →
GREEN-прогон `tests/test_ui_control.py` (`10 passed`, `EXIT`) → полный прогон (фактическое
число passed, `EXIT`, наличие или отсутствие строки предупреждений) → проба потока
(`1 failed`, текст `PytestUnhandledThreadExceptionWarning`) → результат `s6_scan.py`
(`0` нарушений) → `grep` по `pytest.ini` → `hermes plugins validate` → самостоятельные
решения с причиной → что сознательно не сделано → отклонения от промта → sha коммита и
ветка пуша.

## 8. Вопросы (2, каждый с ценой)

1. Цифра плана «105 passed» против фактических 161 в дереве — как фиксировать гейт?
   Вариант A (рекомендую): гейтом считать фактический прогон (`165 passed` до закрытия шага)
   и записать это число в отчёт; текст плана не править. Цена A: в §S6 до закрытия шага
   остаётся устаревшее число, при следующем чтении плана его надо помнить.
   Вариант B: поправить строку гейта в `docs/plans/1-stabilnost.md` сразу. Цена B: план правит
   исполнитель, а по конвейеру его правит закрывающий; плюс лишний файл в диффе шага.
2. Область фильтра предупреждений: Вариант A (рекомендую): только
   `PytestUnhandledThreadExceptionWarning`, как требует §S6. Цена A: `DeprecationWarning`
   из stdlib и Hermes остаются незамеченными. Вариант B: `filterwarnings = error` целиком.
   Цена B: сборка может покраснеть на предупреждении, к шагу не относящемся, и гейт шага
   станет заложником чужого кода.

## 9. Ревью (обязательно)

Шаг не закрывает исполнитель. После гейтов — независимое ревью ролью `reviewer`
(скилл `pipeline-reviewer`) по плану и коду: §S6 `docs/plans/1-stabilnost.md`,
`git show` коммита шага, сами `step_pipeline/project.py`, `step_pipeline/ui_control.py`,
`pytest.ini` и `tests/test_ui_control.py`; отчёт исполнителя источником фактов не является.
Отчёт ревьюера — `docs/reviews/1-S6.md`, ровно одна строка вердикта: `APPROVE` или
`REQUEST_CHANGES`, первая строка блока «Объект ревью» — коммит шага в бэктиках.
При `REQUEST_CHANGES` шаг остаётся открытым, находки правятся, ревью повторяется.
Строку журнала и закрытие шага делает страж после `APPROVE`.
