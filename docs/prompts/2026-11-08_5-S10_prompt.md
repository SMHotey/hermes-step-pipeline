## 1. Роль и цель

Ты — программист конвейера шагов Hermes (`hermes-step-pipeline`), исполняешь шаг S10 плана 5
в ветке `main`. Рабочий каталог — `<корень>`,
оболочка — bash (git-bash), интерпретатор — `.venv/Scripts/python.exe` этого репозитория.

Результат шага: до первой строки кода видно, стоит ли делать и не противоречат ли друг другу
артефакты цикла.

- **Анализатор согласованности** `python .pipeline/analyze.py docs/plans/N-x.md` находит на
  синтетических планах пять классов расхождений: шаг без гейтов (A1), файл вне списка шага
  (A2), разведка без вердикта (A3), план действующего формата без раздела «Разведка» (A4),
  ссылка на несуществующий файл (A5). Код возврата 0 — расхождений нет, 1 — есть, 2 — плана
  или конфигурации нет (`D1`-`D6`).
- **Исход идеи действует.** Явный `Решение: kill` в разделе «Разведка» останавливает
  ведение плана: карточек шагов нет, инцидентного стопа нет, в статусе строка «Исход
  разведки: kill». `needs-clarification` возвращает план к вопросам
  `docs/research/N-questions.md` и называет, сколько ответов не хватает. Отсутствие
  исхода поведение не меняет — иначе встали бы legacy-планы 1-4 и все существующие тесты
  стража (`D7`).
- **Ретроспектива после закрытия плана.** Первый тик по плану, у которого все шаги журнала
  «ЗАКРЫТ», кладёт черновик `docs/reviews/retro-N.md` с фактами из журнала и один раз
  уведомляет владельца; повторный тик файл не перезаписывает (`D8`). Побочный эффект, который
  надо знать: первый же тик в самом репозитории плагина положит черновики для уже закрытых
  планов 1-4 — это ожидаемо, шаг их не правит и `--run` на реальном репозитории в гейтах не
  запускает (только `--status`).
- **Шаблон уточнений** `docs/research/TEMPLATE-questions.md` — один формат таблицы вопросов
  для всех планов; по нему анализатор считает открытые ответы (`D9`).

Движок меняется в трёх местах поведения (`_decide_base`, `run_gate`, `status_text`).
Версия плагина поднимается минором от факта на момент работы (`D11`).

## 4. Что сделать

### 4.0 Решения, принятые за тебя (не переигрывать)

- **D1. `analyze.py` — самостоятельный модуль движка** с прямым запуском:
  `python .pipeline/analyze.py docs/plans/N-x.md`. Импорты — плоские имена соседей
  (`import config as config_mod`, `registry`, `next_step`, `plan_cycle`, `scout_report`),
  как в `gate.py`. `gate.py` импортирует `analyze`, обратного импорта быть не может
  (цикл) — поэтому в `analyze` нет ни строчки про страж.
- **D2. Коды находок — A1-A5** (латиница, «analyze»; рядом с Л1-Л20 линтера и P1-P3
  `plan_cycle`, чтобы код называл инструмент). Вывод — по строке на находку
  `A2 docs/plans/1-demo.md:31 S1: текст`, итог `ИТОГ: PASS — расхождений нет` или
  `ИТОГ: FAIL — находок 3`. Код возврата: `0` — нет находок, `1` — есть, `2` — плана нет
  или проект без `pipeline.json` (в stderr — что именно).
- **D3. A2 «файл вне списка»**: путь в обратных кавычках в тексте шага **вне** пункта
  «Файл:», файл существует в дереве и не объявлен ни в одном пункте «Файл:» ни одного шага.
  Так шаг, де-факто трогающий файл вне своего контракта, ловится, а упоминание соседнего
  шага по имени — нет.
- **D4. A5 «ссылка на несуществующий файл»**: тот же скан, но файла в дереве нет и ни один
  шаг его не объявляет. A2 и A5 взаимоисключающие по построению: сначала проверка
  существования, потом объявленности. Объявленный файл не проверяется на существование —
  его могут создавать.

  артефакт `docs/research/N-prior-art.md` есть и разбирается, исход плана обязан
  совпадать с `Report.decision`; расхождение — та же находка A3 с обоими исходами в тексте.
  Артефакта нет — A3 проверяет только наличие исхода в плане (отсутствие артефакта решает
  страж, а не анализатор).
- **D6. A4 «план без раздела «Разведка»»**: срабатывает только у плана действующего
  формата, дискриминатор — `approval.has_constitution(plan_file)`; у legacy-планов
  молчит. Поиск раздела — `plan_cycle.research_section(text)`, второй регулярки не писать.
- **D7. Исход действует только явно**: `kill` и `needs-clarification` из раздела «Разведка»

- **D8. Ретроспектива — черновик от стража**, а не от агента: файл пишется один раз,
  повторный тик его не перезаписывает (идемпотентность по существованию файла).
- **D9. Шаблон уточнений** задаёт единственную шапку таблицы: `QUESTIONS_COLUMNS` из

- **D10. Документация — добавляющая**: §5b и §11.3 новые, §8 — одна строка. Внутрь §5a и
  таблицы §11.1 не лезть: их правил шаг S9, и второй автор там создаст конфликт.

- **D12. A1 — «гейт, который можно запустить»**, а не «пункт гейтов отсутствует»: у шага нет
  ни одного токена в обратных кавычках ни в одном пункте гейтов. Первые два случая (пункта

### 4.1 `step_pipeline/engine/analyze.py` — новый модуль (главный объём шага)

Докстринг модуля по-русски: зачем (согласованность плана, артефакта разведки и дерева до
первой правки кода), список проверок A1-A5, запуск и коды возврата, источники разбора.
Публичный контракт — ровно такие имена (тесты проверяют их, а не только поведение CLI):

```python
QUESTIONS_COLUMNS = ("№", "Вопрос", "Варианты", "Рекомендация", "Ответ")

@dataclass(frozen=True)
class Finding:
    code: str        # "A1".."A5"
    line: int        # строка файла плана, 1-based
    step: str        # "S1"; "" для плановых находок A3/A4
    message: str

def plan_decision(text: str) -> tuple[str, str]   # (исход, пояснение); ("", "") — исхода нет
def open_questions(path: Path) -> tuple[int, int] | None   # (открытых, всего); None — файла нет
def retro_text(text: str, plan_rel: str, plan_id: str, today: str) -> str
def analyze(plan_file: Path, root: Path) -> list[Finding]
def main(argv: list[str] | None = None) -> int
```

Разбор — только переиспользованием движка, второго парсера плана быть не должно:

- контракт шага (файлы, гейты) — `next_step.plan_steps(cfg, plan_file)`: это ровно то, что
  уедет в карточку, поэтому A1 смотрит на `Step.gates`, а A2 — на `Step.files`;
- тела шагов и номера строк — `registry.headings(lines)` + `registry.section_end(...)`:
  `headings` отдаёт **индекс строки от нуля** (`registry.py:146-153`, `enumerate` без
  `start=1`), а `Finding.line` — 1-based, поэтому в находку идёт `индекс + 1`; прецедент
  перевода ровно один — `plan_lint.py:452` (`Problem(shown, idx + 1, ...)`), на него и
  ссылайся комментарием. Границы раздела шагов — `next_step.steps_section(cfg, lines)`;
  критерий «путь» — `next_step._looks_like_path` (пробела нет и есть `/` или `.`), токены —
  только в обратных кавычках (`next_step._backticks`); эти приватные предикаты
  переиспользуются с комментарием, почему (иначе критерий разъедется с карточкой);
- границы пункта внутри шага — построчный скан секции шага маркером пункта
  `next_step._BULLET_RE` (третий приватный предикат с тем же комментарием); метка пункта —
  префикс до `:` не длиннее 40 символов **и без обратной кавычки в нём** — оба условия
  `section_blocks` (`next_step.py:113-116`); без второго пункта вида «- `Файл:` `app/x.py`»
  перестанет опознаваться как «Файл:», и объявленный файл попадёт в A2.
  Сам `section_blocks` для A2/A5 не годится: он нормализует текст и теряет номера строк,
  а находке нужна строка пункта. Скан идёт только по секции шага, границы которой уже
  дал `registry`;
- раздел разведки — `plan_cycle.research_section(text)`, исход — строка `Решение:` внутри
  него; словарь исходов — `scout_report.DECISIONS`; артефакт —
  `{каталог разведки}/{номер}-prior-art.md` (тот же расчёт, что `gate.scout_artifact`;
  импортировать `gate` из `analyze` нельзя — D1, цикл; ссылку из раздела «Разведка»
  анализатор не парсит) — через `scout_report.check_file(path)` и его `Report.decision`;
  строка находки A3 — заголовок раздела из `registry.headings` (индекс + 1, как в
  предыдущем пункте) по условиям `plan_cycle.research_section`: уровень 2-6,
  `plan_cycle.RESEARCH_MARKER`, не заголовок шага по `plan_cycle.STEP_HEADING_RE`, и для
  уровня выше 2 — вне раздела шагов (`level == 2 or "шаг" not in last_h2.lower()`,
  `plan_cycle.py:92`); без четвёртого условия `### Разведка в проекте` внутри `## Шаги`
  стал бы якорем, а `research_section` такой заголовок отбрасывает. Тело без номеров строк
  `research_section` не отдаёт; A4 и так ставит строку `1`;
- формат плана — `approval.has_constitution(plan_file)`;
- каталог артефактов — ключ `paths.research` из сырого `pipeline.json`, умолчание
  `docs/research`: повторить чтение так же, как `gate.scout_research_dir` (в `config.py`
  этого ключа нет — см. докстринг `scout_research_dir`);
- номер плана — из реестра: `registry.discover(cfg)` и спецификация с тем же путём (`spec.id`),
  а не своё регулярное выражение на имя файла; плана нет в реестре (нет журнала или имя не по
  формату) — номер из имени файла регуляркой реестра и `registry.normalize`; номер не
  определился — A3 проверяет только наличие исхода в плане, артефакт и вопросы не сверяются;
- путь в тексте: токен с `://`, `http`, `www` или `mailto` — это ссылка, а не файл, он
  пропускается; относительный путь проверяется от `root`, абсолютный — как есть; строка
  находки A2/A5 — номер строки файла плана (1-based) = индекс строки из `headings` + 1,
  где путь найден.

Проверки и их тексты (тексты — заготовки для тестов на подстроку, менять по смыслу можно):

def _plan_decision(ctx: dict) -> dict | None:
    """Исход разведки как предусловие плана: kill закрывает, needs-clarification ждёт."""
    kind = str(ctx.get("plan_decision") or "")
    plan_id = ctx.get("plan_id")
    if kind == "kill":
        note = str(ctx.get("plan_decision_note") or "").strip() or "причина — в разделе «Разведка»"
        return {"action": "idle", "plan_done": True, "plan_killed": True,
                "reason": f"план {plan_id} закрыт исходом kill (разведка): {note}"}
    if kind == "needs-clarification":
        opened = ctx.get("questions_open")
        if opened is None:
            detail = f"файла вопросов нет: {ctx.get('questions_rel')}"
        elif opened[0]:
            detail = f"открыто {opened[0]} из {opened[1]}: {ctx.get('questions_rel')}"
        else:
            detail = f"все ответы получены ({opened[1]}) — переведи план в go"
        return {"action": "idle", "plan_clarify": True,
                "reason": f"план {plan_id} ждёт ответов на вопросы — {detail}"}
    return None

## 5. Как проверить (гейты)

у pytest, а не у хвоста пайпа. `pytest.ini` уже содержит `-q`, второй `-q` не добавлять.
`$TMPDIR` — временный каталог сессии Hermes.

grep -E "passed|failed|error" "$TMPDIR/s10_before.log" | tail -1

## 6. Стоп-сигналы

1. **Дерево занято чужой работой.** `git status --porcelain` перед началом показывает
   изменения или неотслеживаемые файлы вне §3 (кроме шести `docs/reviews/5-S*-prompt.md` —
   это постановки, и самой этой постановки в `docs/prompts/`), либо HEAD уже не `8fe1dfa`
   и в §4 адреса разошлись с деревом. Стоп: две работы в одном дереве не разделяются по
   коммитам, а по съехавшим адресам правка бьёт мимо.
2. **Адреса не совпали.** Нет `_decide_base`, `_scout_decision`, `_plan_review_decision`,
   `build_ctx`, `run_gate`, `status_text`, `_local_date` в `engine/gate.py`; нет
   `plan_steps`, `steps_section`, `_looks_like_path` в `engine/next_step.py`; нет
   `research_section` в `engine/plan_cycle.py`; нет `check_file`, `DECISIONS` в
   `engine/scout_report.py`; нет `has_constitution` в `engine/approval.py`; нет
   `atomic_write_text` в `engine/state_io.py`; `test_lock.py` больше не сверяет два списка.
   Останови работу, назови, что именно не совпало, ничего не правь.
3. **Нужен файл вне §3.** Например, `plan_lint.py` («A1 логичнее в линтере»), `stats.py`
   («метрику исхода хочется в панель»), `ui/`, `cli.py`, `pipeline.json`, план — стоп и
   вопрос: это решения D1, D2 и D10, а не мелкая поправка по ходу.
4. **Существующий тест краснеет не по твоей строке.** Сначала причина; если правка требует
   поменять ожидание теста, который к шагу не относится (например, `test_plan_done_is_idle`
   в `tests/engine/test_gate_decide.py` или `test_no_cards_creates_step`), — стоп, назови
   тест, ожидание, факт и гипотезу. Ослаблять и переписывать такие тесты нельзя.
5. **Гейт красный по посторонней причине** (нет `hermes` в PATH, сломан интерпретатор,
   чужой тест падал до шага). Зафиксируй команду, полный текст ошибки и вывод, что причина
   внешняя; шаг не закрывай — постановка требует зелёного гейта, а не объяснения.
6. **План расходится с постановкой.** Например, план требует «анализатор находит расхождения»,
   а хочется «предупреждать и не мешать». Действуй по постановке (решения D1-D12),
   расхождение назови в отчёте, решение не переигрывай.

## 7. Формат отчёта

Отчёт — до коммита, по-русски, по разделам:

1. **Факты до правок** — `git rev-parse HEAD`, замер шага 0 (collected/passed/skipped),
   версия из `plugin.yaml`, состояние дерева (S9 закрыт `7064e55`, `76a3cbc` уже в HEAD).
2. **Что сделано** — по файлам с номерами строк: что добавлено, что изменено, почему именно
   так (одна строка на решение), какие имена появились в контракте `analyze`.
3. **Гейты** — таблица «команда → ожидание → факт → EXIT» для гейтов §5; числа прогонов
   фактические.
4. **Анализатор на реальных планах** — вывод гейта 7 целиком (какие находки, коды, строки)
   и одна строка: правится ли что-то по ним (ответ — нет и почему).
5. **Тесты** — восемь имён и что каждый утверждает; отдельно — что ни один существующий
   тест не изменён (кроме `engine_kit.ENGINE_FILES` — это единственная правка в чужом файле
   тестов, и она о копировании движка).
6. **Что не сделано и почему** — отличия от постановки, отложенные места; если ничего,
   так и скажи.
7. **Коммит** — хеш, список путей, версия из `plugin.yaml`; `git add` только путями из §3
   (чужие файлы в коммит не попадают).

Числа — только фактические, из логов прогонов. «Тесты зелёные» без числа не отчёт.

## 9. Ревью (обязательно)

- Шаг закрывает не исполнитель, а роль `reviewer` (`pipeline-reviewer`) по плану
  `docs/plans/5-platforma.md` и коду дерева.
- Ревьюеру доступны план и код; отчёт исполнителя — не источник фактов, а заявка. Гейты §5
  ревьюер прогоняет своими руками, включая полный набор и гейт 1.
- Вердикт — `APPROVE` или `REQUEST_CHANGES` в `docs/reviews/5-S10.md`. При `REQUEST_CHANGES`
  шаг остаётся открытым: находки правятся, ревью повторяется, и только после `APPROVE`
  появляется строка «ЗАКРЫТ» в журнале плана и коммит закрытия.
- Что смотреть в первую очередь: (1) пять классов находок действительно ловятся на
  синтетических планах, а не на репозитории; (2) `kill` и `needs-clarification` не создают
  карточек и не ставят инцидентный стоп, а отсутствие исхода поведение не меняет —
  существующие тесты стража зелёные; (3) `analyze` не импортирует `gate`, `decide` остался
  чистым, новых чтений диска в нём нет; (4) ретроспектива пишется один раз и не перезаписывается;
  (5) шапка шаблона уточнений и `QUESTIONS_COLUMNS` совпадают; (6) версия и CHANGELOG
  соответствуют фактическому поведению.
