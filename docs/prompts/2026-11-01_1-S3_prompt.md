## 4. Что сделать

1. **`step_pipeline/engine/state_io.py` — новый модуль.** Заголовок модуля словами задачи (зачем: два одновременных тика портят журнал, состояние и отложенный коммит). Публичный контракт ровно такой (имена проверяются тестами):
   - `atomic_write_text(path: Path, text: str) -> None` — создать каталог, записать во временный файл В ТОМ ЖЕ каталоге (имя вида `имя.tmp-PID`), `flush`, `os.fsync`, закрыть, затем `os.replace(tmp, path)`; при исключении временный файл удалить и исключение пробросить. Никакого `write_text` по целевому пути.
   - `save_json(path: Path, data) -> None` — `atomic_write_text(path, json.dumps(data, ensure_ascii=False, indent=2))` (тот же формат, что сейчас у `save_state`).
   - `acquire(state_dir: Path, what: str = "tick", wait: float | None = None, stale_after: float | None = None) -> Lock | None` — `None` означает «блокировка живая и чужая»; иначе вернуть `Lock` с полями `path`, `payload`.
   - `release(lock: Lock | None) -> None` — снять ТОЛЬКО свою блокировку (сверять `pid` и `host`), после снятия файла нет.
   - `locked(state_dir: Path, what: str = "tick") -> контекст-менеджер` — `acquire` на входе, `release` в `finally`.
   - `holder(state_dir: Path) -> dict | None` — разобранная полезная нагрузка блокировки для сообщений вида «тик идёт (pid 1234, с 12:00)».
   - Константы: `LOCK_NAME = "tick.lock"`, `STALE_AFTER = 1800` (секунд), `WAIT = float(os.environ.get("PIPELINE_LOCK_WAIT") or 5)`.
   Файл блокировки — `state_dir / LOCK_NAME`, содержимое JSON: `{"pid": int, "host": str, "at": "ДД.ММ.ГГГГ ЧЧ:ММ:СС", "at_ts": float, "what": str}`. Создание — `os.open(..., O_CREAT | O_EXCL | O_WRONLY)` (замер C); при `FileExistsError` читать полезную нагрузку и решать: блокировка протухла, если `time.time() - at_ts` больше `stale_after`, ИЛИ `host` не равен `socket.gethostname()`, ИЛИ PID не жив. Протухшую снимать (`unlink`) и повторить создание один раз: проиграл гонку — вернуть `None`. Ожидание: `wait` (по умолчанию `WAIT`) секунд мелкими шагами (0.1 с) с повторными попытками, затем `None`. Проверка живости PID: на Windows — `ctypes` `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetExitCodeProcess` = 259 (замер B), на POSIX — `os.kill(pid, 0)`. `os.kill(pid, 0)` на Windows не использовать (замер B: не отличает мёртвый PID от живого).

Решения, принятые за тебя (не переигрывать):
- **D1.** Один лок на проект — `cfg.state_dir / "tick.lock"`, не на план: `tick()` обслуживает все ведомые планы и `retry_pending` по каждому, поэтому лок на план не защищает журнал и состояние проекта.
- **D2.** Примитив блокировки — `os.open` с `O_CREAT|O_EXCL` (замер C), без `msvcrt`/`fcntl`: кроссплатформенно, только stdlib, не держит открытый дескриптор на время тика.
- **D3.** Живость PID: на Windows — `ctypes` + `OpenProcess`/`GetExitCodeProcess` (замер B: `os.kill(pid, 0)` на Windows мёртвый PID не отличает), на POSIX — `os.kill(pid, 0)`.
- **D4.** Протухание: возраст больше `STALE_AFTER` = 1800 с ИЛИ чужой `host` ИЛИ мёртвый PID. Обоснование: живой тик не может быть старше таймаутов вызова — 900 с (`tools.py:111`) и 600 с (`cli.py:170`).
- **D5.** Ожидание блокировки — `PIPELINE_LOCK_WAIT` (по умолчанию 5 с), после него код 0 и «тик уже идёт». Переменная нужна тестам для детерминизма; в конфигурацию `pipeline.json` ключ не добавляется.
- **D6.** Блокировку берёт только `main()`; `save_state`/`write_stop`/`_write_offset` блокировку НЕ берут — иначе тик, держащий лок, самоблокируется на своей же записи состояния.
- **D7.** `append_journal_row` пишет файл плана атомарной записью с тем же текстом: цель шага называет журнал, а kill посреди перезаписи рвёт сам план (сейчас это прямой `write_text`, `gate.py:270`).
- **D8.** Сообщение при живой чужой блокировке содержит подстроку `тик уже идёт`; в `--json` — объект по п. 3. Код возврата в обоих случаях 0 (требование плана), а не 1.
- **D9.** Временные файлы после kill не убираются (вне объёма); целевой файл при этом обязан оставаться целым — это и проверяет тест 1.

## 5. Как проверить (гейты)

Из корня репозитория; вывод в файл, код возврата смотреть у pytest, а не у хвоста пайпа:

```
C:/tmp/venv-s2b/Scripts/python.exe -m pytest tests/engine/test_lock.py > "$TMPDIR/s3-lock.log" 2>&1; echo EXIT=$?
# после шага 3 (тесты есть, gate.py не тронут) ожидается: 5 failed, 1 passed, EXIT=1 — RED
# после шага 4 (правки gate.py) ожидается: 6 passed, EXIT=0 — GREEN
C:/tmp/venv-s2b/Scripts/python.exe -m pytest > "$TMPDIR/s3-all.log" 2>&1; echo EXIT=$?
# ожидается: 132 passed, EXIT=0 (замер сейчас: 126 = 78 движка + 48 плагина, плюс 6 новых)
git status --porcelain
# перед коммитом ожидается: M step_pipeline/engine/gate.py, M step_pipeline/setup_flow.py,
# M tests/engine/engine_kit.py, ?? step_pipeline/engine/state_io.py, ?? tests/engine/test_lock.py;
# неотслеживаемые .hermes/, .idea/, .pipeline/, docs/templates/, pipeline.json остаются как были
git show --stat --oneline HEAD
# после коммита ожидается: ровно пять файлов и sha коммита
```

`-q` к командам не добавлять: в `pytest.ini` уже стоит `addopts = -q`, второй `-q` скрывает итоговую строку. Запись плана «`python -m pytest tests/engine/test_lock.py -q` → 6 passed» означает то же самое; в отчёте — фактическое число прошедших и `EXIT`.

## 6. Стоп-сигналы

Остановиться и доложить (не адаптировать по смыслу), если:
- интерпретатора с pytest нет (`C:/tmp/venv-s2b` пропал) — создать своё окружение через `uv` вне репозитория, назвать его в отчёте; не ставить пакеты в системный `python`, не менять `pytest.ini`, не ослаблять гейт;
- позеленеть тестам мешает не `main()`/`state_io`, а `decide`, `collector`, `run_gate`, `close_step`, `retry_pending` или `tick` — значит лок поставлен не на той границе: правка живёт только в разрешённых местах;
- существующий тест покраснел из-за блокировки (например, два `--run` подряд в `test_gate_e2e.py` или `tests/test_engine_e2e.py`, или тик под `runpy` в `test_tick.py`) — доложить имя теста и вывод, тест не править и не подгонять ожидания;
- тест 1 не краснеет на текущем `save_state` (значит подмена `io.open` не перехватывает запись) — доложить фактическое содержимое файла после обрыва; не переписывать тест на «проверку наличия временного файла»;
- после `kill` дочернего процесса в тестах блокировка остаётся живой дольше шага ожидания или файл блокировки не снимается (`Windows держит файл`) — доложить `holder`, код возврата и текст исключения, а не увеличивать таймауты;
- для «Готово =» требуется правка файлов вне разрешённого списка (`config.py`, `tick.py`, `registry.py`, `pipeline.json`, `.pipeline/`) или новая зависимость — это выход за объём шага;
- полный прогон красный по причине, не относящейся к шагу (нет `hermes` в PATH, кодировка консоли, сеть) — доложить числа и текст ошибки, чужие тесты не править.

Формат доклада: что обнаружено (файл и строки), замер командой, варианты с ценой, рекомендация.

## 7. Формат отчёта

По-русски, до и после коммита, по порядку: `git diff --stat` → ключевые диффы (публичный контракт `state_io.py`, три писателя в `gate.py`, ветки `main()` с блокировкой, оба кортежа `ENGINE_FILES`) → RED-прогон (команда, `EXIT`, имена упавших тестов и строки утверждений) → GREEN-прогон (6 passed, `EXIT`) → полный прогон (фактическое число passed, `EXIT`) → самостоятельные решения с причиной → что сознательно не сделано → отклонения от промта → sha коммита и ветка пуша.
