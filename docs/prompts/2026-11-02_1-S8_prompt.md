### 4.2. `step_pipeline/plan_lint.py` — новый модуль

Шапка-докстринг перечисляет проверки (его будет цитировать спека S13). Импорт проекта —
как в остальных модулях плагина:

```python
try:
    from . import project as proj
except ImportError:  # pragma: no cover - отладка файлом
    import project as proj  # type: ignore
```

Константы и регулярки (каждая — с комментарием, откуда взято правило). Регулярки,
которые уже есть в движке, копировать из указанных строк, а не писать заново: смысл
не должен разойтись с движком ни на символ.

```python
_STEPS_MARKER = "шаг"          # умолчание markers.steps, engine/config.py:48
_JOURNAL_MARKER = "журнал"     # умолчание markers.journal, там же
_STEP_ID_REGEX = r""           # литерал из engine/config.py:51, скопировать как есть
JOURNAL_COLUMNS = 5            # engine/registry.py:33
_HEADING_RE = re.compile(r"")  # строка engine/registry.py:31, скопировать как есть
_NAME_RE = re.compile(r"^\d{1,2}-.+\.md$")      # имя плана: номер, дефис, слаг, .md
_READY_RE = re.compile(r"")    # строка engine/next_step.py:58, скопировать как есть
_BULLET_RE = re.compile(r"")   # строка engine/next_step.py:54, скопировать как есть
```

Строки-источники для копирования: `engine/registry.py:31` (заголовок),
`engine/next_step.py:58` (критерий готовности), `engine/next_step.py:54` (пункт списка),
`engine/config.py:51` (значение `step_id_regex` по умолчанию). В докстринге модуля
отметь, что это осознанная копия правил движка (D5).

API (имена и поля проверяются тестами — не переименовывать):

```python
@dataclass(frozen=True)
class Problem:
    """Одна находка: файл для показа, строка (1-based; 0 — весь файл) и текст."""
    file: str
    line: int
    text: str

    def __str__(self) -> str:
        return f"{self.file}:{self.line}: {self.text}" if self.line else f"{self.file}: {self.text}"


@dataclass(frozen=True)
class Settings:
    """Правила разбора плана: маркеры и регулярка шага из pipeline.json проекта."""
    steps_marker: str
    journal_marker: str
    step_regex: re.Pattern | None      # None — регулярка не компилируется


@dataclass(frozen=True)
class LintResult:
    """Что проверено и что найдено."""
    files: list[Path]
    problems: list[Problem]
```

Функции:

- `settings(project: Path) -> Settings` — читает `proj.read_config(project)`, берёт
  `markers.steps`, `markers.journal`, `step_id_regex`; недостающие ключи — встроенные
  умолчания выше; регулярку компилирует с префиксом `^` (как `engine/config.py:210`);
  ошибка компиляции или отсутствие группы `id` → `step_regex = None`.
- `lint_file(path: Path, project: Path, settings: Settings) -> list[Problem]` — все
  проверки одного файла; `file` в находках — путь относительно проекта, если файл внутри
  него, иначе путь как передан (`path.as_posix()`); проверка имени включается только
  когда каталог файла совпадает с каталогом планов проекта (D2).
- `lint_project(project: Path, plan: str = "") -> LintResult` — разворачивает `plan`
  (номер или путь, D6), собирает файлы и находки; `step_regex is None` → одна находка
  `Problem("pipeline.json", 0, "step_id_regex не компилируется: " + причина)` и пустой
  список файлов; пустой каталог планов и отсутствие `plan` → `files=[]`, `problems=[]`
  (иначе чистый проект после `setup` получает предупреждение и падают существующие тесты
  мастера).

Проверки в `lint_file` — ровно эти десять, каждая даёт находку с номером строки:

1. имя файла (только внутри каталога планов): не совпало с `_NAME_RE` →
   `имя файла не по формату «номер-слаг.md»`, строка 0.
2. нет раздела шагов: ни одного заголовка уровня не ниже 2 с маркером →
   `нет раздела со словом-маркером шагов «шаг»`, строка 0; дальше по файлу проверок нет.
3. дубли раздела шагов: среди заголовков того же уровня, что и первый найденный, больше
   одного → `разделов с маркером шагов «шаг»: N — должен быть один`, строка второго
   такого заголовка (D3).
4. кривой заголовок шага: внутри раздела заголовок, у которого `step_regex` не совпал с
   начала, либо после идентификатора нет точки, либо после точки пусто →
   `заголовок шага не по формату «### S1. Название»`, строка заголовка. Это строже
   движка (он такие заголовки молча пропускает, `next_step.py:194-202`): строгость
   осознанна — шаг, которого движок не видит, и есть «план, ломающийся через сутки».
5. дубль шага: идентификатор уже встречался →
   `шаг S1 повторяется в разделе шагов`, строка второго заголовка.
6. пункты шага (по правилам `next_step.py:70-100` и `:156-159`): нет пункта с меткой,
   начинающейся на «файл» → `шаг S1: нет пункта «Файл:»`; нет пункта с меткой на
   «тест»/«гейт»/«проверк» → `шаг S1: нет пункта «Гейты:»`; такой пункт есть, но после
   двоеточия пусто или прочерк (`—`, `-`, `−`) → `шаг S1: гейты пустые`; нет пункта, в
   котором `_READY_RE` даёт непустой остаток → `шаг S1: нет критерия «Готово =»`. Все
   четыре — строка заголовка шага.
7. выбор раздела журнала — как в движке (`registry.py:101-117`): среди заголовков уровня
   не ниже 2 с маркером журнала берётся первый, в разделе которого есть хотя бы одна
   строка от `|`; если такого нет, но заголовок с маркером есть — берётся первый из них
   (дальше сработает проверка 8); если заголовков с маркером нет вообще →
   `нет раздела-журнала со словом «журнал»`, строка 0 (следствие: `registry.discover`
   такой файл вообще не считает планом — `registry.py:165-183`). Наивный выбор «первый
   заголовок с маркером» запрещён ловушкой 4.
8. строки выбранного раздела журнала: строки от `|`, кроме разделителя (все символы из
   `-: `) и шапки (первая ячейка «дата»/«date»): число ячеек не равно пяти →
   `строка журнала без 5 колонок (нашлось 4)`, строка строки; во второй ячейке нет шага →
   `строка журнала без шага во второй колонке`, строка строки; повтор шага →
   `шаг S1 повторяется в журнале`; ни одной строки шага →
   `в журнале нет ни одной строки шага`, строка 0.
9. расхождение наборов: шаг есть только в разделе →
   `шаг S5 есть только в разделе шагов`, строка заголовка шага; шаг есть только в
   журнале → `шаг S5 есть только в журнале`, строка строки журнала. Сравнение — по
   идентификаторам в верхнем регистре (`registry.py:126`).
10. файл не читается (`OSError`) → `файл не читается: причина`, строка 0; линтер
    продолжает по остальным файлам.

Порядок находок — по файлам в порядке сортировки путей, внутри файла — по номеру строки
(стабильная сортировка в конце `lint_project`), чтобы вывод и тесты были предсказуемы.

### 4.5. Порядок и доказательства

Решения, принятые за тебя (не переигрывать):
- **D1.** `plan_lint.py` — модуль ПЛАГИНА, не движка: в `ENGINE_FILES`
  (`setup_flow.py:27-28`) не вносить, в `.pipeline/` проекта он не копируется, в проекты
  приезжает вместе с плагином. Вторая копия того же списка —
  `tests/engine/engine_kit.py:21-22` — тоже остаётся без `plan_lint`.
- **D2.** Проверка имени файла — только для файлов внутри каталога планов проекта
  (`paths.plans`, по умолчанию `docs/plans`). Без этого «на шаблоне — 0» (§S8) и проверка
  имени несовместимы: шаблон лежит в `templates/`.
- **D3.** Единственность раздела шагов считается по уровню первого найденного раздела,
  а не по всем уровням: иначе шаги с словом «шаг» в названии (план 1 `:113`, план 2
  `:29`/`:88`, план 3 `:55`) дают ложные находки.
- **D4.** Метки пунктов принимаются по префиксам, как в движке: «файл», «тест», «гейт»,
  «проверк»; критерий — «готово» плюс «=» или «:» с непустым остатком. Причина: в
  планах проекта пункт называется «Тесты/гейты» (38 шагов), жёсткая метка «Гейты» дала
  бы 38 ложных находок.
- **D5.** Настройки — из `pipeline.json` проекта, недостающие — встроенные умолчания,
  зеркалящие `engine/config.py:48-51`. Плагин движок не импортирует
  (`project.py:3-8`), поэтому правила повторяются текстом; это осознанное дублирование,
  его обязан упомянуть докстринг модуля. Битый `step_id_regex` — находка, не исключение.
- **D6.** `--plan` принимает номер (`2` → файл `docs/plans/2-*.md` по регулярке имени) и
  путь (абсолютный или относительно проекта) — чтобы можно было проверить черновик до
  копирования в каталог планов; номер — как у `status --plan`. Без флага — все `*.md`
  каталога планов.
- **D7.** Правка `setup_flow.py` разрешена, хотя файла нет в списке §S8: без неё
  требование «в конце setup вызывать без флага и печатать предупреждение» невыполнимо.
  Объём — импорт плюс четыре строки в хвосте `run_setup`; в отчёте это назвать
  отклонением от промта по файлам.
- **D8.** Линтер только читает: ни планов, ни `pipeline.json` не пишет. Строки — 1-based,

## 5. Как проверить (гейты)

## 7. Формат отчёта

По-русски, до и после коммита, по порядку: `git diff --stat` → ключевые диффы (API
модуля, правила проверок, вставка в `cmd_doctor`, четыре строки в `setup_flow`) →
RED-прогон (команда, `EXIT`, текст ошибки сбора) → GREEN-прогон
`tests/test_plan_lint.py` (`9 passed`, `EXIT`) → `tests/test_setup_flow.py` (`9 passed`,
`EXIT`) → полный прогон (фактическое число passed, `EXIT`) → проба линтера на четырёх
планах проекта (`файлов 4 проблем 0`, `EXIT`) → `grep` по счётчику тестов и по
`ENGINE_FILES` → `hermes plugins validate` → самостоятельные решения с причиной → что
сознательно не сделано → отклонения от промта (в том числе D7 по файлам) → sha коммита и
ветка пуша.

Шаг не закрывает исполнитель. После гейтов — независимое ревью ролью `reviewer`
