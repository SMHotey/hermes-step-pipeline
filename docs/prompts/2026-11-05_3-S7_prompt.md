## 4. Что сделать

### 4.1. Ядро валидации (`ui_server.py`)

Рядом с `CONFIG_KEYS` (`ui_server.py:84`) добавь константы `RUNTIME_RE = re.compile(r"^\d+[mh]$")`, `RUNTIME_KEYS = ("step", "review", "prompt")`, `CONFIG_PATH_KEYS = ("plans", "reviews", "prompts", "state")`.

- `_path_error(root: Path, raw: object) -> str` — пустая строка, если путь годен, иначе объяснение по D3: `str(raw or "").strip()` с заменой `\` на `/`; пусто → «путь не может быть пустым»; абсолютный (`Path(...).is_absolute()`, буква диска `C:`, начало с `/` или `~`) → «нужен путь относительно корня проекта»; `..` среди частей → «путь вне корня проекта»; итог `(Path(root).resolve() / Path(*parts)).resolve()` вне корня → «путь вне корня проекта». Части, начинающиеся с точки, проверку проходят и **не отбрасываются** (`.pipeline/state` — законное умолчание движка; отбросить точку значит записать другой путь).
- `_validate_patch(cfg: dict, patch: dict, root: Path) -> tuple[dict | None, list[str], list[str]]` — возвращает (`candidate`, `errors`, `notes`). Пустой `errors` = годно. Тексты ошибок начинаются с имени ключа и двоеточия: `runtimes.step: …`, `paths.plans: …`, `board: …`, `driven_plans: …`. Все ошибки собираются списком (панель показывает все сразу), но действие считает отказом любую.
- `notes` — не блокирующие замечания, их панель показывает рядом с диффом: каталог из `paths.*` не существует («каталог docs/plans не существует — файлов в нём не найдётся»), `driven_plans` пуст («страж не поведёт ни одного плана»), `project` пуст в файле и не задан в патче. `notes` не мешают сохранению.
- Правила по ключам (только те, что есть в патче; чужие ключи файла не судятся): `project`, `board` — `str().strip()`, пусто → отказ; `require_prompt` — bool; `driven_plans` — строка через запятую → список, каждый элемент `*` или цифры (факт 11), иначе `driven_plans: элемент должен быть * или номером плана`; `runtimes.*` — `RUNTIME_RE` и `int(...) > 0` (D2), лишние подключи `runtimes` сохраняются как есть; `paths.*` — `_path_error` (D3), лишние подключи сохраняются.
- Слияние — поверх прочитанного словаря: `cfg[key] = value`, `runtimes`/`paths` — `{**old, **new}`. Не пересобирать словарь с нуля: иначе теряются неизвестные ключи (C6).

### 4.2. Предпросмотр: действие `preview_config`

`act_preview_config(state, payload) -> dict`:

- патч — `payload.get("config")`; не объект → `{"ok": False, "error": "config должен быть объектом"}`;
- читать файл **байтами** (`(root / "pipeline.json").read_bytes()`), чтобы кириллица и отсутствие `\n` в конце пережили круговой рейс; нет файла или `JSONDecodeError` → отказ по D7 («pipeline.json не разбирается как JSON: … — правка отклонена, файл не тронут»);
- `candidate, errors, notes = _validate_patch(...)`; `errors` непуст → `{"ok": False, "error": "\n".join(errors)}`;
- `content = json.dumps(candidate, ensure_ascii=False, indent=2) + "\n"` — ровно формат `proj.write_config` (`project.py:171-173`);
- `diff` — `difflib.unified_diff(current_text.splitlines(True), content.splitlines(True), fromfile="pipeline.json (сейчас)", tofile="pipeline.json (после сохранения)", n=3)`, склейка `"".join`; больше 300 строк — обрезать и дописать строку «дифф обрезан: всего N строк»;
- ответ: `{"ok": True, "changed": [...], "diff": ..., "content": ..., "notes": [...]}`. `changed` — имена ключей патча, как у `save_config`; порядок — как в патче;
- на диск ничего не писать (проверяется тестом по байтам);
- регистрация: `ACTIONS["preview_config"] = act_preview_config` (`ui_server.py:374-383`).

### 4.3. Сохранение: переписать `act_save_config`

- Валидация — тем же `_validate_patch`, что и предпросмотр: один источник правил, иначе панель и API разойдутся.
- Файла нет / не разбирается → отказ (D7).
- Собрать `content` тем же способом, что в 4.2; если `content.encode("utf-8")` совпадает с текущими байтами — `{"ok": True, "changed": [], "noop": True, "note": "изменений нет"}` без записи и без копии (D6).
- Копия до записи: `backup = root / ".pipeline" / "state" / "pipeline.json.bak"`; `backup.parent.mkdir(parents=True, exist_ok=True)`; `backup.write_bytes(current_bytes)`.
- Запись: `proj.write_config(state.project, candidate)`; сразу после — перечитать файл и разобрать JSON. Не разобрался — вернуть байты из копии (`path.write_bytes(current_bytes)`) и отдать `{"ok": False, "error": "записал и не смог прочитать — вернул прежний файл"}` (500 через общий обработчик не нужен: это отказ действия, 400).
- Ответ: `{"ok": True, "changed": [...], "config": candidate, "backup": {...}}` — структура `backup` та же, что в `GET /api/config` (4.5).
- Чтение-проверка-запись — под `state.lock`; `state.note(...)` вызывать **строго после** выхода из `with`: `note()` берёт тот же `Lock` (`ui_server.py:148-150`), а он не реентрантный — вложенный захват повесит запрос навсегда.

### 4.4. Откат: действие `revert_config`

`act_revert_config(state, payload)`:

- копии нет → `{"ok": False, "error": "резервной копии нет — откатывать нечего"}` (400);
- копия не разбирается как JSON → `{"ok": False, "error": "резервная копия повреждена — откат не выполнен, файл не тронут"}` (файл при этом не пишем вовсе);
- иначе `(root / "pipeline.json").write_bytes(backup.read_bytes())` — без пересборки JSON, без `write_config` (C5, D5); ответ `{"ok": True, "restored": True, "bytes": N, "sha256": ...}`;
- откат новую копию не создаёт: повторное сохранение перезапишет её — «одна кнопка» именно так и работает;
- `state.note("pipeline.json восстановлен из копии побайтово")` — вне `with state.lock`;
- регистрация: `ACTIONS["revert_config"] = act_revert_config`.

### 4.5. Маршрут `GET /api/config`

`_get_config(self)` в классе `Handler` плюс ветка в `do_GET` (`ui_server.py:561-602`), рядом с `/api/setup`:

- `self._local_only()` иначе 403 — как у остальных GET;
- ответ: `{"ok": true, "preview": state.preview, "path": str(root / "pipeline.json"), "config": {...}, "errors": [...], "backup": {"exists": bool, "path": ".pipeline/state/pipeline.json.bak", "bytes": N, "saved_at": "2026-11-05T10:00:00"}}`;
- битый файл → `config: {}` и `errors: ["pipeline.json не разбирается: …"]`, статус 200: маршрут читающий, панель должна нарисовать форму и объяснить, почему правка не пройдёт;
- в предпросмотре маршрут работает, отдаёт `config: {}`, если файла нет;
- секретов в `pipeline.json` нет (в `notify` только имена env-переменных) — файл отдаётся целиком, это и есть ответ на «что сейчас в конфигурации».

### 4.6. Форма настроек (`ui/index.html`)

- Блок «Каталоги» в диалоге `id="settings"`: четыре поля `path_plans`, `path_reviews`, `path_prompts`, `path_state`, подпись «от корня проекта».
- Кнопка «Проверить» (`id="config-check"`): собирает тот же патч, что и сохранение (включая `paths`), шлёт `action: "preview_config"` и рисует дифф в `id="config-diff"` (моноширинный, строки `+` и `-` разными классами), показывает `notes` списком. Запрос идёт через `api()` напрямую, **не через `act()`**: `act()` после ответа перезагружает снимок (лишний прогон движка) и показывает тост «готово», а проверка ничего не меняет и тоста не заслуживает.
- «Сохранить» (`id="save-config"`) активна **только после** успешной проверки; любое изменение поля формы (`addEventListener("input")` на `#form-config`) сбрасывает дифф и гасит кнопку — иначе сохранится не то, что показано (C3).
- «Вернуть как было» (`id="config-revert"`) в том же диалоге: активна, когда `GET /api/config` отдал `backup.exists === true`, подпись содержит дату копии; после нажатия форма перезагружается из `/api/config`, дифф очищен.
- Открытие диалога грузит значения из `GET /api/config` (снимок для `paths` не годится, факт 6); прежнее поведение «форма не перетирает ввод пользователя» сохранить: флаг `__configLoaded` продолжает работать для снимка, диалог читает `/api/config` при открытии.
- Ошибку валидации показывать в диалоге в `id="config-error"` (рядом с диффом), а не только тостом: объяснение длиннее строки тоста.

## 7. Формат отчёта

Отчёт — в карточку борды, по-русски, по пунктам; сначала отчёт, затем коммит, sha — отдельной строкой после коммита.

1. Что сделано — по задачам 4.1-4.8, с адресами `path:line` по **своим** правкам (не по постановке).
2. Прогоны Г1 и Г2: команда, фактическое `passed/failed/error`, полный вывод в файл-лог (путь назвать). Цифры рядом с ожиданием §5; расхождение с «не меньше 70» объяснить, а не подогнать.
3. Г4: вывод `git status --short` (пусто) и `git show --stat` (три файла).
4. Список добавленных тестов: одна строка на тест — что именно утверждает.
5. Что осталось и чего не делал (вне объёма) — честно, без «потом доделаю».
6. Изменившиеся по ходу факты дерева (например, коммит S6 успел лечь — какие строки съехали и как искал).

Коммит — один, после зелёных гейтов, сообщение в стиле `git log --oneline` репозитория: `feat(ui): правка конфигурации с валидацией, диффом и откатом`. Слово «ЗАКРЫТ» в журнале плана не ставить: это делает ревьюер после APPROVE.

## 8. Вопросы

Открытых вопросов нет: развилки закрыты решениями D1-D8, работать можно без ответа владельца. Два места, где решение могло быть иным, названы с ценой — если владелец ответит до старта, следуй его ответу.

В1. Формат `runtimes` (D2): принято `Nm`/`Nh`. Цена расширения (`1h30m`, `90s`, `3d`) — свой разбор и три-четыре новых теста; канбану формат безразличен, отказ нужен только ради ранней ошибки.

В2. Резервная копия (D5): одна, до последнего сохранения. Цена истории (несколько копий с метками времени) — каталог, лимит по числу и выбор версии в форме; для «вернуть как было» достаточно одной.

## 9. Ревью (обязательно)

Шаг закрывает независимое ревью роли `reviewer` (`pipeline-reviewer`), не исполнитель.

- Что ревьюер получает: план (`docs/plans/3-panel.md`, §S7), эту постановку, код и тесты в коммите. Отчёт исполнителя — не источник фактов: каждое утверждение проверяется по дереву.
- Что проверяется в первую очередь: C1-C7 против кода, а не против отчёта; «дифф не врёт» (D4) — сверка `content` предпросмотра с записанными байтами; побайтовость отката на файле без завершающего перевода строки; сохранность неизвестных ключей и подклечей; отсутствие правок вне трёх файлов.
- Вердикт: APPROVE — можно ставить «ЗАКРЫТ» в журнале и коммитить закрытие шага; REQUEST_CHANGES — перечень находок с адресами.
- При REQUEST_CHANGES шаг остаётся открытым: находки правятся, гейты Г1-Г4 прогоняются заново, ревью повторяется. Исполнитель шаг не закрывает никогда — ни при зелёных тестах, ни при устном согласии.
