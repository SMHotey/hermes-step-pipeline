## 1. Роль и цель

Ты — программист конвейера шагов Hermes (`hermes-step-pipeline`), исполняешь шаг S11
плана 5 в ветке `main`. Рабочий каталог —
`C:\Users\malik\PycharmProjects\hermes-step-pipeline`, оболочка — bash (git-bash),
интерпретатор — `.venv/Scripts/python.exe` этого репозитория (Python 3.11.15).

Результат шага: при первом запуске человек выбирает «с ботом» или «без бота», не боясь
утечки токена и чужих команд. Конкретно:

- **Бот опционален и по умолчанию выключен.** И CLI, и мастер в панели спрашивают
  «Подключить бота?» с умолчанием «нет»; отказ проходит без строк-предупреждений, а исход
  отказа сохраняется в `pipeline.json` (`notify.skipped`), чтобы мастер не считал шаг
  незавершённым.
- **Токен скрыт.** Ввод — `getpass` (CLI) и `type=password` (панель); в лог, ответ API и
  журнал панели не попадает ни токен, ни его маска.
- **Доступ только владельцу.** После `/start` chat id и owner id подставляются
  автоматически (CLI — уже; панель — новая кнопка «Найти по /start»); в `.env` пишутся три
  переменные, включая `STEP_PIPELINE_TELEGRAM_OWNER_ID`; путь подключения через диалог
  «Уведомления» пишет те же три переменные.
- **В мастере есть строка про BotFather**: вебхук снимается методом API `deleteWebhook`
  (не командой BotFather), privacy mode — `/setprivacy`, «кто может писать» настраивается
  только кодом (allowlist), API у BotFather нет.
- **Повторный запуск предлагает заменить токен** (CLI — вопросом, панель — приглашением в
  логе шага), и замена действительно перезаписывает `.env`.

Затрагиваются `step_pipeline/setup_flow.py`, `step_pipeline/ui_server.py`,
`step_pipeline/ui/index.html`, `tests/test_setup_flow.py`, `tests/test_setup_ui.py` плюс
`step_pipeline/plugin.yaml` и `CHANGELOG.md` (правило `AGENTS.md`). Файлы шага S12
(`engine/gate.py`) не трогаются.

## 4. Что сделать

### 4.0 Решения, которые уже приняты (не переигрывать)

- **D1. Исход «без бота» хранится.** Новый необязательный ключ `notify.skipped` (булево):
  истина — владелец осознанно выбрал без бота. Пишется только по факту выбора (флаг
  `--no-telegram`, ответ «нет», умолчание в неинтерактивном режиме, снятый чекбокс в панели);
  при успешном подключении сбрасывается в `false`. Без него мастер вечно показывает
  «следующий шаг: telegram» — «бот опционален» становится неправдой.
- **D2. Умолчание вопроса — «нет».** `--yes` и не-tty идут по умолчанию, то есть без бота:
  это делает автоматическую установку предсказуемой и убирает нынешнюю пару «warn».
- **D3. Отказ от бота — не предупреждение.** На пути «без бота» ни одной строки
  `log.warn`; исход печатается `log.ok`/`log.step` («Telegram не подключён: уведомления и
  команды выключены — допустимый выбор»). Это касается и `ensure_commands_cron`
  (`setup_flow.py:844-845`): она получает keyword-only параметр `skipped: bool = False` и
  при `enabled=False, skipped=True` печатает `log.ok`, а `warn` оставляет только для
  «бот запрошен, но не сконфигурирован» (`skipped=False`). `warn` в остальных местах
  остаётся там же, где бот запрошен, но не сконфигурирован: плохой токен, нет chat, ошибка
  сети, отказ `getChat`.
- **D4. Токен в логе — ноль символов.** `_mask` удаляется вместе с упоминаниями; в логе
  только путь к `.env`. Маска — это тоже часть секрета.
- **D5. Повторный запуск предлагает замену.** CLI: при токене в окружении и без
  `--telegram-token` — вопрос «Заменить токен бота?» с умолчанием «нет» (только в tty);
  «да» → `getpass`, «нет»/`--yes`/не-tty → прежний токен, `.env` не меняется. Панель
  вопросов не задаёт, но в логе шага пишет приглашение «чтобы заменить, вставь новый токен».
- **D6. Владелец — из достоверного источника.** Приоритет: owner из `/start`
  (`detect_chat_and_owner`), затем поле формы, затем chat id. Фолбэк на chat id совпадает с
  поведением `gate.owner_ids` и верен только для приватного чата; для группы нужен именно
  user id из `/start`.
- **D7. Поиск по `/start` в панели — отдельное действие `detect`.** Кнопка отправляет
  `{step: "telegram", values: {token, detect: "1"}}`; шаг только ищет (ожидание 15 с, шаг
  опроса 2 с), пишет `found: {chat, owner}` в результат и **ничего не пишет на диск**.
  Запись `.env` — отдельным нажатием «Выполнить», после того как владелец увидел chat.
- **D8. Приоритет входов шага `telegram`.** Порядок разбора `given` — сверху вниз, первый
  совпавший пункт решает:
  0. непустое `given.get("detect")` — отдельное действие D7: разбирается **до** пунктов 1-4
     и не пишет на диск ничего (§4.7 п.1). Токен из формы или из `.env` здесь — только вход
     для поиска, а не повод подключить бота: POST `{"token": …, "detect": "1"}` ищет
     chat/owner, `.env` и `pipeline.json` остаются прежними (тесты 14, 16, 18);
  1. непустой `token` в форме → подключаем: три переменные, `notify.enabled = true`,
     `notify.skipped = false` (§4.8 п.1); значение `bot` не важно — владелец вставил токен
     действием (это и есть прежнее «токен подключается даже при снятом чекбоксе»);
  2. `given.get("bot") == "0"` → осознанный выбор «без бота»: `notify.enabled = false`,
     `notify.skipped = true`, `.env` не трогается, `log.ok`, ни одного `warn` (D1, D3);
     **этот пункт сильнее прежнего токена в `.env`** — иначе одно нажатие «Проверить» на
     настроенном боте гасит уведомления (поэтому чекбокс и предзаполняется, §4.6 п.1);
  3. токен есть в `.env` драйвера (`env_values(driver).get(token_env)`) → приглашение
     «чтобы заменить, вставь новый токен», `ok=True`, на диск ничего не пишется;
  4. иначе (токена нет ни в форме, ни в `.env`) → `ok=False`, `error` «нужен токен бота».
  Красный шаг — только пункт 4. Один и тот же вход больше не имеет двух исходов: POST `{}`
  на настроенном проекте попадает в пункт 3 (тест 20), POST `{"bot": "0"}` — в пункт 2
  (тест 23), POST `{"bot": "1"}` без токена — в пункт 4 (тест 13), POST
  `{"token": …, "detect": "1"}` — в пункт 0 и только ищет (тесты 14, 16, 18).
- **D9. Проверки мастера нейтральны к выбору.** `_setup_checks`: при `skipped` — `log.ok`
  «telegram: не настроен — установка без бота, это допустимо»; `warn` только если
  `notify.enabled` истинно, а переменных в `.env` не хватает.
- **D10. Версия — патч от факта.** `plugin.yaml:2` на HEAD — `0.15.0` (S10 поднял минор),
  значит шаг пишет `0.15.1`: движок не меняется, `pipeline.json` получает только
  необязательный ключ. `ENGINE.sha256` и `.pipeline/` не трогать. Заголовок записи

### 4.10 Мастер видит исход «без бота» (D1, D9)

1. `_telegram_fact` (`setup_flow.py:1337-1345`): шаг выполнен, если
   (`notify.enabled` и токен с chat в `.env`) **или** (`notify.skipped` истинно и
   `notify.enabled` ложно). Второе — осознанный выбор, а не «недоделанный шаг». В коде это
   `enabled = bool(notify.get("enabled"))`; `if not enabled: return bool(notify.get("skipped"))`,
   иначе прежняя проверка `.env`. Поэтому `enabled` сбрасывается в `False` там же, где
   ставится `skipped` (§4.8 п.3): иначе на конфиге с прежним подключением факт не станет
   истинным и `next` навсегда останется `telegram`.
2. `SETUP_HINTS["telegram"]` (`:1275`): «необязательно: токен и chat id в .env драйвера;
   без бота шаг закрывается выбором».
3. `_setup_checks` (`:1587-1590`): при `notify.skipped` — `log.ok("telegram: не настроен —
   установка без бота, это допустимо")`; `warn` — только при `notify.enabled` без полного
   `.env`, текст нынешний.
4. `build_config` (`:543-546`) не добавляет `skipped` при первичной установке: ключ
   появляется только после выбора. Повторная установка чужие ключи `notify` сохраняет —
   это утверждает тест `test_build_config_keeps_notify_skipped` (§4.11 п.11).
5. Регресс, который нельзя сломать: `tests/test_setup_ui.py:278` утверждает
   `cron["next"] == "telegram"`, когда Telegram не настраивался и отказа не было. После
   правки это утверждение обязано остаться верным (skipped не выставлен — шаг не выполнен).

   значит, удалять нечего — зафиксируй это в отчёте и иди дальше (после шага маски быть не
   должно).
3. **Нужен файл вне §3.** Например, `engine/gate.py` («owner_ids лучше там»), `snapshot.py`
   (префилл owner в диалоге), `cli.py` (новый флаг), `templates/pipeline.json.example`,
   `doctor.py` — стоп и вопрос: это решения D1, D6 и D9, а не мелкая поправка по ходу.
4. **Существующий тест краснеет не по твоей строке.** Сначала причина; если правка требует
   поменять ожидание теста, который к шагу не относится (например,
   `test_checks_step_reports_lint_problems`, `test_preview_hides_master_and_rejects_post`,
   `test_setup_status_starts_from_project_on_empty_dir`), — стоп, назови тест, ожидание,
   факт и гипотезу. Ослаблять и переписывать такие тесты нельзя.
5. **Гейт красный по посторонней причине** (нет `hermes` в PATH, сломан интерпретатор, чужой
   тест падал до шага). Зафиксируй команду, полный текст ошибки и вывод, что причина
   внешняя; шаг не закрывай — постановка требует зелёного гейта, а не объяснения.
6. **Требование выполнимо только ценой секретности.** Например, «покажем маску токена,
   иначе непонятно, какой токен заменяем», «положим owner в snapshot, чтобы был префилл»,
   «запишем токен в лог для отладки». Стоп: D4 и D6 держат границу, спорное — вопрос
   владельцу, а не компромисс в коде.
7. **Для `notify.skipped` требуется менять движок, валидатор или шаблон конфига.** Стоп:
   ключ необязательный, движок его не читает, `owner_ids` работает по переменной окружения.
   Если для записи ключа нужна правка `engine/*` — решение неверно понято, вернись к D1.

## 7. Формат отчёта

Отчёт — до коммита, по-русски, по разделам:

1. **Факты до правок** — `git rev-parse HEAD`, состояние дерева, замер гейта 0
   (collected/passed/skipped), версия из `plugin.yaml`.
2. **Что сделано** — по файлам с номерами строк: что добавлено, что изменено, почему именно
   так (одна строка на решение D1-D10), какие новые ключи/значения появились в контракте
   шага мастера (`found`), в `pipeline.json` (`notify.skipped`) и в подписи
   `ensure_commands_cron` (keyword-only `skipped`).
3. **Гейты** — таблица «команда → ожидание → факт → EXIT» для всех десяти гейтов §5; числа
   прогонов фактические.
4. **Тесты** — 16 новых функций в `tests/test_setup_flow.py` и 10 в `tests/test_setup_ui.py`:
   имя и что утверждает каждый; отдельно — блокирующие тесты §4.11 п.2-3 (полный `run_setup`
   без бота и шаг `cron` панели без единой строки `  ! `); отдельно — тесты находки 2 круга 2
   (п.22 и п.26: предзаполнение чекбокса и повторное нажатие, не гасящее бота); отдельно —
   что ни один существующий тест не ослаблен и почему правка
   `test_panel_has_setup_tab_hidden_in_preview` (если была) не меняет старых утверждений.
5. **Безопасность** — четыре факта с доказательством: токена нет в логе шага и в stdout
   установки; `_mask` удалён; в ответе API и `state.log` панели токена нет; полный
   `run_setup` без бота и шаг `cron` панели не печатают ни одной строки `! ` (§4.11 п.2-3).
6. **Что не сделано и почему** — отличия от постановки, отложенные места; если ничего, так
   и скажи.
7. **Коммит** — хеш, список путей, версия из `plugin.yaml`; `git add` только путями §3,
   сообщение `feat(setup): ... (план 5, S11)`. Шаг не закрывать: строку журнала пишет страж
   после `APPROVE`.

Числа — только фактические, из логов прогонов. «Тесты зелёные» без числа не отчёт.

## 8. Вопросы

1. **Ключ `notify.skipped` — новый ключ `pipeline.json`, а не запись в состоянии?** Так
   решено (D1): факт «владелец выбрал без бота» принадлежит проекту, а не сессии, и мастер
   читает его в `setup_status`. Цена альтернативы: держать выбор в `.pipeline/state/` — тогда
   `setup_status` читает два источника, а `doctor` и перенос проекта теряют выбор. По
   умолчанию — D1.
2. **Полный запрет маски не мешает диагностике?** Постановка держит D4: в логе только путь к
   `.env`, а «какой токен заменяем» владелец видит по имени бота (`@username`) из `get_me`.
   Цена запрета: при двух ботах в разных профилях номер токена не сверить глазами; цена маски
   — часть секрета уезжает в журнал панели и в переписку. По умолчанию — D4.
3. **Пятнадцати секунд на поиск по `/start` в панели хватит?** D7 держит 15 с и кнопку
   повтора: POST не должен висеть минуту, браузер ждёт ответ. Цена большего ожидания —
   риск таймаута прокси и «зависшая» панель; цена меньшего — владелец не успевает написать
   боту и жмёт кнопку снова. По умолчанию — 15 с.

## 9. Ревью (обязательно)

- Шаг закрывает не исполнитель, а роль `reviewer` (`pipeline-reviewer`) по плану
  `docs/plans/5-platforma.md` и коду дерева. Ревизия 4 закрывает 4 находки ревью постановки
  `docs/reviews/5-S11-prompt.md` (круг 3: блокирующая — невыполнимая проверка `notify` в
  тесте 16, значимые — стабы теста 3 и `detect` в приоритете D8, стилистическая —
  `_perform_step` в списке §3); находки кругов 1-2 закрыты ревизиями 2-3. Ревью результата —
  отдельный файл `docs/reviews/5-S11.md`.
- Ревьюеру доступны план и код; отчёт исполнителя — не источник фактов, а заявка. Гейты §5
  ревьюер прогоняет своими руками, включая полный набор и гейты 1-2.
- Вердикт — `APPROVE` или `REQUEST_CHANGES` в `docs/reviews/5-S11.md`. При `REQUEST_CHANGES`
  шаг остаётся открытым: находки правятся, ревью повторяется, и только после `APPROVE`
  появляется строка «ЗАКРЫТ» в журнале плана и коммит закрытия.
- Что смотреть в первую очередь: (1) установка без бота не печатает ни одной строки с `! `
  на обоих путях — и в полном `run_setup` (`ensure_commands_cron`, `setup_flow.py:844-845`),
  и в шаге `cron` панели, — и всё равно доходит до «проверок»: `notify.skipped` действительно
  читается мастером; (2) токен не встречается ни в логе CLI, ни в логе/ответе панели, ни его
  частями, `_mask` удалён; (3) панель пишет три переменные, owner берётся из `/start`, detect
  ничего не пишет на диск и не гасит поле токена; (4) повторный запуск спрашивает замену в CLI
  и приглашает в панели, старый токен не теряется при отказе; (5) текст про BotFather называет
  вебхук, privacy mode и allowlist, а снятие вебхука названо методом API `deleteWebhook`, не
  командой BotFather; (6) существующие тесты панели и мастера зелёные, регресс
  `next == "telegram"` без выбора сохранён; (7) ключ `notify.skipped` не потребовал правок
  движка; (8) `enabled=False` ставится там же, где `skipped=True`, — иначе на конфиге с
  прежним подключением факт шага не закрывается.
