## 1. Роль и цель

Ты — исполнитель шага S6 плана 2. Результат: страж умеет три вещи, которых не умел, и это
проверено тестами: (1) заказывает постановку следующего шага, пока текущий ещё в работе;
(2) не закрывает текущий шаг, пока постановки следующего нет; (3) не начинает шаг, постановка
которого разъехалась с кодом, — но только по явной настройке и только когда это действительно
расхождение. Оба поведения выключаются ключами `pipeline.json`.

Готово = (дословно из плана, `docs/plans/2-upravlenie.md:146-148`):
1. на тестовом проекте шаг N не закрывается без постановки N+1;
2. постановка N+1 появляется, пока N в работе;
3. устаревшая постановка N блокирует старт до ревью;
4. `prompt_review: never` возвращает прежнее поведение.

Строку «ЗАКРЫТ» в журнале, коммит закрытия и ревью делает не ты: журнал закрывает страж после
APPROVE ревьюера, ревью — роль `reviewer` (`pipeline-reviewer`). Ты сдаёшь код движка, конфиг,
два файла тестов, версию с CHANGELOG и отчёт по §7.

Объём — один срез: 4 правила плана и два ключа конфига. Шаг оценочно на 1.5 дня; если
для «Готово =» нужна правка `next_step.py`, `registry.py`, UI или `.pipeline/` — это стоп-сигнал §6,
а не расширение объёма.

### 2.5. Где «по-простому» ломается (это и есть основная работа шага)

- **Лимит действий.** `max_actions` по умолчанию 1, и тик обрывается, как только действие
  не применилось (`gate.py:2448-2452`: «второй попытки в этом тике нет»). Поэтому правило
  «заказ постановки не блокирует работу над N» нельзя кодировать действием, которое каждый тик
  возвращает `applied=False`: это навсегда застопорит и другие планы (в этом проекте ведутся
  планы 2 и 3). Ожидание обязано быть решением `idle`, а не повторяющимся отказом.
- **Инвариант D5.** Ключ шага считается по `decision["step"]` (`gate.py:2168-2176`); действие
  предзаказа адресует шаг N+1, поэтому не конфликтует с действием по шагу N в том же тике.
- **`card_of` и похожие имена.** `card_of(cards, "review")` ловит ключи, оканчивающиеся на
  `:review` или `:review:{номер}` (`gate.py:427-430`). Ключ ревью постановки с суффиксом
  `:promptreview` под этот шаблон НЕ попадает (перед `review` стоит `t`, а не `:`), то есть
  карточку ревью постановки нельзя перепутать с ревью шага.
- **Идемпотентность.** Настоящая борда дедуплицирует по `--idempotency-key`; поддельная
  (`stub_hermes.py`) — нет. Поэтому решение обязано само проверять, что карточка заказа уже есть,
  и не создавать вторую.

## 4. Что сделать

### 4.0. Решения, принятые за тебя (не переигрывать; в отчёте — список фактически реализованных)

- D1. Имена действий: `create_prompt` (заказ постановки N+1; подпись «постановка» в
  `snapshot.py:44-47` уже есть) и `create_prompt_review`. Ключ карточки ревью постановки —
  `planloop:{план}:{шаг}:promptreview`, отчёт — `docs/reviews/{префикс}-{шаг}-prompt.md`
  (для этого проекта `docs/reviews/2-S6-prompt.md`).
- D2. Правило 5 плана читается БУКВАЛЬНО: предзаказ и гейт закрытия не работают, если N+1 —
  последний шаг плана, и если N — последний (следующего нет). Причина: иначе предпоследний шаг
  нельзя закрыть, а весь существующий набор тестов (планы из 2 шагов) стал бы красным.
- D3. Гейт закрытия действует только при `require_prompt: true` И `prefetch_prompt: true`:
  проекту, который постановок не требует, незачем требовать их для закрытия.
- D4. Свежесть постановки — «между `recon_commit` и HEAD нет правок вне `docs/`», проверка
  `git diff --quiet {recon}..HEAD -- . :(exclude)docs` (код 0 — свежая, 1 — устарела, прочее —
  считать устаревшей). Почему не «`recon_commit` равен HEAD»: коммит самой постановки двигает HEAD,
  буквальное равенство не наступает никогда и правило 3 превратилось бы в «ревью каждой
  постановки». Проверено на временном репозитории 04.11.2026: docs-коммит после recon → `EXIT=0`,
  кодовый коммит → `EXIT=1`, неизвестный sha → `EXIT=128`.
- D5. Режим `auto`: постановка без `recon_commit` ревью не требует (у всех существующих
  постановок и у заглушек в тестах отметки нет — иначе шаг встанет на пустом месте);
  `always` — требует всегда; `never` — не требует никогда.
- D6. Вердикт ревью постановки принимается, только если в отчёте есть строка `recon_commit:`
  со значением, равным отметке в шапке постановки. Иначе — стоп с причиной: ревью не про эту
  версию постановки.
- D7. `REQUEST_CHANGES` по постановке — инцидентный стоп, автоматического второго круга нет:
  движок не умеет переписывать постановку, петля заказов жгла бы время постановщика.
- D8. Неизвестное значение `prompt_review` — `ConfigError` при загрузке (fail-fast),
  а не тихий откат к `auto`.
- D9. Гейт закрытия сообщает владельцу фразу из плана: «шаг N принят, но закрыть не могу:
  нет постановки N+1» (тест утверждает подстроку).
- D10. Гейт закрытия живёт в РЕШЕНИИ, а не в отказе `apply`: постановки N+1 нет и карточки заказа
  нет — решение `create_prompt` с признаком `after_close` и фразой D9; карточка заказа уже есть —
  `idle` с той же причиной. В `apply` остаётся защитная проверка (гонка), но повторяющегося
  `applied=False` каждый тик быть не должно (§2.5).

   затем от 7 до 40 шестнадцатеричных символов; регистр не важен.
2. `prompt_recon(path) -> str | None` — прочитать файл (utf-8, `errors="replace"`) и вернуть
   найденный sha в нижнем регистре; файла нет или отметки нет — `None`.
3. `head_commit(p) -> str` — `git rev-parse HEAD` в `Path(p.repo)`; сбой или не-репозиторий —
   пустая строка (свежести нет, постановка считается устаревшей).
4. `prompt_fresh(p, recon) -> bool` — `recon` непустой и `git diff --quiet {recon}..HEAD --
   . :(exclude)docs` вернул 0 (D4). Коды 1 и прочие — `False`.
5. `prompt_review_rel(p, step_id)` / `prompt_review_path(p, step_id)` — по образцу
   `_report_rel` (`gate.py:435-436`), имя файла `{префикс}-{шаг}-prompt.md`.
6. Вердикт по произвольному отчёту: вынести тело `verdict_of` (`gate.py:282-303`) в
   `verdict_at(path)`, а `verdict_of` оставить тонкой обёрткой над `review_path` — поведение
   и возвращаемые поля не меняются, существующие тесты обязаны пройти без правок.
7. `prompt_verdict(p, step_id)` = `verdict_at(prompt_review_path(...))`, плюс значение
   `recon_commit`, найденное в отчёте (для сверки по D6) — вернуть его отдельным ключом
   `recon` в том же словаре.
8. `next_prompt_step(steps, step_id) -> dict | None` — шаг N+1 или `None` по D2:
   индекс шага в списке, `None`, если `индекс + 1 >= len(steps) - 1`.

### 4.3. Состояние шага в `build_ctx` (`gate.py:646-680`)

Добавить в `ctx` (и в ветку отказа сборщика `gate.py:663-666` — безопасные умолчания):
- `prefetch` — `p.cfg.prefetch_prompt`; `prompt_review` — `p.cfg.prompt_review`;
- `prompt` — `prompt_rel(p, sid)` или `None`; `prompt_recon` — отметка из файла;
  `prompt_fresh` — свежесть по D4;
- `prompt_report` — `prompt_review_rel(p, sid)`; `prompt_verdict` — словарь вердикта ревью
  постановки или `None`;
- `steps` — список шагов плана из пакета сборщика (`pkg["steps"]`, поля id/title/days/owner/closed,
  `gate.py:284-286`), по нему считается N+1;
- `next_step` — `next_prompt_step(steps, sid)` или `None`;
- `next_prompt` — `prompt_rel(p, next_step["id"])` или `None`;
- `next_cards` — `read_cards(p, f"planloop:{p.plan_id}:{next_id}:")` или пустой список.

Все чтения в `decide`/`_decide_base` — через `.get` с умолчаниями (§2.4): рукописные `ctx`
в юнит-тестах этих ключей не имеют и обязаны работать как раньше.

### 4.4. Решения (`decide`/`_decide_base`)

1. Предзаказ (правило 2). Хелпер `_prefetch_decision(ctx)`: включён `prefetch`; в `steps` есть
   текущий шаг и `next_step`; карточка шага N уже существует (`card_of(ctx["cards"], "step")`
   не пуст — «шаг взят в работу»); постановки N+1 нет (`next_prompt is None`); карточки заказа
   N+1 нет (`card_of(ctx["next_cards"], "prompt")` пуст). Тогда — решение
   `{"action": "create_prompt", "step": id(N+1), "data": next_step, "reason": ...}`.
   Вызов — в `decide` после обработки стоп-флага: только если `base["action"] == "idle"` и в `base`
   нет `approval_blocked`, `incident`, `plan_done`.
2. Гейт закрытия (правило 1). В ветке APPROVE (`gate.py:822-824`): если `prefetch` и
   `require_prompt`, есть `next_step`, постановки N+1 нет — при отсутствии карточки заказа вернуть
   `create_prompt` с `after_close: True` и точной причиной из D9; при наличии карточки — `idle`
   с той же причиной и id карточки. Иначе — `close_step` как сейчас.
3. Ревью постановки (правило 3). В ветке «карточки шага ещё нет» (`gate.py:764-778`) ПЕРЕД
   `create_step`: нужен ли ревью (`prompt` есть, режим по D5 и свежесть по D4). Если нужен:
   карточки `:promptreview` нет → решение `{"action": "create_prompt_review", "step": sid,
   "data": step}`; карточка в работе → `idle` с её id; карточка `done` и вердикт APPROVE с
   совпадающим `recon` (D6) → пропустить к `create_step`; вердикт REQUEST_CHANGES, вердикта нет,
   отчёт не про эту версию или карточка упала → `stop` с конкретной причиной (D7).
   Порядок проверок в этой ветке: hold → риск-hold → ревью постановки → `create_step`.

### 4.5. Побочные действия (`run_gate`, ветки по `action`)

1. `create_prompt`: полный контракт шага получить сборщиком — `collector(p, step_id).get("next")`
   (образец обработки отказа — `create_rereview`, `gate.py:1984-1992`: `SystemExit` → инцидентный
   стоп). Ключ `planloop:{план}:{шаг N+1}:prompt`, заголовок и тело — как в `create_step`
   (`gate.py:1931-1933`), профиль `p.cfg.prompter`, скиллы `p.cfg.prompt_skills`, время
   `p.cfg.prompt_runtime`. `detail` — «постановка N+1 заказана заранее: карточка id» или
   «карточку заказа создать не удалось». Уведомление владельцу — только при `after_close`
   (текст причины D9); в обычном предзаказе молчим, чтобы не спамить.
2. `create_prompt_review`: карточка с ключом `planloop:{план}:{шаг}:promptreview`, заголовок
   `[ревью постановки {план} {шаг}] {название}`, профиль `p.cfg.reviewer`, скиллы
   `p.cfg.review_skills`, время `p.cfg.review_runtime`, тело — §4.6. `detail` — id карточки.
3. `close_step`: перед `append_journal_row` защитная проверка гейта (D10): не выполнен —
   `applied=False`, `detail` = причина D9, без коммита и без записи журнала.

## 7. Формат отчёта

До коммита, по порядку:
1. `git status --short` и `git diff --stat` — что фактически изменилось (список путей).
2. Реализованные решения D1–D10: по каждому одна строка — сделано как решено либо отклонено
   с причиной.
3. Новые тесты: имена всех 10 функций и фактические итоги прогонов (`6 passed`, `4 passed`,
   `10 passed`) с `EXIT`.
4. Полный прогон: число `passed`/`skipped`/`failed` и `EXIT`; сравнение с ориентиром §5.2.
5. `hermes plugins validate`: `EXIT` и хвост вывода; появились ли новые строки предупреждений.
6. Гейты §5.4–§5.6: каждая команда → фактический вывод или число → `EXIT`.
7. Коммит: `sha`, сообщение, факт пуша (или причина, почему пуша не было). Файлы — только из §3.
8. Что сознательно не сделано из «не входит в задачу» и любые отклонения от этого промта.
Язык отчёта — русский, без пересказа промта.

## 8. Вопросы (каждый с ценой вариантов; больше трёх не задавать)

1. Правило 5 плана прочитано буквально: постановка не заказывается и закрытие не тормозится,
   когда следующий шаг — последний в плане (D2). Вариант A — оставить как есть: последний шаг
   получает постановку обычным заказом при старте, стоимость нулевая. Вариант B — считать
   правилом «если N последний, следующий не заказывается»: тогда предпоследний шаг нельзя закрыть
   без постановки последнего, а 2-шаговые тесты движка придётся переписать. Рекомендация — A.
   Подтверждаешь?
2. Ревью постановки принимается только с отметкой `recon_commit` в отчёте ревьюера (D6).
   Вариант A — как решено: ревью не про эту версию постановки не принимается, шаг встаёт в стоп
   с внятной причиной. Вариант B — принимать APPROVE без сверки: дешевле на один стоп, но
   постановку можно подменить после ревью и шаг стартует непроверенным. Рекомендация — A.
   Подтверждаешь?
3. `REQUEST_CHANGES` по постановке даёт инцидентный стоп без автоматического второго круга (D7).
   Вариант A — стоп: владелец или постановщик переписывает постановку, цикл заказов не крутится.
   Вариант B — автоматически заказывать постановку заново повторно с замечаниями ревьюера: плюс
   круг времени постановщика и риск петли, если замечания не снимаются. Рекомендация — A.
   Подтверждаешь?

## 9. Ревью (обязательно)

Шаг не закрывает исполнитель. После гейтов — независимое ревью ролью `reviewer`
(скилл `pipeline-reviewer`) по плану и коду: вердикт APPROVE или REQUEST_CHANGES, отчёт
`docs/reviews/2-S6.md` с ровно одной строкой вердикта. При REQUEST_CHANGES журнал не закрывается,
шаг остаётся открытым, находки правятся, ревью повторяется. Отчёт исполнителя ревьюеру источником
фактов не служит: он читает план и код, а по новой логике — сами файлы движка и тестов.

Что ревьюер проверяет как минимум:
1. правило 2 работает: пока шаг N в работе, постановка N+1 заказывается один раз (идемпотентность
   по ключу), и это НЕ блокирует работу над N;
2. правило 1 работает: без постановки N+1 журнал не пишется, шаг открыт, владельцу уходит фраза
   из плана, и ожидание не превращается в повторяющийся отказ действия каждый тик;
3. правило 3 работает: свежая постановка стартует без ревью, устаревшая — блокирует старт до
   вердикта; вердикт без сверки версии постановки не принимается;
4. `prompt_review: never` и `prefetch_prompt: false` возвращают прежнее поведение (проверить
   прогоном тестов, а не на слово);
5. тесты утверждают значения (действие, ключ карточки, статус журнала, текст причины), ровно 10
   новых функций, ни один существующий тест не изменён и не ослаблен;
6. новые ключи конфига валидируются, старый `pipeline.json` без них читается с умолчаниями;
7. в диффе только разрешённые §3 файлы; `.pipeline/`, `docs/`, UI, план не тронуты;
8. версия `0.7.0` и секция CHANGELOG на месте; в роли постановщика появилось требование
   `recon_commit`, и оно же есть в теле заказа постановки.
