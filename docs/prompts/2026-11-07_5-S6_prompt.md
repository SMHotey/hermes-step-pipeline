### 2.4. Порядок переходов: где план и код расходятся

`docs/PLAN-FORMAT.md:193-194`: «план → разведка на его основе → правка плана по разведке
→ ревью плана → утверждение → шаги». В коде запись утверждения (`plan_accept.py:225`)
по-прежнему публикует план в реестр, а предусловия шага — блокировка по утверждению
(`gate.py:1194-1200`) и вердикт ревью (`gate.py:1420-1427`). Перестановка блоков до
публикации плана означала бы менять `plan_accept.py`, `registry.plan_started` и порядок
ветвей в `decide`, то есть ещё три файла вне объёма шага.

Решение по умолчанию: шаг делает вердикт ревью **условием шага**, а не условием
публикации плана. Неутверждённый план по-прежнему виден в реестре, но шаги не начинаются
ни без записи утверждения, ни без `APPROVE` по текущей версии плана. Так закрывается
«Готово =» шага (правка после `APPROVE` требует повторного ревью) и не ломаются
легаси-планы. Цена: буквальный порядок из `PLAN-FORMAT.md:193-194` не достигнут — это
вопрос владельцу, §8, вопрос 3, там же варианты и цена перестановки.

## 4. Что сделать

### T1. Новый модуль `step_pipeline/engine/approval.py`

Назначение: одно место, где решается «можно ли начинать шаги», — запись утверждения и
привязка вердикта ревью к sha256 файла плана. Импортов движка нет: только stdlib
(`hashlib`, `json`, `re`, `pathlib`, `typing`), как у `plan_cycle.py:1-20` — тот же
принцип «файл копируется в проект и работает без плагина». Размер — 120-170 строк:
меньше не покроет шесть состояний ревью, больше означает, что в модуль затащили лишнее.

Содержимое:

1. **Переезд помощников чтения.** `APPROVAL_TEMPLATE`, `approval_file_for`,
   `sha256_file`, `read_approval` переезжают сюда из `registry.py:89-111` по смыслу
   дословно. `registry.py` оставляет их реэкспортом, чтобы не менять
   `gate.py:2080,2085` и `tests/engine/test_approval.py:46,76,96,138,163,195`.
   Нормализация номера плана (`normalize`, `registry.py:62-68`) остаётся в `registry.py`:
   на ней держатся `state_file_for` и `stop_file_for`. В модуле номер берётся как есть —
   `spec.id` из `discover()` уже нормализован, — а обёртка `registry.approval_file_for`
   нормализует номер перед вызовом, чтобы поведение публичной функции не изменилось.
2. `VERDICT_RE` — переезжает из `gate.py:132` без изменения шаблона. `gate.verdict_at`
   берёт шаблон отсюда; второго шаблона в движке не появляется.
3. `PLAN_SHA_RE` — метка версии отчёта. Образец — `RECON_RE` (`gate.py:190`):
   `plan_sha256`, затем `:` или `=`, необязательный обратный апостроф, ровно 64 hex,
   `re.IGNORECASE`. Функция `plan_sha_of(text)` возвращает sha в нижнем регистре или
   `None`.
4. `has_constitution(plan_file)` — правило `gate.py:554-570` переезжает: строка
   `Конституция:` (`CONSTITUTION_MARK`) в шапке до первого `## `; нет файла или он не
   читается — `False`, без исключения. `gate.plan_has_constitution(p)` остаётся обёрткой
   на одну строку.
5. `review_path(cfg, plan_id)` возвращает `Path(cfg.reviews_dir) / f"plan-{plan_id}.md"`.
   `gate.plan_review_path(p)` делегирует сюда; сигнатура и все вызовы сохраняются.
6. `review_status(cfg, spec)` возвращает словарь
   `{state, reason, path, verdict, report_sha, label_sha, file_sha}`.
   `label_sha` — sha из метки отчёта, `file_sha` — фактический sha256 файла плана
   (имена не путать: это разные вещи). Состояния:

       нет строки «Конституция:» в плане   → skipped, reason пустой
       отчёта нет                          → missing
       вердикт не распознан (NONE/AMBIGUOUS) → invalid
       метки в отчёте нет                  → unbound
       sha из метки не равен sha плана     → stale
       иначе                               → fresh

   В `reason` — причина плюс путь отчёта. Для `stale` — первые 12 символов обоих sha и
   слова «повторное ревью»; для `unbound` — имя метки `plan_sha256` и путь отчёта; для
   `invalid` — что именно распознано. `path` — `str` пути отчёта (как у `verdict_at`),
   `verdict` — распознанный вердикт либо `None`, `report_sha` — поле `sha` из
   `verdict_at`.
7. `evaluate(cfg, spec)` возвращает
   `{state, reason, ok, block_kind, record, sha256, review, report}`:
   - `review = review_status(cfg, spec)`; `report = review["path"]`;
   - `sha256 = sha256_file(spec.file)`, `record = read_approval(cfg, spec.id)`;
   - `state`: `missing` (записи нет или она битая — текст причины прежний,
     `registry.py:125-129`), `changed` (sha256 не совпал или в записи пуст — текст прежний,
     `registry.py:131-136`, вторая половина фразы теперь про повторное ревью), `approved`;
   - `ok`: `True`, если `state == "approved"` и `review["state"]` в паре
     (`fresh`, `skipped`). Легаси-планы (`skipped`) получают `True`;
   - `block_kind`: `"approval"` при `missing` или `changed`; `"review"` при `approved` и
     `review["state"]` в наборе (`missing`, `invalid`, `unbound`, `stale`); иначе пустая
     строка;
   - `reason` — причина, по которой шаги стоят: при `block_kind == "approval"` прежний
     текст про утверждение, при `block_kind == "review"` — `review["reason"]`, иначе
     пустая строка.

Контракт старого ключа не ломается: `state`, `reason`, `record`, `sha256` и тексты причин
`missing`/`changed` остаются такими, какими их проверяют
`tests/engine/test_approval.py:60-79`. Новые ключи (`ok`, `block_kind`, `review`, `report`)
добавляются, старые не переименовываются.

## 8. Вопросы

Три решения, которые постановка приняла по умолчанию. Если владелец ответит иначе —
меняется только названная часть, остальное в силе.

1. **Имя метки версии: `plan_sha256:` (по умолчанию) или `plan_hash:`?** Параллель с
   `recon_commit:` (`gate.py:190`) даёт `plan_sha256`. Цена позднего переименования —
   парсер, текст карточки и все уже написанные отчёты ревью.
2. **Предел кругов повторного ревью.** В предлагаемом решении повторное ревью по
   устаревшему `APPROVE` не ограничено `PLAN_REVIEW_MAX_ROUNDS` (`gate.py:168,1483`):
   каждый новый устаревший вердикт даёт новый круг. По умолчанию — оставить без предела. Цена: при неаккуратном
   ревьюере цикл может повторяться, зато правка плана никогда не проходит молча; предел
   потребует ветки эскалации владельцу, как у `REQUEST_CHANGES`.
3. **Порядок переходов (§2.4).** По умолчанию: запись утверждения по-прежнему публикует
   план в реестре, а шаги открывает пара «запись плюс `APPROVE` про эту версию». Буквальный
   порядок из `docs/PLAN-FORMAT.md:193-194` (утверждение после ревью как условие
   публикации) — отдельный шаг: правка `plan_accept.py`, `registry.plan_started` и порядка
   ветвей `decide`. Цена перестановки сейчас — три файла вне объёма шага и разрыв с S5.

## 9. Ревью (обязательно)

Шаг закрывает не исполнитель, а независимая роль `reviewer` (`pipeline-reviewer`).
Ревьюеру доступны план `docs/plans/5-platforma.md` (раздел S6), эта постановка, код,
тесты и `CHANGELOG.md`; отчёт исполнителя — не источник фактов, а материал для проверки.

Формат вердикта — файл `docs/reviews/5-S6.md`, одна строка `## ВЕРДИКТ: APPROVE` либо
`## ВЕРДИКТ: REQUEST_CHANGES`. `APPROVE` разрешает закрытие шага. При `REQUEST_CHANGES`
шаг остаётся открытым: находки правятся, ревью повторяется; строку «ЗАКРЫТ» в журнале и
коммит закрытия делает закрывающий шаг только после `APPROVE`.

Ревьюер проверяет в первую очередь:

1. дверь к шагам (`_plan_review_decision`) действительно требует привязки вердикта к
   sha256 плана и не пропускает ни устаревший, ни непривязанный `APPROVE`;
2. mtime-проверки свежести в движке не осталось (`plan_review_verdict_fresh` удалён);
3. старые ключи `approval_status` и тексты причин целы — 10 тестов
   `tests/engine/test_approval.py` зелёные без правок файла;
4. повторное ревью не плодится на каждом тике (проверка незакрытой карточки);
5. `approval.py` в обоих списках `ENGINE_FILES`, цикла импортов нет, stdlib-чистота;
6. версия и запись `CHANGELOG.md` соответствуют правилам `AGENTS.md`.
