## 1. Роль и цель

Ты — исполнитель шага S6 плана 4. Появляется командный путь «черновик → проверка →
утверждение»: агент-планировщик пишет план в подкаталог `drafts/` каталога планов, а переносит его
в каталог планов только владелец командой `hermes pipeline plan --accept N`. Вместе с
переносом пишется запись утверждения с sha256 — её будет читать страж в шаге S7.

Готово = три подкоманды работают: `--list` показывает черновики и утверждённые планы с
номерами; `--check` проверяет черновик и делегирует линтеру `step_pipeline/plan_lint.py`,
когда тот есть (в этом репозитории он есть — шаг 1-S8), а когда его нет — делает
минимальные проверки сам через `.pipeline/next_step.py --json`; `--accept` с ошибками
возвращает код 1 и печатает ошибки, при успехе переносит файл из `drafts/` в каталог
планов и пишет `plan_N_approval.json` с sha256, совпадающим с содержимым файла; повторный
accept того же содержимого сообщает «уже утверждён» и не перезаписывает дату первого
утверждения; `python -m pytest tests/test_plan_accept.py` даёт ровно 9 passed.

### 5.1. `step_pipeline/plan_accept.py` — новый модуль

Шапка модуля и импорты — по стилю `plan_mode.py:1-28`: докстринг по-русски с объяснением

`plan_lint` — именно имя модуля на уровне модуля: тесты подменяют его через
`monkeypatch.setattr(plan_accept, "plan_lint", None)`, и это единственная точка, которой
проверяется запасной путь.

Публичный состав (имена фиксированы — на них опираются тесты и шаг S7):

- `plans_dir(project) -> Path` — каталог планов из `paths.plans` (умолчание `docs/plans`),
  повторяет `plan_lint.py:82-86`, но живёт здесь, чтобы работать без линтера.
- `drafts_dir(project) -> Path` — `plans_dir(project) / "drafts"`.
- `approval_file(project, plan_id) -> Path` —
  `proj.state_dir(Path(project)) / f"plan_{normalize(plan_id)}_approval.json"`.
- `plan_number(name: str) -> str | None` — номер из имени файла по образцу
  `engine/registry.py:30` (`^\d{1,2}-`), нормализованный как `registry.normalize`
  (`01` → `1`); `None`, если префикса нет.
- `now_iso() -> str` — `datetime.now().isoformat(timespec="seconds")`. Отдельная функция,
  а не вызов в глубине: тест подменяет её, чтобы проверить «дата первого утверждения не
  перезаписана», не завися от секунды запуска.
- `find_draft(project, value) -> Path` — номер или путь к черновику. Номер: файлы
  `drafts_dir` с этим номером; ноль — `ValueError` с текстом
  `черновика с номером N нет в каталоге черновиков`; больше одного —
  `черновиков с номером N несколько: a.md, b.md`. Путь: существует и оканчивается `.md`,
  иначе `ValueError` с текстом про ненайденный файл.
- `find_plan(project, plan_id) -> Path | None` — утверждённый файл с этим номером в
  `plans_dir`, или `None`.
- `check_draft(project, draft: Path) -> list[str]` — список ошибок; пустой список = чисто.
  Если `plan_lint is not None` — `[str(p) for p in plan_lint.lint_project(project,
  str(draft)).problems]` и больше ничего. Если `None` — запасные проверки из 5.2.
- `accept(project, value) -> int` — утверждение номера; печатает результат сам, возвращает
  код 0/1. Порядок и тексты — 5.3.

## 10. Решения и допущения

- D1. Запасной `--check` показывает черновик движку через временный `pipeline.json` с
  абсолютным `paths.plans` и `PIPELINE_CONFIG`: разбор остаётся один — движковый
  (`engine/registry.py`, `engine/next_step.py`), второй парсер шагов в плагине не появляется.
  Поддержка `PIPELINE_CONFIG` есть с 0.1.0 (§2), поэтому способ годится для любой
  вендоренной копии.
- D2. Ошибки запасного пути — без пути и номера строки: движок их не отдаёт, а свой разбор
  ради номеров был бы третьим парсером. Ошибки линтера, наоборот, идут как `Problem.__str__`.
- D3. `--list` не показывает статус утверждения: это прерогатива шага S7, а два источника
  истины об утверждении разъедутся.
- D4. Запись утверждения — в каталоге состояния (`proj.state_dir`), потому что S7
  (`docs/plans/4-planner.md:151-159`) читает `plan_N_approval.json` именно оттуда; ключи
  `plan`, `file`, `sha256`, `approved_at`, `profile` фиксированы.
- D5. Профиль в записи — `HERMES_PROFILE` или `default`, как в установщике (`setup_flow.py:1031`):
  отдельного источника имени текущего профиля в плагине нет.
- D6. `--json`, `--force` и прочие флаги не добавляются: контракт шага их не требует, а
  S7 читает файл записи, а не вывод CLI.
- D7. Номер плана берётся из имени файла и нормализуется (`01` → `1`); файл без числового
  префикса в `--list` виден, но утвердить его нельзя — так же его не увидит и движок.
- D8. `now_iso()` вынесена в публичную функцию модуля ради проверяемости даты первого
  утверждения: без подмены тест зависел бы от попадания в ту же секунду.
- D9. Версия плагина и `CHANGELOG.md` не меняются: ни движок, ни формат `pipeline.json`
  шаг не трогает.
