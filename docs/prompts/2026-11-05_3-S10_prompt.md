## 1. Роль и цель

Ты — исполнитель шага S10 плана 3 в репозитории плагина `hermes-step-pipeline`. Рабочая директория — `<корень>`, оболочка — bash (git-bash), интерпретатор — `.venv/Scripts/python.exe`. Код, комментарии, тесты и отчёт — по-русски (`AGENTS.md`, «Конвенции»).

Результат шага одним абзацем: в панели появляется вкладка «Уведомления» с мастер-выключателем (по умолчанию выключен), таблицей проектов реестра (чекбокс «уведомлять» плюс галочки видов событий), кнопкой «Показать тестовое уведомление» и кнопкой разрешения Notification API; сервер выводит события внимания из уже собираемого состояния плана и карточки (шаг пошёл в работу, шаг закрыт, правки по ревью, стоп/инцидент, падение карточки, лимит времени, квота провайдера, действие тика, простой плана) и отдаёт их в снимке и кадре SSE, браузер всплывает их после явного разрешения, то же сообщение уходит в Telegram при доступном канале; настройки живут в `projects.json` (на проект плюс глобальный переключатель), пишутся атомарно, чужие ключи не теряются, битый файл панель не роняет, а объясняет; тестовая кнопка показывает уведомление и не засоряет историю доставок.

Шаг закрывает не исполнитель: после зелёных гейтов карточка уходит на независимое ревью роли `reviewer` (`pipeline-reviewer`), и только APPROVE даёт запись «ЗАКРЫТ» в журнале плана.

Контракт шага (из §S10 плана, `docs/plans/3-panel.md:205-240`), по нему сверяется ревью:

- C1. Экран «Уведомления»: мастер-выключатель (по умолчанию выключен — разрешение даёт пользователь), таблица подключённых проектов с чекбоксом «уведомлять» и набором галочек по видам событий, кнопка «показать тестовое уведомление». Ограничение названо прямо на экране: уведомления приходят, только когда вкладка панели открыта; при закрытой вкладке события остаются в ленте.
- C2. Набор событий ровно из девяти видов плана (id и подписи — §4.2): шаг пошёл в работу, шаг закрыт (APPROVE), ревью вернуло REQUEST_CHANGES, стоп или инцидент плана, карточка упала (`crashed`), лимит времени (`timed_out`), квота провайдера (`rate_limited`), тик сделал действие, простой плана дольше N часов. Источник событий единый — состояние плана и карточки (снимок, `history.jsonl`, `task_runs`, состояние плана), второго источника нет.

- C5. Тот же набор и тот же текст уходит в Telegram, когда канал доступен; расходятся только настройки по проектам.
- C6. Тестовая кнопка показывает уведомление с пометкой «тест» и не пишет в историю доставок; в Telegram тестовая кнопка экрана уведомлений ничего не отправляет (для канала остаётся прежняя кнопка «Тест» в настройках, действие `test_telegram`).

### 2.2. Решения (приняты до кода; оспаривать их в отчёте, а не в коде)

- D1. Настройки уведомлений живут ТОЛЬКО в `projects.json`: в контейнере — `"notify": {"enabled": false}` (глобальный переключатель), в записи проекта — `"notify": {"enabled": true, "events": ["step_closed", "..."]}`. Нет ключа — считается «выключено», `events` — набор по умолчанию. `pipeline.json notify` (D2) не переименовывается и не дублируется.
- D2. Два `notify` — разные вещи в разных файлах: `pipeline.json notify` — канал Telegram (токен, чат, префикс, сторож), `projects.json notify` — что и куда слать панели. Экран обязан назвать это словами, чтобы владелец не путал.
- D3. Виды событий фиксированы (девять id плана), порядок — как в §4.2. Набор по умолчанию при включении проекта — семь «внимательных» видов; `tick_action` и `plan_idle` по умолчанию выключены (шум), но доступны в списке галочек. Неизвестный id при записи отбрасывается, дубликаты схлопываются, порядок приводится к D3.
- D4. Дедупликация — по ключу `f"{project_id}:{plan}:{step}:{kind}"`: одна запись истории, три попытки с одним исходом и повторный стоп дают одно событие (берётся самое свежее время и текст). Внутрипроцессные отметки доставки — `State.notified` (ключ → epoch); отметки живут в памяти сервера, после перезапуска событие может напомнить о себе ещё раз — это ограничение назвать в докстринге, в тестах на него не опираться.
- D5. Поток — существующий кадр SSE: `_snapshot_body` добавляет `data["notify"]`, новых имён SSE-событий нет (кадр остаётся `event: snapshot`). Тело кадра обязано быть детерминированным при неизменных данных: никаких «N минут назад», никаких отметок доставки в теле (иначе падает тест 304, tests/test_ui_server.py:369-383).
- D6. События считаются из уже собираемого снимка (`snap.snapshot`) плюс одно чтение `task_runs` по карточкам снимка. Движок (`gate.py`, `next_step.py`) в этом шаге не вызывается ни разу: тесты считают вызовы (tests/test_ui_server.py:378, :415), лишний запуск — падение.
- D7. Первый кадр потока — только пометка: он не всплывает в браузере и не отправляет сообщение в Telegram (`State.notify_primed`). Причина: перезагрузка страницы открывает новый поток, и без этого правила каждое открытие панели заново всплывало бы старые события. Доставка начинается со второго кадра.
- D8. Telegram-зеркало — одна точка доставки, `_events` после отправки кадра (там же, где браузер получает данные). Условия отправки одновременно: глобальный переключатель включён, проект включён, вид включён, `snap.telegram_state(root)` даёт `enabled` и `token_set` и непустой `chat`. Текст — тот же, что у события, с префиксом `prefix` из `pipeline.json` (как делает `gate.notify`). Ошибка отправки не роняет поток: пишется в `state.note` и в историю доставок с `channel: "telegram-error"` не пишется — только в лог сервера.
- D9. История доставок — `.pipeline/state/notify_deliveries.jsonl` (через `proj.state_dir`), одна строка JSON на доставку: `ts`, `at`, `project`, `plan`, `step`, `kind`, `text`, `channel`. `/api/notify` отдаёт последние 50 валидных строк (`deliveries`), битые пропускает. Тестовая кнопка туда не пишет и в Telegram не шлёт (C6).
- D10. Объём файлов — только четыре: `step_pipeline/project.py`, `step_pipeline/ui_server.py`, `step_pipeline/ui/index.html`, `tests/test_ui_server.py`. Версия плагина и `CHANGELOG.md` не трогаются (в §S10 их нет; выпуск версии — отдельная задача), `AGENTS.md` не трогается, движок и роли не трогаются, план и журнал не правятся.

### 4.2. Набор событий (единый словарь; id, подпись, источник, текст)

| id | подпись в интерфейсе | источник (факт) | текст уведомления |
|---|---|---|---|
| `step_started` | шаг в работе | карточка шага с ключом `planloop:{план}:{шаг}:step` и непустым `started_at` из `snapshot.cards`; время — `started_at` | «шаг {шаг} пошёл в работу (план {план})» |
| `step_closed` | шаг закрыт (APPROVE) | строка истории с `kind == "close_step"`; время — `ts` строки | «шаг {шаг} закрыт: APPROVE» |
| `changes_requested` | ревью вернуло правки | строки истории `kind` из `create_fix`, `create_rereview`; время — `ts` самой свежей | «ревью вернуло правки: шаг {шаг}» |
| `plan_stopped` | стоп или инцидент плана | поле `stop` в списке планов (`plans[]`, словарь с `kind`/`reason`) и строки истории `kind == "stop"`; время — `ts` строки, иначе время файла `plan_N_stop.json`, иначе `ts` события | «стоп плана {план}: {причина}» для `kind == "owner"`, иначе «инцидент плана {план}: {причина}» |
| `card_crashed` | карточка упала | попытка из `snap._attempts` с `outcome == "crashed"`; время — `started_at` попытки | «карточка упала: шаг {шаг} ({карточка})» |
| `card_timed_out` | лимит времени | попытка с `outcome == "timed_out"` | «карточка упёрлась в лимит времени: шаг {шаг}» |
| `card_rate_limited` | упёрся в квоту | попытка с `rate_limited == True` из `snap._attempts` (правило `outcome`/текст/`429` уже там) | «упёрся в квоту провайдера: шаг {шаг}» |
| `tick_action` | тик сделал действие | строки истории, НЕ отображённые в другие виды: `create_step`, `create_prompt`, `create_prompt_review`, `create_prompt_fix`, `create_review`, `retry_pending`, `hold_risk`, `tg_dialog`; `idle` действием не считается | «тик: {подпись действия} — план {план} {шаг}» |
| `plan_idle` | простой плана | `snap._plan_state(root, план).waiting_since`, порог — `notify.watchdog_hours` из `pipeline.json` (по умолчанию 3, как `WATCHDOG_DEFAULT_HOURS` движка) | «план {план} простаивает {длительность}» (через `snap._duration`) |

Правила вывода: план и шаг берутся из ключа карточки (регулярка `planloop:([^:]+):([^:]+):`) и из полей строки истории; событие без шага допустимо (`step` = `""`), ключ дедупликации тогда `проект:план::вид`. Сортировка — свежие сверху, потолок — 50 событий в ответе. Текст — одна строка без переводов строк; `plan_idle` — единственный вид, где число зависит от текущего времени (это допустимо, но в тело кадра он попадает только при наличии события).

Имена тестов — ровно эти (ревью сверяет по именам). Дополнительные тесты добавлять можно, переименовывать эти — нельзя.

## 5. Как проверить (гейты)

Все команды — из корня репозитория `<корень>`, оболочка bash, интерпретатор `.venv/Scripts/python.exe`. Вывод и `EXIT` каждого гейта — в отчёт; код возврата смотреть по самой команде pytest, а не по хвосту пайпа.

- Г1. Файл шага целиком: `.venv/Scripts/python.exe -m pytest tests/test_ui_server.py` — ожидается `121 passed`, EXIT 0. База замера: на recon тем же сбором — 113 тестов (tests/test_ui_server.py), плюс восемь новых = 121. Любое другое число — объяснить в отчёте, а не подгонять.
- Г2. Весь набор: `.venv/Scripts/python.exe -m pytest` — ожидается `455 passed`, EXIT 0. База замера: `--collect-only` на recon — 447; плюс восемь новых = 455. Падение в `tests/engine/` — стоп-сигнал: движок шаг не трогает.
- Г3. Число тестовых функций в файле: `grep -c "^def test_" tests/test_ui_server.py` — ожидается `116` (108 на recon плюс 8).
- Г4. Новые тесты собираются теми именами: `.venv/Scripts/python.exe -m pytest tests/test_ui_server.py -k "notify or event_kinds or event_dedup" --collect-only -q` — ожидается ровно 8 собранных узлов; имена совпадают со списком §4.5.
- Г5. Манифест и security-скан: `hermes plugins validate step_pipeline` — без ошибок (манифест, инструменты, скан). Если `hermes` в PATH нет — зафиксировать факт в отчёте, а не выдумывать результат.
- Г6. Объём правки: `git status --porcelain` — изменены ровно четыре файла шага (`step_pipeline/project.py`, `step_pipeline/ui_server.py`, `step_pipeline/ui/index.html`, `tests/test_ui_server.py`), плюс те же три неотслеживаемых отчёта ревью; `git diff --stat -- step_pipeline/snapshot.py step_pipeline/engine step_pipeline/roles step_pipeline/plugin.yaml CHANGELOG.md docs/plans` — пусто.
- Г7. Значения, а не присутствие ключей: в тестах утверждаются конкретные значения из §4.5 (например, `events == ["step_closed"]`, `len(rate_limited) == 1`, `deliveries == []`), а не факт наличия поля. Тест, который проходит при пустом ответе, считается невыполненным.

## 6. Стоп-сигналы

Остановиться и доложить (не «адаптировать по смыслу»), если:

1. Для события не хватает данных в `snap.snapshot` (нет `started_at` у карточки, нет поля `stop` у плана, нет `waiting_since`) — править `snapshot.py` запрещено; описать, чего не хватает и что предлагаешь.
2. Чтобы получить событие, нужен второй источник (свой опрос борды, отдельный файл состояния, второй запуск движка) — это противоречит C2/D6, шаг так не делается.
3. Существующий тест вне §4.5 падает из-за твоей правки и лечится только изменением `snapshot.py`, `engine/**` или ожиданий чужих тестов — это выход за объём.
4. Гейт красный по посторонней причине (нет `hermes` в PATH, сломано окружение, чужие падения в `tests/engine/`) — привести команду и вывод, не переписывать тесты под зелёный.
5. Живой `projects.json` у пользователя в форме списка, либо структура `notify` уже занята другим смыслом — зафиксировать факт и спросить, не конвертировать файл молча.
6. Recon не совпал: `git rev-parse HEAD` не `5c4fc07…`, либо `wc -l` файлов шага отличается больше чем на 30 строк, либо адрес из §2.1 не находится по якорю — сверить и доложить расхождение до правок.
7. Требуется тронуть секреты, `.env`, cron-джобы, сеть в тестах или реальную отправку в Telegram — этого в шаге нет.

## 7. Формат отчёта

Отчёт — в карточку (комментарий/результат), по-русски, до коммита и до запроса ревью:

1. Что сделано — по файлам, с именами новых функций и якорей (`notify_feed`, `notify_deliver`, `GET/POST /api/notify`, `POST /api/notify/test`, вкладка `notify`).
2. Гейты: по каждому из §5 — точная команда, число из вывода (`121 passed`, `455 passed`, `116`, `8` собранных узлов), `EXIT`.
3. Расхождения recon с фактом: адрес съехал, поле называется иначе, число тестов не то — с командой и выводом.
4. Принятые внутри шага решения (если пришлось выбирать) и почему; отклонения от §2.2 — отдельной строкой.
5. Ограничения и что не вошло: первый кадр не доставляет (D7), отметки доставки в памяти сервера, возможные дубли с `gate.notify`, проект не в реестре не настраивается.
6. Ручные проверки, если делал (открыть панель, разрешение браузера, тестовая кнопка): что видел.
7. Список изменённых файлов из `git status --porcelain`.

Отчёт не заменяет ревью и не закрывает шаг.

## 8. Вопросы

Три развилки, по каждой — решение по умолчанию уже принято в §2.2; если владелец не ответил, работай по умолчанию и назови это в отчёте.

1. Дубли в Telegram. Панель шлёт свой набор, движок (`gate.notify`) шлёт свои стоп, простой и сводку — на один стоп владелец может получить два сообщения. Варианты: (а) оставить оба источника — принято по умолчанию, цена: редкие дубли; (б) гасить зеркало для видов, которые уже шлёт движок — цена: «тот же набор» в Telegram сужается, нужна сверка в ревью.
2. Проект, запущенный из командной строки и не вписанный в `projects.json`, настраивать нельзя (`editable: false`). Варианты: (а) так и оставить — принято, цена: уведомления включаются только для проектов реестра; (б) писать настройки по корню в отдельный файл — цена: второй реестр, вне плана шага.
3. Реестр в форме списка (без контейнера) не даёт записать глобальный переключатель: POST вернёт 400 с текстом. Варианты: (а) отказ с объяснением — принято, цена: владельцу нужно добавить контейнер `projects` вручную; (б) молча конвертировать список в словарь — цена: меняет формат файла владельца без его согласия.

## 9. Ревью (обязательно)

Шаг закрывает не исполнитель. После зелёных гейтов карточка уходит на независимое ревью роли `reviewer` (`pipeline-reviewer`), вердикт — APPROVE или REQUEST_CHANGES в `docs/reviews/3-S10.md`.

Ревьюеру доступны план (`docs/plans/3-panel.md`, §S10) и код; отчёт исполнителя источником фактов не является — числа и утверждения он проверяет сам, прогоняя гейты §5 на своей стороне.

Ревьюер сверяет: девять видов событий и их источники (§4.2), настройки в `projects.json` с сохранением чужих ключей и атомарностью, отсутствие вызовов движка в новом коде, детерминированность тела кадра (тест 304 жив), первый кадр без доставки, троттлинг 30 с и дедупликацию, тексты экрана с оговоркой про открытую вкладку, имена и значения восьми тестов (§4.5), отсутствие правок вне четырёх файлов.

При REQUEST_CHANGES шаг остаётся открытым: находки правятся, гейты прогоняются заново, ревью повторяется. Строка «ЗАКРЫТ» в журнале плана и коммит закрытия — только после APPROVE.
