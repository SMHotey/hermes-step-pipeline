## 1. Роль и цель

Ты — разработчик движка `hermes-step-pipeline` (Python 3.11, только stdlib). Результат:

## 5. Как проверить (гейты)

Из корня репозитория; вывод в файл, код возврата смотреть у pytest, а не у хвоста пайпа:

```
python -m pytest tests/engine/test_commit.py > "$TMPDIR/s2-commit.log" 2>&1; echo EXIT=$?
# до правки ожидается: 4 failed, 1 passed, EXIT=1 (RED, его надо показать)
# после правки ожидается: 5 passed, EXIT=0
python -m pytest > "$TMPDIR/s2-all.log" 2>&1; echo EXIT=$?
# ожидается: 104 passed, EXIT=0 (замер сейчас: 99 = 51 движка + 48 плагина, плюс 5 новых)
git status --porcelain
# до коммита ожидается: `M step_pipeline/engine/gate.py` и `?? tests/engine/test_commit.py`;
# чужие правки из блока 2 остаются как были
git show --stat --oneline HEAD
# после коммита ожидается: в коммите ровно два файла и его sha
```

`-q` к командам не добавлять: в `pytest.ini` уже стоит `addopts = -q`, второй `-q` скрывает итоговую строку с числом прошедших. Запись плана «`python -m pytest tests/engine/test_commit.py -q` → 5 passed» означает то же самое; отчитываться фактическим числом прошедших и `EXIT`.

## 6. Стоп-сигналы

Остановиться и доложить (не адаптировать по смыслу), если:
- позеленеть тестам мешает не `commit_and_push`, а `close_step`, `run_gate`, `retry_pending`, `append_journal_row` или `_run` — значит решение не то: правка живёт только в `gate.py:274-296`;
- `git commit -- пути` не берёт новый untracked файл после `git add` или `git diff --cached --name-only -- пути` пуст при реально изменённом файле (CRLF, `.gitignore`, `--import-mode`) — доложить `git status --porcelain`, `git diff --stat`, версию git; не лечить повторным `git add -A` и не менять порог проверки;
- RED не воспроизвёлся у тестов 1–4 (они зелёные до правки) — не тот репозиторий или в `pipeline.json` выключен коммит; проверить `p.cfg.git_commit`, `p.cfg.git_push`, `p.repo`;
- полный прогон красный по причине, не относящейся к шагу (нет `hermes` в PATH, кодировка консоли, сеть) — доложить числа и текст ошибки, чужие тесты не править;
- `git status` показывает в индексе файлы вне двух разрешённых до коммита шага;
- для «Готово =» требуется новая зависимость, правка `.pipeline/` или миграция — это выход за объём шага.

Формат доклада: что обнаружено (файл и строки), замер командой, варианты с ценой, рекомендация.

## 7. Формат отчёта

По-русски, до и после коммита, по порядку: `git diff --stat` → полный дифф `commit_and_push` → RED-прогон (команда, `EXIT`, четыре имени упавших тестов и строки утверждений) → GREEN-прогон (5 passed, `EXIT`) → полный прогон (фактическое число passed, `EXIT`) → самостоятельные решения с причиной → что сознательно не сделано → отклонения от промта → sha коммита и ветка пуша.

Платить ли накопленный версионный долг этим шагом? «Грабли» плана (строки 49–50) требуют минимум минорной версии на любое изменение поведения движка; S1 прошёл без бампа, и ревьюер оставил это значимой находкой (`docs/reviews/1-S1.md:123-129`), теперь к нему добавляется S2. Вариант A (рекомендую, D6): шаг без бампа, версия и `CHANGELOG` — отдельным релизным действием перед публикацией плагина; цена — долг растёт, `.pipeline/VERSION` в проектах покажет «0.1.0 → 0.1.0». Вариант B: поднять 0.1.0 → 0.2.0 и записать оба шага в `CHANGELOG` этим коммитом; цена — выход за объём §S2, третий файл в коммите и находка ревьюера «расширение объёма».

## 9. Ревью (обязательно)

Шаг не закрывает исполнитель. После гейтов — независимое ревью ролью `reviewer` (скилл `pipeline-reviewer`) по плану и коду: §S2 `docs/plans/1-stabilnost.md`, `git show` коммита шага, сами `step_pipeline/engine/gate.py` и `tests/engine/test_commit.py`; отчёт исполнителя источником фактов не является. Отчёт ревьюера — `docs/reviews/1-S2.md`, ровно одна строка вердикта: `APPROVE` или `REQUEST_CHANGES`, и первая строка блока «Объект ревью» — коммит шага в бэктиках. При `REQUEST_CHANGES` шаг остаётся открытым, находки правятся, ревью повторяется. Строку журнала и закрытие шага делает страж после `APPROVE`.
