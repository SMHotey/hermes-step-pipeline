### 2.3 Почему у `tick.py` 32 %, хотя тестов семь

`.coveragerc:6-9` ограничивает замер шаблонами `**/step_pipeline/*.py`,
`**/step_pipeline/engine/*.py`, `**/.pipeline/*.py`. Четыре теста разбора `.env` грузят
**копию** тика из `profiles/ИМЯ/scripts/pipeline_tick.py` (`test_tick.py:31-38`) — этот
путь не подходит ни под один шаблон, поэтому в замер не попадает **ни одна строка этих
четырёх тестов**. Сам файл `step_pipeline/engine/tick.py` исполняется только в двух
тестах `find_gate` (`:80-97`), то есть в замере участвуют импорт модуля и тело
`find_gate()` — по арифметике ~21 утверждение из 62 (~34 %), замер S10 дал
`tick.py 62 42 32%` (`docs/reviews/1-S10.md:37`). Цифра 32 % — **ожидание**, снятое
ревьюером S10; первичен твой собственный замер (§6, гейт 4).

Следствие, которое нельзя проигнорировать: **тест, который исполняет копию файла вне
шаблонов `.coveragerc`, не двигает покрытие ни на строку.** Чтобы дойти до 80 %,
новые тесты обязаны исполнять модуль `step_pipeline/engine/tick.py` (и
`step_pipeline/engine/step_card.py`) — тем же способом, что `load_tick(TICK)`
(`test_tick.py:22-28`, `TICK = ENGINE / "tick.py"`, `:19`).

Порог 80 % в утверждениях: `tick.py` — 62 утверждения, нужно **≥ 50 покрытых**;
`step_card.py` — 45 утверждений, нужно **≥ 36 покрытых**.

### 2.5 Как устроен честный замер (и почему не по всему набору)

Штатный рецепт записан в `pytest.ini:6`: `coverage run --parallel-mode -m pytest`,
затем `coverage combine` и `coverage report -m`, с `COVERAGE_PROCESS_START` и
`COVERAGE_FILE`. Полный набор с подпроцессным крючком в S10 шёл 429 с
(`docs/reviews/1-S10.md:37`) и даёт агрегат по 18 файлам — для цели шага («покрытие
двух файлов ≥ 80 %») это лишние семь минут, потому что per-file строка от остальных
тестов не меняется: `tick.py` и `step_card.py` исполняются только тестами этих двух
файлов.

Поэтому замер шага — по двум тестовым файлам, с изолированным файлом данных
`.coverage.s12` (он уже игнорируется: `git check-ignore -v .coverage.s12` →
`.gitignore:15:.coverage.*`), `--fail-under=0` на отчёте, чтобы порог агрегата
`fail_under = 75` (`.coveragerc:20`) не выдавал чужую ошибку. `.coveragerc` **не
править**: шаблоны `include` и правило `[paths]` (`:11-16`) — часть честности замера.

Данных прошлых замеров в дереве нет: `ls -a | grep '^\.coverage'` → только
`.coveragerc`, поэтому смешивать нечего, но изоляция имени всё равно обязательна
(в CI и у других сессий файлы могут появиться).

## 6. Как проверить (гейты)

Все команды — из корня репозитория, интерпретатор проекта, **без второго `-q`** (D2).

Гейт 1. Новый файл отдельно:

```bash
.venv/Scripts/python.exe -m pytest tests/engine/test_step_card.py > "$TMPDIR/s12-g1.log" 2>&1; echo EXIT=$?
tail -3 "$TMPDIR/s12-g1.log"
```

Ожидается: `3 passed` или `4 passed` (по числу тестов задачи 4) и `EXIT=0`.

Гейт 2. Оба файла шага (гейт плана, строка `плана:213`):

```bash
.venv/Scripts/python.exe -m pytest tests/engine/test_tick.py tests/engine/test_step_card.py > "$TMPDIR/s12-g2.log" 2>&1; echo EXIT=$?
tail -3 "$TMPDIR/s12-g2.log"
grep -c "^def test_" tests/engine/test_tick.py tests/engine/test_step_card.py
```

Ожидается: `13 passed` (7 существующих + 3 в тик + 3 в `step_card.py`; при четырёх
тестах в `step_card.py` — `14 passed`), `EXIT=0`, счётчики `10` и `3` (или `4`).
Число `8` из плана не ожидается — обоснование в §3, пункт 6 и §4 D1; если фактическое
число иное, в отчёте назвать, какие тесты сверх счёта появились или каких не хватает.

Гейт 3. Полный набор — регрессии:

```bash

```

Ожидается: `221 passed` (208 + 13, `ЭТО ОЖИДАНИЕ` — базовая цифра из S11 не
перепроверялась), `EXIT=0`. Красный тест по причине, не связанной с шагом, — §7,
стоп-сигнал 4.

Гейт 4. Честный per-file замер (изолированный файл данных).

Сначала **baseline, до первой правки тестов** (файла `test_step_card.py` ещё нет, поэтому
в прогоне только существующий файл и только строка тика):

```bash
.venv/Scripts/python.exe -m coverage run --parallel-mode -m pytest tests/engine/test_tick.py > "$TMPDIR/s12-cov-base.log" 2>&1; echo BASE_RUN_EXIT=$?
```

Ожидается одна строка `step_pipeline\engine\tick.py` с процентом около **32 %**

прирост был виден числом, а не на словах; если baseline расходится с 32 % — это первая
строка объяснения в отчёте.

Финальный замер после всех правок:

```bash

.venv/Scripts/python.exe -m coverage run --parallel-mode -m pytest tests/engine/test_tick.py tests/engine/test_step_card.py > "$TMPDIR/s12-cov-run.log" 2>&1; echo RUN_EXIT=$?
```

## 7. Стоп-сигналы

Останавливаться и докладывать (без «адаптирую по смыслу»), если:

1. Чтобы позеленеть, нужна правка файла вне разрешённых двух — движка, `.coveragerc`,
   `pytest.ini`, `ci.yml`, `conftest.py`, `engine_kit.py`, `stub_hermes.py`. Доклад:
   какой файл, какая строка, почему тестом не обойтись.
2. Код расходится с постановкой: набор кандидатов `find_gate` (`tick.py:64-75`) другой;
   `step_card.main` печатает другой заголовок, другой ключ карточки или другие коды
   возврата; `gate._create_card` (`gate.py:752-776`) вызывает `hermes` не так, как
   описывает §2.4. Значит, постановка снята с другого HEAD — не подгонять тест под код
   молча.
3. Покрытие не доходит до 80 % ни при каких честных тестах, либо доходит только через
   `# pragma: no cover`, `skip`/`xfail`, удаление строк из `include` или правку
   `.coveragerc`: ослаблять замер нельзя, шаг не закрыт.
4. Гейт красный по посторонней причине (флейк e2e, чужая правка `docs/CONTEXT.md`,
   отсутствующий `coverage`), либо падает тест, который до шага был зелёным, и причина
   не в твоих правках. Назвать тест, ошибку и `EXIT`, тест не править.
5. Новый тест требует установленного `hermes`, сети или живого профиля Hermes:
   контракт шага — «тесты не требуют установленного hermes», путь один — `hermes_stub`.
6. Замер не показывает файл вовсе, или `coverage combine` смешивает данные прошлых
   прогонов (в отчёте появились строки `pytest-*`, `.pipeline\` или чужие файлы):
   сначала разобраться с изоляцией `COVERAGE_FILE`, цифру в отчёт не писать.
7. Приходится трогать существующие 7 тестов `test_tick.py` не дополнением, а
   переписыванием (D5): это меняет предмет проверки прошлого шага.

Формат доклада при стопе: файл и строки, команда и её полный вывод (≤ 200 строк),
варианты с ценой, рекомендация.

## 8. Формат отчёта

Отчёт — в карточке (`kanban_complete`), до закрытия шага, по порядку и с числами:

1. `git diff --stat` и `git show --stat` коммита шага (sha и сообщение).
2. Что сделано по тестам: имя теста → что проверяет → какой файл движка исполняет
   (для доказательства, что тест идёт по файлу, а не по копии).
3. Гейты 1-3: команда, число (`N passed`) и `EXIT` для каждого; счётчики
   `grep -c "^def test_"` по двум файлам.
4. Гейт 4: baseline и финальный отчёт, дословно строки `tick.py` и `step_card.py`
   (`stmts`, `miss`, процент) и `REPORT_EXIT`; расхождение с ожиданием — объяснить.
5. Решения, принятые самостоятельно, с причиной: где применена подмена `__file__` и
   почему; какие ветки оставлены непокрытыми и почему это не мешает порогу; почему
   тестов в `step_card.py` столько, сколько их есть.
6. Что сознательно не сделано: правка строки `плана:213` («8 passed»), per-file порог
   в `ci.yml`, переписывание четырёх `.env`-тестов, любой рефакторинг движка.
7. Отклонения от промта и открытые вопросы (в том числе по §9).

Язык отчёта — русский, вывод команд — не более 200 строк на команду (большой вывод в
файл и `grep` по нему).

## 9. Вопросы

1. Строка плана `docs/plans/1-stabilnost.md:213` обещает `8 passed`, а выполнимо
   `13`-`14` (в `test_tick.py` уже 7 тестов, плюс минимум три в тик и три в
   `step_card.py`). Принято: шаг не правит план, устаревшую строку исправляет тот, кто
   закрывает шаг после ревью; цена альтернативы — правка одной строки прямо сейчас, но
   тогда план меняет исполнитель, а не закрывающий.
2. Замер: принято считать покрытие по двум тестовым файлам с изолированным
   `COVERAGE_FILE` (быстро и точно для per-file цели). Цена альтернативы — полный
   прогон с подпроцессным крючком (~7 минут, как в S10) даёт тот же процент по этим
   двум файлам, но заодно обновляет агрегат в `TOTAL`.
3. Нужен ли отдельный per-file гейт в `ci.yml` для `tick.py` и `step_card.py`, чтобы
   регресс ниже 80 % ловила сборка, а не ревьюер? Принято: в этом шаге нет — `ci.yml` и
   `.coveragerc` вне разрешённых файлов; цена — отдельный шаг, зато порог перестаёт
   быть обещанием в отчёте.

## 10. Ревью (обязательно)

Шаг закрывает не исполнитель. После кода, гейтов и коммита шаг уходит на независимое
ревью роли `reviewer` (скилл `pipeline-reviewer`): вердикт `APPROVE` или
`REQUEST_CHANGES` в `docs/reviews/1-S12.md`, первая строка файла — коммит шага в
обратных бэктиках. Ревьюеру доступны план (`docs/plans/1-stabilnost.md` §S12) и код
(`tests/engine/test_tick.py`, `tests/engine/test_step_card.py`, движок
`step_pipeline/engine/tick.py`, `step_pipeline/engine/step_card.py`,
`tests/engine/conftest.py`, `tests/engine/engine_kit.py`, `tests/engine/stub_hermes.py`)
и его собственные прогоны; отчёт исполнителя источником фактов не считается — гейты 1-4
ревьюер прогоняет сам, включая замер покрытия. При `REQUEST_CHANGES` шаг остаётся
открытым: находки правятся, ревью повторяется; строка «ЗАКРЫТ» в журнале и коммит
закрытия — только после `APPROVE`, и журнал пишет страж.
