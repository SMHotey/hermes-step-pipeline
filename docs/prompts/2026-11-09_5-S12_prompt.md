## 1. Роль и цель

Ты — программист конвейера шагов Hermes (`hermes-step-pipeline`), исполняешь шаг S12 плана 5
в ветке `main`. Рабочий каталог — `<корень>`,
оболочка — bash (git-bash), интерпретатор — `.venv/Scripts/python.exe` этого репозитория
(Python 3.11.15).

Результат шага: бот в Telegram — собеседник, а не громкоговоритель, и слушает только
владельца. Конкретно:

- **Ответ приходит целиком.** Ответ агента любой длины доставляется: до 3900 символов —
  одним сообщением, длиннее — несколькими кусками, ни один кусок не превышает лимит
  Telegram. Обрезки `out[: TG_TEXT_LIMIT - 100]` и `answer[:TG_TEXT_LIMIT]` больше нет.
- **Видно, что бот работает.** Перед ответом агента уходит `sendChatAction` с
  `action="typing"` и повторяется, пока агент думает; сбой «печатает» ответ не отменяет.
- **Защита от флуда.** Свободный текст владельца ограничен: не больше `max` сообщений за
  `window` секунд (по умолчанию 5 за 60), лишние не запускают агента, о первом отсеве
  владелец получает одно предупреждение, квота живёт в файле состояния и переживает новый
  процесс. Команды с «/» квоту не тратят — аварийный `/stop` проходит всегда.
- **Чужой не получает ничего, но попадает в лог.** В stderr пишутся user id и chat id
  отправителя (`?`, если поля нет); текст чужого сообщения не печатается и в историю не
  пишется; чужое сообщение квоту владельца не тратит.
- **`/help` называет защиту от флуда** и по-прежнему перечисляет все семь команд.

Затрагиваются `step_pipeline/engine/gate.py` и `tests/engine/test_tg_commands.py` плюс
`step_pipeline/plugin.yaml` и `CHANGELOG.md` (правило `AGENTS.md`). Потолки диалога
(таймаут 240 с, `--max-turns 8`, `--run-budget 200`, ротация 40 сообщений / 120k токенов) —
уже сделаны шагом 2-S4 и здесь не переделываются, только упоминаются в комментариях.

## 4. Что сделать

### 4.0 Решения, которые уже приняты (не переигрывать)

- **D1. Один помощник отправки.** Новый `send_answer(token, chat, text)` режет ответ
  `split_message` и отправляет куски по порядку; обе ветки цикла (`gate.py:2905-2910`
  диалог и `gate.py:2918-2919` команда) переходят на него, обе обрезки удаляются. Причина:
  обрезка живёт в двух местах, разбиение — в одном; правка «только в диалоге» оставляет
  класс дефекта в командной ветке.
- **D2. Один порог.** `split_message` получает значение по умолчанию `limit=TG_TEXT_LIMIT`
  (3900) вместо 3500; вызовы без аргумента. Существующие тесты передают `limit=3500` явно
  (`tests/engine/test_tg_commands.py:256, 262`) и не меняются. Причина: 3900 — уже
  действующий потолок (`gate.py:2372`), меньше 4096; второе число в чате не нужно.
- **D3. «Печатает» с обновлением.** `send_typing(token, chat)` — одна отправка
  `sendChatAction` c `action="typing"`; в ветке диалога она идёт **до** `ask_agent`, затем
  поток `_typing_keepalive(token, chat, stop_event, interval=TYPING_REFRESH)` повторяет её
  каждые 4 секунды (action в Telegram живёт около 5 с), поток гасится в `finally` через
  `threading.Event` и `join(timeout=1.0)`, создаётся с `daemon=True`. Результат action
  игнорируется: сбой «печатает» ответ не отменяет и в stderr не пишется. Причина: 5 секунд
  индикатора при ответе до 240 секунд — фикция, а не «печатает».
- **D4. Защита от флуда только для свободного текста.** Ключ
  `notify.commands.rate_limit = {"max": 5, "window": 60}`; `max <= 0` — без лимита; состояние
  `cfg.state_dir/tg_rate.json` вида
  `{"555000111": {"count": N, "window_start": epoch, "warned": true|false}}`; время — только
  `_now()` (`gate.py:2045`); команды с «/» квоту не тратят (аварийный `/stop` должен проходить
  всегда); превышение — сообщение не обрабатывается, в stderr строка, **одно** предупреждение
  на окно, дальше тишина; `result["limited"]` — счётчик отсеянных, CLI (`gate.py:3972-3974`)
  печатает `, отсечено по частоте: N` при N > 0. Причина порога 5/60: это одна пачка вопросов;
  дальше очередь агентских ответов по 240 с растёт быстрее, чем владелец читает.
- **D5. Чужие попытки — id и ничего больше.** Строка `gate.py:2900` дополняется id чата:
  `[commands] чужой отправитель {sender_id or '?'} (чат {sender_chat or '?'}) — игнор`.
  Текст сообщения не печатается, в историю тиков не пишется, `ignored` считается как сейчас,
  квоту владельца чужое сообщение не тратит (фильтр стоит выше лимита). Причина: план требует
  id, а чужой текст в cron-логе — лишняя запись чужих данных.
- **D6. `/help` говорит о защите.** В `TG_HELP` (`gate.py:2374-2385`) добавляется строка
  `Слишком частые сообщения не обрабатываются (защита от флуда).` — без чисел и без имени
  ключа конфига: числа живут в `pipeline.json`, дублировать их в справке значит разойтись с
  ними. Семь команд остаются перечисленными.

### 4.1 Ответ уходит целиком (D1, D2)

1. `split_message` (`gate.py:2769`): подпись становится
   `def split_message(text: str, limit: int = TG_TEXT_LIMIT) -> list[str]:`. Докстринг
   дополняется одной фразой: порог — `TG_TEXT_LIMIT` (3900), лимит Telegram 4096, запас на
   служебные символы. Алгоритм не меняется.
2. Новый помощник сразу после `split_message` (перед `_timeout_answer`, `gate.py:2790`):

   ```python

       """Отправить ответ целиком: длинный текст уходит несколькими сообщениями."""
       for chunk in split_message(text):
           sent = _tg_call(token, "sendMessage", chat_id=chat, text=chunk,
                           disable_web_page_preview="true")
           if not sent.get("ok"):
               print(f"[commands] ответ не доставлен: {sent.get('description')}", file=sys.stderr)
               break
   ```

   Строка о недоставке переезжает сюда: иначе после правки она окажется в двух ветках.
3. `ask_agent` (`gate.py:2842`): `return out[: TG_TEXT_LIMIT - 100]` → `return out`. Комментарий

   обрезка здесь делала разбиение фиктивным». Больше в `ask_agent` ничего не меняется.
4. Ветка диалога (`gate.py:2903-2913`): вместо цикла по `split_message` — `send_answer(token, chat, answer)`;
   `_log_chat(cfg, "tg_dialog", text, started)` и `result["handled"] += 1` остаются на местах.
5. Ветка команды (`gate.py:2914-2923`): `answer[:TG_TEXT_LIMIT]` заменяется на `send_answer(token, chat, answer)`;
   прежняя проверка `sent.get("ok")` и `print` из ветки убираются (они уже внутри помощника).
   `_log_chat(cfg, "tg_command", text, started)` остаётся — история пишется и при недоставке,

### 4.2 «Печатает» (D3)

1. Константа `TYPING_REFRESH = 4.0` рядом с `TG_TEXT_LIMIT` (`gate.py:2372`), комментарий:
   «action `typing` в Telegram живёт около 5 секунд — обновляем чаще».
2. Два помощника рядом с `send_answer`:

   ```python
   def send_typing(token: str, chat: str) -> None:
       """«Печатает» в чате: сбой action не влияет на ответ и не пишется в stderr."""
       _tg_call(token, "sendChatAction", chat_id=chat, action="typing")

   def _typing_keepalive(token: str, chat: str, stop_event, interval: float = TYPING_REFRESH) -> None:
       """Держать «печатает», пока агент думает: гасится через stop_event."""
       while not stop_event.wait(interval):
           send_typing(token, chat)
   ```

   Результат `_tg_call` не проверяется: `_tg_call` по контракту (`gate.py:2388-2400`) не бросает,
   а «печатает» — косметика, из-за неё ответ отменять нельзя.
3. В ветке диалога, **до** `ask_agent`:

   ```python
   send_typing(token, chat)
   stop_event = threading.Event()
   keep = threading.Thread(target=_typing_keepalive, args=(token, chat, stop_event), daemon=True)
   keep.start()
   try:
       answer = ask_agent(cfg, text, chat)
   finally:
       stop_event.set()
       keep.join(timeout=1.0)
   ```

   `import threading` — в шапку `gate.py` между `tempfile` и `time` (алфавитный порядок, stdlib).
4. Поток не переживает итерацию цикла и не пишет в состояние. Других потоков, блокировок и
   `time.sleep` в шаге нет; `stop_event.wait(interval)` — единственное ожидание.

### 4.3 Защита от флуда (D4)

1. Константы рядом с именами файлов состояния (`gate.py:2441-2442`):
   `RATE_STATE_NAME = "tg_rate.json"`, `RATE_DEFAULTS = {"max": 5, "window": 60}`.
2. `rate_settings(cfg) -> dict` — по образцу `dialog_settings` (`gate.py:2473-2489`): читает
   `cfg.notify["commands"]["rate_limit"]`, если там словарь; `max` и `window` приводятся
   `_as_int` (`gate.py:2459`); `window <= 0` → 60, отрицательный `max` → 0; мусор в конфиге
   не ломает, а даёт умолчания.
3. `_rate_path(cfg) -> Path` — `Path(cfg.state_dir) / RATE_STATE_NAME`; чтение терпимое к
   битому JSON и отсутствию файла — ровно как `_read_dialogs` (`gate.py:2496-2501`).
4. `rate_allow(cfg, chat) -> dict` возвращает `{"allowed": bool, "warn": bool}`:

   - `rate_settings(cfg)["max"] <= 0` → `{"allowed": True, "warn": False}`, файл не читается и
     не пишется (лимит выключен конфигом);
   - иначе берётся запись чата (`str(chat)`) — словарь `{"count", "window_start", "warned"}`;
   - `now = _now()`; если записи нет или `now - window_start >= window` — окно новое:
     `count = 0`, `warned = False`, `window_start = now`;
   - `count >= max` → `warn = not warned`, `warned = True`, запись сохраняется,
     `allowed = False`;
   - иначе `count += 1`, запись сохраняется, `allowed = True`.
   - Запись — через `state_io.save_json` (`state_io.py:69`); `OSError` печатается в stderr
     одной строкой, и лимит **не** отказывает в обработке (fail-open: потерять сообщение
     владельца хуже, чем пропустить лишнее).
5. В `poll_commands` — **после** фильтра чужих (`gate.py:2897-2901`), **до** ветки диалога:

   ```python
   if not text.startswith("/"):

       if not quota["allowed"]:
           result["limited"] += 1
           if quota["warn"]:
               settings = rate_settings(cfg)
               send_answer(token, chat,
                           f"слишком часто: не больше {settings['max']} сообщений"
                           f" за {settings['window']} с — это сообщение не обработано.")
           print(f"[commands] слишком часто: чат {chat} — сообщение не обработано",
                 file=sys.stderr)
           continue
   ```

   Команды с «/» до этого блока не доходят — квоту они не тратят.
6. `result` (`gate.py:2853`) получает ключ `"limited": 0`; печать `--commands`
   (`gate.py:3972-3974`): в `extra` добавляется `f", отсечено по частоте: {result['limited']}"`,
   когда счётчик не ноль (форма — как у `чужих проигнорировано`).
7. Отсеянное сообщение в историю тиков не пишется: строка stderr и счётчик — всё, что нужно;
   иначе лог тиков заполнится мусором (образец того, что пишется в историю, —
   `_log_chat`, `gate.py:2613`).

## 7. Формат отчёта

Отчёт — до коммита, по-русски, по разделам:

1. **Факты до правок** — `git rev-parse HEAD`, состояние дерева, гейт 0 (collected/passed/
   skipped), версия из `plugin.yaml`.
2. **Что сделано** — по файлам с номерами строк: что добавлено, что изменено, что удалено;
   по строке на решение D1-D8 (какое решение закрыто и чем именно в коде).
3. **Гейты** — таблица «команда → ожидание §5 → факт → EXIT» для всех одиннадцати гейтов;
   числа прогонов фактические. Если гейт 3 (`hermes plugins validate`) недоступен — строка
   «недоступно» с причиной, а не выдуманный PASS.
4. **Тесты** — 14 новых функций: имя и что утверждает каждая; отдельно T5 (поток

   что 34 прежних теста не ослаблены (в диффе набора только добавленные строки).
5. **Что не сделано и почему** — отличия от постановки, отложенные места; если ничего, так
   и скажи одной строкой.
6. **Коммит** — хеш, список путей (§3 плюс ничего), версия из `plugin.yaml`, сообщение
   `feat(engine): двусторонняя связь — целые ответы, «печатает», защита от флуда (план 5, S12)`.

Числа — только фактические, из логов прогонов. «Тесты зелёные» без числа не отчёт.

## 8. Вопросы

1. **Лимит только на свободный текст — не общий?** Решено в D4: аварийный `/stop` и `/status`
   должны проходить всегда, а дорогой прогон — это именно текст агенту. Цена общего лимита:
   в момент паники владелец шлёт команды пачкой и упирается в квоту, `/stop` не доходит.
   Цена текущего решения: команды никто не ограничивает, поток из 200 `/plans` подряд даст
   200 ответов (дешёвых). По умолчанию — D4.
2. **Порог 5 сообщений за 60 секунд — верный?** Цена большего (10/60): до 40 минут очереди
   агентских ответов по 240 с, пока владелец пишет новое. Цена меньшего (2-3/60): обычная
   пачка из четырёх вопросов натыкается на отказ. Порог живёт в `pipeline.json`, меняется без
   правки кода: `notify.commands.rate_limit`. По умолчанию — 5/60.
3. **Поток-обновлятор «печатает» — не лишняя сложность в тике?** Цена без потока: индикатор
   гаснет через 5 секунд, то есть при ответе до 240 секунд его практически нет. Цена потока:
   ещё один daemon-поток, живущий только на время `ask_agent` и гасимый в `finally`. По
   умолчанию — с потоком (D3).
