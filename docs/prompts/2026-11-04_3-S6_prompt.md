## 1. Роль и цель

Ты — исполнитель шага S6 плана 3 в репозитории `hermes-step-pipeline`. Цель шага: один
экран на все репозитории, где стоит конвейер, — владелец видит, что происходит в каждом,
и управляет ими, не открывая второй терминал и второй порт.

Результат шага: реестр проектов читается сервером панели; API принимает выбор проекта;
у каждого проекта своё состояние, свой кэш снимка и свои проверки; в шапке —
переключатель, в «Обзоре» — сводная таблица; действия адресованы выбранному проекту и
подписаны его именем; проект без `.pipeline` показывается как «не установлен»; ключ
`project_root` в манифесте плагина задаёт проект по умолчанию и реально читается.

## 2. Контекст (факты) и принятые решения

Все адреса проверены в текущем дереве (HEAD `2eae092`, дерево чистое, S5 закрыт). Формат
«факт → где смотреть». Решения ниже — **обязательные**: исполнитель их не пересматривает.

**D1. Гейт шага.** Числа «19 passed» в §S6 нет; базой считается 65 собираемых тестов в
`tests/test_ui_server.py` (60 функций `test_` плюс параметризации 3 и 4). Приёмка — полный
зелёный прогон файла, число в отчёт рядом с фактом.

**D2. `project_root`.** Манифест получает ключ `project_root` (тип `str`, не секрет,
с описанием), значение Hermes хранит в `plugins.entries.step_pipeline.settings.project_root`
профиля. Читает его `project.py`: новая функция `configured_project_root()` возвращает
`Path` или `None`; порядок — переменная окружения `PIPELINE_PROJECT_ROOT`, затем
`plugins.entries.step_pipeline.settings.project_root` из `config.yaml` в home профиля
(см. задачу 1), разбор **без PyYAML** (по образцу `setup_flow.profile_provider()`,
`setup_flow.py:685-715`: ключ верхнего уровня, отступы — но на четыре уровня).
Потребитель — `cli._project()` (`cli.py:117-120`): пустой
`--project` → `configured_project_root()` или `proj.find_project()`. Тест
`tests/test_manifest_hygiene.py:39-46` переписывается: вместо запрета ключа — проверка,
что каждый ключ `config_schema` либо встречается в исходниках плагина (`project.py`,
`setup_flow.py`, `doctor.py`, `ui_server.py`) по имени, либо объявляет `env:` и тогда
встречается **имя переменной**. Без второй ветки правило ложно для telegram-ключей: их
имена есть только в `plugin.yaml:21,25` и в тесте, а в коде живут
`STEP_PIPELINE_TELEGRAM_BOT_TOKEN` (`setup_flow.py:76`) и
`STEP_PIPELINE_TELEGRAM_CHAT_ID` (`doctor.py:119`). `ui_port` остаётся запрещённым (его
никто не читает).

**D3. Разовые пути.** В парсере `ui` (`cli.py:73-84`) — `--extra-project PATH` с
`action="append"`; `cmd_ui` передаёт список в `ui_server.serve()` и `ui_control.start()`;
`ui_control.start()` (`ui_control.py:63-80`) добавляет по `["--extra-project", path]` на
каждый путь, чтобы `--detach` не терял их.

**D4. Реестр — только чтение.** Панель читает файл реестра и никогда его не пишет.
Создаёт и правит реестр владелец руками (образец — в этом файле, раздел «Что сделать»,
задача 1). Запись реестра из мастера установки — **не входит в эту задачу**.

**D5. Идентификаторы.** У записи реестра есть `id` (если не задан — `proj.slug(name или
имя каталога)`, `project.py:173`); дубликаты разводятся суффиксом `-2`, `-3`. Разовый
путь из командной строки получает тот же `id` из имени каталога и в файл не пишется.
Именно `id` — значение параметра `project` в API.

**D6. Состояние на проект.** Сервер держит `states: dict[str, State]` — по одному `State`
на проект (свой `log`, `cache`, `checks`, `checks_lock`). `Handler.state` остаётся
состоянием проекта по умолчанию — на него опираются существующие тесты
(`tests/test_ui_server.py:37-45`: фикстура `server` берёт `RequestHandlerClass.state`),
ломать их нельзя. Рядом —
`Handler.registry` (список записей с разрешённым `State`).

**D7. Выбор проекта в API.** GET-маршруты принимают `?project=ID`; POST
`/api/action`, `/api/plan-mode`, `/api/setup` — поле `project` в теле JSON. Нет параметра
— проект по умолчанию (тот, с которым запущен сервер). Неизвестный `id` — ответ 400 с
перечнем доступных `id`. Новый маршрут `GET /api/projects` отдаёт реестр со сводкой
(поля — задача 3).

**D8. Стоимость сводки.** Сводная строка фонового проекта не запускает полный снимок:
достаточно одного `gate.py --plans` плюс чтение файла состояния плана
(`snapshot._plan_state`, `snapshot.py:324`) для простоя. Поля `total` в `--plans` нет

как раньше и своим кэшем `snap.snapshot`.

**D9. «Не установлен».** Признак — отсутствие `PROJECT_ROOT/.pipeline/gate.py`

## 4. Что сделать

**Задача 1. Реестр в `project.py`.**
Новые функции (имена — эти, на них опираются тесты):
- `hermes_home() -> Path` — **home профиля**, а не корень Hermes: `HERMES_HOME`, если задан
  (в процессе, запущенном Hermes, он уже указывает на каталог профиля — у `default` это
  корень Hermes, у именованного `…/hermes/profiles/ИМЯ_ПРОФИЛЯ`); иначе при именованном
  `HERMES_PROFILE` — `LOCALAPPDATA/hermes/profiles/ИМЯ_ПРОФИЛЯ`; иначе `LOCALAPPDATA/hermes`,
  если каталог есть; иначе `~/.hermes`. Раскладка Hermes 0.21.5:
  `hermes_cli/profiles.py:306-318` (`get_profile_dir`), `:2356-2373` (`resolve_profile_env`,
  значение кладётся в `HERMES_HOME`, `hermes_cli/main.py:631`). Образец —
  `setup_flow.hermes_home()` (`setup_flow.py:302-310`, там же условие `is_dir()`); импорт
  `setup_flow` из `project.py` запрещён (циклический: `setup_flow.py:29`, `:33`), поэтому
  блок дублируется осознанно.
- `projects_file() -> Path` — `PIPELINE_PROJECTS_FILE`, иначе
  `hermes_home()/projects.json` — файл лежит **прямо в home профиля**, никакого
  `profiles/ИМЯ_ПРОФИЛЯ/projects.json` (такого каталога в именованном профиле нет).
- `read_projects() -> list[dict]` — читает реестр, ничего не пишет. Формат файла:

  `{ "projects": [ { "id": "hermes-step-pipeline", "name": "Конвейер шагов", "root": "<корень>" } ] }`

  Возвращает записи `{"id", "name", "root"}` (`root` — `Path`). Нет файла, битый JSON,

- `configured_project_root() -> Path | None` — `PIPELINE_PROJECT_ROOT`, затем
  `plugins.entries.step_pipeline.settings.project_root` из `config.yaml` **в home профиля**

  Нечитаемый файл, отсутствие ключа, несуществующий каталог → `None`.

## 5. Как проверить (гейты)

Окружение: Windows, bash (git-bash), корень — `<корень>`.

## 6. Стоп-сигналы

Остановиться, зафиксировать факт в отчёте и доложить (не «адаптировать по смыслу»), если:

1. **Адрес не совпал.** Файл, строка или символ из «Контекста» не про то, что написано.
   Продолжать можно только если символ найден и расхождение объяснимо поздними коммитами
   (`2ddcfe8`, `2eae092`, `4122422`); иначе — стоп.
2. **Дерево грязное или шаг уже закрыт.** `git status --short` на старте не пуст (кроме
   твоего собственного отчёта), или журнал `docs/plans/3-panel.md` показывает S6 закрытым.
   Шаг не начинать: правки смешаются или работа уже сделана.
3. **Нужен файл вне списка.** Требуется менять что-то, кроме девяти разрешённых позиций
   (включая `snapshot.py`, `setup_flow.py`, `engine/`, `pipeline.json`).
4. **Манифест не оживить без побочного.** Ключ `project_root` не проходит проверку
   `hermes plugins validate` или требует правки `ui_port` и прочих ключей.
5. **Гейт красный по чужой причине.** Падение в тестах, которых ты не касался, отсутствие
   pytest, сломанное окружение. Чужое не чинить — доложить с полным выводом.
6. **Нужны сеть, секрет или прод.** Любая проверка, требующая Telegram-токена, реального
   профиля Hermes или записи в настоящий реестр — стоп; в тестах путь реестра только через
   `PIPELINE_PROJECTS_FILE` или изолированный `HERMES_HOME`.
7. **Запись в реальный профиль.** Любой тест или прогон создал или изменил файл в
   реальном `LOCALAPPDATA/hermes/profiles/...` — немедленно остановиться, удалить
   созданное, доложить.

## 7. Формат отчёта

Отчёт — в карточку борды, по-русски, в этом порядке:

1. `Что сделано` — по задачам 1-8, каждая строкой с `file:line`.
2. `Гейты` — точные команды, фактическое `passed/failed/skipped`, код возврата каждой.
3. `Расхождения с постановкой` — что не совпало с фактами, что сделано иначе и почему;
   отсутствие расхождений пишется явно.
4. `Не сделано` — что осталось и почему (если всё сделано — так и написать).
5. `Коммит` — sha, `git show --stat`, список файлов; отдельная строка — подтверждение, что
   файлы S5 и план в коммит не попали.
6. `Риск` — что в этом шаге может сломаться у владельца и как это заметить.

Черновик отчёта — **до коммита**; после коммита в отчёт дописывается sha.

## 9. Ревью (обязательно)

Шаг закрывает **не исполнитель**, а роль `reviewer` (скилл `pipeline-reviewer`) по плану и
коду: источники — `docs/plans/3-panel.md` §S6, эта постановка и фактический код на HEAD.

Ревьюер обязан: сверить выполнение по каждому пункту «Что сделать» и «Границы» (что
запрещено — проверить, что НЕ сделано), сам прогнать гейты раздела 5, проверить, что

Строка «ЗАКРЫТ» в журнале плана и коммит закрытия шага — только после `APPROVE`.
