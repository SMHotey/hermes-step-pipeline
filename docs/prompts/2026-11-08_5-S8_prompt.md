## 4. Что сделать

### 4.1 `step_pipeline/stats.py` — новый файл, только stdlib

Модуль не импортирует движок (`docs/CONTEXT.md:44`) и ничего не пишет на диск: только
читает файлы проекта. Ни одна функция не бросает исключений наружу — нечитаемый файл
попадает строкой в `errors`, а его числа считаются нулём.

Публичный API — три функции и константы разбора:

```python
RESEARCH_MARKER = "разведка"
CONSTITUTION_MARK = "Конституция:"              # шапка плана (approval.py:42)
EDIT_MARK_RE = re.compile(r"прав\w*\s+по\s+разведке\s*:\s*(\d+)", re.IGNORECASE)
VERDICT_RE = re.compile(r"^#{0,4}\s*ВЕРДИКТ\s*:\s*(APPROVE|REQUEST_CHANGES)\s*$",
                        re.IGNORECASE | re.MULTILINE)
PLAN_SHA_RE = re.compile(r"plan_sha256\s*[:=]\s*`?([0-9a-f]{64})", re.IGNORECASE)
PLAN_FILE_RE = re.compile(r"^(\d{1,2})-")       # номер плана — группа 1
STEP_HEADING_RE = re.compile(r"^#{3,}\s+[A-Za-z]{1,4}\d+[A-Za-z]?(?:-\d+)?\b")
# Имя группы `id` разорвано на две строки: гейт формы (C3) принял бы его за заглушку.
DEFAULT_STEP_ID_REGEX = (r"(?P<"
                         r"id>[A-Za-z]{1,4}\d+[A-Za-z]?(?:-\d+)?)")  # дословно config.py:55
JOURNAL_COLUMNS = 5                            # registry.JOURNAL_COLUMNS:43

def cycle_metrics(root, cfg=None) -> dict      # все числа; root — Path проекта
def cycle_tiles(metrics) -> list[dict]         # четыре плитки для панели
def render_cycle(metrics) -> str               # одна строка «Цикл: …» для --status
```

Литерал в блоке выше (две соседние строки склеиваются — в рантайме строка одна) —
дословная копия умолчания `step_id_regex` из `step_pipeline/engine/config.py:55` (группа
`id` именованная): сверь его с файлом. Импортировать умолчание из движка нельзя —
инвариант `docs/CONTEXT.md:44`. `None` здесь не годится: движок собирает шаблон как
`"^" + regex` (`config.py:319`), и умолчание-`None` дало бы `TypeError` на проекте без
ключа `step_id_regex` (тест 5).

`cfg` — сырой словарь `pipeline.json` (как `proj.read_config`: словари `paths` и
`markers`); `None` — умолчания. Читаются ключи `paths.plans` (`docs/plans`),
`paths.reviews` (`docs/reviews`), `paths.research` (`docs/research`, ключа в проекте
нет — умолчание), `paths.state` (`.pipeline/state`), `markers.journal` (`журнал`) и
верхнеуровневый `step_id_regex` (умолчание `DEFAULT_STEP_ID_REGEX`).

Правила счёта — R1-R9. Каждое правило в докстринге модуля со ссылкой на источник в
движке (§2.1): при правке движка расхождение должно находиться по ссылке.

R1. План — файл вида `NN-имя.md` в каталоге планов (`PLAN_FILE_RE`), в тексте которого
есть заголовок уровня 2-6 (`#` заголовка документа не считается), в заголовке которого
есть маркер журнала `markers.journal`, и хотя бы одна строка таблицы этого раздела
(начинается с `|`, ячеек не меньше пяти, вторая ячейка распознаётся `step_id_regex`) —
дословно правило `registry.journal_section:165-181` и `step_of_row`
(`engine/registry.py:184-190`), которым `discover`:229-245 отбирает планы. `plans_total` —
число таких файлов. Если `step_id_regex` не компилируется или в нём нет группы `id` —
строка в `errors`, счёт идёт на `DEFAULT_STEP_ID_REGEX` (движок в `config.py:318-325`
падает с `ConfigError`, но метрика падать не имеет права).

R2. Разведка в плане — заголовок уровня 2-6, в тексте которого есть «разведка» без
регистра, который не является заголовком шага (`STEP_HEADING_RE` по восстановленной
строке) и не лежит внутри раздела шагов (уровень выше 2 при последнем заголовке
уровня 2 со словом «шаг» не считается) — дословно правило `plan_cycle.research_section`
(`engine/plan_cycle.py:73-107`).

R3. Артефакт плана — файл `N-prior-art.md` в каталоге разведки, где N — номер плана
(`engine/gate.py:536`). `plans_with_research` — планы, у которых есть И R2, И артефакт.
План с R2 без артефакта попадает в `research_gap` (список номеров).

R4. Вердикты — только по разделу артефакта, в заголовке которого есть «кандидат»
(разбор разделов — как `scout_report.split_sections`: заголовки `## `); нет такого
раздела — считать нечего, в `errors` строка «нет раздела «Кандидаты»». Строки таблицы —
строки, начинающиеся с `|`; первая строка таблицы — шапка, строка-разделитель
(все ячейки непусты и состоят только из `-` и `:`, `scout_report._is_separator:137-139`) пропускается. Вердикт — последняя ячейка строки (это работает
и на восьми колонках шаблона, и на пяти колонках старого артефакта).
Классификация ячейки без учёта регистра, в этом порядке:
- `candidates_own`: есть «своё» ИЛИ есть «не берём» (отрицание проверяется ДО «берём»);
- `candidates_with_solution`: есть «берём» ИЛИ «форкаем»;
- `candidates_unknown`: всё остальное, включая пустую ячейку.
Вторые таблицы файла (например «Что берём и куда это ложится» в `5-prior-art.md`)
не считаются: они вне раздела «Кандидаты».

R5. Правки по разведке — `EDIT_MARK_RE` по тексту плана, только у планов с R3.
`edits_total` — сумма, `edits_plans` — сколько планов имеют отметку, `edits_per_plan` —
`round(edits_total / edits_plans, 1)` либо `None`, когда отметок нет.

R6. Ревью плана — файл `plan-N.md` в каталоге отчётов (`engine/approval.py:136`).
Вердикт — разбор как `approval.verdict_at:103-119`: собрать ВСЕ совпадения `VERDICT_RE`
(`finditer`, не `search`); ни одного — `invalid`; все совпадают (даже если строк было
несколько) — берётся этот вердикт; два разных — `invalid` (движок называет это
`AMBIGUOUS`; панель читает так же — `snapshot.py:921-923`, «первое совпадение» не
побеждает нигде). Метка версии — `PLAN_SHA_RE`; `sha256` файла плана — по сырым байтам
(`hashlib`, как `sha256_file` в `approval.py:70`). Состояние по плану, ровно одно:
- `skipped` — в шапке плана (строки до первого `## `) нет строки `Конституция:`: движок
  ревью такому плану не назначает (`approval.has_constitution:84-95`);
- `missing` — файла нет (план действующего формата);
- `invalid` — файл есть, а вердикта нет либо он неоднозначен;
- `pending` — `REQUEST_CHANGES`;
- `unbound` — `APPROVE`, но метки `plan_sha256:` нет (`REQUEST_CHANGES` сюда не
  доходит: его забрал `pending`);
- `stale` — `APPROVE`, метка есть и не равна sha256 файла плана;
- `fresh` — `APPROVE` и метка равна sha256 файла плана.
Состояния `skipped`/`missing`/`invalid` — дословно `approval.review_status:141-185`;
`pending`/`unbound`/`stale`/`fresh` — правило постановки: движок вердикт в ветках метки
не проверяет (`REQUEST_CHANGES` с совпавшей меткой даёт у него `fresh`, `approval.py:172-185`),
поэтому `pending` отсекает отказ сразу после `invalid` (гейт разбирает `REQUEST_CHANGES`
отдельно и раньше — `gate.py:1526-1545`), а `unbound`/`stale`/`fresh` описывают только
`APPROVE`. Метрике нужно отличать «ждут решения» от «устарело».
Счётчики по состояниям: `plan_reviews` — число `fresh`, `plan_reviews_stale` — `stale`,
`plan_reviews_unbound` — `unbound`, `plan_reviews_pending` — `pending`,
`plan_reviews_skipped` — `skipped`. `missing` и `invalid` счётчиков не получают — они
видны в `by_plan`.

R7. Круги ревью плана — строки истории `history.jsonl` (по строке на действие,
`engine/gate.py:3604`): считаются записи с `action` = `create_plan_review` и `plan`,
равным номеру плана. Битые строки JSON пропускаются и попадают в `errors` одной
строкой «история: пропущено строк N» (только если N больше нуля).
`plan_reviews_first` — планы в состоянии `fresh`, у которых ровно один круг.

R8. `errors` — список строк, порядок — порядок обхода. Пустой список означает «все файлы
прочитаны». Отсутствие каталогов планов, отчётов, разведки — не ошибка: это проект,
где механизм ещё не работал, все счётчики нули.

R9. `by_plan` — список словарей по планам, по возрастанию номера:
`{"plan": "5", "research": True, "artifact": "docs/research/5-prior-art.md",
  "candidates": 5, "own": 3, "edits": None, "review": "fresh", "rounds": 1}`.
Поле `artifact` — путь относительно корня проекта или пустая строка; `edits` — число из
отметки либо `None`; `review` — состояние из R6; `rounds` — круги из R7.

`cycle_tiles(metrics)` — ровно четыре плитки в этом порядке, формат каждой
`{"label": str, "value": str, "hint": str}`; значения уже строками, страница их только
рисует (правило «страница — рисовальщик», `snapshot.py:467-472`):

1. `планов с разведкой` — значение `«N из M»`, подсказка — номера планов с разведкой либо
   «ни одного»; если `research_gap` не пуст, к подсказке добавить «без артефакта: …».
2. `вердиктов без готового решения` — значение `«own из total»` (при нулевом total —
   прочерк), подсказка — «готовых N, своих M, нераспознанных K».
3. `правок по разведке на план` — значение из `edits_per_plan` либо прочерк, подсказка —
   «N правок в M планах» либо «отметок нет».
4. `ревью плана с первого раза` — значение `«first из plans_total»`, подсказка —
   «свежих вердиктов N, не привязанных к текущей версии M, ждут K, без ревью S»;
   M — сумма `stale` и `unbound` (в подсказке они не разделяются, но различимы в
   `by_plan`), K — `pending`, S — `skipped` (план без строки `Конституция:`).

`render_cycle(metrics)` — одна строка без переводов строки:
`Цикл: планов 5, с разведкой 1, кандидатов 5 (готовых 2, без готового 3), правок по разведке —, ревью плана 0 из 5 (с первого раза 0)`.
Прочерк вместо числа правок — когда `edits_per_plan` равен `None`; иначе число.

В конце модуля — блок `if __name__ == "__main__":` (ручная проба владельца):
аргумент — путь проекта (по умолчанию текущий каталог), печать `render_cycle` после
`cycle_metrics`, код возврата 0. UTF-8 в stdout — как в движке (`errors="replace"`).

     свежего вердикта ревью плана (`approval.review_status`); не берёт готовое решение
     без вердикта на кандидата (`scout_report` R3); не считает метрики руками и не
     правит историю; не трогает владельческие ключи `profiles` и `driven_plans`.
5. Стиль — как в остальном файле: короткие абзацы, таблицы только там, где они уже есть.

### 4.7 Версия и журнал изменений

`step_pipeline/plugin.yaml` (строка 2 сейчас `version: 0.13.0`) — следующая версия по
последнему числу: шаг S7 поднял минор до `0.13.0`, S8 добавляет модуль и ключ снимка без

## 5. Как проверить (гейты)

Рабочий каталог — корень репозитория. Вывод каждого прогона — в файл, код возврата
смотреть у pytest, а не у хвоста пайпа. `pytest.ini` уже содержит `-q`, второй `-q` не
добавлять (AGENTS.md).

```
# 0. Замер ДО правок — база для гейтов 3 и 4
.venv/Scripts/python.exe -m pytest > "$TMPDIR/s8_before.log" 2>&1; echo EXIT=$?
grep -E "passed|failed|error" "$TMPDIR/s8_before.log" | tail -1
# замер постановщика на 462455d: собрано 523 теста (`--collect-only`), из них один skip —
# ожидание 522 passed, 1 skipped. Фактическое число запиши в отчёт: оно база для «+5 passed».

# 1. Новый файл: ровно пять тестов и все зелёные
.venv/Scripts/python.exe -m pytest tests/test_stats.py > "$TMPDIR/s8_stats.log" 2>&1; echo EXIT=$?
# ожидается: 5 passed, EXIT=0

# 2. Число тестов глазами, не только прогоном
grep -c "def test_" tests/test_stats.py     # ожидается 5

# 3. Соседи панели и CLI: число не изменилось
.venv/Scripts/python.exe -m pytest tests/test_ui_server.py tests/test_preview.py tests/test_cli_ui_port.py > "$TMPDIR/s8_ui.log" 2>&1; echo EXIT=$?
# ожидается: 132 passed, 1 skipped, EXIT=0 (замер постановщика — столько же, 2:49)

# 4. Полный набор: passed = замер шага 0 плюс пять, failed не вырос
.venv/Scripts/python.exe -m pytest > "$TMPDIR/s8_all.log" 2>&1; echo EXIT=$?
# ожидается: 527 passed, 1 skipped, ни одного падения (замер шага 0 — 522 + 5)

# 5. Манифест плагина
hermes plugins validate step_pipeline
# ожидается: отчёт без ошибок, EXIT=0 (CLI в PATH есть)

# 6. Ручная проба на этом репозитории — числа из файлов, а не из тестов
.venv/Scripts/python.exe -m step_pipeline.stats . | grep "Цикл:"
# в stderr будет RuntimeWarning от runpy («found in sys.modules after import of package») —
# это норма для `python -m` внутри пакета, на stdout не влияет и гейт не валит.
# ожидается ровно:
# Цикл: планов 5, с разведкой 1, кандидатов 5 (готовых 2, без готового 3), правок по разведке —, ревью плана 0 из 5 (с первого раза 0)

# 7. Снимок получает ключ, страница получает блок
.venv/Scripts/python.exe -m step_pipeline.snapshot . > "$TMPDIR/s8_snap.json"; echo EXIT=$?
grep -c '"cycle"' "$TMPDIR/s8_snap.json"           # ожидается 1
grep -c 'id="cy-grid"' step_pipeline/ui/index.html # ожидается 1
grep -c "renderCycle" step_pipeline/ui/index.html  # ожидается 2 (определение и вызов)

# 8. Строку цикла печатает та же функция, что рисует `--status`, — на коде ЭТОГО дерева
#    (`hermes pipeline status` из PATH исполняет установленную копию плагина; оговорка
#    после гейтов). Скрипт подаётся в stdin: `python -c` блокируется политикой инструментов.
printf '%s\n' \
  'from step_pipeline.snapshot import snapshot' \
  'from step_pipeline.cli import render_status' \
  'print(render_status(snapshot(".")))' \
  | .venv/Scripts/python.exe - | grep "Цикл:"
# ожидается: ровно одна строка, дословно та же, что в гейте 6; EXIT=0 (код возврата grep).
# до шага тот же прогон даёт ноль строк — замер постановщика на 462455d: cycle_lines=0, EXIT=0

# 9. Дерево: только файлы шага, владельческие ключи целы
git status --porcelain   # ожидается: только девять путей шага — stats.py, tests/test_stats.py,
                         # cli.py, snapshot.py, ui_server.py, ui/index.html, CONTEXT.md,
                         # plugin.yaml, CHANGELOG.md; пять неотслеживаемых отчётов ревью
                         # (5-S2/S3/S4/S6/S8-prompt.md) лежали в дереве и до шага — норма
git diff pipeline.json   # ожидается: пусто
```

Оговорка к гейту 8. `hermes pipeline status --project .` исполняет установленную копию
плагина из профиля Hermes, а не это дерево: замер постановщика
`PYTHONVERBOSE=1 hermes pipeline status --project . 2>&1 | grep -m1 "plugins.*cli"` дал
`...hermes\profiles\prompter\plugins\step_pipeline\cli.py`, а сам каталог
`...hermes\plugins\step_pipeline` побайтно равен коммиту `328d44e`. Правки `stats.py`,
`cli.py`, `snapshot.py` этого шага в копию не попадают, поэтому
`hermes pipeline status --project . | grep "Цикл:"` до пуша честно даёт пустой вывод —
это не падение шага и не повод лезть в копию. Строку в CLI владелец увидит после пуша и
`hermes plugins update step_pipeline`; в объём шага это действие не входит.

Если гейт 6 даёт не ту строку, а гейт 1 зелёный, — ошибка в правилах счёта, а не в
фикстуре: разбирать по `by_plan`, а не править ожидание в постановке.

## 6. Стоп-сигналы

Остановиться и доложить (не адаптировать по смыслу), если:

1. На старте или в середине работы `git status --porcelain` показывает незакоммиченные
   правки файлов, которые правит этот шаг (`cli.py`, `snapshot.py`, `ui_server.py`,
   `ui/index.html`): значит их трогает параллельная сессия — дождаться коммита и
   перепроверить адреса по имени функции. На момент постановки дерево чистое; пять
   неотслеживаемых отчётов ревью постановок — не повод останавливаться: они вне файлов
   шага и в коммит не входят.
2. Понадобилось изменить `step_pipeline/engine/**` или `.pipeline/`: шаг S8 движок не
   меняет, а копию в проекте приводит `setup --upgrade`.
3. Для счёта не хватает данных, которых нет в файлах (например истории тиков нет вовсе):
   не додумывать — записать нулём и назвать причину в отчёте.
4. Числа на реальном репозитории разошлись с §2.2: доложить команду и вывод, не
   подгонять код и не переписывать ожидание.
5. Гейт красный по причине, которой не было в замере шага 0 (например
   `tests/test_ui_server.py` упал на форме снимка): доложить строку падения, чужие тесты
   не править.
6. `pipeline.json` попал в дифф или в снимке появился `cycle` внутри `decision` —
   значит ключи владельца или форму решения стража трогают, а не показывают.

Формат доклада: что обнаружено (файл и строки), замер (команда и вывод), варианты с
ценой, рекомендация.

## 7. Формат отчёта

До коммита, по порядку, на русском:

1. `git status --porcelain` и `git diff --stat`: какие файлы и сколько строк.
2. Ключевые диффы: константы и функции `stats.py` (правила R1-R9 и их источники),
   блок в `render_status`, три точки `snapshot.py`, секция и `renderCycle` в странице.
3. Решения, принятые самостоятельно, с причиной (D1, D2 и все отступления; спорное —
   вопрос владельцу, не догадка).
4. Строки гейтов: команда, фактическое число `passed`, `EXIT`, рядом замер шага 0.
5. Вывод гейта 6 дословно — это и есть «числа из файлов».
6. Отклонения от постановки по пунктам, с обоснованием.
7. Что сознательно не сделано (движок, старый артефакт разведки, счётчики для S9-S10) и
   версия с строкой `CHANGELOG.md`.
8. После отчёта — коммит только перечисленных в §3 файлов (явные пути, без `git add -A`),
   затем `git log -1 --format=%H` в отчёт и `git push`.

## 8. Вопросы (≤3, каждый с ценой)

1. Где живут числа: сейчас это плагин — `hermes pipeline status` и панель, а
   `gate.py --status --json` ключа `cycle` не получает. Цена второго варианта —
   правка движка внутри S8, новая синхронизация `ENGINE.sha256` и `setup --upgrade` во
   всех проектах-приёмниках. Принято: плагин, движок не трогаем. Оставляем так?
2. Старый артефакт `docs/research/5-prior-art.md` не проходит `scout_report` (5 колонок,
   нет строки «Решение:»). Принято: считать вердикты по последней ячейке и ничего не
   переписывать. Цена строгого варианта — привести артефакт к шаблону S3 руками (около
   получаса и правка чужого артефакта задним числом). Оставляем мягкий счёт?
3. Метрика «с первого раза» опирается на историю тиков: у планов, прошедших ревью до
   включения механизма, кругов в истории нет, и в число они не попадут. Принято:
   строго `rounds == 1`. Цена послабления (`rounds == 0` тоже «с первого раза») —
   число завышено и не отличает механизм от ручного ревью. Оставляем строго?

## 9. Ревью (обязательно)

Шаг не закрывает исполнитель. После зелёных гейтов — независимое ревью ролью `reviewer`
(скилл `pipeline-reviewer`) по плану `docs/plans/5-platforma.md` и по коду. Отчёт
исполнителя ревьюеру источником фактов не является: он читает план, diff и постановку
`docs/prompts/2026-11-08_5-S8_prompt.md`. Вердикт — APPROVE или REQUEST_CHANGES, ровно
одна строка вердикта в `docs/reviews/5-S8.md`, первая строка отчёта — `recon_commit:`
с полным sha коммита шага. При REQUEST_CHANGES шаг остаётся открытым: находки правятся,
ревью повторяется. Строка «ЗАКРЫТ» в журнале плана и коммит закрытия — только после
APPROVE.
