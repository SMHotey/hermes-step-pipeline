## 1. Роль и цель

Ты — разработчик плагина `hermes-step-pipeline` (Python 3.11, зависимости — только stdlib
и Hermes). Код, комментарии, коммит и отчёт — по-русски.

Цель шага: свежая установка конвейера не падает на первом же воркере роли. Доверие проекта
(`skills trust`) перестаёт быть вещью «только для драйвера и только при setup»: его получают
все три профиля-роли, оно обновляется при `--upgrade`, а `doctor` без ручных действий
показывает, какому профилю доверия не хватает, и печатает готовую команду починки.

Готово = выполнено всё перечисленное:

1. `run_setup` оформляет доверие одному и тому же списку ролей (драйвер, промптер, ревьюер)
   через единый помощник; наблюдаемое поведение и тексты строк лога сохранены.
2. У `setup` появляется флаг `--no-trust`: с ним доверие не оформляется, в лог идёт
   предупреждение, установка продолжается. Ключ `no_trust`, который тестовый помощник уже
   кладёт в `argparse.Namespace`, начинает работать.
3. `--upgrade` оформляет доверие тем же трём ролям, взятым из `pipeline.json` проекта;
   конфиг, Telegram и cron при обновлении по-прежнему не трогаются.
4. `doctor` без записи и без вызова `hermes` проверяет, что проект доверен всем трём
   профилям: на недоверенную роль печатает проблему с готовой командой
   `hermes -p ИМЯ skills trust "ПУТЬ"`, на полное доверие — строку-заметку.
5. `python -m pytest tests/test_setup_flow.py` → `13 passed` (9 существующих + 4 новых),
   `EXIT=0`; новые тесты фиксируют вызовы trust для трёх профилей (setup и upgrade),
   проблему и OK в `doctor`.
6. Полный набор `python -m pytest` → `235 passed`, `EXIT=0`; существующие тесты не
   правились, `tests/test_plan_lint.py` (в нём живёт тест `doctor`) остаётся зелёным.

### 2.4 Как Hermes хранит и как проверяет доверие (установленный Hermes 0.21.5)

- `hermes_cli/main_agent_cmds.py:184-241` — `_cmd_skills_trust`: путь приводится
  `Path(raw).expanduser().resolve()`, строка дописывается в `skills.trusted_project_dirs`
  через `load_config`/`save_config` профиля; повторный вызов печатает «Already trusted»
  и тоже возвращает код 0.
- `agent/skill_utils.py:476-492` — рабочая семантика совпадения:
  `Path(root).resolve() in {Path(entry).expanduser().resolve() for entry in ...}`.
- Файл настроек профиля — файл `config.yaml` в каталоге профиля, ключ лежит блок-списком.
  Живой пример (профиль `pipeline`):

```
$ sed -n '20,24p' "$LOCALAPPDATA/hermes/profiles/pipeline/config.yaml"
  trusted_project_dirs:
    - <корень>
security:
```

- Каталог профилей привязан к корню Hermes, а не к текущему `HERMES_HOME`
  (`hermes_cli/profiles.py:174-184`), поэтому `proj.profile_dir`
  (`step_pipeline/project.py:145-149`) даёт правильный путь.
- Read-only команды для доверия нет: `hermes skills trust` без пути берёт корень git
  от текущего каталога, с путём — ПИШЕТ в конфиг. Значит `doctor` обязан читать
  `config.yaml` сам, иначе он будет менять систему при проверке.

### 2.5 Почему читаем файл, а не зовём `hermes` и не берём PyYAML

- `AGENTS.md`: зависимости плагина — только stdlib и Hermes; внешние пакеты не добавлять.
- Прецедент разбора файла без PyYAML: `plugin_version()`

## 6. Как проверить (гейты)

Все команды — из корня репозитория, интерпретатор `.venv/Scripts/python.exe`, без второго

```bash

tail -3 "$TMPDIR/s15-g1.log"
```

Ожидается `13 passed`, `EXIT=0` (9 существующих + 4 новых). Иное число — назвать

## 8. Формат отчёта

Отчёт — в карточке (`kanban_complete`), до закрытия шага, по порядку и с числами:

1. `git diff --stat` и `git show --stat` коммита шага (sha и сообщение).
2. Что сделано по задачам 1-6: адреса изменений (`path:line`), где помощник доверия,
   как разбирается `config.yaml`, что именно печатает `doctor`.
3. Гейты 1-6: команда, строка итога, число, `EXIT` для каждого; для гейта 5 — три числа.
4. Расхождения с планом, названные явно: «8 passed» против фактических 13 (§2.7), `-q` из
   плана против `pytest.ini:3`, отсутствие доверия в `upgrade` на HEAD.
5. Решения, принятые самостоятельно, с причиной: точные имена помощников, форма замера
   совпадения пути, что делать с ролью, у которой нет каталога профиля.
6. Что сознательно не сделано: S16-смоук, credentials, `.env` в cron-скрипте, версия,
   `CHANGELOG.md`, существующие тесты, план и журнал, переустановка плагина и обновление
   `.pipeline/` (владелец), и почему `doctor` на этой машине исполняет старый код (§2.9).
7. Отклонения от промта и открытые вопросы.

Язык отчёта — русский; вывод команд — не более 200 строк на команду (большой вывод в файл
и `grep` по нему).

## 10. Ревью (обязательно)

Шаг закрывает не исполнитель. После правок, гейтов и коммита шаг уходит на независимое
ревью роли `reviewer` (скилл `pipeline-reviewer`): вердикт `APPROVE` или `REQUEST_CHANGES`

Ревьюеру доступны план (`docs/plans/1-stabilnost.md` §S15) и код:

`step_pipeline/cli.py` (флаг `--no-trust`, проверка в `doctor`),
`tests/test_setup_flow.py` (четыре новых теста), а также неизменённые
`tests/test_plan_lint.py`, `tests/helpers.py`, `tests/conftest.py`,
`step_pipeline/project.py`, `step_pipeline/engine/**`, `docs/CONTEXT.md` (грабли 1-S15,

Отчёт исполнителя источником фактов не считается: ревьюер сам сверяет поведение с планом,

страж.
