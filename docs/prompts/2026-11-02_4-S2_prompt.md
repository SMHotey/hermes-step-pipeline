   текущем дереве замером: `parse_args(["status", "--json"])` → вывод `status True True`, `EXIT=0`
   (то есть `args.cmd`, `args.json` и `args.handler` ведут себя как ожидается). Отдельного скрипта
   для этой проверки не нужно. Команды вида `python -c "..."` политика Hermes может заблокировать
   как исполнение скрипта — поэтому ручные пробы в этом шаге пишутся файлом (§5), а не флагом `-c`.
5. **Коммит и пуш ТОЛЬКО двух файлов:** `git add step_pipeline/cli.py tests/test_cli_plan_mode.py`
   → коммит `feat(cli): подкоманда plan-mode — терминальный переключатель режима (план 4 S2)` →
   `git push`. Строку журнала плана (`docs/plans/4-planner.md:176`) не трогать — её пишет страж
   после APPROVE.

Решения, принятые за тебя (не переигрывать):
- **D1.** `action` — позиционный аргумент `nargs="?"`, `default=""`, без `choices`; проверка
  значения в обработчике. Цена: `hermes pipeline plan-mode bogus` и голый `plan-mode` дают наш
  код 2 и нашу строку `usage` из одного места, обработчик тестируется напрямую; минус — справка
  argparse не перечисляет допустимые значения (их перечисляет `help` и `usage`-строка).
- **D2.** Режим в тексте и в JSON — строки `on`/`off` в нижнем регистре, булевых `true/false` в
  выводе нет (см. вопрос 1).
- **D3.** `--json` печатает ровно один объект через существующий `_dump`; у `status` поля `mode`
  и `file`, у `on`/`off` добавляется `changed` (и `changed_at` из payload, когда изменилось).
- **D4.** `on`/`off` идемпотентны: файл пишется только при реальном изменении состояния, поэтому
  `changed_at` — дата последнего настоящего переключения, а повтор печатает «без изменений».
- **D5.** `--project` по умолчанию `""`, как у всех прочих подкоманд; разбор пути — существующим
  `_project` (`find_project` вверх по `pipeline.json`, `PIPELINE_REPO` учитывается). Своего
  поиска не писать.
- **D6.** Коды возврата: `status` — 0 всегда (и при `off`), `on`/`off` — 0, неизвестное действие
  — 2, ошибка записи не ловится в обработчике (`run()` печатает `ошибка: OSError: ...` и даёт 1).
- **D7.** Никаких вызовов `proj.run_hermes` в этой подкоманде нет вовсе: режим — локальный файл.
  Тесты не патчат и не зовут `run_hermes`; требование «Важно» плана выполнено тем, что вызовов
  нет (сеть, `hermes`, `git` не нужны).
- **D8.** Подсказка в `run()` (`cli.py:342`) правится в этом же файле; строка `help` в
  `step_pipeline/__init__.py:18` НЕ правится (вне файлов шага) и остаётся без `plan-mode` —
  осознанное расхождение, назвать в отчёте.
- **D9.** Версия и `CHANGELOG` в шаге не меняются (вопрос 2).
- **D10.** Ровно семь тестов, без классов и параметризации: план фиксирует «7 passed».

## 5. Как проверить (гейты)

Из корня репозитория. Код возврата смотреть у самой команды, а не у хвоста пайпа; логи — вне
репозитория (`$TMPDIR`; если переменная пуста, возьми `$LOCALAPPDATA/Temp`):

```
C:/tmp/venv-s2b/Scripts/python.exe -m pytest tests/test_cli_plan_mode.py > "$TMPDIR/p4-s2-cli.log" 2>&1; echo EXIT=$?
# после п. 1 (тесты есть, CLI не тронут): ожидается падение всех 7 тестов, EXIT=1 — RED
# после п. 2: ожидается 7 passed, EXIT=0 — GREEN
C:/tmp/venv-s2b/Scripts/python.exe -m pytest > "$TMPDIR/p4-s2-all.log" 2>&1; echo EXIT=$?
# ожидается 161 passed, EXIT=0 (замер до шага: 154 = 54 плагина + 100 движка, плюс 7 новых)
grep -nE "plan-mode|PLAN_MODE_(ACTIONS|USAGE)|cmd_plan_mode" step_pipeline/cli.py
# ожидается: add_parser, константы, set_defaults(handler=cmd_plan_mode), подсказка в run(), тело обработчика
git status --porcelain
# перед коммитом среди своих: M step_pipeline/cli.py, ?? tests/test_cli_plan_mode.py;
# M docs/CONTEXT.md, ?? .hermes/, ?? .pipeline/, ?? docs/templates/, ?? pipeline.json — чужие, не трогать
git show --stat --oneline HEAD
# после коммита ожидается: ровно два файла и sha коммита
```

`-q` к командам не добавлять: в `pytest.ini` уже стоит `addopts = -q`, второй `-q` скрывает
итоговую строку. Запись плана «`python -m pytest tests/test_cli_plan_mode.py` → 7 passed» означает
то же самое; в отчёте — фактическое число прошедших и `EXIT`.

Дополнительно, без правок кода, проверить руками вывод на настоящем каталоге вне pytest
(`pipeline.json` не нужен: без него `paths.state` берётся по умолчанию). Команду `python -c "..."`
политика Hermes может заблокировать как исполнение скрипта, поэтому проба пишется файлом ВНЕ
репозитория — `"$LOCALAPPDATA/Temp/p4-s2-probe.py"` (в репозиторий этот файл не класть и в коммит
не добавлять):

```python
import sys
import tempfile
from argparse import Namespace
from pathlib import Path

REPO = Path(r"<корень>")
sys.path.insert(0, str(REPO / "tests"))
import helpers  # noqa: F401,E402
import cli  # noqa: E402

tmp = Path(tempfile.mkdtemp())
for action, as_json in (("status", False), ("off", False), ("status", True), ("toggle", False)):
    code = cli.cmd_plan_mode(Namespace(action=action, project=str(tmp), json=as_json))
    print(f"--- {action} json={as_json} -> код {code}")
```

Запуск:

```
C:/tmp/venv-s2b/Scripts/python.exe "$LOCALAPPDATA/Temp/p4-s2-probe.py"; echo EXIT=$?
```

Ожидается: коды 0, 0, 0 и 2 (последний — `toggle`); строки `Режим планировщика: on`,
`Режим планировщика: off (было on) — действует со следующей сессии`, JSON `{"mode": "off", ...}`,
и `usage: hermes pipeline plan-mode status|on|off [--project PATH] [--json]` в stderr. Фактический
вывод — в отчёт одной строкой на вызов.

## 6. Стоп-сигналы

Остановиться и доложить (не адаптировать по смыслу), если:
- `step_pipeline/plan_mode.py` не содержит `state_file`/`read_mode`/`write_mode` или `write_mode`
  не возвращает payload с `changed_at` — значит расхождение промта с кодом, а файл шага S1
  править нельзя;
- для «Готово =» нужна правка файла вне двух разрешённых — включая `tests/helpers.py`,
  `tests/conftest.py`, `step_pipeline/__init__.py` или `step_pipeline/plan_mode.py`;
- `plan-mode` в `cli.py` уже зарегистрирован (кто-то сделал параллельно) — доложить и не
  дублировать подкоманду;
- argparse мешает: `nargs="?"` ломает разбор прочих подкоманд, `--json` конфликтует с чем-то в
  родительском парсере или `parse_args(["plan-mode", ...])` не разбирается — доложить вывод;
- семь тестов не получаются без параметризации, классов или ослабления проверок — план фиксирует
  «7 passed», восьмой тест или параметризация меняют число;
- существующий тест покраснел из-за правки CLI (импорт пакета, конфликт имён, `Namespace`) —
  доложить имя теста и вывод; чужие тесты не править и ожидания не подгонять;
- полный прогон красный по посторонней причине (кодировка консоли, отсутствие `hermes`, сеть) —
  доложить числа и текст ошибки;
- интерпретатора с pytest нет (`C:/tmp/venv-s2b` пропал) — создать своё окружение через `uv`
  вне репозитория и назвать его в отчёте; в системный `python` пакеты не ставить;
- для вывода или JSON нужна новая зависимость, переменная окружения или ключ `pipeline.json` —
  это выход за объём шага.

Формат доклада: что обнаружено (файл и строки), замер командой, варианты с ценой, рекомендация.

## 7. Формат отчёта

По-русски, до и после коммита, по порядку: `git status --porcelain` до коммита → `git diff
--stat` после `git add` → что именно добавлено в `cli.py` (аргументы подкоманды, константы,
сигнатура и ветки обработчика, обновлённая подсказка в `run()`) → RED-прогон (команда, `EXIT`,
фактическая итоговая строка) → GREEN-прогон (7 passed, `EXIT`) → полный прогон (фактическое число
passed, `EXIT`) → фактический вывод всех четырёх ручных вызовов из §5 → самостоятельные решения с
причиной → что сознательно не сделано (подпись в `__init__.py`, версия, `CHANGELOG`) → отклонения
от промта → sha коммита и ветка пуша.

## 8. Вопросы (2, каждый с ценой)

1. Чем представлять режим в `--json`: строками `"on"`/`"off"` (вариант A, рекомендую) или булевым
   `true`/`false` (вариант B)? Цена A: JSON совпадает с текстовым выводом и с формулировкой плана
   «on или off», но потребителю нужно сравнивать строку. Цена B: JSON идиоматичнее для машин, зато
   появляются два разных представления одного состояния (текст `on`/`off`, JSON `true`/`false`) и
   тест на поля `mode`/`file` фиксирует булево, которое человек в терминале не увидит.
2. Поднимать ли версию плагина этим шагом? Вариант A (рекомендую, D9): не поднимать, минор
   `0.2.0 → 0.3.0` и запись в `CHANGELOG` делает шаг S7 (`docs/plans/4-planner.md:150`,
   `:165-166`). Цена A: долг версии растёт до трёх шагов (S1 + S2), `.pipeline/VERSION` в проектах
   остаётся прежним. Вариант B: поднять сейчас — цена в том, что `plugin.yaml` и `CHANGELOG.md`
   вне файлов шага, и S7 поднимет версию второй раз за план.

## 9. Ревью (обязательно)

Шаг не закрывает исполнитель. После гейтов — независимое ревью ролью `reviewer`
(скилл `pipeline-reviewer`) по плану и коду: §S2 `docs/plans/4-planner.md`, `git show` коммита
шага, сами `step_pipeline/cli.py` и `tests/test_cli_plan_mode.py`; отчёт исполнителя источником
фактов не является. Отчёт ревьюера — `docs/reviews/4-S2.md`, ровно одна строка вердикта:
`APPROVE` или `REQUEST_CHANGES`, и первая строка блока «Объект ревью» — коммит шага в бэктиках.
При `REQUEST_CHANGES` шаг остаётся открытым, находки правятся, ревью повторяется. Строку журнала
и закрытие шага делает страж после `APPROVE`.
